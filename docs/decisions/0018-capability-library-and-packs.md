# 0018: 能力库——声明式能力包、三档信任与生效组合

## 背景

使用者的诉求是把这一块规划成**插件式的能力中心，任何人都可以自行开发插件扩展能力**，理念参考 DeepSeek Harness（下称 dsh），实现参考 clowder 的插件模块。

`0014-plugin-contribution-points.md` 已经回答了「**能插什么**」——12 个具名贡献点、三条准入公理、两条上下文纪律。本决策回答的是下一个问题：「**插进来的东西长什么样、凭什么被允许进来、进来之后在界面上怎么表达**」。事实基础仍是 `../research/plugin-architecture-dsh-clowder.md`，本次针对 clowder 的 `packages/api/src/domains/plugin/` 全套与其 `docs/decisions/021-f129-pack-system-architecture.md`（Pack 系统）做了第二轮核查。

**ADR 0014 的立场不变**：不引入 Cordis 或等价插件框架，新增可替换点仍按 ADR 0008 逐个判断，第 1 节的四条触发条件继续门控**建造顺序**。本决策定的是**目标形态与档位**，使得现在写的代码不会把这个形态堵死——不是排期。

### 与两个参考项目的结构差异（本决策的事实基础）

| | dsh | clowder | PersonaHub |
| --- | --- | --- | --- |
| 执行体在哪 | 进程内（自己就是 harness） | 进程内 + 受控子进程 | **进程外**：Codex / Claude Code / OpenCode 三个自带完整工具体系的 CLI |
| 扩展单位 | Cordis 插件（代码） | YAML manifest 声明的资源 | 待定（本决策） |
| 产物用途 | 会话记录 | 会话与协作产物 | **要当证据用**：Artifact + Evidence + Provenance 构成可信交付 |

两条由此推出的判断，是本决策与两个参考项目分岔的地方：

1. **PersonaHub 不需要自己做工具运行时。** 模型可见的工具已经由三个 CLI 各自拥有。再做一套会与它们重叠、要为三个 adapter 各写一遍注入，而且工具调用发生在 CLI 进程内——PersonaHub 看不见，无法保证证据链。
2. **插件贡献物会影响「结论可不可信」。** 一个 squad 决定谁验证谁，一份 check 决定验收过不过，一段 skill 决定 agent 看到什么指令。因此能力模块必须**当成证据链的一部分**来设计，不能当成功能开关。两个参考项目都没有这条约束。

---

## 决策

### 1. 划界：工具属于执行体，方法属于 PersonaHub

> **插件在 PersonaHub 里贡献的不是「模型能用的工具」，而是「人和系统用来组织工作的方法」。**

这与 PRD 第 643 行对 Skill 的定义一致（可复用 workflow / prompt / operating procedure，长期是从成功 Issue 中沉淀的**协作资产**），也与 ADR 0006 把执行世界留在 adapter 侧的取舍一致。

唯一的例外处理是 **MCP / 外部工具声明**：能力包**可以声明**「这套方法需要挂哪些 MCP server」，但 PersonaHub **不实现 MCP 运行时**——由各 adapter 把声明翻译成自己的配置格式注入，并把「本次挂了哪些工具」写进 Run 事件（第 5 节规则四）。理由：一次声明三个 CLI 都能用，且证据链不断；代价是要维护三种注入格式，这个代价由 adapter 各自承担，不进核心。协议层本身仍在 v0.8（见 `../personahub-architecture.md`），本决策只保留声明位。

### 2. 三个用词

| 词 | 指什么 | 面向 |
| --- | --- | --- |
| **能力面** | 一级工作面，装**可选能力**；tab 由插件贡献，全部可停用。已装能力包不在这里，在设置 · 插件 | 用户界面 |
| **能力包**（Capability Pack） | 可分享的声明式单位，零代码 | 用户与包作者 |
| **插件** | **只指需要代码的那一类**（adapter / 外部进程），即第 4 节的 T2 | 开发者与技术文档 |

**不把三者统一叫「插件」。** 理由有二：90% 的贡献不写代码，都叫插件会让人以为要写代码；更重要的是**信任度不同的东西不能共用一个词**——「安装插件」这个动作在用户心里是同一个动作，而 T0 与 T2 的风险差着一个数量级。

**一处例外与它的补偿**（2026-09-02，随 design.md V3.21）：设置里管理准入的那一组，界面上叫**「插件」组**——这是使用者的用词。本节的实质诉求（**风险不同的东西界面上不能长得一样**）改由**组内的子区划分**承担：能力包（声明式）与插件（代码）分成两个子区，各自写自己那句必须出现的话。用词纪律在文档与开发者语境里不变；只有那一个界面组名是通称。

### 3. 能力包是一份声明式目录

```text
<pack-id>/
├── pack.yaml        身份 / 版本 / 兼容契约 / 贡献声明 / 需要的授权
├── skills/          可复用操作规程（Markdown + frontmatter）
├── squads/          编组：步骤 × 角色 × 上下文围栏
├── graphs/          协作图定义（只能引用宿主已注册的 node kind）
├── contracts/       输出契约 schema（*_v1）
├── checks/          验收规则（只能引用白名单 checker id）
├── knowledge/       领域资料 → 进资源库，不进 prompt
└── adapters/        代码。唯一需要单独准入的一类（T2）
```

前七项零代码，对应 clowder Pack 的「前 8 层 YAML/MD，最后 1 层才是开发者的事」。核查后本项目的零代码比例只会更高，因为执行世界本来就在 CLI 那边。

**四道扫描校验直接抄 clowder `PluginRegistry.scan()`**（这四条是被实践打磨过的，逐条抄）：

1. **目录名必须等于 manifest `id`**，否则 skip 并打印原因；
2. **保留 id 直接拒绝**（宿主内建能力的 id 不可被占用）；
3. **跨包命名冲突用 claims 表边扫边占坑**，冲突者整包 skip；
4. **候选先按 id 排序再逐个准入**，保证扫描结果与目录遍历顺序无关（可复现）。

**命名空间强制加包前缀，同名不覆盖而是拒绝。** dsh 的注册表按提供方优先级解析出胜出者，PersonaHub 不采用：静默覆盖会让「为什么这次结果和上次不一样」不可解释，而可解释正是本产品的承诺。需要替换时由使用者在能力库里显式选一个。这条与代码里已有的先例一致——`server/src/runtime/adapter-registry.ts` 的 `registerUnique()` 就是「重复注册是编程错误，应当响亮失败」。

### 4. 三档信任

**没有沙箱就没有 marketplace。** 本地单用户工具，代码类永远是「你自己放进目录的东西」。

| 档 | 内容 | 权力 | 准入方式 |
| --- | --- | --- | --- |
| **T0 声明式** | skills / squads / graphs / contracts / knowledge | 只改「派谁、看什么、怎么验」，无执行权 | schema 校验，**未知字段 fail-closed** |
| **T1 引用式** | 定时规则（`factoryId` 白名单）、check、MCP 声明 | 只能引用宿主已注册的可执行体 | 白名单 + 逐项显式授权 |
| **T2 代码** | adapter / 外部进程 | 与宿主同权 | 手工放入本地目录 + 逐项确认 |

T1 的白名单模型抄自 clowder 的 `ScheduleFactoryRegistry`：**插件只能命名一个白名单 `factoryId`，永不提供可执行脚本**（ADR 0014 P10 已记录此判断）。

**每个能力项有自己的状态，包状态是派生的**：

```text
发现 → 校验失败 ┐
            ├→ 待授权 → 已安装（未启用）→ 已启用 → 局部失效 → 停用 → 卸载
```

包级四态直接抄 clowder 的 `enabled / configured / not_configured / partial`。其中 **`partial` 最重要**——它是「装了一半」的唯一诚实表达；clowder 还额外做了「标了 `optional` 的资源不计入 partial」，这条一并抄。

**失败局部化**：单包坏掉只 skip 它自己，保留可见错误态，不影响其余（ADR 0014 准入公理三）。

### 5. 五条硬规则

1. **声明 ≠ 授权。** manifest 说自己提供什么只是候选，宿主校验、准入、激活之后它才存在。（clowder 公理，ADR 0014 已收录，此处不重复展开。）
2. **只能加严，不能放宽。** 「实现与验证不能同源」（PRD 7.5）、「`claimed` 不进验证类上下文」（ADR 0013）这类属于不可覆盖的底座；能力包可以加**更严**的规则，永远不能放宽。抄 clowder 的双轨信任边界 KD-9：硬约束轨只能加严，默认行为轨才可覆盖。
3. **不原样注入，走编译。** 能力包的 skill / squad 文本经 schema 解析后组装成 canonical block 进入上下文，**社区包只能填数据槽，不能写系统级指令**。同上，KD-9。
4. **agent 可见即已记录。** 任何进入执行上下文的能力包贡献物（含第 1 节的 MCP 声明）必须落成 ThreadEvent，能从事件流重建。这是插件不能偷偷污染上下文的唯一保证（dsh 运行时不变量，ADR 0014 上下文纪律一）。
5. **版本钉住证据。** 每次 Run 记录当时生效的能力包 `id@version` + 内容摘要；**能力包升级不改写历史 Run 的解释**。这条两个参考项目都没有——只有这里的产物要被当证据用。治理形态照搬既有的 `WorkflowTemplateAdminService`（版本 + 激活），不新开一条写路径（ADR 0014 准入公理二）。**本地自建的编组与 skill 同样按 `id@version` 记录**，不因为「不是从包里来的」而例外——ADR 0012 第 5 条允许现算编组表现的前提就是这条：编组改一版就是另一段样本。

### 6. 生效组合视图（可见性保证）

dsh 的可见性保证是 `dsh --profile web --dump-config`：**打印出来的每一行都能被用户自己的 patch 替换**。PersonaHub 不抄 profile / bundle / patch 三层组装——那是「一切皆插件」运行时的配套——但**必须抄这条保证**，形式是「本次生效组合」视图：

> 这一次派工，agent 看到哪些 skill、受哪些规则约束、上下文围栏拦掉了什么，**逐条列出并标明每条来自哪个包**。

它不是锦上添花：`design.md` §4.6（执行组合选择器「把判断依据摊开」）与 §3.6.4（「过滤不能是静默的」）两处已有承诺，在能力包进场之后**只有这个视图能兑现**——否则「为什么这次验证结论不一样」将无法回答。

### 7. T2 的前端贡献：声明式 surface

> **插件声明一个 tab，宿主渲染它；插件不提供任何前端代码。**

第 6 节保证了「这一次派工用了什么」可见，本节回答另一个问题：**一个带自己数据的插件，它的界面从哪来。**

```yaml
# <pack-id>/pack.yaml
surfaces:
  - id: inbox
    label: 订阅
    mount: capability                # 只能挂能力面
    kind: table                      # 宿主提供的形态，当前只有一种
    columns: [标题, 来源, 抓取时间, 状态]
    actions:
      - { id: archive, label: 归档,     target: host.library.archive }
      - { id: dig,     label: 深入拆解, target: host.issue.createWithRoom }
```

**准入判据（这是本节最重要的一条）**：

> **能声明 surface 的插件，必须满足「它缺失时核心链路不受影响」。**

核心链路是项目 · Issue · Room · Run · Artifact · Evidence · 记忆 · 统计 · 设置。RSS 订阅满足——没有它照样建 Issue、拉 Room、派工、验收；adapter 不满足——没有它派不了工，因此 **adapter 永远不得声明 surface**，它在设置 · 运行时。依赖方向是单向的：可选层可以调核心层，反向禁止。

四条硬规则：

1. **数据真相源留宿主。** 插件贡献界面与自己的抓取/处理逻辑，**不贡献存储**；进入执行上下文的贡献物仍由宿主按第 5 节规则五钉 `id@version`。
2. **动作只能引用宿主白名单。** 首批两个：`host.library.archive`、`host.issue.createWithRoom`。理由是 design.md §3.3.3 那条判断——**任何一次真正执行都必须有 Issue / Run / Attempt / Artifact / Evidence 的来源链**；插件自己拼一条创建任务的捷径会绕开它，走白名单则这条链自动完整。
3. **挂载点只在能力面的 tab 内。** 不进协作 Dock、不进派工弹层、不进第 6 节的「本次生效组合」视图——那些是证据视图，必须由宿主独占渲染。
4. **插件能新增数据，不能新增交互范式。** 需要第二种 `kind` 时那是宿主的一次性投入。**不开放插件提供渲染代码**：本机没有沙箱，同源 JS 能读 DOM 与调用宿主全部 API，而凭据就在设置 · 运行时（第 11 节记为明确不做）。

**热插拔的边界**：启用 = 注册（surface、schedule、路由）；停用 = 注销 + 停止调用；**不做 Node 模块卸载**。参考项目里 dsh 靠 HMR + 事务式重组，clowder 是「重启 rehydrate」（`../research/plugin-architecture-dsh-clowder.md` 第 3 节）；PersonaHub 与 clowder 同源（Fastify 单进程 + SQLite），因此只承诺注册/注销级。声明式 surface 让前端那一半天然满足：停用后宿主不再渲染它，没有需要卸载的东西。

**与 ADR 0014 的关系**：本节把 P12 从 C 档改为「声明式开放（B）/ 代码渲染关闭（C）」，理由三条记在 0014 的 P12 条目下。

### 8. 沉淀闭环与导出隐私边界

clowder 的 `Experience = Me × Pack + Growth` 在本项目有一个精确同构：

| clowder | PersonaHub | 可分享性 |
| --- | --- | --- |
| Growth（关系果实） | **Memory**（项目事实） | **私有，导出默认不含** |
| Pack（文化种子） | **Skill / Squad / graph / check** | 可导出可分享 |
| 蒸馏回流（KD-11） | PRD v0.6「从 Done Issue 提取 skill candidate」 | 方法回流，原始数据不回流 |

因此**能力包既是输入也是输出**：沉淀出来的 skill 应当能导出成能力包。由此得到一条必须写死的边界（抄 clowder AC-B7）：

> **导出能力包默认不含 Memory 原始数据与 Evidence，只含方法。**

个人工具尤其需要这条——项目事实（内网地址、客户名、未公开的架构问题）不该跟着一份 skill 泄漏出去。

### 9. 与 ADR 0014 清单的映射

本决策不改 0014 的档位判断，只补「进来之后长什么样」：

| 0014 贡献点 | 本决策归属 |
| --- | --- |
| P1 Agent Adapter | **T2**，唯一真 seam，补外部注册入口 |
| P2 Graph Definition / P3 输出契约 | **T0**，`graphs/` 与 `contracts/`，第 5 条规则五钉版本 |
| P4 Evidence typed ref kind | 不开放贡献：kind 表是证据语义的一部分，改表需要核心决策 |
| P5 Workflow Template / P6 Squad | **T0**，数据不是代码，走既有 `WorkflowTemplateAdminService` 校验与审计 |
| P7 路由推荐规则 | **T0**，关键词表先外置为配置数据 |
| P8 验证策略 / P9 执行世界 | 维持 0014 的 C 档，不因能力库而提前开缝 |
| P10 后台任务 / 调度 | **T1**，`factoryId` 白名单 |
| P11 MCP tools | **T1 声明位**，运行时归 adapter（第 1 节） |
| P12 UI 面板 | **声明式 surface 转 B 档**（第 7 节）；插件提供渲染代码维持 C 档 |

### 10. 建造顺序（受 ADR 0014 触发条件门控）

| 阶段 | 内容 | 触发条件 |
| --- | --- | --- |
| 0（可随 F012 顺手得到） | manifest 解析、四道扫描校验、所有权元数据、**生效组合视图**、**编组与 skill 统一为一种 schema**（`steps[]` 可选，有 steps 即为编组） | 无需额外触发：F012 Squad 落地时本来就要决定 squad 存哪、怎么校验、界面怎么显示来源；统一 schema 是在那个决定里少定一种类型，代价为负 |
| 1 | T0 能力包的导入 / 启用 / 停用 / 导出 | 出现第一份真实的、要分享给别人的 squad 或 skill |
| 2 | T1 白名单引用（定时、check、MCP 声明） | 自动化中心落地，或 MCP 进入排期（当前 v0.8） |
| 2.5 | **声明式 surface**：`surfaces` 声明的 schema、`table` 一种 kind、首批两个白名单动作（`host.library.archive` / `host.issue.createWithRoom`） | 第一个 T2 插件落地，且它带自己的数据与视图（如 RSS 订阅） |
| 3 | T2 外部 adapter 的目录准入 | ADR 0014 第 1 节四条触发条件满足任意两条 |

**阶段 0 不构成额外框架**，这是它可以现在做的理由：F012 无论如何都要回答「squad 定义存哪、怎么校验、界面上怎么标来源」，把答案写成能力包的形状，代价是零。

### 11. 明确不做

| 不做 | 理由 |
| --- | --- |
| 模型可见的工具注册表 / 自研 MCP 运行时 | 第 1 节：与三个 CLI 的工具体系重叠，且证据链无法覆盖进程内的工具调用 |
| profile / bundle / patch 三层组装 | 那是「一切皆插件」运行时的配套；本项目组装点是 squad 与 workflow template，已有治理 |
| 远程 marketplace / 签名 / 安装信任链 | clowder K-2A~D 四个切片建成后至今 dormant——不敢上线是最好的证据 |
| **插件提供渲染代码**（React / JS 组件、iframe 之外的任意前端） | 本机没有沙箱：同源 JS 能读 DOM 与调用宿主全部 API，而凭据在设置 · 运行时。第 7 节的声明式 surface 已覆盖需求，且宿主渲染顺带保证 UI 一致与动作走白名单 |
| 能力包覆盖同名贡献 | 第 3 节：静默覆盖让结果差异不可解释 |
| 能力包贡献 Evidence ref kind | 第 9 节 P4：证据语义不外包 |
| 导出时携带 Memory / Evidence | 第 8 节隐私边界 |

## 后果

**正面**：

- 「任何人都能开发插件」这句话有了可落笔的对象：一份目录结构、一张档位表、一条准入状态机。作者不必读源码就知道自己能贡献什么、会被怎么校验。
- 用词把风险差异表达出来了：能力包（数据）与插件（代码）是两个词，界面上也会是两种准入流程。
- 「生效组合视图」把 dsh 最值钱的一条可见性保证，接到了本项目已经存在的两处产品承诺上（§4.6、§3.6.4），不是新增概念。
- 阶段 0 与 F012 合并，能力库不需要独立立项就能拿到骨架。

**负面 / 代价**：

- MCP 声明位要求每个 adapter 各写一份注入翻译。这是刻意选择：代价局部在 adapter，收益是一次声明三处可用且证据链不断。
- 「同名不覆盖而是拒绝」会让使用者在冲突时必须做一次显式选择，比自动优先级麻烦。这是用便利换可解释。
- 本决策的多数内容在触发条件满足前不会有代码。与 ADR 0014 一样，**清单过期比没有清单更糟**——改动 §8 表中任一位置的结构时，本决策随之更新。

**复核触发条件**：ADR 0014 第 1 节四条触发条件满足任意两条；或第一次出现「同一份 skill 要在两个人之间传」的真实需求（那会把阶段 1 提前）；或 MCP 进入实际排期（会把第 1 节的划界推到需要验证的位置）。

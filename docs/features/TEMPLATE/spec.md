## 4. 需求

使用稳定 ID，方便 design、tasks、code review 和 tests 引用。需要时优先使用 EARS 风格：

- 普遍性需求：`系统应当 ...`
- 事件触发：`当 <触发条件> 时，系统应当 ...`
- 状态约束：`在 <状态> 期间，系统应当 ...`
- 异常行为：`如果 <错误/非法条件>，系统应当 ...`

### 功能需求

### Requirement: 需求名称（`FR-001`）

系统应当 ...

#### Scenario: 场景名称

- GIVEN ...
- WHEN ...
- THEN ...

### 数据 / 实体需求

当 feature 创建或修改持久化实体时填写本节。

- **DR-001**：`<实体>` 应当存储 ...
- **DR-002**：`<实体 A>` 应当通过 ... 关联到 `<实体 B>`。
- **DR-003**：当 ... 时，系统应当保留已有数据。

### 事件 / Trace 需求

当 feature 写入 ThreadEvent、run event、audit event、evidence ref 或其他 trace 数据时填写本节。

- **TR-001**：当 ... 时，系统应当写入 `<event.type>`，payload 包含 ...
- **TR-002**：该事件应当可以通过 ... 查询。
- **TR-003**：该事件应当引用 evidence/artifact id ...

### API / 接口需求

当 feature 新增或修改 HTTP API、CLI contract、adapter contract 或前后端接口时填写本节。

- **IR-001**：接口应当提供 ...
- **IR-002**：请求应当包含 ...
- **IR-003**：响应应当包含 ...
- **IR-004**：非法请求应当返回 ...

### UX 需求

填写用户可见行为。这里不做最终视觉设计，只说明必须存在的状态和交互。

- **UX-001**：UI 应当允许用户 ...
- **UX-002**：UI 应当为 ... 展示 loading / empty / error 状态。
- **UX-003**：UI 不应要求用户 ...

### 非功能需求

- **NFR-001**：性能：...
- **NFR-002**：可靠性 / 恢复：...
- **NFR-003**：安全 / escalation 边界：...

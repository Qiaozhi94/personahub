## 1. 产品意图

PersonaHub 面向同时使用多个本地 AI CLI 的个人开发者，把“表达开发目标、选择合适的
AI 成员、执行、验证、恢复和查看证据”收进一条可控旅程。它不是聊天壳，也不是要求用户
理解调度引擎的运维面板。

用户购买的结果不是“启动了一个 agent”，而是：

1. 不离开 PersonaHub，也不在多个终端之间复制上下文，就能把一个真实 coding 目标交出去。
2. 执行期间随时知道进行到哪一步、是否需要自己、接下来会发生什么。
3. 系统只在验证通过且证据完整时宣告完成；失败时给出原因、影响和安全恢复动作。
4. 用户保留对推荐、危险操作、阻塞恢复和长期沉淀的最终控制权。

成功终点是一个可信的 Done：目标结果、文件变化、验证结论和可追溯证据同时存在。单纯
“进程退出成功”“agent 说完成了”或“测试很多”都不构成 Done。

### 1.1 产品承诺

- 本地优先、单用户、开箱即进入工作台，不依赖云账号或 landing page。
- Project 管理工作上下文，Workspace 提供真实文件与执行边界；第一阶段一对一绑定。
- 一个任务拥有连续的活动记录，AI 成员可交接而无需用户复制上下文。
- 系统推荐工作方式和执行者并解释原因，用户确认后才启动真实工作。
- **P0 阶段阶段间流转完全由用户指派驱动**：一个阶段完成后系统停下来，展示产出与建议，
  由用户决定下一步交给谁；系统不自行接力。验证失败回到修复，不能收敛或需要判断时进入
  Blocked。
- Done 必须绑定 Evidence Summary；原始日志、事件和 ID 保留可追溯，但不占据默认视线。

### 1.2 真实技术约束

这些约束限制旅程可承诺的行为，但不直接决定页面结构：

| 约束 | 对旅程的影响 |
| --- | --- |
| 本地 Node.js 服务 + Vite/React 客户端 | 应用需要本地服务可用；首次启动必须能识别“服务未就绪”并给恢复动作 |
| 本地 SQLite，单进程、单用户 | 数据默认留在本机；不设计账号、组织或多人权限步骤 |
| Project 第一阶段只绑定一个本地 Workspace | 首次设置只要求选择一个本地目录；多 Workspace 不进入主路径 |
| 同一 Workspace 的写执行受排他锁保护 | 多个任务可能排队；界面必须区分“排队”与“执行中”并解释原因 |
| 三个 CLI adapter 均为 one-shot Run | 后续指令通过已保存的活动、交接和证据重组上下文，不暗示 CLI 进程永久在线 |
| Adapter 可用性按 Workspace 判定 | “可执行”检查必须针对当前 Project 的 Workspace，而不是只显示全局已安装 |
| Coordinator 当前是确定性规则，不是语义型 LLM | 推荐理由应展示规则和排除原因，不用“AI 已理解一切”之类文案 |
| 推荐确认后才创建 Issue 与 Run | 推荐页必须是明确的人类闸门，取消不能留下半成品任务 |
| 写任务串行；未验证强制隔离前只读节点也物理串行 | 图上可展示并行分工，但进度文案不得承诺同时运行 |
| Run 可 completed / failed / interrupted / cancelled | 失败、中断、取消必须可区分，不能统一显示为“出错” |
| Blocked 只能由用户处理后回 Ready | 恢复动作不会静默自动重跑；用户能复核变化后再次启动 |
| 推送凭据默认不下发，越界/不可逆操作需 escalation | 被阻止时说明保护机制和待确认事项，不把认证失败原文丢给用户 |
| SSE 事件可重放，重启恢复持久状态 | 刷新或服务重启后应恢复可解释状态，已完成步骤不应看似丢失或重复 |

## 2. 核心用户、任务与范围

### 2.1 核心用户

第一阶段只为一种核心用户优化：希望把真实 coding 工作交给多个本地 AI CLI，同时保留
控制权、独立验证和证据链的个人开发者。用户熟悉代码仓库和 CLI，但不应被要求理解
PersonaHub 的运行时表、事件协议或图调度术语。

### 2.2 Jobs-to-be-Done

| 时机 | 用户想完成的事 | 成功感受 |
| --- | --- | --- |
| 第一次打开 | 用已有代码目录和本地 AI CLI 快速完成最小设置 | “现在可以创建任务了” |
| 有开发目标时 | 用一句目标得到可解释建议，确认后运行到可信 Done | “我不用当人工路由器，但仍能控制启动” |
| 执行异常时 | 看懂发生了什么，并从安全状态恢复 | “系统没有掩盖问题，也没有擅自继续” |

### 2.3 P0 / P1 边界

**P0 旅程共四条**，按用户回到应用的理由划分（不按系统流程划分）：

| | 旅程 | 用户此刻的理由 | 频次 |
| --- | --- | --- | --- |
| **J1** | 首次配置到能干活（§4） | “我刚装上，怎么开始” | 一次性 |
| **J2** | 发起一个任务（§5） | “我有个开发目标” | 高 |
| **J3** | 跟进执行中的任务（§6） | “那个任务怎么样了”“该我了吗” | **最高** |
| **J4** | 消化一个完成的任务（§7） | “做完了吗、做对了吗、然后呢” | 高 |

三条划分原则：

- **异常恢复不是独立旅程**，是 J3 的分支（§6.3）——用户的目标始终是「把任务推进下去」，
  没有人为了「恢复一个异常」而打开应用。降级不等于降低覆盖要求。
- **介入不是异常处理，是常驻能力**（§6.5）——「阶段完成后指定下一步给谁」属于正常流程。
- **不按 UI 区域划分旅程**，否则会得到「左栏旅程/右栏旅程」，那是页面结构而非用户旅程。
  区域归属见 §6.4 信息需求矩阵。

P1 允许渐进展示：高级执行方案调整、多成员 roster 调整、Room 内协作、Artifact 详情、
Evidence 导出、Memory/Skill 候选确认。它们不能阻塞 P0 主路径，也不能让创建任务出现
第二个同级入口。

### 2.4 跨旅程的导航能力（不构成独立旅程）`[2026-08-14]`

有些能力 PRD 明确要求，但它们服务于所有旅程，不对应某个特定时机，因此不单列为旅程：

| 能力 | PRD 依据 | 要求 |
| --- | --- | --- |
| 创建、查看、**切换 Project** | §7.1 验收、§10 左侧导航 | 在 J2/J3/J4 中随时可用；切换后保持各任务自身状态，不重置进行中的执行 |
| Issues 列表 | §10 左侧导航 | 能看出每个任务当前状态与是否需要用户，无需逐个点开 |
| Agents / Skills / Settings 入口 | §10 左侧导航 | 常驻可达，但不与创建任务主入口竞争视觉权重 |

**判断标准**：用户不会「为了切换 Project」而打开应用——他打开是为了 J2/J3/J4 中的某件事，
切换只是路上的动作。把导航能力误列为旅程，会稀释真正的旅程焦点。

后移：非 coding workflow、多人协作、Board、跨 Project/多 Workspace、云端 runtime、自动长期
Memory/Skill 写入、任意图编辑器和物理并行写入。

## 3. 概念与披露规则

### 3.1 用户必须理解的概念

| PRD 概念 | 默认用户用语 | 披露方式 |
| --- | --- | --- |
| Project | 项目 | 一级上下文；说明它汇总任务、AI 成员和设置，不把它说成文件夹 |
| Workspace | 代码目录 | 仅在首次设置、切换项目和诊断时出现；显示规范化路径与 Git 分支。`[2026-08-14]` 心智是「这件工作属于哪个项目空间」（开始工作前先确定归属），不是可切换的组织维度 |
| Issue | 任务 | 全程主对象；高级信息可补充内部称为 Issue |
| Thread | 活动 | 默认按关键进展组织；对话、交接和事件属于同一任务活动，不要求先理解 Thread 类型 |
| Agent | AI 成员 | 显示名称、CLI、模型、**能力项**和当前可用性；不做强拟人包装。`[2026-08-14]` **以能力项而非固定角色描述成员**——agent 背后是 CLI 与模型，角色是可变的工作分配而非身份属性；界面按「能做什么」呈现，不按「它是 reviewer」呈现 |
| Coordinator | 方案推荐 | 作为“系统如何给出建议”的能力解释，不要求用户配置一个假 Agent |
| Issue Type | 任务类型 | P0 固定为 coding，默认不要求选择；多类型真实可用后才渐进展示 |
| Workflow Template | 工作方式 | 推荐确认时展示**建议路径与完成标准**（验证要求、什么算 Done），模板名为次级信息。`[2026-08-14]` 它是**建议与判据**，不是强制执行顺序——每一步的实际去向由 J3.2 的交接决定，见 §6.2 |
| Agent Team Template | 建议成员组合 | 只在调整推荐成员时按需出现；不作为首次设置前置知识 |
| Validation Policy | 完成要求 | 展示可读的验证清单、轮次和证据要求，不展示策略结构 |
| Collaboration Topology / Graph | 执行方案 | 用阶段/分工图解释，不先暴露图引擎术语 |
| Room | 协作现场 | 仅复杂任务出现；说明目标、成员、阶段和用户可介入动作 |
| Artifact | 阶段成果 | 复杂任务按需展示为计划、研究结论、实现记录、验证结果 |
| Evidence / Evidence Summary | 验证证据 / 完成摘要 | Done 的核心信任依据，默认展示摘要并允许追溯来源 |
| Blocked / escalation | 需要你处理 | 必须同时给出原因、影响和推荐动作 |
| Memory / Skill | 记忆候选 / 可复用做法 | Done 后按需展示，保存前必须让用户确认来源与用途 |

### 3.2 不应要求用户理解的实现概念

| 实现概念 | 默认处理 |
| --- | --- |
| Run / GraphRun / NodeRun / Attempt / EdgeTraversal | 翻译为“阶段、步骤、尝试”；仅诊断详情显示内部 ID 和精确状态 |
| ThreadEvent / Trace Events / event cursor | 汇总为可读活动；原始事件流默认折叠 |
| Handoff Packet | 展示为“已交接给谁、交接了什么”；JSON 契约默认隐藏 |
| capability tags / resolver / effective availability | 展示为“适合原因”或“不可用原因”，不暴露匹配字段 |
| Validation Policy JSON / round CAS / schema invariant | 产品层只展示完成要求、当前轮次和剩余机会；内部策略结构隐藏 |
| typed refs / provenance manifest | 展示可点击来源；ref 字符串只在复制诊断信息时出现 |
| Provenance Gate | 用户只看到“来源是否可信、保存是否需确认”；gate 名称和判定结构默认隐藏 |
| SQLite schema / WAL / migration | 不进入正常旅程；只在本地数据诊断中出现 |
| workspace lock / queue internals | 默认说“另一个任务正在使用此代码目录”；技术详情按需展开 |
| adapter protocol / auth probe 命令 / SSE | 只展示可见结果和修复动作，原始协议放诊断详情 |

### 3.3 通用披露规则

- 默认层只回答：现在在哪一步、是否需要我、下一步是什么。
- 第二层回答：谁做了什么、为何这样选、验证了什么、哪里失败。
- 第三层才提供：原始日志、事件、命令、路径、ID、规则命中和引用字符串。
- 状态词使用用户结果语言；内部枚举可在诊断详情中作为辅助，不得成为唯一说明。
- 每个视图最多一个主操作；不可执行时主操作保持可见并明确说明缺少什么。

## 4. J1 · 首次配置到能干活

### 4.1 触发、目标与终点

- 触发：首次打开应用，或当前没有可执行的 Project。
- 目标：绑定一个真实代码目录，并确认存在可用的实现与**独立**验证路径。
- 成功终点：工作台明确显示「可以创建任务」，创建任务主入口获得焦点。
- 时间目标：无外部文档辅助，5 分钟内完成。

### 4.2 主路径

| 步骤 | 用户动作 | 系统反馈 | 此刻最关心的问题 | 概念披露 | 可观察验收 |
| --- | --- | --- | --- | --- | --- |
| J1.1 | 打开应用 | 直接进入工作台，显示 3 项设置清单：代码目录、AI 成员、执行检查 | “从哪里开始？” | 只说项目/代码目录/AI 成员 | 5 秒内出现唯一“开始设置”主操作 |
| J1.2 | 选择或输入代码目录，并给项目命名 | 校验路径、读权限和 Git 基本信息；预览项目名与分支 | “选对目录了吗？” | Project/Workspace 用“项目/代码目录”表达 | 结果在 2 秒内明确为通过或给出可修复原因 |
| J1.3 | 确认项目 | 本地保存项目，进入 AI 成员检查；不要求先浏览空工作台 | “下一步还缺什么？” | 不显示数据库或内部 ID | 清单自动推进，已完成项可返回修改 |
| J1.4 `[2026-08-14]` | **配置至少两个 coding CLI adapter** | 针对当前代码目录逐个显示可用性、模型与能力项；说明为何建议两个 | “为什么要配两个？” | 展示 AI 成员、CLI、模型、能力项；probe 细节折叠 | 真实检查有 loading / 成功 / 失败 / 重试；只配一个时明确提示后果而非静默放行 |
| J1.5 | 运行执行检查 | 检查实现与验证路径是否可用；独立性不足时给出**警告而非阻塞** | “现在能安全开始吗？” | 显示验证路径，不暴露 resolver/capability 字段 | **必需项 = 至少一个可用 adapter**；第二个 adapter 是强烈建议项，缺失时以警告呈现并说明后果，不阻断“设置完成” |
| J1.6 | 选择“创建第一个任务” | 进入唯一任务创建入口，保留当前项目上下文 | “下一步该输入什么？” | 只显示任务目标 | 从首次打开到此不超过 5 分钟 |

**为什么是两个 adapter（J1.4 的依据）**：PRD §7.5 要求 validator 与 implementation 的
`cli_provider` 与 `default_model` **至少一项不同**，否则该 Issue 的 Done 必须标记为
「同源验证」，不享受同等自动信任等级。配置两个不同 CLI adapter 是满足这条要求最直接的
方式，同时让「换个成员来做」在第一天就成立。若用户环境确实只有一个可用 CLI，如实标记
同源验证，不伪装成跨模型验证。

### 4.3 空、错误与恢复

| 状态 | 原因与影响 | 推荐主操作 | 恢复后的保证 |
| --- | --- | --- | --- |
| 没有代码目录 | 尚不能执行真实任务 | “选择代码目录” | 返回 J1.2，不产生空 Project |
| 路径不存在/不可读 | 无法读取或验证代码 | “重新选择” | 保留已输入项目名，不保留无效绑定 |
| 不是 Git 仓库 | 可执行，但变化追踪与恢复能力降低 | “仍然使用”或次要“换目录” | 明确限制，不把警告冒充阻塞 |
| 未检测到 CLI | 没有可启动的 AI 成员 | “查看安装指引” | 返回后可一键重新检测 |
| CLI 未登录/Key 无效 | 当前代码目录下不可用 | “完成登录并重试” | 真实 probe 通过前不显示可执行 |
| 只配置了一个 adapter | 可以执行，但验证独立性较低 | “再配一个”或次要“继续并标记同源验证” | Done 始终保留同源标识 |
| 本地服务不可用 | 页面无法读写本地状态 | “重新连接” | 不丢失已持久化的设置进度 |

### 4.4 不可逆操作

首次配置没有不可逆操作。替换代码目录或删除项目属于后续设置动作，必须单独确认并说明
对历史任务的影响，不能混入首次配置主路径。

## 5. J2 · 发起一个任务

### 5.1 触发、目标与终点

- 触发：当前 Project 已处于「可以创建任务」状态，用户有一个开发目标。
- 目标：把目标交出去并真正启动执行。
- 成功终点：任务显示为「已排队」或「运行中」。
- 操作目标：从输入目标到启动不超过 3 次主要操作，且全局只有一个创建入口。

### 5.2 主路径

| 步骤 | 用户动作 | 系统反馈 | 此刻最关心的问题 | 概念披露 | 可观察验收 |
| --- | --- | --- | --- | --- | --- |
| J2.1 | 从固定主入口输入开发目标并提交 | 保留原文，进入建议生成；若信息不足只问一个必要问题 | “系统理解我要什么了吗？” | 使用“目标”，不要求填 Issue schema | 页面只有一个创建任务主入口 |
| J2.2 | 查看推荐方案；必要时调整 | 展示建议的第一步执行者、验证方式、选择理由与不可用候选的原因；每次调整后重新校验成员在当前 Workspace 的可用性与能力 | “为什么这样安排，能改吗？” | 转译为“执行方案”；规则来源可展开 | 推荐不声称语义理解；确认前不创建 Issue/Run，调整不留下执行记录 |
| J2.3 | 选择“确认并开始” | 原子创建任务和执行单元；立即显示已排队或运行中 | “到底启动了吗？” | 不暴露 GraphRun ID | 从 J2.1 到启动最多 3 次主要操作；重复点击不重复创建 |

### 5.3 空、错误与恢复

| 状态 | 原因与影响 | 推荐主操作 | 恢复后的保证 |
| --- | --- | --- | --- |
| 目标为空或不可执行 | 无法形成任务 | “补充目标” | 不创建 Issue/Run |
| 用户取消推荐 | 用户尚未批准真实执行 | “返回修改目标” | 不创建 Issue/Run；保留目标草稿供继续编辑 |
| 没有合格 AI 成员 | 推荐无法满足执行或验证能力 | “修复 AI 配置” | 返回后保留目标和已选项 |
| 推荐有冲突/无唯一候选 | 系统拒绝猜测 | “选择执行者” | 显式选择后重新校验 Workspace 可用性与能力 |
| Workspace 正被使用 | 当前任务安全排队，不代表故障 | “查看队列” | 获锁后按顺序启动，期间可取消排队 |

## 6. J3 · 跟进执行中的任务

**这是频次最高的一条旅程。** PRD §6 第一屏的默认状态即「中间默认显示最近 active Issue
的 primary Thread」——用户回到应用最常见的理由不是创建新任务，而是「那个任务怎么样了」。

### 6.1 触发、目标与终点

- 触发：任务已启动（排队中/运行中/验证中）——**既包括 J2.3 确认后连续观察，也包括关闭后
  重新回到应用**；或收到需要判断的提示。
- 目标：知道进行到哪一步、是否需要自己、下一步会发生什么；必要时介入纠正。
- 成功终点：任务推进到 Done，或用户明确选择了改变策略/停止/等待。

### 6.2 主路径

| 步骤 | 用户动作 | 系统反馈 | 此刻最关心的问题 | 概念披露 | 可观察验收 |
| --- | --- | --- | --- | --- | --- |
| J3.1 | 打开任务，或不操作只观察 | 持续回答当前阶段、是否需要用户、下一步；关键活动展开，技术日志折叠 | “进行到哪、要不要我？” | 默认展示阶段/成员/摘要 | 状态变化后 2 秒内有可见反馈；无需盯日志判断进度 |
| J3.2 `[2026-08-14]` | 阶段完成，**指派下一步** | **停在这里等待指派**：展示上一步的结论与产出、建议的执行者及理由、可选成员及其能力项 | “这一步做完了什么？下一步该给谁？” | 用“交给谁”表达，不暴露 proposal/dispatch 术语 | 任务停在明确的等待状态，**不自行接力**；指派说明与可选成员在同一视区；指派后立即启动，无二次确认 |
| J3.3 | 等待验证结果 | 明确标注被验证的版本与执行者，以及依据哪些验证要求 | “验的是刚才那份结果吗？” | 展示验证要求清单 | 验证对象与执行者可见，不需要用户推断 |
| J3.4 | 查看验证结果 | pass 且证据完整才进入 Done；fail 则携带 findings 回到修复 | “为什么能相信结论？” | 显示轮次、独立性与关键证据 | pass 时 Done 与 Evidence Summary 在同一状态更新中出现 |
| J3.5 `[2026-08-14]` | fail 后判断**趋势** | 展示本轮 findings 与上一轮的重复项，重复即提示「这一项第 N 轮仍未解决」 | “这样下去能收敛吗？” | 用“第 N 轮 / 仍未解决的问题”表达，不暴露 round CAS 与策略结构 | **每一轮结束都是介入点**，不必等撞上限；重复与新增 findings 视觉可区分 |
| J3.6 `[2026-08-14]` | 判断不会收敛时改变策略 | 提供换执行者、改验证要求、补充约束、直接叫停四条动作，均无需先进入 Blocked | “我能换个方法吗？” | 用结果语言表达四条动作 | 任意轮次可执行，且不丢失已产出的证据与 findings |

### 6.2.1 P0 采用完全手动指派 `[2026-08-14 决策]`

**决策**：P0 阶段阶段间流转**完全由用户指派驱动**，系统不自行接力。J3.2 是常态步骤，
不是异常介入。

**这不违背 PRD §4.1 的核心承诺。** 该承诺要消除的是「在多个 CLI 之间反复切换、**复制
上下文**和手动下发工作指令」。完全手动指派下：

| 仍然自动 | 需要用户 |
| --- | --- |
| handoff packet 生成与传递（上一步结论、变更文件、证据引用自动带给下一棒） | 决定下一步交给谁 |
| agent 启动、执行、事件记录 | — |
| 验证执行与结论判定（一旦指派了验证者） | — |
| 证据收集与 Evidence Summary | — |

用户**从不需要复制上下文**，只需要回答「下一步给谁」这一个问题。人肉路由器的负担被消除
的是"搬运"，不是"决策"。

**为什么 P0 选完全手动**：

1. **固定顺序为了表达「可能循环」付出的状态成本极高**——F004 为此引入了
   `validation_round_count`、`max_validation_rounds`、不可变 `validation_round`、round CAS、
   独立且显式的 round reset、reset 后仍 Blocked 需二次 unblock。而在手动指派下，
   「再检视一轮」就是「下一步还是给检视者」，不需要任何额外状态。`BUG-003`
   （中断 validator 死锁 round 槽位）正是这套状态机的复杂度代价。
2. **手动指派的实现难度接近于零**，难度曲线在后面——等真的需要自动调度时，
   已有真实的指派数据可以判断该自动化什么。
3. **它天然解掉 NOTE-003/005/006/007**：换人是用户自己的动作，不存在"不解释"；
   指派入口即主路径，不存在"找不到"；每个阶段结束都是介入点，不存在"只能等撞上限"。

**后续演进**：出现"每次都指派给同一个人"的重复模式后，再考虑「记住选择 / 自动继续」
选项；语义型主 Agent 自动调度属于更后面的阶段，需先修订 ADR 0007（当前裁定 Coordinator
为进程内确定性规则引擎、只推荐不派工）。

### 6.3 异常分支：理解与安全恢复

异常不是独立旅程，而是本条旅程的分支——用户的目标始终是「把任务推进下去」。

| 步骤 | 用户动作 | 系统反馈 | 此刻最关心的问题 | 可观察验收 |
| --- | --- | --- | --- | --- |
| J3.7 | 进入异常任务 | 置顶状态卡同时显示“发生了什么、影响什么、建议做什么” | “需要我吗？” | 进入后无需滚动即可看到状态与主操作 |
| J3.8 | 查看原因摘要 | 展示最后成功阶段、失败阶段、Workspace 是否安全、未完成事项 | “已有成果还在吗？” | 明确哪些结果保留、哪些未经验证；错误码/stderr/事件 ID 折叠 |
| J3.9 | 选择推荐动作，或先补充信息/授权/更换成员 | 提交前预览动作影响；不支持的恢复路径明确拒绝 | “按下后会发生什么？” | 主操作唯一，危险授权需单独确认 |
| J3.10 | 确认恢复 | Issue 先回 Ready，再由用户明确重新启动；新尝试引用旧结果但不覆盖旧记录 | “会不会重复或跳步？” | 已完成步骤不重复；新旧尝试都可追溯 |

**分类恢复规则**：

| 异常 | 原因与影响 | 推荐主操作 | 禁止的误导行为 |
| --- | --- | --- | --- |
| failed | AI/命令明确失败，当前阶段未完成 | “按建议重试” | 不显示为系统中断或 Done |
| interrupted | 服务/进程异常退出，进行中尝试不可信 | “从此步骤重新开始” | 不把重启前 running 假装成功 |
| cancelled | 用户主动停止 | “重新开始” | 不自动恢复，不与 failed 混淆 |
| Adapter 不可用 | 指定成员在当前 Workspace 无法执行 | “重新检查”或“选择替代成员” | 不静默换成列表第一个可用成员 |
| Workspace 忙 | 另一个写任务持锁 | “查看队列” | 不称为崩溃，不并发写入 |
| 权限/危险动作 | 需要凭据或可能造成不可逆/越界影响 | “审查请求” | 不把原始认证错误作为唯一解释 |
| validation fail | 结果不满足要求但尚可修复 | “查看 findings 并修复” | 不丢失 findings，不重置轮次 |
| round limit | 多轮验证未收敛 | “审查并重置验证预算” | reset 不得自动 unblock 或自动运行 |
| 需求冲突/证据不足 | 只能由用户补充判断 | “补充决定/证据” | 不让 AI 猜测后继续 |
| 实现失败 | 当前结果不能进入验证 | “查看建议并重试” | 新尝试保留旧失败原因与已产出证据 |

### 6.4 信息需求矩阵 `[2026-08-14 新增]`

每个状态下用户必须一眼回答什么，以及该信息落在**中间协作现场**还是**右栏快照**。
划分标准见 `reviews/concept-mapping.md` §5.1：**事件进中间，快照进右栏**。

| 任务状态 | 必须一眼回答 | 中间（事件与动作） | 右栏（快照与索引） |
| --- | --- | --- | --- |
| 已排队 | 在等什么、前面几个 | 排队说明 | 队列位置、占锁任务 |
| 执行中 | 现在哪一步、谁在做、要不要我 | run events 流 | 执行者状态、耗时、本步已产出 |
| **等待指派**（P0 常态） | **上一步产出了什么、可选的下一步是谁** | **交接卡片 + 指派入口** | 可选成员及其能力项与可用性 |
| 验证中 | 验的是哪个版本、由谁验 | validation events | 验证要求清单、执行者 |
| 反复未收敛 | **第几轮、哪些 findings 重复** | **各轮 findings 对比 + 四条动作** | 第 N 轮 / 共 M 轮 |
| Blocked | 卡在什么、影响什么、怎么解 | Blocked 卡片 + 推荐动作 | blocker 类型摘要 |
| Done | 交付了什么、验证结论 | 完成事件 | Evidence 索引、文件变化摘要 |

三条推论：

1. **每行的「必须一眼回答」即需求级 E2E 的断言点**，可直接用于 `ST-T03` 旅程—测试映射。
2. **所有动作都在中间**（PRD §10 明确要求），右栏不承载动作，只做快照与索引。
3. **右栏内容随状态变化，但布局不必重排**——它承载的是快照，固定区块顺序即可。

### 6.5 执行期间的介入能力

**依据**：PRD §5 Room 定义已承诺 Human Lead 能力（打断、纠正方向、要求暂停、指定某个
agent 接手、要求提供证据或重做），v0.1/v0.2 未落地；dogfood NOTE-003~007 的共同根因
即「执行现场缺少人的位置」。

用户在任务执行期间**始终**具备以下能力，不需要先进入某个特殊模式：

| 能力 | 何时可用 | 用户语义 | 边界 |
| --- | --- | --- | --- |
| 指定下一步由谁做 | 任意时刻 | “换 <成员> 来做这一步” | 受当前阶段能力要求约束；不匹配时说明原因而非静默拒绝 |
| 打断当前执行 | 运行中 | “先停一下” | 停止后 Workspace 必须回到安全状态，已产出结果标注为“未经验证” |
| 补充约束或纠正方向 | 任意时刻 | “补充要求：…” | 作为下一轮明确输入，不覆盖历史记录 |
| 要求提供证据 / 重做 | 任一阶段结束后 | “这一步证据不足，重做” | 重做计为新尝试，旧尝试可追溯 |

**指派的交互形态**：以 `@` 触发成员列表为主入口，与常驻选择器并存。

- `@` 是从 IM 到 clowder 通用的指派心智，成本低、直觉强；v0.2 只实现了常驻下拉，
  用户打 `@` 无反应，导致能力存在但不可达（NOTE-006）。
- 借鉴 clowder 的机械规则：**`@句柄` 仅在行首独立一行时生效**（行中、URL 内不路由），
  避免正文提及成员名被误判为指派。markdown 列表/引用前缀后的首字符合法。
- **指派能力属于 Thread，不属于 Room**。Room 是阶段性临时协作现场，而单 agent 顺序执行
  时根本没有 Room；若指派只在 Room 内可用，最常见的场景反而无法介入。Room 增加的是
  多成员、拓扑与终止条件，不是「能不能指派」本身。

### 6.6 设计前提：自动回路是复杂度所在

> **系统自动决定下一步的地方，都是复杂度所在**——不因为链条是「顺序」就简单。
> 凡是存在自动回路（实现 → 验证 → findings 回流 → 再实现）的路径，都必须提供
> **可见的收敛信号**与**人的介入点**；这条对单 agent 顺序执行、多 agent 协作和未来的
> Room 一视同仁。

判断依据：

- **复杂度来自循环，不来自并发。** 顺序执行只是拓扑简单（一条线），一旦加上失败回流
  就成了带循环的状态机——终止条件、状态累积（round count、findings、workspace 是否
  干净）、“何时判定不会收敛”全都要设计。而顺序执行恰恰是自动回路最容易形成的地方：
  写 → 审这条固定链天然构成回环。
- **换成多 agent 并不能消解它。** review → 打回 → 重做 → 再 review，参与者从一个换成
  三个，循环照旧。因此介入能力不能设计成“复杂协作才需要的高级功能”。
- **手动指派不解决不收敛，只是转移判断权。** 同一个问题三个成员都修不好时，复杂度仍在，
  只是从系统转到了人身上；且手动指派要求用户持续在场，链条一长本身就是负担。

因此介入能力按**自动回路**而非按协作形态定义：哪里有系统自动决定下一步，哪里就要有
收敛信号和介入点。

### 6.7 不可逆操作

Git push、force push、跨 Workspace 写入和不可逆删除不作为普通运行按钮的隐含副作用。
触发时任务进入需要用户处理的状态，说明动作、影响范围和默认拒绝结果；未明确授权不得继续。

拒绝危险请求、保持 Blocked、取消排队或取消运行都是安全默认值。授权 push、force push、
跨 Workspace 写入、不可逆删除，以及重置完整验证预算，均需独立确认并写入活动记录；
确认文案必须展示具体对象和影响，不能用笼统「继续」。

## 7. J4 · 消化一个完成的任务 `[2026-08-14 新增]`

### 7.1 触发、目标与终点

- 触发：任务进入 Done，或用户回来查看已完成的任务。
- 目标：判断交付了什么、能不能信、接下来做什么。
- 成功终点：用户无需阅读原始日志即可判断结果，且每条结论都可逐项追溯到证据。

**为什么它是独立旅程**：PRD §7.6 / §7.7 各有独立验收条款（evidence summary 可导出、
evidence refs 可追溯到 thread events、memory 有来源可查、memory 不污染 Thread 原始记录）。
但**用户不会为了「生成一份 evidence summary」而打开应用**——他打开是为了确认「做完了吗、
做对了吗、然后呢」，因此本旅程以判断为轴，不以产物为轴。

### 7.2 主路径

| 步骤 | 用户动作 | 系统反馈 | 此刻最关心的问题 | 概念披露 | 可观察验收 |
| --- | --- | --- | --- | --- | --- |
| J4.1 | 查看完成摘要 | 默认显示结果、变更文件、测试/构建结论、风险与后续建议 | “交付了什么？” | Evidence Summary 为主，refs/日志折叠 | 无需阅读原始日志即可判断结果 |
| J4.2 | 追溯某条结论的依据 | 从摘要任一条目下钻到对应证据与原始事件 | “这条结论凭什么？” | 展示可点击来源；ref 字符串只在复制诊断信息时出现 | 每条验证结论都能追到 thread event，不存在无来源结论 |
| J4.3 | 判断验证可信度 | 明确标注是否为「同源验证」及其含义 | “这个验证独立吗？” | 用“验证独立性”表达，不暴露 provider/model 匹配规则 | 同源验证在 Done 状态上持续可见，不只在完成瞬间提示 |
| J4.4 `[P1]` | 导出或沉淀 | 手动触发导出 Markdown；memory candidates 需用户确认后才写入 | “这次经验要留下来吗？” | 展示候选来源与用途 | 默认不自动写入 workspace 文件系统，不自动写长期 Memory |

### 7.3 空、错误与恢复

| 状态 | 原因与影响 | 推荐主操作 | 恢复后的保证 |
| --- | --- | --- | --- |
| 证据不完整 | 即使 agent 声称完成也不能 Done | “补充验证” | 证据补齐并重新验证后才允许 Done |
| 同源验证 | 可以完成，但验证独立性较低 | “了解影响”或“用另一成员复验” | Done 始终保留同源标识，不因时间推移淡化 |
| 摘要与实际变更不一致 | 结论不可信 | “查看原始变更” | 以原始事件为准，摘要标注为待复核 |

### 7.4 P0 / P1 边界

- **P0**：J4.1–J4.3。Evidence Summary 的生成、展示与追溯是「可信 Done」的构成部分，
  不是可选项。
- **P1**：J4.4 导出 Markdown 与 Memory 确认写入。PRD §7.7 明确 memory 自动保存的安全
  前提 Provenance Gate 要到 v0.5 才落地，因此 P0/P1 阶段一律需用户确认。

## 9. 可观察验收指标

1. **首次可执行时间**：从首次工作台可交互开始计时，到“可以创建任务”状态出现为止，
   无外部文档辅助不超过 5 分钟；测试记录开始/结束时间、阻塞点和是否查看外部资料。
2. **创建入口与操作数**：所有工作台空/非空状态只有一个同级创建任务主入口；从聚焦目标输入
   到任务显示“已排队/运行中”不超过 3 次主要操作，Playwright 按实际点击计数。
3. **运行信息优先级**：在 1440×900 首屏内无需滚动即可找到当前阶段、是否需要用户、下一步；
   scripted dogfood 要求操作者在 10 秒内回答三问，答错任一项即失败。
4. **阻塞说明完整性**：每个 Blocked/failed/interrupted fixture 同时可见原因、影响和且仅一个
   推荐主操作；测试不得通过读取内部 error code 或展开原始日志完成判断。
5. **常见恢复可理解性**：对 Adapter 不可用、进程中断、validation fail、round limit 和权限请求，
   scripted dogfood 操作者须在每个状态出现后 30 秒内、不展开原始日志地选择正确恢复动作；
   选错、超时或必须查看 error code 才能判断均为失败。恢复后状态、历史尝试与证据保持可追溯。
6. **指派可完成性** `[2026-08-14]`：阶段完成后，操作者须在不展开任何折叠区的前提下答出
   「上一步产出了什么、可选的下一步是谁」，并在 15 秒内完成一次指派。答错任一项、
   或需要翻找才能找到指派入口，均为失败。
7. **不收敛可判断性** `[2026-08-14]`：第 2 轮验证失败后，操作者须在 15 秒内答出「哪些问题是
   上一轮就有的」；重复 findings 与新增 findings 必须视觉可区分，不允许只靠逐条比对文字。
8. **结论可追溯性** `[2026-08-14]`：Done 摘要中任取一条验证结论，须能在 2 次点击内到达其
   原始事件；不存在无来源结论。同源验证标识在 Done 状态上持续可见。

## 10. 页面拼装的行为边界 `[2026-08-14 改写]`

页面拼装（重置计划 M4）必须覆盖本文三条旅程及状态矩阵，不得从现有 React 页面
反推行为。拼装可以用静态数据模拟本地检查、执行、验证和恢复，但每个模拟反馈必须遵守
本文的状态与披露规则。未在本文定稿的争议点必须回到旅程评审，不交给拼装阶段自行决定。

**与参考项目素材的关系**：拼装从 multica / clowder-ai 的冻结页取形态，但取舍依据是本文。
剪贴规则——**每剪一个区块，必须能指回本文的某一步和某个信息需求；指不回去的一律删掉**。
若某个旅程步骤找不到任何参考区块可承载，只有两种可能：本文写得太抽象（回来改），
或它属于空白区（记入 `reviews/blank-areas.md`，原创设计）。

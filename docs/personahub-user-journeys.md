## 1. 产品意图

PersonaHub 面向同时使用多个本地 AI CLI 的个人开发者，把“表达开发目标、选择合适的
AI 成员、执行、验证、恢复和查看证据”收进一条可控旅程。它不是聊天壳，也不是要求用户
理解调度引擎的运维面板。

用户购买的结果不是“启动了一个 agent”，而是：

1. 不离开 PersonaHub，也不在多个终端之间复制上下文，就能把一个真实 coding 目标交出去。
2. 执行期间随时知道进行到哪一步、是否需要自己、接下来会发生什么。
3. 系统只在验证通过且证据完整时宣告完成；失败时给出原因、影响和安全恢复动作。
4. 用户保留对推荐、危险操作、阻塞恢复和长期沉淀的最终控制权。

成功终点是一个可信的 Done：目标结果、文件变化、验证结论和可追溯证据同时存在。单纯
“进程退出成功”“agent 说完成了”或“测试很多”都不构成 Done。

### 1.1 产品承诺

- 本地优先、单用户、开箱即进入工作台，不依赖云账号或 landing page。
- Project 管理工作上下文，Workspace 提供真实文件与执行边界；第一阶段一对一绑定。
- 一个任务拥有连续的活动记录，AI 成员可交接而无需用户复制上下文。
- 系统推荐工作方式和执行者并解释原因，用户确认后才启动真实工作。
- 实现结束后自动进入独立验证；验证失败回到修复，不能收敛或需要判断时进入 Blocked。
- Done 必须绑定 Evidence Summary；原始日志、事件和 ID 保留可追溯，但不占据默认视线。

### 1.2 真实技术约束

这些约束限制旅程可承诺的行为，但不直接决定页面结构：

| 约束 | 对旅程的影响 |
| --- | --- |
| 本地 Node.js 服务 + Vite/React 客户端 | 应用需要本地服务可用；首次启动必须能识别“服务未就绪”并给恢复动作 |
| 本地 SQLite，单进程、单用户 | 数据默认留在本机；不设计账号、组织或多人权限步骤 |
| Project 第一阶段只绑定一个本地 Workspace | 首次设置只要求选择一个本地目录；多 Workspace 不进入主路径 |
| 同一 Workspace 的写执行受排他锁保护 | 多个任务可能排队；界面必须区分“排队”与“执行中”并解释原因 |
| 三个 CLI adapter 均为 one-shot Run | 后续指令通过已保存的活动、交接和证据重组上下文，不暗示 CLI 进程永久在线 |
| Adapter 可用性按 Workspace 判定 | “可执行”检查必须针对当前 Project 的 Workspace，而不是只显示全局已安装 |
| Coordinator 当前是确定性规则，不是语义型 LLM | 推荐理由应展示规则和排除原因，不用“AI 已理解一切”之类文案 |
| 推荐确认后才创建 Issue 与 Run | 推荐页必须是明确的人类闸门，取消不能留下半成品任务 |
| 写任务串行；未验证强制隔离前只读节点也物理串行 | 图上可展示并行分工，但进度文案不得承诺同时运行 |
| Run 可 completed / failed / interrupted / cancelled | 失败、中断、取消必须可区分，不能统一显示为“出错” |
| Blocked 只能由用户处理后回 Ready | 恢复动作不会静默自动重跑；用户能复核变化后再次启动 |
| 推送凭据默认不下发，越界/不可逆操作需 escalation | 被阻止时说明保护机制和待确认事项，不把认证失败原文丢给用户 |
| SSE 事件可重放，重启恢复持久状态 | 刷新或服务重启后应恢复可解释状态，已完成步骤不应看似丢失或重复 |

## 2. 核心用户、任务与范围

### 2.1 核心用户

第一阶段只为一种核心用户优化：希望把真实 coding 工作交给多个本地 AI CLI，同时保留
控制权、独立验证和证据链的个人开发者。用户熟悉代码仓库和 CLI，但不应被要求理解
PersonaHub 的运行时表、事件协议或图调度术语。

### 2.2 Jobs-to-be-Done

| 时机 | 用户想完成的事 | 成功感受 |
| --- | --- | --- |
| 第一次打开 | 用已有代码目录和本地 AI CLI 快速完成最小设置 | “现在可以创建任务了” |
| 有开发目标时 | 用一句目标得到可解释建议，确认后运行到可信 Done | “我不用当人工路由器，但仍能控制启动” |
| 执行异常时 | 看懂发生了什么，并从安全状态恢复 | “系统没有掩盖问题，也没有擅自继续” |

### 2.3 P0 / P1 边界

P0 必须连续可完成：首次设置、创建并执行 coding 任务、查看进度、自动验证、查看 Done
证据、处理常见 Blocked/failed/interrupted 并安全恢复。

P1 允许渐进展示：高级 Workflow/Topology 选择、多 Agent roster 调整、Room 内介入、Artifact
详情、历史 Memory/Skill 候选。它们不能阻塞 P0 主路径，也不能让创建任务出现第二个同级入口。

后移：非 coding workflow、多人协作、Board、跨 Project/多 Workspace、云端 runtime、自动长期
Memory/Skill 写入、任意图编辑器和物理并行写入。

## 3. 概念与披露规则

### 3.1 用户必须理解的概念

| PRD 概念 | 默认用户用语 | 披露方式 |
| --- | --- | --- |
| Project | 项目 | 一级上下文；说明它汇总任务、AI 成员和设置，不把它说成文件夹 |
| Workspace | 代码目录 | 仅在首次设置、切换项目和诊断时出现；显示规范化路径与 Git 分支。`[2026-08-14]` 心智是「这件工作属于哪个项目空间」（开始工作前先确定归属），不是可切换的组织维度 |
| Issue | 任务 | 全程主对象；高级信息可补充内部称为 Issue |
| Thread | 活动 | 默认按关键进展组织；对话、交接和事件属于同一任务活动，不要求先理解 Thread 类型 |
| Agent | AI 成员 | 显示名称、CLI、模型、**能力项**和当前可用性；不做强拟人包装。`[2026-08-14]` **以能力项而非固定角色描述成员**——agent 背后是 CLI 与模型，角色是可变的工作分配而非身份属性；界面按「能做什么」呈现，不按「它是 reviewer」呈现 |
| Coordinator | 方案推荐 | 作为“系统如何给出建议”的能力解释，不要求用户配置一个假 Agent |
| Issue Type | 任务类型 | P0 固定为 coding，默认不要求选择；多类型真实可用后才渐进展示 |
| Workflow Template | 工作方式 | 推荐确认时展示阶段和验证方式；模板名为次级信息 |
| Agent Team Template | 建议成员组合 | 只在调整推荐成员时按需出现；不作为首次设置前置知识 |
| Validation Policy | 完成要求 | 展示可读的验证清单、轮次和证据要求，不展示策略结构 |
| Collaboration Topology / Graph | 执行方案 | 用阶段/分工图解释，不先暴露图引擎术语 |
| Room | 协作现场 | 仅复杂任务出现；说明目标、成员、阶段和用户可介入动作 |
| Artifact | 阶段成果 | 复杂任务按需展示为计划、研究结论、实现记录、验证结果 |
| Evidence / Evidence Summary | 验证证据 / 完成摘要 | Done 的核心信任依据，默认展示摘要并允许追溯来源 |
| Blocked / escalation | 需要你处理 | 必须同时给出原因、影响和推荐动作 |
| Memory / Skill | 记忆候选 / 可复用做法 | Done 后按需展示，保存前必须让用户确认来源与用途 |

### 3.2 不应要求用户理解的实现概念

| 实现概念 | 默认处理 |
| --- | --- |
| Run / GraphRun / NodeRun / Attempt / EdgeTraversal | 翻译为“阶段、步骤、尝试”；仅诊断详情显示内部 ID 和精确状态 |
| ThreadEvent / Trace Events / event cursor | 汇总为可读活动；原始事件流默认折叠 |
| Handoff Packet | 展示为“已交接给谁、交接了什么”；JSON 契约默认隐藏 |
| capability tags / resolver / effective availability | 展示为“适合原因”或“不可用原因”，不暴露匹配字段 |
| Validation Policy JSON / round CAS / schema invariant | 产品层只展示完成要求、当前轮次和剩余机会；内部策略结构隐藏 |
| typed refs / provenance manifest | 展示可点击来源；ref 字符串只在复制诊断信息时出现 |
| Provenance Gate | 用户只看到“来源是否可信、保存是否需确认”；gate 名称和判定结构默认隐藏 |
| SQLite schema / WAL / migration | 不进入正常旅程；只在本地数据诊断中出现 |
| workspace lock / queue internals | 默认说“另一个任务正在使用此代码目录”；技术详情按需展开 |
| adapter protocol / auth probe 命令 / SSE | 只展示可见结果和修复动作，原始协议放诊断详情 |

### 3.3 通用披露规则

- 默认层只回答：现在在哪一步、是否需要我、下一步是什么。
- 第二层回答：谁做了什么、为何这样选、验证了什么、哪里失败。
- 第三层才提供：原始日志、事件、命令、路径、ID、规则命中和引用字符串。
- 状态词使用用户结果语言；内部枚举可在诊断详情中作为辅助，不得成为唯一说明。
- 每个视图最多一个主操作；不可执行时主操作保持可见并明确说明缺少什么。

## 4. 旅程一：首次设置到“可以创建任务”

### 4.1 触发、目标与终点

- 触发：首次打开应用，或当前没有可执行的 Project。
- 目标：绑定一个真实代码目录并确认至少有一条可用的实现/验证路径。
- 成功终点：工作台明确显示“可以创建任务”，创建任务主入口获得焦点。
- 时间目标：无外部文档辅助，5 分钟内完成。

### 4.2 主路径

| 步骤 | 用户动作 | 系统反馈 | 此刻最关心的问题 | 概念披露 | 可观察验收 |
| --- | --- | --- | --- | --- | --- |
| J1.1 | 打开应用 | 直接进入工作台，显示 3 项设置清单：代码目录、AI CLI、执行检查 | “从哪里开始？” | 只说项目/代码目录/AI CLI | 5 秒内出现唯一“开始设置”主操作 |
| J1.2 | 选择或输入代码目录，并给项目命名 | 校验路径、读权限和 Git 基本信息；预览项目名与分支 | “选对目录了吗？” | Project/Workspace 用“项目/代码目录”表达 | 结果在 2 秒内明确为通过或给出可修复原因 |
| J1.3 | 确认项目 | 本地保存项目，进入 AI CLI 检查；不要求先浏览空工作台 | “下一步还缺什么？” | 不显示数据库或内部 ID | 清单自动推进，已完成项可返回修改 |
| J1.4 | 选择已检测到的 CLI，或按引导完成登录/API key 配置 | 针对当前代码目录显示可用性、模型和实现/验证能力 | “它真的能在这里工作吗？” | 展示 AI 成员、CLI、模型；probe 细节折叠 | 真实检查有 loading、成功、失败和重试状态 |
| J1.5 | 运行执行检查 | 检查实现与验证路径；若同源则说明信任等级较低但不伪装独立验证 | “现在能安全开始吗？” | 显示验证路径，不暴露 resolver/capability 字段 | 所有必需项通过后出现“设置完成” |
| J1.6 | 选择“创建第一个任务” | 进入唯一任务创建入口，保留当前项目上下文 | “下一步该输入什么？” | 只显示任务目标 | 从首次打开到此不超过 5 分钟 |

### 4.3 空、错误与恢复

| 状态 | 原因与影响 | 推荐主操作 | 恢复后的保证 |
| --- | --- | --- | --- |
| 没有代码目录 | 尚不能执行真实任务 | “选择代码目录” | 返回 J1.2，不产生空 Project |
| 路径不存在/不可读 | 无法读取或验证代码 | “重新选择” | 保留已输入项目名，不保留无效绑定 |
| 不是 Git 仓库 | 可执行，但变化追踪与恢复能力降低 | “仍然使用”或次要“换目录” | 明确限制，不把警告冒充阻塞 |
| 未检测到 CLI | 没有可启动的 AI 成员 | “查看安装指引” | 返回后可一键重新检测 |
| CLI 未登录/Key 无效 | 当前代码目录下不可用 | “完成登录并重试” | 真实 probe 通过前不显示可执行 |
| 只有同源验证 | 可以执行，但验证独立性较低 | “继续并标记同源验证” | Done 始终保留同源标识 |
| 本地服务不可用 | 页面无法读写本地状态 | “重新连接” | 不丢失已持久化的设置进度 |

### 4.4 不可逆操作

首次设置没有不可逆操作。替换代码目录或删除项目属于后续设置动作，必须单独确认并说明
对历史任务的影响，不能混入首次设置主路径。

## 5. 旅程二：输入目标到可信 Done

### 5.1 触发、目标与终点

- 触发：当前 Project 已处于“可以创建任务”状态。
- 目标：输入 coding 目标，确认系统建议，运行、验证并获得可信结果。
- 成功终点：任务为 Done，目标结果、文件变化、验证结论与来源证据同时可见。
- 操作目标：从输入目标到启动不超过 3 次主要操作，且只有一个创建入口。

### 5.2 主路径

| 步骤 | 用户动作 | 系统反馈 | 此刻最关心的问题 | 概念披露 | 可观察验收 |
| --- | --- | --- | --- | --- | --- |
| J2.1 | 从固定主入口输入开发目标并提交 | 保留原文，进入建议生成；若信息不足只问一个必要问题 | “系统理解我要什么了吗？” | 使用“目标”，不要求填 Issue schema | 页面只有一个创建任务主入口 |
| J2.2 | 查看推荐方案；必要时调整高级选项 | 展示工作方式、阶段、建议 AI 成员、验证方式、选择理由和不可用候选原因；每次调整后重新校验成员在当前 Workspace 的可用性与能力 | “为什么这样安排，能改吗？” | Workflow/Topology 转译为执行方案；规则来源可展开 | 推荐不声称语义理解；确认前不创建 Issue/Run，调整不留下执行记录 |
| J2.3 | 选择“确认并开始” | 原子创建任务和执行单元；立即显示已排队或运行中 | “到底启动了吗？” | 不暴露 GraphRun ID | 从 J2.1 到启动最多 3 次主要操作；重复点击不重复创建 |
| J2.4 | 不操作，或查看活动 | 顶部持续回答当前阶段、是否需要用户、下一步；关键活动展开，技术日志折叠 | “进行到哪、我要做什么？” | 默认展示阶段/AI 成员/摘要 | 状态变化后 2 秒内有可见反馈；无需盯日志判断进度 |
| J2.5 | 等待实现完成 | **换人这一刻必须是可见事件**：说明实现已完成、按哪个工作方式进入验证、由谁执行、依据什么验证要求；同时给出「接管」入口 | “为什么现在换人了？验证的是刚才的结果吗？” | 展示交接摘要、文件变化、验证要求；工作方式可一键跳转查看/修改 | 明确标注被验证版本与执行者；**交接说明与「接管」入口在同一视区内可见** |
| J2.5a `[2026-08-14]` | 不操作（默认），或在倒计时内选择接管 | 默认放行并显示短倒计时（如"3 秒后交给 <验证者>"）；用户可在此否决、改指派执行者、或补充约束后再放行 | “我还来得及干预吗？” | 用"接管/换人/补充要求"表达，不暴露 proposal/dispatch 术语 | 不操作时自动继续，不额外增加正常路径成本；接管后原交接不丢失，作为新一轮输入 |
| J2.6 | 查看验证结果 | pass 且证据完整才进入 Done；fail 则回到修复并携带 findings | “为什么能相信完成？” | 显示验证轮次、独立性和关键证据 | Done 与 Evidence Summary 同一状态更新中出现 |
| J2.6a `[2026-08-14]` | fail 后查看本轮 findings 与**轮次趋势** | 展示本轮 findings 与上一轮的重复项；重复即给出显式提示「这一项第 N 轮仍未解决」 | “这样下去能收敛吗？” | 用"第 N 轮 / 仍未解决的问题"表达，不暴露 round CAS 与策略结构 | **每一轮结束都是介入点**，不必等撞上限；重复 findings 必须与新增 findings 视觉可区分 |
| J2.6b `[2026-08-14]` | 判断不会收敛时主动改变策略 | 提供换执行者、改验证要求、补充约束、直接叫停四条动作，均不需要先进入 Blocked | “我能换个方法吗？” | 用结果语言表达四条动作 | 用户可在任意轮次执行，且不丢失已产出的证据与 findings |
| J2.7 | 查看完成摘要 | 默认显示结果、变更文件、测试/构建结论、风险和后续建议；可追溯原始证据 | “交付了什么，还要做什么？” | Evidence Summary 为主，refs/日志折叠 | 用户无需阅读原始日志即可判断结果，仍可逐项追溯 |

### 5.3 空、错误与恢复

| 状态 | 原因与影响 | 推荐主操作 | 恢复后的保证 |
| --- | --- | --- | --- |
| 目标为空或不可执行 | 无法形成任务 | “补充目标” | 不创建 Issue/Run |
| 用户取消推荐 | 用户尚未批准真实执行 | “返回修改目标” | 不创建 Issue/Run；保留目标草稿供用户继续编辑 |
| 没有合格 AI 成员 | 推荐无法满足执行或验证能力 | “修复 AI 配置” | 返回后保留目标和已选高级项 |
| 推荐有冲突/无唯一候选 | 系统拒绝猜测 | “选择执行者” | 显式选择后重新校验 Workspace 可用性与能力 |
| Workspace 正被使用 | 当前任务安全排队，不代表故障 | “查看队列” | 获锁后按顺序启动，期间可取消排队 |
| 实现失败 | 当前结果不能进入验证 | “查看建议并重试” | 新尝试保留旧失败原因和已产出证据 |
| 验证失败但可继续 | findings 回流，进入下一轮修复 | “查看修复计划” | 当前 findings 成为新一轮明确输入 |
| 证据不足 | 即使 agent 声称完成也不能 Done | “补充验证” | 证据补齐并重新验证后才允许 Done |

### 5.4 执行期间的介入能力 `[2026-08-14 新增]`

**依据**：PRD 第 5 节 Room 定义已承诺 Human Lead 能力（打断、纠正方向、要求暂停、
指定某个 agent 接手、要求提供证据或重做），v0.1/v0.2 未落地；dogfood NOTE-003~007
的共同根因即"执行现场缺少人的位置"。

用户在任务执行期间**始终**具备以下能力，不需要先进入某个特殊模式：

| 能力 | 何时可用 | 用户语义 | 边界 |
| --- | --- | --- | --- |
| 指定下一步由谁做 | 任意时刻 | “换 <成员> 来做这一步” | 受当前阶段能力要求约束；不匹配时说明原因而非静默拒绝 |
| 打断当前执行 | 运行中 | “先停一下” | 停止后 Workspace 必须回到安全状态，已产出结果标注为"未经验证" |
| 补充约束或纠正方向 | 任意时刻 | “补充要求：…” | 作为下一轮明确输入，不覆盖历史记录 |
| 否决即将发生的交接 | 交接倒计时内（J2.5a） | “我来决定交给谁” | 否决不等于失败；任务保持可继续状态 |
| 要求提供证据 / 重做 | 任一阶段结束后 | “这一步证据不足，重做” | 重做计为新尝试，旧尝试可追溯 |

**指派的交互形态**：以 `@` 触发成员列表为主入口，与常驻选择器并存。

- `@` 是从 IM 到 clowder 通用的指派心智，成本低、直觉强；v0.2 只实现了常驻下拉，
  用户打 `@` 无反应，导致能力存在但不可达（NOTE-006）。
- 借鉴 clowder 的机械规则：**`@句柄` 仅在行首独立一行时生效**（行中、URL 内不路由），
  避免正文提及成员名被误判为指派。markdown 列表/引用前缀后的首字符合法。
- **指派能力属于 Thread，不属于 Room**。Room 是阶段性临时协作现场，而单 agent 顺序执行
  时根本没有 Room；若指派只在 Room 内可用，最常见的场景反而无法介入。Room 增加的是
  多成员、拓扑与终止条件，不是"能不能指派"本身。

### 5.4.1 设计前提：自动回路是复杂度所在 `[2026-08-14]`

> **系统自动决定下一步的地方，都是复杂度所在**——不因为链条是「顺序」就简单。
> 凡是存在自动回路（实现 → 验证 → findings 回流 → 再实现）的路径，都必须提供
> **可见的收敛信号**与**人的介入点**；这条对单 agent 顺序执行、多 agent 协作和未来的
> Room 一视同仁。

判断依据：

- **复杂度来自循环，不来自并发。** 顺序执行只是拓扑简单（一条线），一旦加上失败回流
  就成了带循环的状态机——终止条件、状态累积（round count、findings、workspace 是否
  干净）、"何时判定不会收敛"全都要设计。而顺序执行恰恰是自动回路最容易形成的地方：
  写 → 审这条固定链天然构成回环。
- **换成多 agent 并不能消解它。** review → 打回 → 重做 → 再 review，参与者从一个换成
  三个，循环照旧。因此介入能力不能设计成"复杂协作才需要的高级功能"。
- **手动指派不解决不收敛，只是转移判断权。** 同一个问题三个成员都修不好时，复杂度仍在，
  只是从系统转到了人身上；且手动指派要求用户持续在场，链条一长本身就是负担。

因此本文的介入能力（5.4）按**自动回路**而非按协作形态来定义：哪里有系统自动决定下一步，
哪里就要有收敛信号和介入点。

### 5.5 不可逆操作

Git push、force push、跨 Workspace 写入和不可逆删除不作为普通运行按钮的隐含副作用。
触发时任务进入需要用户处理的状态，说明动作、影响范围和默认拒绝结果；未明确授权不得继续。

## 6. 旅程三：失败、中断或等待判断后的安全恢复

### 6.1 触发、目标与终点

- 触发：任务 failed、interrupted、cancelled、Blocked，或刷新/重启后发现未完成执行。
- 目标：无需解析 error code 或全量日志，就能理解原因、影响和安全下一步。
- 成功终点：用户明确选择后，任务回到 Ready、发起可追踪的新尝试，或保持停止；系统不擅自继续。

### 6.2 主路径

| 步骤 | 用户动作 | 系统反馈 | 此刻最关心的问题 | 概念披露 | 可观察验收 |
| --- | --- | --- | --- | --- | --- |
| J3.1 | 打开异常任务或从全局提醒进入 | 置顶状态卡同时显示“发生了什么、影响什么、建议做什么” | “需要我吗？” | 用失败/中断/已取消/需要处理区分状态 | 进入任务后无需滚动即可看到状态与主操作 |
| J3.2 | 查看原因摘要 | 展示最后成功阶段、失败阶段、Workspace 是否安全、未完成事项 | “已有成果还在吗？” | 默认摘要；错误码、stderr、事件 ID 折叠 | 明确哪些结果保留、哪些未经验证 |
| J3.3 | 选择推荐动作，或先补充信息/授权/更换 AI 成员 | 提交前预览动作影响；不支持的恢复路径明确拒绝 | “按下后会发生什么？” | 展示 Ready/新尝试的用户语义 | 主操作唯一，危险授权需单独确认 |
| J3.4 | 确认恢复 | Issue 先回 Ready，再由用户明确重新启动；新尝试引用旧结果但不覆盖旧记录 | “会不会重复或跳步？” | Attempt 翻译为“第 N 次尝试” | 已完成步骤不重复；新旧尝试都可追溯 |
| J3.5 | 观察恢复结果 | 正常回到旅程二 J2.4；若再次失败，更新原因而非叠加模糊错误 | “问题解决了吗？” | 保持同一状态语言 | 恢复状态在 2 秒内更新，刷新后保持一致 |

### 6.3 分类恢复规则

| 异常 | 原因与影响 | 推荐主操作 | 禁止的误导行为 |
| --- | --- | --- | --- |
| failed | AI/命令明确失败，当前阶段未完成 | “按建议重试” | 不显示为系统中断或 Done |
| interrupted | 服务/进程异常退出，进行中尝试不可信 | “从此步骤重新开始” | 不把重启前 running 假装成功 |
| cancelled | 用户主动停止 | “重新开始” | 不自动恢复，不与 failed 混淆 |
| Adapter 不可用 | 指定 AI 成员在当前 Workspace 无法执行 | “重新检查”或“选择替代成员” | 不静默换成列表第一个可用成员 |
| Workspace 忙 | 另一个写任务持锁 | “查看队列” | 不称为崩溃，不并发写入 |
| 权限/危险动作 | 需要凭据或可能造成不可逆/越界影响 | “审查请求” | 不把原始认证错误作为唯一解释 |
| validation fail | 结果不满足要求但尚可修复 | “查看 findings 并修复” | 不丢失 findings，不重置轮次 |
| round limit | 多轮验证未收敛 | “审查并重置验证预算” | reset 不得自动 unblock 或自动运行 |
| 需求冲突/证据不足 | 只能由用户补充判断 | “补充决定/证据” | 不让 AI 猜测后继续 |

### 6.4 不可逆操作

拒绝危险请求、保持 Blocked、取消排队或取消运行都是安全默认值。授权 push、force push、
跨 Workspace 写入、不可逆删除，以及重置完整验证预算，均需独立确认并写入活动记录；确认
文案必须展示具体对象和影响，不能用笼统“继续”。

## 7. 跨旅程状态矩阵

| 用户可见状态 | 系统含义 | 是否需要用户 | 默认下一步 | 可用主操作 |
| --- | --- | --- | --- | --- |
| 尚未设置 | 缺 Project/Workspace/可执行 AI 路径 | 是 | 完成最小设置 | 开始设置 |
| 可以创建任务 | 必需检查已通过 | 否 | 输入目标 | 创建任务 |
| 正在生成建议 | 确定性规则正在形成候选 | 否 | 等待推荐 | 取消 |
| 等待确认 | 尚未创建真实执行 | 是 | 审查建议 | 确认并开始 |
| 已排队 | Workspace 锁被其他任务占用 | 否 | 等待安全执行 | 查看队列 |
| 运行中 | 实现/研究/综合步骤正在执行 | 否 | 等待或查看进展 | 查看当前步骤 |
| 验证中 | 独立验证路径正在检查结果 | 否 | 等待结论 | 查看验证要求 |
| 即将交接 `[2026-08-14]` | 实现完成，倒计时后交给验证者 | 否（可介入） | 等待自动继续 | 接管 |
| 正在修复 | validation findings 已回流 | 否 | 完成下一轮实现 | 查看 findings |
| 反复未收敛 `[2026-08-14]` | 连续多轮出现重复 findings，尚未达上限 | 是（建议） | 改变策略或继续 | 查看重复项 |
| 需要你处理 | 权限、冲突、不收敛或证据缺失 | 是 | 处理原因后回 Ready | 执行推荐动作 |
| 已中断 | 宿主/进程中断，当前尝试不可信 | 是 | 从对应步骤新建尝试 | 从此步骤重新开始 |
| 已取消 | 用户主动停止 | 是 | 保持停止或重新开始 | 重新开始 |
| 已完成 | 验证通过且证据完整 | 否 | 查看/导出结果 | 查看完成摘要 |

## 8. 可观察验收指标

1. **首次可执行时间**：从首次工作台可交互开始计时，到“可以创建任务”状态出现为止，
   无外部文档辅助不超过 5 分钟；测试记录开始/结束时间、阻塞点和是否查看外部资料。
2. **创建入口与操作数**：所有工作台空/非空状态只有一个同级创建任务主入口；从聚焦目标输入
   到任务显示“已排队/运行中”不超过 3 次主要操作，Playwright 按实际点击计数。
3. **运行信息优先级**：在 1440×900 首屏内无需滚动即可找到当前阶段、是否需要用户、下一步；
   scripted dogfood 要求操作者在 10 秒内回答三问，答错任一项即失败。
4. **阻塞说明完整性**：每个 Blocked/failed/interrupted fixture 同时可见原因、影响和且仅一个
   推荐主操作；测试不得通过读取内部 error code 或展开原始日志完成判断。
5. **常见恢复可理解性**：对 Adapter 不可用、进程中断、validation fail、round limit 和权限请求，
   scripted dogfood 操作者须在每个状态出现后 30 秒内、不展开原始日志地选择正确恢复动作；
   选错、超时或必须查看 error code 才能判断均为失败。恢复后状态、历史尝试与证据保持可追溯。

## 9. 页面拼装的行为边界 `[2026-08-14 改写]`

页面拼装（重置计划 M4）必须覆盖本文三条旅程及状态矩阵，不得从现有 React 页面
反推行为。拼装可以用静态数据模拟本地检查、执行、验证和恢复，但每个模拟反馈必须遵守
本文的状态与披露规则。未在本文定稿的争议点必须回到旅程评审，不交给拼装阶段自行决定。

**与参考项目素材的关系**：拼装从 multica / clowder-ai 的冻结页取形态，但取舍依据是本文。
剪贴规则——**每剪一个区块，必须能指回本文的某一步和某个信息需求；指不回去的一律删掉**。
若某个旅程步骤找不到任何参考区块可承载，只有两种可能：本文写得太抽象（回来改），
或它属于空白区（记入 `reviews/blank-areas.md`，原创设计）。

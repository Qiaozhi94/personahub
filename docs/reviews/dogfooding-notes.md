# PersonaHub 使用体验记录（dogfooding notes）

> 记录使用过程中**不算 bug 但影响体验**的发现（不直觉的交互、缺失的能力、术语不一致、文档跟不上实现等）。
> 是 bug 就进 [`docs/reviews/dogfooding-bugs.md`](dogfooding-bugs.md)，不要记两份。
> 存放于 `docs/reviews/dogfooding-notes.md`（纳入 git）。
> 主表是**唯一事实源**（状态/发现时间/类型/去向以主表为准；时间统一本地时区 Asia/Singapore，UTC+8），详情块只补「现象/期望/影响范围/备注」这类不适合塞进表格的内容。
> 状态流转：`open`（待处理）→ `adopted`（已采纳，去向填 BACKLOG 条目或 Feature ID）→ `dismissed`（决定不做，详情块写理由）。
> **旅程步骤**（必填）=该问题落在哪条旅程的哪一步；P0 旅程尚未定稿时填 `—`。与 `dogfooding-bugs.md` 合并计数，同一步骤累计出现 ≥2 次即触发 <a href="self-test-system-plan.md">`self-test-system-plan.md`</a> §7.2「重复即升级」，须补该步骤的需求级 spec。

## 详情

### NOTE-001：点击 adapter 名字进入编辑，无可发现性

- **现象**：左侧 adapter 管理列表里，名字是可点击的编辑入口，但没有 hover 态、下划线、图标或任何视觉提示，看起来就是纯文本。
- **期望**：名字可点击应该有明显的可交互提示（hover 高亮/光标变化/编辑图标），或者干脆给每行加一个显式的"编辑"按钮，别让"点名字"是隐藏操作。
- **影响范围**：每个第一次用 adapter 管理面板的人都会踩，属于核心操作的可发现性问题。
- **根因**（已定位，暂不修）：`AdapterRow.tsx` 名字用的是裸 `<button>`，没走项目自己的 `Button` 组件；同文件里紧挨着的 Revalidate/Delete 按钮都用 `variant="ghost"` + `title`，唯独名字漏套。
- **备注**：暂不单独修，并入后续「前端体验提升」专项统一处理，届时参考本机 `D:\Projects\clowder-ai`、`D:\Projects\multica` 的页面设计。

### NOTE-002：新建 adapter 的入口是"Configure adapter"按钮，缺少直觉的新建入口

- **现象**：新建 adapter 靠点击"Configure adapter"按钮触发，按钮文案读起来像"配置某个已有 adapter"，不像"新建"。
- **期望**：预期是列表旁边有个 `+` 之类的新建按钮；如果保留现有按钮，至少文案要能读出"新建"的意思（比如"Add adapter"/"新建 adapter"）。
- **影响范围**：同 NOTE-001，第一次用会卡在"怎么创建"上。
- **根因**（已定位，暂不修）：`AdapterDialog.tsx:119` 新建态 DialogTitle 和 `AdapterSettings.tsx:93` 按钮文案都硬编码复用了 `"Configure adapter"`，没有像提交按钮那样用 `isEdit` 区分成 "Add"/"Edit"。
- **备注**：暂不单独修，并入后续「前端体验提升」专项统一处理，届时参考本机 `D:\Projects\clowder-ai`、`D:\Projects\multica` 的页面设计。

### NOTE-003：多 agent 自动接力缺少机制解释

- **现象**：给一个 agent 布置"写一个 python 脚本"的任务，它写完后**立刻自动**把工作交给了另一个
  agent 执行。整个过程没有任何解释：为什么现在换人、是谁做的决定、依据什么规则、下一个 agent
  被要求做什么。用户当时不知道这是产品设计的行为，还是自己误配了什么。
- **查证结论（2026-08-13）**：这是 **F004 Autonomous Validation 的设计行为**，不是缺陷——
  implementation Run 完成后自动触发 validator Run，Issue 从 `Running` 推进到 `Validating`。
  spec 原文：「让 PersonaHub 在 implementation Run 完成后自动进入 validator 检查」。
- **期望**：换人这一刻，Thread 里应该有一条可读的说明——「实现完成，按 <workflow 名> 进入验证
  阶段，由 <agent> 执行，依据 <validation policy>」，并给出「查看/修改这个流程」的入口。
- **影响范围**：**每一个首次使用多 agent 的用户都会遇到**。它直接损伤 PRD §2 的竞争力
  `graph-orchestrated`——协作编排发生了，但用户看不见、不理解，等同于没有。
- **备注**：进入本轮旅程设计（P1）的必需输入；是三条 P0 旅程第 2 条「输入目标运行到可信 Done」
  的关键断点。

### NOTE-004：流程配置入口不可发现

- **现象**：用户不知道"写完自动交给下一个 agent"这件事是**可配置的**，也找不到在哪配置。
- **查证结论**：流程由 **Workflow Template** 决定，验证方式由 **Validation Policy** 决定；
  F008 已提供 Workflow Template 管理 UI，但明确「不做可视化流程编辑器/拖拽画布」。
  也就是说能力存在，但入口与心智模型没有建立起来。
- **期望**：从"发生了自动流转"的那条 Thread 消息，应能一键跳到决定这次流转的模板配置。
  配置入口不应只存在于 Settings 深处，等用户凭空想起去找。
- **影响范围**：与 NOTE-003 同源。用户理解不了机制 → 也就不会去找配置 → 认为产品不可控。
- **备注**：本条与 NOTE-003 应作为**同一个旅程步骤**的问题一起解，不要拆成两个独立修复。

### NOTE-005：无法把一段任务单独指派给指定 agent

- **现象**：用户希望"这段任务由我指定的 agent 做"，但找不到办法；只能眼看着系统自动接力。
- **查证结论**：F005 Manual Multi-Agent Routing **做了手动指派，但作用域与用户预期不同**——
  它提供的是 Thread composer 里的 agent 选择器，控制的是「**下一轮指令**交给哪个 adapter」；
  spec 明确「手动路由改变的是下一个 Run 交给谁，不改变同一时刻只能有一个 Run 在写 workspace」，
  且「不做 Coordinator 自动推荐/自动选择」。它**不改变** implementation→validation 这条流程编排。
- **缺口**：用户想要的是"对流程中的某一段指定执行者"（阶段级指派），现有能力是"对下一条指令
  指定执行者"（轮次级指派）。两者不是一回事，而界面上没有区分，导致用户以为手动指派失效了。
- **期望**：至少让用户能看出这两种控制的区别，并知道在自动流转发生前如何介入/接管。
- **影响范围**：直接关系产品的"可控感"。PRD §2.2 承诺"用户保留对推荐、危险操作、阻塞恢复的
  最终控制权"，当前实现只兑现了轮次级。
- **备注**：是否补齐阶段级指派，应在 P1 旅程定稿时决定；与 F011 Work Room「观察、打断、纠偏」
  的产品价值高度相关，可作为 v0.3 重估的输入。

### NOTE-006：打 @ 没有 agent 列表，实现的是下拉选择器

- **现象**：用户在 Thread composer 里按直觉输入 `@`，期待弹出 agent 列表，结果什么都没有，
  因此认为"手动指派做不了"。
- **查证结论（2026-08-13）**：**@ 提及功能从未实现**。F005 spec 写的是「Thread composer 提供
  一个 agent 选择器（**例如 @ 提及或下拉**）」——二选一，实现选择了下拉。
  `web/src/components/thread/AgentSelector.tsx` 是一个常驻可见的 `<select>`，代码里没有任何
  mention 解析逻辑。**因此不算实现缺陷，是交互形态与用户直觉不匹配。**
- **反常之处**：该组件的注释明确写了 `always visible (never hidden for a single/zero-adapter
  Project)`——它一直在屏幕上，用户却没意识到那就是手动指派入口。说明**"常驻可见"并不等于
  "可发现"**：用户带着"@ 某人"的心智来，看不见下拉；看见了也不会把"Agent 下拉"理解成
  "我可以换人做这件事"。
- **期望**：补 `@` 触发的 agent 列表（与下拉并存，不是替换）。`@` 是从 IM 到 clowder 都通用的
  指派心智，成本低、直觉强。
- **影响范围**：直接挡住 F005 的全部价值——功能做了但用户用不到，等同于没做。
- **备注**：与 NOTE-005 是同一件事的两面：NOTE-005 是能力边界问题（只能轮次级），
  NOTE-006 是入口问题（能力存在但找不到）。修复时应一起考虑。

### NOTE-007：验证不收敛期间没有介入点

- **现象**：真实开发不是"开发者→审视者"一次过。可能检视好几轮，也可能问题一直不收敛。
  用户在这个过程中**没有任何位置可以说"这样下去不行，换个人/换个方法"**。
- **查证结论**：F004 的设计是——validation fail 带 findings 回流下一轮，失败计入
  `validation_round_count`，**达到 `max_validation_rounds` 才进入 `Blocked`**，届时 Inspector
  展示 blocked reason 与最近 findings。也就是说：**round 1 到 N-1 之间，系统不给用户任何
  介入点**，只能等它撞上限。
- **问题的本质**：当前把"反复不收敛"当作**异常**处理（数到上限就阻塞兜底），
  但在真实开发中它是**常态**。用户需要的不是"撞墙后被告知撞墙了"，而是在第 2、3 轮就能
  判断趋势并改变策略。
- **加重因素**：`BUG-003`（高，仍 open）——「中断 validator 死锁 round 槽位，重验证无法开始」。
  即用户想中断都会把系统卡死，介入路径在实现层也是断的。
- **期望**：每一轮验证结束（无论 pass/fail）都应是一个可介入点，至少提供：查看本轮 findings、
  换执行者、改验证要求、直接叫停。轮次趋势（第 2 轮 findings 与第 1 轮是否重复）应可见——
  重复的 findings 是"不会收敛"的最强信号。
- **影响范围**：这是三条 P0 旅程第 3 条「失败后理解原因并安全恢复」的核心。
- **设计前提**：**复杂度来自自动回路加不收敛，不来自「单 agent」或「顺序」本身。**
  顺序执行只是拓扑简单，加上失败回流就成了带循环的状态机；换成多 agent 也一样会有
  review → 打回 → 重做的循环，手动指派同样不解决不收敛，只是把判断权转移给人。
  因此介入点按**自动回路**定义，而非按协作形态定义——哪里有系统自动决定下一步，
  哪里就要有收敛信号和介入点。详见 `personahub-user-journeys.md` §5.4.1。

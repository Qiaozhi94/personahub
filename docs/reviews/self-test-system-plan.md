# PersonaHub 开发自测试体系

> **定位**：常驻流程文档，描述 PersonaHub 三层测试体系的职责边界、门禁命令与证据落点。
> 不是某一轮整改的阶段计划——阶段性整改结束后本文继续生效。
>
> **与其他文档的关系**：`docs/SOP.md` 规定开发步骤与真实环境测试纪律，本文规定测试**分层**
> 与**门禁**；两者冲突时以 SOP 为准并回来修本文。本文只有一处外部输入依赖（第 5 节的 P0
> 旅程清单），其余内容独立成立。

## 1. 这套体系要解决的问题

v0.2 收口时自动化测试规模不小，但首次 dogfood 立刻撞到阻塞性缺陷和核心操作找不到的问题。
根因不是某个组件质量差，而是**完成定义只覆盖到 FR/AC 和代码正确性，没有任何一层为"用户
能否从目标出发走完一条完整旅程"负责**。

结论有两条，本文其余部分都是它们的展开：

1. 需要一层显式的**需求级**测试，判据是旅程能否走通，不是组件是否渲染正确。
2. 每一层都要有**强制执行点**和**可机械判定的通过口径**，否则跳过没有代价。

## 2. 现状基线（2026-08-13 实测）

改造前必须认清已有的能力，避免重复建设：

| 事实 | 位置 | 含义 |
|---|---|---|
| `npm run verify` 串联 lint / format:check / typecheck / server+web 测试 / 文档门禁 / build | `package.json` | 任务级门禁已完整，无需新建 |
| Playwright 基建可用，含 API seed 与 mock run 支持 | `e2e/playwright.config.ts`、`e2e/tests/support/{seed,mock-run}.ts` | 需求级**框架已就位**，缺的是用例 |
| E2E 只有一条 spec | `e2e/tests/f005-layout.spec.ts` | 需求级覆盖近乎为零 |
| CI 已有独立 `e2e` job，push main 与 PR 都跑 `npm run test:e2e`，失败上传 report | `.github/workflows/ci.yml` | **远端门禁已存在**，缺的是本地入口 |
| `npm run verify` 不含 `test:e2e` | `package.json` | 本地自检发现不了旅程断裂 |
| dogfood 记录有固定落点与校验脚本 | `dogfooding-bugs.md` / `dogfooding-notes.md` / `npm run bug:log` | 发布级记录格式已就位 |
| spec 的 AC 行本身就是「FR → 测试用例」映射，但只有 **19/74** 条写了引用 | `docs/features/0.{1,2}/*/spec.md` §6 | 映射层**已存在但不完整**，且无门禁 |

**因此本轮的动作是「补旅程用例 + 补本地门禁入口 + 补齐 AC 映射 + 统一判定口径」，不是重建
测试框架，不是新建 CI job，也不是另造一份测试目录文件。**

## 3. 三层测试模型

| 层级 | 回答的问题 | 手段 | 触发点 | 证据落点 |
|---|---|---|---|---|
| 任务级 | 这次改动有没有破坏局部契约？ | 单元 + 接口/集成 + jsdom 组件测试 + typecheck | 每个任务完成后 | `npm run verify` 通过记录 |
| 需求级 | 受影响的用户旅程还能不能被真实用户走通？ | Playwright 真实浏览器 E2E | Feature 进入 review 前、推 main 前 | spec 文件、失败截图/trace、CI e2e job |
| 发布级 | 真实用户在真实环境完成闭环后，认不认可？ | 人工 dogfood + 真实 CLI 运行 | 版本收口前 | dogfood 记录、`dogfooding-bugs.md` / `dogfooding-notes.md` |

### 3.1 任务级

- **负责**：函数/模块契约、API 输入输出、DB 迁移、组件在给定 props 下的行为、边界值与异常分支。
- **不负责**：真实布局、可发现性、跨页面的操作连续性。jsdom 测试通过**不构成**"页面能用"的证据。
- **通过判据**：`npm run verify` 全绿。
- **纪律**：新增行为必须同批次带上任务级测试；修 bug 必须补回归用例，并在 `dogfooding-bugs.md`
  的"回归测试"列填具体用例名（现有条目已是这个格式）。

### 3.2 需求级（本体系新增的一层）

- **负责**：一条用户旅程从触发到闭环的完整路径——入口能否被找到、每步是否有可见反馈、失败后
  能否恢复。
- **不负责**：细粒度断言和边界值。那些留在任务级，挤进 E2E 只会让它变慢变脆。
- **组织方式**：**一条旅程一个 spec 文件**，按用户动作顺序断言，不按页面或组件拆用例。
  按组件拆的用例永远发现不了可发现性问题和步骤断裂——那正是 dogfood 撞到的问题模式。
- **数据策略（既定，不再是待定项）**：一律走 HTTP API 播种（`support/seed.ts`）+ mock run
  （`support/mock-run.ts`），**不在 E2E 里驱动真实 CLI adapter**。真实 adapter 的验证归发布级。
  理由：真实 CLI 耗时不可控且依赖外部凭证，放进强制门禁会让门禁不可信。
- **通过判据**：`npm run test:e2e` 全绿，且三条 P0 旅程各自的 spec 无 skip / fixme 标记。

### 3.3 发布级

- **负责**：主观判断——"这是不是我预想的样子"、"术语看不看得懂"、"卡不卡手"。以及**唯一**
  跑真实 CLI adapter 的场合。
- **不设自动化替代方案**：这一层的价值就在于人的判断，能自动化的部分本就该沉到需求级。
  因此只固定场景清单和记录格式，保证每次收口都真的跑过。
- **遵循 SOP「真实环境测试纪律」**：本机即真实环境，不得标记为"待用户在真实环境验证"而跳过；
  只有客观不可执行（缺凭证/缺二进制）才允许延后，并须写明缺什么、补齐后如何执行。
- **通过判据**：见第 6 节场景清单与第 7 节口径。

## 4. 门禁命令与执行点

| 命令 | 组成 | 什么时候必须跑 |
|---|---|---|
| `npm run verify` | 现状不变（不含 E2E） | 每个任务完成后；本地高频循环 |
| `npm run verify:release`（**待建**） | `verify` + `test:e2e:install` + `test:e2e` | 推 main 前、Feature 状态改为 done 前、版本收口前 |
| CI `verify` + `e2e` 两个 job | 已存在，保持不变 | push main 与 PR 自动触发 |

规则：

- **执行点是"推 main 前"，不是"PR 合并前"**。本项目日常直推 main，把门禁挂在 PR 流程上等于
  没有门禁。若某轮改用分支+PR，CI 已有的 `e2e` job 自动覆盖，无需另行设计。
- 本地与 CI **复用同一条 `npm run test:e2e`**，不允许 CI 另开一套 E2E 清单。
- `verify` 保持不含 E2E，避免拖慢日常循环——真实浏览器一轮的成本量级与其余检查不同。
- 真实环境测试未执行时必须**显式失败或记录客观阻塞原因**，不能写成通过。

### 4.1 引入 E2E 的过渡策略（必须遵守）

CI 的 `e2e` job 已是强制门禁。若在旅程尚未修通时直接提交断言完整旅程的 spec，**整改期内每次
提交都会红**，反而逼人绕过门禁。因此：

1. 新旅程 spec 先以 `test.fixme` 提交——用例存在、断言可读、但不计入失败。
2. 对应旅程整改通过后，同一 commit 里移除 `fixme` 标记，该旅程转入强制。
3. `fixme` 状态的 spec 必须在第 8 节任务清单里有对应未勾选任务；不允许长期挂着。

## 5. 分级测试清单

清单的价值不在于"有一份完整目录"，而在于**能看出哪里没被覆盖**。因此清单**不手写**：仓库现有
162 个测试文件、约 1825 个用例，任何手写目录写完当天就开始腐烂，且没有门禁能发现它错了。

清单由两个维度构成，互相正交，都要有：

| 维度 | 回答 | 载体 | 粒度 |
|---|---|---|---|
| **纵向：AC 映射** | 每条需求有没有测试？ | spec 的 AC 行（已有格式） | 74 条 AC |
| **横向：旅程矩阵** | 串起来能不能走通？ | `docs/reviews/journey-test-matrix.md` | 3 条 P0 旅程 |

### 5.1 纵向：AC → 测试用例映射

**载体是 spec 里已有的 AC 行，不新建文件。** F006/F007 已经是标准格式，照抄：

```
- [x] **AC-001**（`FR-001`、`FR-002`）：<验收结论>。—— 实现 <文件>；
  测试 [任务级]：<测试文件>「<用例名>」；测试 [需求级]：<spec 文件>「<用例名>」。
```

规则：

- 每条 AC 必须给出**测试文件 + 可定位的用例名**，或写明"只能人工验证"及理由；
  第三种情形是"**由门禁覆盖**"（如"全量回归通过"这类 AC，判定方式是 `npm run verify` 全绿）。
- **每组引用必须标层级**（`[任务级]` / `[需求级]`）。没有标记等同于未覆盖。
- **落在 P0 旅程路径上的 AC，必须有 `[需求级]` 引用**；不在 P0 路径上的可以只有 `[任务级]`。
  哪些 AC 在 P0 路径上，由 5.2 的旅程矩阵给出——这是纵横两个维度真正的接口。
- 用例名必须真实存在——由门禁校验（见 7.4），改测试名不同步改 spec 会直接红。
- 新 Feature 的 AC 从第一天就带引用，是 Feature 状态改 `done` 的前置条件。
- 历史回填范围：F001（10）、F002（12）、F003（12）、F004（11）、F005（1）、F006（1）、F008（8），
  共 **55 条**，见 T008。

**历史回填只做这一层的"引用补齐"，不逐条补写测试**。0.1/0.2 的任务级覆盖已经很厚（1825 个
用例），缺的是"哪条需求由哪个用例证明"这条线索；真正的洞在需求级——全仓只有 1 个 E2E spec。

### 5.2 横向：旅程—测试映射矩阵

**输入**：三条 P0 旅程的定义，由 <a href="product-experience-reset-plan.md">`product-experience-reset-plan.md`</a>
R007 产出。这是本文唯一的外部输入依赖；在它落地前，其余各节均可独立推进。

旅程确定后，产出矩阵（落点 `docs/reviews/journey-test-matrix.md`），每条旅程的每一步映射到：

1. 自动化测试文件（spec + 用例名），或明确写出"只能人工验证"的理由。
2. 前置数据与环境（seed 调用、mock run 参数）。
3. 用户动作与**预期可见反馈**。
4. 失败恢复动作及其预期状态。
5. 证据保存位置。

没有映射的旅程步骤，不得靠"整体看起来测试很多"视为已覆盖。

## 6. 发布级场景与记录回流

### 6.1 固定场景清单

版本收口前逐条执行并记录实际耗时：

1. 干净数据库的首次启动与配置。
2. 已有 Project、历史 Issue、既有 Adapter 的升级场景。
3. 一个真实 coding Issue 跑到 Done（**真实 CLI**）。
4. 主动取消、进程重启或 Adapter 不可用后的恢复。
5. validation 失败/中断 → unblock → 重试 → 完成。

首次执行时**五条全跑并记录耗时**；是否分「每次必跑 / 抽查」两级，用这次实测数据决定，不凭
估算提前分级。

### 6.2 记录回流

- 已确认缺陷 → `dogfooding-bugs.md`，`npm run bug:log` 校验。
- 不算 bug 的交互/易用性/术语问题 → `dogfooding-notes.md`。
- 每条记录须能追溯到**具体旅程步骤**。同一步骤反复出问题 = 该步骤需求级覆盖不足，补用例，
  不是只修单点。
- 每次 dogfood 后回填状态与去向（`adopted` 填 BACKLOG 条目或 Feature ID / `dismissed` 写理由），
  不允许长期堆积 `open`。

## 7. 演进闭环

清单是静态的，缺陷是持续来的。**没有触发器的"持续改进"等于备忘录**，因此把演进拆成四个可
执行、可检查的触发器——每一个都规定了"发生什么 → 必须做什么 → 谁来卡"。

### 7.1 逃逸定级：缺陷补在它逃过的那一层

每条 bug 入 `dogfooding-bugs.md` 时，必须回答"**本该被哪一层拦住**"，回归用例就补在那一层：

| 逃逸层级 | 说明 | 补什么 |
|---|---|---|
| 任务级 | 契约/边界/分支错了 | 单元或接口用例（现有习惯，已在做） |
| 需求级 | 各组件都对，但连起来走不通、入口找不到 | E2E spec 的对应步骤断言 |
| 发布级 | 只有真实 CLI / 真实数据才暴露 | 扩充 6.1 场景清单，说明如何复现 |

反模式：不管什么 bug 都补单测。可发现性问题补单测等于没补——它下次照样逃出去。

### 7.2 重复即升级

同一旅程步骤**第二次**出问题（bugs 或 notes 表任一），强制补该步骤的需求级 spec，不接受再修
单点。第二次出现是"这一步没有覆盖"的证据，不是"这次运气不好"。

### 7.3 `fixme` 不过夜

`test.fixme` 的 spec 必须在第 9 节任务清单有对应未勾选任务。允许暂时红转黄（见 4.1），不允许
无主挂着——无主的 fixme 会变成永久的假覆盖。

### 7.4 漂移即失败

以下不一致必须让 `npm run verify` 直接失败，而不是靠人复查：

- AC 引用的测试文件不存在，或引用的用例名在该文件中找不到。
- AC 行既无测试引用，又无"只能人工验证"/"由门禁覆盖"标注（历史 Feature 回填完成后启用）。
- 引用未标层级，或 P0 旅程路径上的 AC 缺 `[需求级]` 引用（旅程矩阵产出后启用）。

这一条是整套机制能"自演进"而不是"自愿维护"的关键。前三条靠纪律，第四条靠门禁；只有第四条
在无人盯着时仍然生效。

## 8. 通过与停止条件

收口判定必须能机械执行，因此按两个记录表各自的既有字段定义（bugs 表用高/中/低，notes 表无
严重度列，不要用统一的 Critical/High 口径去套）：

1. `npm run verify:release` 全绿（含真实浏览器 E2E）。
2. 三条 P0 旅程的 spec 无 `skip` / `fixme` 残留。
3. `dogfooding-bugs.md` 中严重度=**高**且状态≠`fixed` 的条目数为 **0**（`npm run bug:log` 可查）。
4. `dogfooding-notes.md` 中落在三条 P0 旅程步骤上的条目无 `open`；不在 P0 路径上的可留 `open`。
5. 第 6.1 节五个场景全部执行并留下记录。
6. 74 条 AC 全部带测试引用或人工验证理由（7.4 门禁自动判定）。

任一项失败，版本回到整改。**不得把核心路径不可用写进"已知限制"后继续收口。**

## 10. 未决与后续深入

本文当前只承担「把缺口、边界和门禁定下来」，不追求一次写全。已知待深入方向：

- dogfood 场景分级——等 T002 的实测耗时数据。
- 需求级测试与 Feature 门禁（`gate_version`）的衔接方式。
- E2E 用例数增长后的执行时长上限与分片策略（当前 `workers: 1`、串行）。

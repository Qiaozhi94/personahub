# PersonaHub 开发自测试体系

> **定位**：常驻流程文档，描述 PersonaHub 三层测试体系的职责边界、门禁命令与证据落点。
> 不是某一轮整改的阶段计划——阶段性整改结束后本文继续生效。
>
> **与其他文档的关系**：`docs/SOP.md` 规定开发步骤与真实环境测试纪律，本文规定测试**分层**
> 与**门禁**；两者冲突时以 SOP 为准并回来修本文。本文只有一处外部输入依赖（第 5 节的 P0
> 旅程清单），其余内容独立成立。

## 1. 这套体系要解决的问题

v0.2 收口时自动化测试规模不小，但首次 dogfood 立刻撞到阻塞性缺陷和核心操作找不到的问题。
根因不是某个组件质量差，而是**完成定义只覆盖到 FR/AC 和代码正确性，没有任何一层为"用户
能否从目标出发走完一条完整旅程"负责**。

结论有两条，本文其余部分都是它们的展开：

1. 需要一层显式的**需求级**测试，判据是旅程能否走通，不是组件是否渲染正确。
2. 每一层都要有**强制执行点**和**可机械判定的通过口径**，否则跳过没有代价。

## 2. 现状基线（2026-08-13 实测）

改造前必须认清已有的能力，避免重复建设：

| 事实 | 位置 | 含义 |
|---|---|---|
| `npm run verify` 串联 lint / format:check / typecheck / server+web 测试 / 文档门禁 | `package.json` | 任务级门禁已完整，无需新建 |
| Playwright 基建可用，含 API seed 与 mock run 支持 | `e2e/playwright.config.ts`、`e2e/tests/support/{seed,mock-run}.ts` | 需求级**框架已就位**，缺的是用例 |
| E2E 只有一条 spec | `e2e/tests/f005-layout.spec.ts` | 需求级覆盖近乎为零 |
| CI 已有独立 `e2e` job，push main 与 PR 都跑 `npm run test:e2e`，失败上传 report | `.github/workflows/ci.yml` | **远端门禁已存在**，缺的是本地入口 |
| `npm run verify` 不含 `test:e2e` | `package.json` | 本地自检发现不了旅程断裂 |
| dogfood 记录有固定落点与校验脚本 | `dogfooding-bugs.md` / `dogfooding-notes.md` / `npm run bug:log` | 发布级记录格式已就位 |
| spec 的 AC 行本身就是「FR → 测试用例」映射，但只有 **19/74** 条写了引用 | `docs/features/0.{1,2}/*/spec.md` §6 | 映射层**已存在但不完整**，且无门禁 |

**因此本轮的动作是「补旅程用例 + 补本地门禁入口 + 补齐 AC 映射 + 统一判定口径」，不是重建
测试框架，不是新建 CI job，也不是另造一份测试目录文件。**

## 3. 三层测试模型

| 层级 | 回答的问题 | 手段 | 触发点 | 证据落点 |
|---|---|---|---|---|
| 任务级 | 这次改动有没有破坏局部契约？ | 单元 + 接口/集成 + 跨端契约 + jsdom 组件测试 + typecheck | 每个任务完成后 | `npm run verify` 通过记录 |
| 需求级 | 受影响的用户旅程还能不能被真实用户走通？ | Playwright 真实浏览器 E2E | Feature 进入 review 前、推 main 前 | spec 文件、失败截图/trace、CI e2e job |
| 发布级 | 真实用户在真实环境完成闭环后，认不认可？ | 人工 dogfood + 真实 CLI 运行 | 版本收口前 | dogfood 记录、`dogfooding-bugs.md` / `dogfooding-notes.md` |

### 3.1 任务级

- **负责**：函数/模块契约、API 输入输出、DB 迁移、组件在给定 props 下的行为、边界值与异常分支。
- **不负责**：真实布局、可发现性、跨页面的操作连续性。jsdom 测试通过**不构成**"页面能用"的证据。
- **通过判据**：`npm run verify` 全绿。
- **纪律**：新增行为必须同批次带上任务级测试；修 bug 必须补回归用例，并在 `dogfooding-bugs.md`
  的"回归测试"列填具体用例名（现有条目已是这个格式）。

#### 3.1.1 六类必备测试

任务级不是"随便写点测试"。按**改动碰到了哪一层**决定必须补哪一类，一类都不能用另一类顶：

| # | 类型 | 什么改动触发它 | 落点 | 必须断言什么 |
|---|---|---|---|---|
| 1 | 纯单元 | 新增/修改纯函数：解析器、分类器、schema 校验、normalizer | `server/tests/unit/` | 正例 + **每一类拒绝原因各一条**；不碰 DB、不起服务 |
| 2 | 数据层 | 改 schema、加表/索引、改仓储 | `server/tests/integration/migration-v*.test.ts`、`*-repository.test.ts` | 迁移幂等、约束真的生效（写冲突数据应被 DB 拒绝，不能只靠 service 拦） |
| 3 | 服务与状态机 | 跨仓储写入、事务、workspace 锁、Run/Issue 状态流转 | `server/tests/integration/` | 事务回滚、并发/交错、**重启后的恢复语义** |
| 4 | HTTP 契约 | 新增或修改 API | `server/tests/integration/`（minimal Fastify app） | 状态码 + `ErrorCode` + 字段白名单；用户级错误不得退化成 `INTERNAL_ERROR` |
| 5 | 前端组件/hook | 新增组件、hook、错误态 | `web/src/*.test.tsx` | loading / error / empty 三态齐全，不只测 happy path |
| 6 | **跨端契约** | 新增或修改 `api-client` 的请求构造（方法、header、body 形状） | 见 3.1.3 | 真实客户端 × 真实 Fastify，**不 stub `fetch`** |

**断言必须落在可观察终态，不是内部调用发生了。** BUG-001 不是没测试，而是断言了中间步骤
（claim 成功），没断言最终效果（validator 真的被派工）。"某个函数被调用了"不构成通过条件——
终态是数据库里的状态、返回给调用方的结果、或用户能看到的东西。需求级已有等价规则（3.2.1 第 2 段），
任务级同样适用。

补充两条本仓库的特有约定：

- **adapter 协议**属于第 1 类 + 第 3 类的组合：输出解析走 normalizer 单测（`codex-trace-normalizer.test.ts`
  等），派发链路走 fake CLI 夹具（`server/tests/helpers/fake-*.mjs`）。**接新 adapter 两类都要有。**
- 第 3 类里"重启后的恢复语义"是硬要求，不是加分项——BUG-001/BUG-003 都是这一类漏测。

#### 3.1.2 挑 UT 还是集成

- 分支组合多、不碰 IO → **纯单元**（如 `validateStepsSchema` 的 16 个拒绝分支、`classifyQueuedRun`
  的状态×角色矩阵）。
- 跨组件、碰 DB / 锁 / 事务 / 时序 → **集成**。
- **UT 永远抓不到"A 忘了调 B"**（UT 里 B 是假的）。本项目的核心风险正是这类跨组件时序问题，
  因此集成测试占比高是刻意的，**不要为了金字塔比例好看而给集成路径补等价的 UT**。

#### 3.1.3 第 6 类：跨端契约（本仓库的已知盲区）

**这条缝有过实际逃逸**：BUG-002（`apiFetch` 对无 body 的 POST 也发 `Content-Type: application/json`，
Fastify 拒空 body → 500）。前端测试把整个 `apiClient` mock 掉（`web/src/test/api-client-mock.ts`），
后端测试不知道前端会怎么发请求，**两边各自全绿**。

现有 `web/src/api-client.test.ts` 已覆盖**响应解析**（绕过模块 mock、用真实 `Response`），但仍
stub `global.fetch`——它断言的是自己的预期，不是真实服务端的接受行为。缺的正是另一半。

规则：

- 覆盖对象是**请求构造**：HTTP 方法、header（尤其 `Content-Type` 的有无）、body 序列化形状。
- **不得 stub `fetch`**：用真实 `apiClient` 打真实 Fastify 实例（可复用 server 集成测试里的
  minimal app），断言服务端真的接受并返回预期状态码。
- 落点定在 **server 工作区**：真实 Fastify 与既有 helpers 都在那里，`api-client.ts` 只依赖
  `@personahub/shared`，可直接跨工作区引入；反向（web 里起 Fastify）需要给 web 引入后端依赖，
  代价更大。
- 优先覆盖**无 body 的写操作**（cancel、activate、deactivate 这类），它们是这条缝的高发区。

不这么做的代价：这类缺陷只能靠需求级 E2E 兜住，而 E2E 是分钟级的重型手段且只覆盖三条 P0
旅程——**用最贵的一层去补最基础的缝，是错配**。

**已落地（2026-08-14）**：`server/tests/integration/api-client-contract.test.ts`，2 条用例，
0.3s。跨工作区引入 `web/src/lib/api-client.ts` 可行；唯一的 shim 是把相对 `/api` 解析到测试
服务器 origin，method/header/body 原样转发。已用**故障注入**验证它真的会失败——把
`apiFetch()` 改回无条件设 `Content-Type` 后，两条用例同时红，且复现 BUG-002 的原始症状
（`INTERNAL_ERROR` 而非 `RUN_NOT_FOUND`）。**不能失败的测试没有价值，新增门禁类用例都应这样
验一次。**

### 3.2 需求级（本体系新增的一层）

- **负责**：一条用户旅程从触发到闭环的完整路径——入口能否被找到、每步是否有可见反馈、失败后
  能否恢复。
- **不负责**：细粒度断言和边界值。那些留在任务级，挤进 E2E 只会让它变慢变脆。
- **组织方式**：**一条旅程一个 spec 文件**，按用户动作顺序断言，不按页面或组件拆用例。
  按组件拆的用例永远发现不了可发现性问题和步骤断裂——那正是 dogfood 撞到的问题模式。
- **数据策略（既定，不再是待定项）**：一律走 HTTP API 播种（`support/seed.ts`）+ mock run
  （`support/mock-run.ts`），**不在 E2E 里驱动真实 CLI adapter**。真实 adapter 的验证归发布级。
  理由：真实 CLI 耗时不可控且依赖外部凭证，放进强制门禁会让门禁不可信。
- **通过判据**：`npm run test:e2e` 全绿，且三条 P0 旅程各自的 spec 无 skip / fixme 标记。

#### 3.2.1 每条旅程 spec 的五段必备内容

一条旅程 spec 不是"点几下能过就行"。缺任何一段视为该旅程未覆盖：

| # | 段落 | 必须断言什么 | 为什么是必备 |
|---|---|---|---|
| 1 | **入口可发现** | 从应用初始视图出发找到入口并点击，**禁止直接 `page.goto()` 跳过入口** | NOTE-001/002 两条都是"功能没问题、入口找不到"，直接 goto 会把这类问题测没了 |
| 2 | **主路径逐步反馈** | 每个用户动作后有**可见的**状态变化（文案/状态徽标/列表项），不是只断言接口被调用 | "点了没反应"是最典型的旅程断裂 |
| 3 | **失败与恢复** | 至少一条失败路径：错误信息可读 + 用户能回到可继续的状态 | 发生故障时能否自救，只有走一遍才知道 |
| 4 | **空态与首次使用** | 干净数据下的第一屏有明确的下一步指引，不是空白页 | 新库首启是 dogfood 场景 1，也是最常被跳过的路径 |
| 5 | **刷新/重连后一致** | 刷新页面后状态不丢；SSE 断线重连后按 `event_sequence` 补读不重不漏 | 本项目实时链路是核心机制，AC 层面已有要求（F002 AC-010、F003 AC-012） |

技术约束（避免 E2E 变慢变脆）：

- 数据一律用 `support/seed.ts` 播种、`support/mock-run.ts` 造 Run，**不驱动真实 CLI**。
- 断言用**用户可见的文本与角色**（role/label/text），不用 CSS 选择器和内部 test-id 链。
- 一条旅程一个 spec 文件，串行执行；细粒度边界值不下沉到这里，回任务级写。

### 3.3 发布级

- **负责**：主观判断——"这是不是我预想的样子"、"术语看不看得懂"、"卡不卡手"。以及**唯一**
  跑真实 CLI adapter 的场合。
- **不设自动化替代方案**：这一层的价值就在于人的判断，能自动化的部分本就该沉到需求级。
  因此只固定场景清单和记录格式，保证每次收口都真的跑过。
- **遵循 SOP「真实环境测试纪律」**：本机即真实环境，不得标记为"待用户在真实环境验证"而跳过；
  只有客观不可执行（缺凭证/缺二进制）才允许延后，并须写明缺什么、补齐后如何执行。
- **通过判据**：见第 6 节场景清单与第 8 节口径。

#### 3.3.1 每个场景必须留下的三类证据

只写"跑过了"不算数。每个 6.1 场景执行后记录：

1. **真实运行证据**：Run id / Issue id、真实 CLI 的 adapter 名与耗时。
2. **主观判断**：是否符合预期，不符合的部分逐条落到 `dogfooding-bugs.md` 或 `dogfooding-notes.md`。
3. **阻塞说明**（若未跑成）：按 SOP「真实环境测试纪律」写明哪条测试、为什么跑不了、缺什么、
   补齐后如何执行——不允许静默跳过或写成通过。

#### 3.3.2 真实 CLI 测试：本机具备环境，不得跳过

**本机装有本项目要求的全部 agent CLI（codex / claude / opencode），因此 `REAL_*` 门控的测试
必须真跑，不允许因为"默认不跑"就长期不跑。**（2026-08-14 用户明确）

- 涉及文件：`server/tests/integration/real-*.test.ts` 与 `graph-cli-acceptance.test.ts`，
  由 `REAL_CODEX` / `REAL_CLAUDE` / `REAL_OPENCODE` 三个环境变量门控。
- **建议串行执行**（`--maxWorkers=1 --no-file-parallelism`）：3.1 那套 8 worker 的并行配置是为
  fake 夹具调的，串行能排除一个混淆变量。但**串行并不能解决 CLI 本身变慢**——见下方分诊规则。
- **失败分诊：先判环境，再判产品。** 真实 CLI 的红有两类，混淆它们会导致去修根本不存在的
  bug，或者反过来把真缺陷当成"今天网络不好"：

  | 症状 | 先做什么 |
  |---|---|
  | Issue 停在 `Validating`、graph 停在 `running`、硬超时 | 跑一次基线探测（下方），拿到单次往返耗时 |
  | 结构性错误：字段缺失、状态机走错、契约不符 | 直接按产品缺陷处理，记 `dogfooding-bugs.md` |

  基线探测（约 30s，与产品无关）：

  ```
  codex exec --skip-git-repo-check "reply with exactly: PONG"
  ```

  **健康时应在数秒内返回。** 若一句 PONG 就要 30s+，说明 CLI 侧已降级（配额节流/服务波动），
  此时所有真实测试的耗时预算都不再成立，结果不足以判定产品健康——按 SOP 记录客观阻塞原因、
  择时重跑，**不要写成通过，也不要立 bug**。

- **实测记录（2026-08-14）**：`real-codex-e2e` 在 21:54 单跑 **24s 通过**；随后连续跑了约 30 次
  真实 Codex 调用，一小时内同一条用例变成 **262s 且停在 `Validating`**，基线 PONG 探测 31s。
  并行跑 11 文件 5 条红、串行跑 6 条红——**串行更差，因此"并发争抢"不是主因**，主因是 CLI
  侧吞吐降级。Claude / OpenCode 组同期 7 个文件全过。次日重跑（基线 PONG 仍 24s）结果完全
  一致：4 文件 6 条红，29 分钟。

- **已排除的两个可能**（避免下次重复排查）：
  1. **不是 Codex CLI 版本变更**：Node 22 与 24 下装的都是 `@openai/codex` 0.147.0。
  2. **不是 app-server 协议变更**：直接探测 `codex app-server --listen stdio://`，`initialize`
     0.4s 正常应答并推送 `remoteControl/status/changed` 事件。**协议握手完好，卡的是模型回合**
     ——`real-codex-validation` 的 180s 硬超时发生在等待 final message 阶段，`round_count`
     始终为 0，说明 validator 回合从未产出结果。
  排查顺序建议照抄：版本 → 协议握手 → 回合完成。前两步都是秒级，第三步才昂贵。
- **执行时机**：版本收口前必跑一轮，与 6.1 的 dogfood 场景同批次；结果按 3.3.1 记录。
  它们是发布级里唯一自动化的部分——省掉的是人的操作，不是人的判断。
- **不进 `verify`**：真实模型调用耗时不可控（单条 e2e 实测 24s），放进本地高频循环会让
  4.2 的时长预算直接失效，也会让门禁变得不可信（网络/额度波动导致的红）。
- **不进 CI**：CI runner 没有凭据，也不该有。
- **环境缺失时按 SOP 处理**：显式写明哪条测试、缺什么、补齐后如何执行，不得静默跳过或
  写成通过。

**踩坑记录（2026-08-14）**：nvm-windows 的全局 npm 包**按 Node 版本隔离**。从 Node 22 升到
24 后，装在 22 下的 `@openai/codex` 与 `opencode-ai` 全部失联，`REAL_*` 测试即使打开也只会
因为找不到二进制而失败。切换 Node 大版本后必须同时确认：`npm rebuild better-sqlite3`
（原生模块 ABI）**和**全局 CLI 是否需要重装。

### 3.4 准入清单

Feature 状态改 `done` 前逐条对照，任一条为否即不得改状态：

- [ ] 改动碰到的每一层都补了 3.1.1 对应类型的测试（不是用别的类型顶）。
- [ ] 每条新增 AC 带 `[任务级]` 引用；落在 P0 旅程上的还带 `[需求级]` 引用（见 5.1）。
- [ ] 受影响旅程的 spec 五段内容完整（见 3.2.1），无 `fixme` 残留或已在第 9 节挂任务。
- [ ] 本轮修的每个 bug 都按 7.1 定级并把回归用例补在逃逸的那一层。
- [ ] `npm run verify:release` 全绿。

## 4. 门禁命令与执行点

| 命令 | 组成 | 什么时候必须跑 |
|---|---|---|
| `npm run verify` | lint / format:check / typecheck / 测试 / 文档门禁 / `check:e2e-fixme`（**不含 build 与 E2E**） | 每个任务完成后；本地高频循环 |
| `npm run verify:release` | `verify` + `build` + `test:e2e:install` + `test:e2e` | 推 main 前、Feature 状态改为 done 前、版本收口前 |
| CI `verify` + `e2e` 两个 job | verify job 追加一步 `npm run build` | push main 与 PR 自动触发 |

规则：

- **执行点是"推 main 前"，不是"PR 合并前"**。本项目日常直推 main，把门禁挂在 PR 流程上等于
  没有门禁。若某轮改用分支+PR，CI 已有的 `e2e` job 自动覆盖，无需另行设计。
- 本地与 CI **复用同一条 `npm run test:e2e`**，不允许 CI 另开一套 E2E 清单。
- `verify` 保持不含 E2E，避免拖慢日常循环——真实浏览器一轮的成本量级与其余检查不同。
- 真实环境测试未执行时必须**显式失败或记录客观阻塞原因**，不能写成通过。

### 4.1 引入 E2E 的过渡策略（必须遵守）

CI 的 `e2e` job 已是强制门禁。若在旅程尚未修通时直接提交断言完整旅程的 spec，**整改期内每次
提交都会红**，反而逼人绕过门禁。因此：

1. 新旅程 spec 先以 `test.fixme` 提交——用例存在、断言可读、但不计入失败。
2. 对应旅程整改通过后，同一 commit 里移除 `fixme` 标记，该旅程转入强制。
3. `fixme` 状态的 spec 必须在第 9 节任务清单里有对应未勾选任务；不允许长期挂着。
   由 `npm run check:e2e-fixme` 强制（见 7.3）。

### 4.2 时长预算

测试时长必须是**被管理的属性**，不是"跑着跑着就变慢了"的自然结果。随开发深入，用例只增不减，
不设预算就一定失控。

| 门禁 | 预算 | 2026-08-14 实测 |
|---|---|---|
| `npm run verify` | **< 5 分钟** | **123s**（优化前 550s） |
| 单条旅程 E2E | **< 60 秒** | 尚无用例 |
| `npm run verify:release` | **< 10 分钟** | 待 E2E 用例落地后测 |
| CI 全流程（两个 job 并行） | **< 20 分钟** | 待测 |

规则：

- **超预算按缺陷处理**，记入 `dogfooding-notes.md`，不允许"就这样吧"。
- 每次版本收口记录一次实际时长到 `RETROSPECTIVE.md`——**趋势比绝对值重要**。
- 优化顺序永远是「先找最慢的 5 个文件」，不是「加机器」或「删测试」。

**E2E 准入门槛（最重要的一条）**：任务级可以靠并行和缓存压下来，需求级每条都是分钟级、压不动。
因此未来的时长膨胀风险几乎全在需求级：**旅程 spec 不得随意新增**——P0 旅程就是三条，新问题
默认补任务级，只有 §7.2「重复即升级」触发时才允许新增旅程覆盖。

#### 4.2.1 已落地的优化（2026-08-14）

| 改动 | 效果 |
|---|---|
| `server/vitest.config.ts` 开 `fileParallelism` + `maxWorkers: 8` + `testTimeout: 20s` | server 测试 266s → 59s（连跑两次全绿） |
| `lint` 加 `--cache` | 97s → 热缓存 5s |
| `verify` 移出 `build`，由 CI 与 `verify:release` 承担 | 省 44s |
| **合计** | **`npm run verify` 550s → 123s（4.5×）**，用例一条没删 |

两条踩坑记录，改配置前必读：

- **并行失败的根因是子进程饿死，不是数据串扰**。`git init` 与 fake CLI 夹具是同步子进程，
  22 个 worker 满载时单次调用能跑到 9.8 秒，撞穿 5 秒默认超时。限流到 8 worker 后连跑两次全绿。
- **本机最优值搬到 CI 是负优化**。GitHub runner 只有 2–4 核，因此 `maxWorkers` 按 `process.env.CI`
  取 2。

## 5. 分级测试清单

清单的价值不在于"有一份完整目录"，而在于**能看出哪里没被覆盖**。因此清单**不手写**：仓库现有
162 个测试文件、约 1825 个用例，任何手写目录写完当天就开始腐烂，且没有门禁能发现它错了。

清单由两个维度构成，互相正交，都要有：

| 维度 | 回答 | 载体 | 粒度 |
|---|---|---|---|
| **纵向：AC 映射** | 每条需求有没有测试？ | spec 的 AC 行（已有格式） | 74 条 AC |
| **横向：旅程矩阵** | 串起来能不能走通？ | `docs/reviews/journey-test-matrix.md` | 3 条 P0 旅程 |

### 5.1 纵向：AC → 测试用例映射

**载体是 spec 里已有的 AC 行，不新建文件。** F006/F007 已经是标准格式，照抄：

```
- [x] **AC-001**（`FR-001`、`FR-002`）：<验收结论>。—— 实现 <文件>；
  测试 [任务级]：<测试文件>「<用例名>」；测试 [需求级]：<spec 文件>「<用例名>」。
```

规则：

- 每条 AC 必须给出**测试文件 + 可定位的用例名**，或写明"只能人工验证"及理由；
  第三种情形是"**由门禁覆盖**"（如"全量回归通过"这类 AC，判定方式是 `npm run verify` 全绿）。
- **每组引用必须标层级**（`[任务级]` / `[需求级]`）。没有标记等同于未覆盖。
- **落在 P0 旅程路径上的 AC，必须有 `[需求级]` 引用**；不在 P0 路径上的可以只有 `[任务级]`。
  哪些 AC 在 P0 路径上，由 5.2 的旅程矩阵给出——这是纵横两个维度真正的接口。
  **这条取舍的代价要说清楚**：不在 P0 路径上的界面（如 F008 的模板管理 UI、runtime health
  面板）只有任务级覆盖，出现 NOTE-001 那类"点了没反应"的可发现性问题**没有任何一层会发现**。
  接受这个代价的理由是 E2E 成本（见 4.2），不是因为那些界面不重要——扩大需求级覆盖前，
  它们的可发现性只能靠发布级 dogfood 兜。
- 用例名必须真实存在——由门禁校验（见 7.4），改测试名不同步改 spec 会直接红。
- 新 Feature 的 AC 从第一天就带引用，是 Feature 状态改 `done` 的前置条件。
- 历史回填范围：F001（10）、F002（12）、F003（12）、F004（11）、F005（1）、F006（1）、F008（8），
  共 **55 条**，见 ST-T08。

**历史回填只做这一层的"引用补齐"，不逐条补写测试**。0.1/0.2 的任务级覆盖已经很厚（1825 个
用例），缺的是"哪条需求由哪个用例证明"这条线索；真正的洞在需求级——全仓只有 1 个 E2E spec。

### 5.2 横向：旅程—测试映射矩阵

**输入**：三条 P0 旅程的定义，由 <a href="product-experience-reset-plan.md">`product-experience-reset-plan.md`</a>
M3-T04 产出。这是本文唯一的外部输入依赖；在它落地前，其余各节均可独立推进。

旅程确定后，产出矩阵（落点 `docs/reviews/journey-test-matrix.md`），每条旅程的每一步映射到：

1. 自动化测试文件（spec + 用例名），或明确写出"只能人工验证"的理由。
2. 前置数据与环境（seed 调用、mock run 参数）。
3. 用户动作与**预期可见反馈**。
4. 失败恢复动作及其预期状态。
5. 证据保存位置。

没有映射的旅程步骤，不得靠"整体看起来测试很多"视为已覆盖。

## 6. 发布级场景与记录回流

### 6.1 固定场景清单

**先跑自动化的那部分**：`REAL_CODEX=1 REAL_CLAUDE=1 REAL_OPENCODE=1 npm -w @personahub/server run test`
（见 3.3.2）。它覆盖真实 CLI 的派发、验证、跨 provider 与队列语义；下面五个场景是它覆盖不了的
人工判断部分，不要用它替代。

版本收口前逐条执行并记录实际耗时：

1. 干净数据库的首次启动与配置。
2. 已有 Project、历史 Issue、既有 Adapter 的升级场景。
3. 一个真实 coding Issue 跑到 Done（**真实 CLI**）。
4. 主动取消、进程重启或 Adapter 不可用后的恢复。
5. validation 失败/中断 → unblock → 重试 → 完成。

首次执行时**五条全跑并记录耗时**；是否分「每次必跑 / 抽查」两级，用这次实测数据决定，不凭
估算提前分级。

### 6.2 记录回流

- 已确认缺陷 → `dogfooding-bugs.md`，`npm run bug:log` 校验。
- 不算 bug 的交互/易用性/术语问题 → `dogfooding-notes.md`。
- 每条记录须能追溯到**具体旅程步骤**。同一步骤反复出问题 = 该步骤需求级覆盖不足，补用例，
  不是只修单点。
- 每次 dogfood 后回填状态与去向（`adopted` 填 BACKLOG 条目或 Feature ID / `dismissed` 写理由），
  不允许长期堆积 `open`。

## 7. 演进闭环

清单是静态的，缺陷是持续来的。**没有触发器的"持续改进"等于备忘录**，因此把演进拆成四个可
执行、可检查的触发器——每一个都规定了"发生什么 → 必须做什么 → 谁来卡"。

### 7.1 逃逸定级：缺陷补在它逃过的那一层

每条 bug 入 `dogfooding-bugs.md` 时，必须回答"**本该被哪一层拦住**"，回归用例就补在那一层：

| 逃逸层级 | 说明 | 补什么 |
|---|---|---|
| 任务级 | 契约/边界/分支错了 | 单元或接口用例（现有习惯，已在做） |
| 需求级 | 各组件都对，但连起来走不通、入口找不到 | E2E spec 的对应步骤断言 |
| 发布级 | 只有真实 CLI / 真实数据才暴露 | 扩充 6.1 场景清单，说明如何复现 |

反模式：不管什么 bug 都补单测。可发现性问题补单测等于没补——它下次照样逃出去。

**门禁（已生效）**：`dogfooding-bugs.md` 主表有 **逃逸层级** 列，`npm run bug:log` 校验其为
`任务级`/`需求级`/`发布级` 之一，缺失或非法即退出码 1。**不设 "unknown" 逃生舱**——允许不回答，
这条触发器就等于不存在。

### 7.2 重复即升级

同一旅程步骤**第二次**出问题（bugs 或 notes 表任一），强制补该步骤的需求级 spec，不接受再修
单点。第二次出现是"这一步没有覆盖"的证据，不是"这次运气不好"。

**门禁（已生效）**：两张主表都有 **旅程步骤** 列，`npm run bug:log` 跨两份文档合并计数，
出现 ≥2 次的步骤会被单独列出并标注"需要需求级 spec"。P0 旅程定稿前该列填 `—`，`—` 不计入
重复统计。

### 7.3 `fixme` 不过夜

`test.fixme` 的 spec 必须在第 9 节任务清单有对应未勾选任务。允许暂时红转黄（见 4.1），不允许
无主挂着——无主的 fixme 会变成永久的假覆盖。

**门禁（已生效）**：`npm run check:e2e-fixme`（已接入 `verify`）扫描 `e2e/tests/**/*.spec.ts`
的无条件停放标记（`test.fixme`、具名 `test.skip`、`describe.skip`），要求第 9 节存在**未勾选**
任务提及该 spec 的文件名；无主即退出码 1。任务勾掉后该 spec 若仍停放，同样报错——完成的任务
意味着没人再对它负责。

**刻意不匹配条件跳过**（Playwright 的 `test.skip(condition, reason)`、vitest 的 `describe.skipIf`）：
那些表达的是"本环境跑不了"，归 SOP 的真实环境测试纪律与 3.3.2 管，不是本门禁的对象。

### 7.4 漂移即失败

以下不一致必须让 `npm run verify` 直接失败，而不是靠人复查：

- AC 引用的测试文件不存在，或引用的用例名在该文件中找不到。
- AC 行既无测试引用，又无"只能人工验证"/"由门禁覆盖"标注（历史 Feature 回填完成后启用）。
- 引用未标层级，或 P0 旅程路径上的 AC 缺 `[需求级]` 引用（旅程矩阵产出后启用）。

这一条是整套机制能"自演进"而不是"自愿维护"的关键。前三条靠纪律，第四条靠门禁；只有第四条
在无人盯着时仍然生效。

## 8. 通过与停止条件

收口判定必须能机械执行，因此按两个记录表各自的既有字段定义（bugs 表用高/中/低，notes 表无
严重度列，不要用统一的 Critical/High 口径去套）：

1. `npm run verify:release` 全绿（含真实浏览器 E2E）。
2. 三条 P0 旅程的 spec 无 `skip` / `fixme` 残留。
3. `dogfooding-bugs.md` 中严重度=**高**且状态≠`fixed` 的条目数为 **0**（`npm run bug:log` 可查）。
4. `dogfooding-notes.md` 中落在三条 P0 旅程步骤上的条目无 `open`；不在 P0 路径上的可留 `open`。
5. 第 6.1 节五个场景全部执行并留下记录。
6. 74 条 AC 全部带测试引用或人工验证理由（7.4 门禁自动判定）。
7. `REAL_*` 真实 CLI 测试本轮跑过并通过（见 3.3.2）；未跑成的按 SOP 显式记录原因。

任一项失败，版本回到整改。**不得把核心路径不可用写进"已知限制"后继续收口。**

## 11. 体系的资产观

**自动化用例不是这套体系的主要资产，是它的当期表现。** 这一节存在的目的是防住两类具体误判：
为了省时间砍掉不产出用例的层，以及拿"用例数增长"当质量指标。

### 11.1 资产按耐久度排序

| # | 资产 | 为什么比用例耐久 |
|---|---|---|
| 1 | **测试基建与夹具** | `e2e/tests/support/{seed,mock-run}.ts`、`server/tests/helpers.ts` 的 `createTestServices()`、`helpers/fake-*.mjs`。夹具在，补一条用例是分钟级；夹具不在，一条要半天 |
| 2 | **判据与边界** | 第 3 节每层"负责/不负责"的划分。换框架、重写实现后依然成立 |
| 3 | **映射关系** | AC↔用例（5.1）、旅程↔步骤（5.2）。没有它，1825 个用例只是一堆绿灯，答不出"这条需求由谁证明" |
| 4 | **逃逸历史** | `dogfooding-bugs.md` 的逃逸层级分布。项目特有、买不到，直接决定下一步该投在哪一层 |
| 5 | 自动化用例 | 随重构大批失效，会腐烂、会变慢 |

**判据：能被一次重构清零的东西不是资产。** 产品体验重置会作废一批 UI 断言（见 3.2.1），但上面
1–4 项一条都不损失——这本身就是排序的证明。

### 11.2 两个必须避免的误判

- **"发布级不产出用例，投入产出比最低"** → 它产出的 dogfood 记录与逃逸定级是 §7.1/§7.2 两个
  触发器的**唯一数据来源**。砍掉它，演进闭环立即断开，体系退回静态检查清单。
- **"用例数增长 = 质量提升"** → 用例数不是指标。见 11.3。

### 11.3 负资产

以下三类使体系变差，清理它们和新增用例同等重要：

1. **腐烂用例**：断言的是早已不存在的行为。由 7.4 的 AC 映射门禁间接暴露——映射不上的用例本身可疑。
2. **假覆盖**：`test.fixme` 长期挂着，看着有用例其实没跑。由 7.3 卡。
3. **慢用例**：挤占 4.2 的时长预算，逼人跳过门禁。由 4.2 的预算规则卡。

### 11.4 因此体系设计的取舍原则

优先保护本金：**投在夹具、判据、映射和记录格式上的时间，优先于多写几条用例**。用例可以重写，
上述四项重写一次的代价是数周。

## 12. 资产管理

11.1 排出了四类资产，本节规定每类**归谁、什么时候更新、什么机制防它腐烂**。没有归属的资产
必然腐烂——`server/tests/helpers.ts` 长到 419 行、超过 `docs/SOP.md` 的 350 行硬上限而无人察觉，
就是这条规律的现成例子。

| 资产 | 真相源 | 更新时机 | 防腐机制 |
|---|---|---|---|
| 测试基建/夹具 | `server/tests/helpers.ts`、`server/tests/helpers/`、`e2e/tests/support/` | 接新 adapter、加新实体、E2E 需要新播种时 | 适用 SOP 行数上限（见 12.1） |
| 判据与边界 | **本文** | 每次版本收口复审（见 12.2） | `AUTHORITATIVE_DOCS` 门禁 |
| 映射关系 | 各 spec 的 AC 行 + `journey-test-matrix.md` | Feature 改 `done` 前 | §7.4 漂移门禁（ST-T09） |
| 逃逸历史 | `dogfooding-bugs.md` / `dogfooding-notes.md` 主表 | 每次 dogfood 后 | `npm run bug:log` 校验 |

### 12.1 夹具按一等代码管理

测试夹具不是"测试里的辅助文件"，它是 1 号资产：夹具崩，所有依赖它的用例一起崩。因此：

- 适用 `docs/SOP.md` 的行数约定（200 行建议拆分 / 350 行硬上限），与 `src/` 同等对待。
- 夹具的破坏性改动（改签名、改默认播种内容）要在同一次提交里修完所有调用方，不留 TODO。
- ESLint 对 `**/tests/**` 放宽了未使用变量等规则，**放宽的是风格检查，不是结构约束**——
  行数与拆分纪律照旧适用。

### 12.2 体系自身的复审节奏

本文规定测试如何演进，但规则自己也会过时。**没有复审节奏的流程文档三个月后必然与实际脱节。**

- **节奏**：每次版本收口时对照本文一次，与 dogfood 同一批次进行。
- **对照什么**：3.1.1 的六类是否仍覆盖当下的改动类型；3.2.1 的五段是否有该加的；6.1 的五个
  场景是否需要增删；4.2 的时长预算是否仍现实。
- **结论落点**：写进 `docs/reviews/RETROSPECTIVE.md`，需要改规则的部分回到本文修改并记录日期。
- **不做的事**：不为"文档看起来更完整"而扩写。规则只在被现实证伪时才改。

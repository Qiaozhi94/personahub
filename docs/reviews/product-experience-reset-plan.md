# PersonaHub 产品体验重置与开发计划调整方案

> 结论：暂停当前功能开发。先完成用户旅程定稿、可点击 HTML 原型定稿和开发自测试
> 体系设计，再依据定稿结果输出整体整改方案。F009–F012 保留为历史规划输入，但不得
> 原样进入开发，也不在本阶段修改业务代码、API、schema 或测试。

## 1. 背景与问题判断

v0.2 已完成大量功能、契约和自动化测试，但首次短时间 dogfood 就暴露出阻塞性问题和
核心操作不可发现的问题。根因不是单个组件质量不足，而是当前流程的完成定义主要围绕
Feature、FR/AC 和代码正确性，没有把“用户能否从目标出发完成一条完整旅程”作为发布
前置条件。

当前流程存在四个结构性缺口：

1. 用户旅程虽然散落在 PRD 和 Feature spec 中，但没有产品级、跨 Feature 的体验真相源。
2. user-facing Feature 没有强制原型门禁，0.2 可以在未做真实浏览器人工点击验证时收口。
3. `npm run verify` 不包含真实浏览器 `test:e2e`，组件测试无法发现可发现性和完整操作路径问题。
4. dogfood 发生在版本收口后，承担了本应由开发自测试和发布验收提前发现的问题。

## 2. 本轮目标、范围与暂停规则

### 目标

- 重新确认 PersonaHub 当前阶段最重要的用户目标和完整操作旅程。
- 用独立、可点击的 HTML 原型表达目标体验，不受现有 React 页面结构限制。
- 建立任务级（单元/接口）、需求级（Playwright 真实浏览器）、发布级（用户使用反馈）三层自测试流程。
- 评估现有 v0.3 计划受影响的范围，形成后续整体整改的输入。

### 本轮范围

- PRD 中 v0.1–v0.3 承诺范围内的用户目标：首次配置、任务执行、失败恢复。
- 从产品意图重新推导的信息架构、入口、状态反馈和错误恢复方式。
- 开发流程、Feature 门禁、E2E 和 dogfood 验收方式。

### 清白起点原则（clean-room）

用户旅程和原型**从 PRD、architecture、system-design 与 ADR 重新推导，不参考任何现有实现、
现有页面结构、组件命名或代码逻辑**。原因：现有实现正是被 dogfood 判定为偏离预期的对象，
以它为起点会把既有的信息架构和术语当成既定事实，只做局部修补。

具体约束：

- 工作流 A、B 阶段不阅读 `web/` 源码，不以现有页面截图为设计输入。
- 不因"现在已经这样实现了"而保留某个入口、术语或步骤；只因"PRD 要求"而保留。
- 现有实现与既有 dogfood 问题记录（`dogfooding-bugs.md` / `dogfooding-notes.md`）
  **只在 P3 影响面分析阶段作为差距对照输入使用**，不进入旅程设计和原型设计阶段。

### 暂停规则

- F009–F012 保持 `draft`，不得推进到 `ready-for-development`。
- 暂停新业务代码、schema、API、组件重构和非紧急 bug 修复。
- 本阶段只允许调研、旅程文档、HTML 原型、检视记录和测试流程设计。
- 用户明确批准原型前，不输出可直接执行的详细代码任务，不提前实现“看起来确定”的页面。

## 3. 工作流 A：用户旅程梳理

**预计时间：1–2 个工作日。**

### A1. 产品意图重建

不做现状还原，直接从设计文档重新推导（见"清白起点原则"）：

- 读 `docs/personahub-prd.md`，抽出产品承诺的用户目标、核心概念和成功定义。
- 读 `docs/personahub-architecture.md` / `-system-design.md` / `docs/decisions/`，
  只提取**真实的技术约束**（本地优先、CLI adapter 进程模型、SQLite 单机、
  workspace 排他锁等），用来判断旅程是否可实现，不用来推导页面结构。
- 列出 PRD 层面的概念清单（Project / Issue / Thread / Agent / Workflow / Evidence…），
  标注每个概念是"用户必须理解的"还是"实现细节，不应出现在界面上"。

**产出**：产品意图摘要、技术约束清单、概念清单及其暴露级别。

### A2. 核心用户与核心任务确认

第一阶段只围绕一个核心用户：希望把真实 coding 工作交给多个本地 AI CLI，同时保留
控制权和验证证据的个人开发者。

优先验证三个 P0 任务：

1. 首次打开应用后完成最小配置并进入可执行状态。
2. 输入开发目标、确认系统建议并运行到可信的 Done。
3. 任务失败、中断或等待人工判断后，理解原因并安全恢复。

**产出**：用户定义、Jobs-to-be-Done、P0/P1 范围边界。

### A3. 目标旅程设计

每条旅程必须包含：

- 触发条件、用户目标与成功终点。
- 用户动作、系统反馈和此刻最关心的问题。
- 主路径、空状态、错误路径、恢复路径和不可逆操作。
- 每一步涉及的产品概念，以及哪些概念应隐藏或渐进展示。
- 可观察、可计时的验收标准。

**产出**：目标旅程表、状态矩阵、术语与信息披露规则。

### A4. 建议验收指标

- 首次用户无外部文档辅助，在 5 分钟内进入“可以创建任务”状态。
- 创建任务只有一个主入口，从输入目标到启动不超过 3 次主要操作。
- 运行页面优先回答“进行到哪一步、是否需要我、下一步是什么”。
- 阻塞状态必须同时展示原因、影响和一个推荐主操作。
- 用户无需阅读内部 error code 或原始日志完成常见恢复。

### A5. 旅程定稿门禁

- 第 1 轮：全量检查目标、范围、步骤、异常和恢复是否完整。
- 修改后第 2 轮：只复核 diff 及相邻步骤。
- Critical/High 体验问题清零，并由用户明确批准。

**退出条件**：用户旅程成为后续原型的唯一行为输入；未通过的争议点不得交给原型阶段猜测。

## 4. 工作流 B：前端 HTML 原型

**预计时间：2–4 个工作日，在工作流 A 初稿通过后开始，与工作流 C 并行推进。**

### B0. UX 设计参考基线

原型的视觉与交互方向参考本机两个开源项目 `D:\Projects\clowder-ai` 与
`D:\Projects\multica`。参考方式已有现成的调研结论，**先读调研文档再看代码，不重做竞品分析**：

| 参考源 | 读哪一节 | 用来回答 |
|---|---|---|
| `docs/research/multica-analysis-report.md` | §4 页面效果与信息架构、§7.2 UI 转译 | 主视觉基调与工作台骨架 |
| `docs/research/clowder-ai-analysis-report.md` | §4 页面效果与信息架构、§7.2 UI 转译 | 协作/角色/证据类信息如何组织 |

调研已给出的结论直接作为本轮起点，不再重新论证：

- **视觉基调取 multica**：简洁、冷静、功能导向的工程协作工具风格；不采用 clowder-ai 的
  情感化、强 IP 角色和多工作面叙事 UI，避免早期界面复杂化。
- **协作逻辑取 clowder-ai**：Task Thread、Agent Profile、Handoff、Review、Trace、Memory
  这套"agent 是有身份的长期成员"的组织方式，但用 multica 的克制视觉去表达。
- **两份调研给出的页面骨架高度一致**，可作为原型第一版布局的默认假设，再按工作流 A 的
  旅程校正：左侧 Projects / Tasks / Agents / Settings，中间主区 Board 或 Task Detail，
  右侧上下文 Assignee / Runtime / Trace / Decisions / Blockers，Run Log / Thread 放详情区。

约束与执行节奏：

- 参考的是**页面级 UX 组织方式**，不是功能清单。任何"因为 multica/clowder 有这个功能所以
  我们也做"的推论一律拒绝——功能范围只由 PRD 和工作流 A 的旅程决定。
- 上述三条结论在 B1/B2 阶段**直接采纳，不再重新论证**。调研报告是基于 README 写的，页面
  骨架这一层已经够用，B0 阶段不花时间通读两个项目的前端代码。
- **只有在 B3/B4 遇到具体交互细节说不清时才去读真实代码**（典型场景：运行中状态怎么呈现进度
  与"是否需要我"、blocked 时怎么同时给出原因和推荐动作、日志/证据的折叠层级怎么分）。此时
  按 `docs/SOP.md`「参考开源项目验证设计假设的节奏」定点去挖，带着具体问题读，不做通读。

### B1. 信息架构草图

先确定页面关系，不先设计视觉细节：

- Project、任务、Agent、配置和运行状态的一级/二级层级。
- 创建任务的唯一主入口及高级选项的渐进展示方式。
- 执行进度、Thread、技术日志、人工介入和最终证据的关系。
- 桌面宽屏与 1024px 窗口下的信息优先级。

**产出**：页面地图和区域职责说明。

### B2. 低保真可点击骨架

首批覆盖以下状态：

1. 首次启动和渐进式设置。
2. 工作台空状态与创建任务。
3. 推荐方案确认。
4. 任务运行中与不需要人工介入。
5. Done 结果、Blocked 状态及恢复。

**产出**：单文件 HTML/CSS/JS 原型，可直接本地打开。

### B3. 交互和视觉细化

- 所有可点击目标有明确视觉提示、hover/focus/disabled 状态。
- 主操作每个视图最多一个；次要操作不与主操作竞争。
- 普通用户信息默认展开，原始事件、日志、ID 和规则命中详情默认折叠。
- Loading、empty、error、blocked、done 均有明确反馈和下一步。
- 沿用 `docs/decisions/0004-ui-styling-stack.md` 的样式栈与 OKLCH token 体系（这是已生效的
  技术决策，不是"现有实现"），但布局、信息密度和组件组合允许完全重新设计。

### B4. 原型检视

第 1 轮全量检视有限检查清单：

- 可发现性、信息层级、术语、操作反馈。
- 三条 P0 旅程是否可连续完成。
- 空状态、错误状态和恢复路径。
- 1024×768、1440×900、1920×1080 三档窗口。
- 键盘焦点、对比度和文本溢出等基础可访问性。

修改后第 2 轮只复核修订区域和相邻交互；仅在第 2 轮引入新问题时追加一次第 3 轮，
不进行无限全量重审。

### B5. 用户定稿

用户按场景清单亲自操作原型。反馈统一归为：

- 必须修改：阻塞旅程或明显违背预期。
- 后移：不影响 P0 旅程，可进入后续 Feature。
- 不采纳：记录理由，避免下一轮反复提出。

**退出条件**：用户明确说“原型定稿”；单纯没有新反馈不等于批准。

## 5. 工作流 C：开发自测试体系

**流程设计预计 1–2 个工作日，在工作流 A 初稿通过后开始，与工作流 B 并行推进；实际门禁在重构实施阶段落地。**

### C1. 三层测试模型

| 层级 | 责任 | 手段 | 执行时机 | 主要证据 |
|---|---|---|---|---|
| 任务级 | 一个实现动作没有破坏局部契约 | 单元测试 + 接口（API/集成）测试 + typecheck | 每个任务完成后 | 测试报告、`npm run verify` 通过记录 |
| 需求级 | 受影响的用户旅程切片能被真实用户走通 | **Playwright 真实浏览器端到端** | Feature 进入 review 前 | E2E 用例、失败截图/trace、异常与恢复用例 |
| 发布级 | 真实用户在真实环境能完成闭环并认可 | 人工 dogfood + 用户使用反馈 | 版本收口前 | scripted dogfood 记录、真实 CLI 运行证据、`dogfooding-bugs.md` / `dogfooding-notes.md` 回填 |

各层的职责边界，避免上一层替下一层背锅：

- **任务级只证明契约没坏，不证明好用**。jsdom 组件测试归在这一层，它验证组件行为，
  不能作为"页面能用"的证据。
- **需求级是本轮新增的强制层，也是这次问题的直接补丁**。仓库已有 Playwright 基建
  （`e2e/playwright.config.ts`、`npm run test:e2e`），但目前只有一条 `f005-layout.spec.ts`，
  且 `test:e2e` 未接入 `npm run verify`——能力早就在，缺的是强制执行。整改的核心动作是
  **补旅程覆盖 + 接入强制门禁**，不是重建测试框架。
- **发布级承认自己不可自动化**。它的价值就在于人的主观判断（"这是不是我预想的样子"），
  因此不设"自动化替代方案"，只固定场景清单和记录格式，保证每次收口都真的跑过。

### C2. 旅程—测试映射

用户旅程每一步必须映射到：

- 自动化测试文件或明确说明为何只能人工验证。
- 测试前置数据和环境。
- 用户动作与预期可见反馈。
- 失败恢复动作及其预期状态。
- 证据保存位置。

没有映射的旅程步骤不得靠"整体看起来测试很多"视为已覆盖。

**需求级 E2E 的第一批用例就是三条 P0 旅程本身**（A2 定义的：最小配置进入可执行状态、
输入目标运行到可信 Done、失败后理解原因并安全恢复），一条旅程一个 spec 文件，按用户动作
顺序断言，不按页面或组件拆分用例。这样做的原因：

- C2 的旅程—测试映射天然成立，不需要事后再补一张对照表。
- 直接避免这次 dogfood 暴露的问题模式——"组件渲染全部正确，但旅程走不通"。按组件拆的用例
  永远发现不了可发现性问题和步骤断裂。
- 组件级、边界值的细粒度断言留在任务级（jsdom / 接口测试），不挤进 E2E，避免 E2E 变慢变脆。

### C3. 统一验证入口整改要求

- `npm run verify` 保持本地高频入口，覆盖 lint/typecheck/单元/组件测试，不在这一层强制跑真实浏览器
  E2E，避免拖慢日常本地循环。
- 新增覆盖真实浏览器 E2E 的强制门禁命令（如 `npm run verify:release`），PR 合并前与版本收口前
  必须跑；本地与 CI 复用同一条命令，不允许 CI 另开一套 E2E 清单。
- jsdom UI 测试用于组件行为，不得替代真实布局和完整点击路径；真实布局验证只能靠 E2E 门禁完成。
- 真实环境测试未执行时必须明确失败或记录客观阻塞原因，不能写成通过。

### C4. 固定 dogfood 场景

版本收口前至少执行：

1. 干净数据库的首次启动和配置。
2. 已有 Project、历史 Issue 和既有 Adapter 的升级场景。
3. 一个真实 coding Issue 正常运行到 Done。
4. 主动取消、进程重启或 Adapter 不可用后的恢复。
5. validation 失败/中断、unblock、重试并最终完成。

### C5. 用户反馈的记录与回流

发布级的产出是主观判断，必须有固定落点，否则会像这次一样只留在记忆里：

- 使用中发现的确认缺陷 → `docs/reviews/dogfooding-bugs.md`，`npm run bug:log` 校验。
- 不算 bug 的交互/易用性/术语问题 → `docs/reviews/dogfooding-notes.md`。
- 每条记录必须能追溯到具体旅程步骤；反复出现在同一步骤的问题，说明该步骤的需求级 E2E
  覆盖不足，需要补用例而不是只修单点。
- 每次 dogfood 后回填 note 的状态与去向（`adopted` / `dismissed`），不允许长期堆积 `open`。

### C6. 完成与停止条件

- Critical/High 正确性和体验问题清零。
- 原型关键交互与实现一致。
- 自动化门禁全绿，真实浏览器旅程通过。
- 发布级 dogfood 三类数据状态通过。
- 任一项失败，版本回到整改；不得把核心路径不可用写入“已知限制”后继续收口。

## 6. 当前 v0.3 开发计划修改评估

### 总体判断

F009–F012 都处于 `draft`，当前暂停不会造成已实现代码或 migration 的返工，成本主要是
重新审视产品优先级和 Feature 边界。原计划技术依赖顺序基本自洽，但它从 Artifact、
Room、Squad 等领域能力出发，没有先证明当前核心工作台是否好用。因此建议保留技术研究，
废止现有时间线和“评审通过即可开发”的假设。

| 项目 | 当前判断 | 建议处理 | 原因 | 重新进入计划的条件 |
|---|---|---|---|---|
| F009 Artifact Foundation | 技术基础有价值，但不是当前体验阻塞的直接解法 | 保留 draft，重新评估 UI 范围 | 可能增加 Inspector 复杂度 | 原型明确 Artifact 在旅程中的用户价值与入口 |
| F010 Artifact Coding Slice | 依赖 F009，且会深度改变执行与结果呈现 | 暂停并重写旅程映射 | 当前核心执行旅程尚未稳定 | 新工作台整改完成，Artifact 消费路径通过原型验证 |
| F011 Work Room | 与“观察、打断、纠偏”高度相关，产品价值可能保留 | 保留概念，重做交互与范围 | 现有三栏 Thread 体验未验证，直接加 Room 风险最高 | 原型先证明单 Issue 的观察与介入模型 |
| F012 Squad | 便利性能力，不解决当前阻塞主流程 | 明确后移 | 依赖 F011，且会增加设置复杂度 | Room 被真实使用并出现重复成员配置需求 |
| v0.3 25–40 日时间线 | 建立在现有 Feature 顺序和范围不变的假设上 | 作废，定稿后重估 | 旅程和整体整改会改变范围 | 整改影响面、迁移方案和测试矩阵完成 |

### 建议替换后的阶段顺序

P2（工作流 B）与 P3（工作流 C）共享同一启动点（工作流 A 初稿通过），并行执行，不是串行。

## 7. 整体整改阶段的规划原则

原型定稿后先做影响面分析，不立即全仓重写。**这里是现有实现第一次被允许作为输入的地方**
（见"清白起点原则"）：把定稿旅程与现有实现逐条对照，产出「可复用 / 需改造 / 需废弃」三类
结论，并把 `dogfooding-bugs.md` / `dogfooding-notes.md` 的开放项映射到对应旅程步骤，确认
新设计确实解掉了它们，而不是换个位置重现。

整改任务按用户旅程垂直切片，而不是按"先全部后端、再全部前端"分层：

1. 首次设置切片：Project、Workspace、Agent、诊断与相应测试。
2. 创建任务切片：统一入口、推荐确认、启动反馈与幂等测试。
3. 运行观察切片：进度、关键事件、日志层级和人工补充。
4. 阻塞恢复切片：原因、影响、推荐动作、恢复状态机和回归测试。
5. 完成结果切片：结果摘要、文件变化、验证证据和可信 Done。

每个切片独立实现、独立验证、独立复核；上一个切片未通过真实浏览器旅程前，不进入
下一个切片。

## 8. 风险与控制

| 风险 | 影响 | 控制方式 |
|---|---|---|
| 原型不断扩展到 v0.3 新能力 | 无法定稿，重构范围失控 | 首轮只覆盖 PRD 中 v0.1–v0.2 承诺范围；新增想法进入后移清单 |
| clean-room 变成"重新发明一遍" | 白白丢掉已被验证有效的设计判断 | 允许并鼓励复用 PRD/ADR/调研结论；被禁止的只是把现有页面结构和代码逻辑当成设计输入 |
| 参考项目功能被顺手抄进范围 | 范围膨胀，偏离 PersonaHub 自身定位 | B0 已限定只参考页面级 UX 组织方式；功能范围只由 PRD 与工作流 A 决定 |
| 只调整视觉、不改变旅程 | 阻塞问题换皮保留 | 每个页面决策必须追溯到旅程步骤 |
| 原型与真实约束脱节 | 定稿后实现不可行 | 关键状态/API 假设同步做轻量可行性核对，不提前编码 |
| 全仓一次性重构 | 回归范围过大，无法定位问题 | 按五个垂直切片逐个闭环 |
| 自动化再次替代人工使用 | 可发现性问题重复发生 | 发布前固定真实浏览器 dogfood，不允许豁免核心旅程 |

## 9. 评审、批准与执行门禁

本计划采用有限两轮文档检视：

1. 第 1 轮全量检查范围、依赖、产出、退出条件和现有计划影响。
2. 根据反馈修改。
3. 第 2 轮只复核修改 diff 及相邻契约。
4. 用户明确批准后，本计划才成为执行依据。
5. 批准前不继续用户旅程、HTML 原型、自测试整改或业务开发。

# PersonaHub 产品体验重置与开发计划调整方案

> 结论：暂停当前功能开发。先从本机 `clowder-ai` 与 `multica` 的真实代码还原各自用户
> 旅程，并分别还原可点击的参考页面；用户看过并选择借鉴方向后，再设计 PersonaHub
> 用户旅程、产品原型和开发自测试体系。F009–F012 保留为历史规划输入，但不得原样进入
> 开发，也不在本阶段修改业务代码、API、schema 或测试。
>
> **2026-08-12 方法修正**：参考页面的还原方式由「手写单文件静态 HTML」改为「渲染冻结」
> （第 3.1 节）。前者已实测失败两次，产物 `multica/prototype/` 与 `clowder-ai/prototypes/`
> 均为 agent 自造 design system 的结果，与真值无对应关系。后者已完成 multica 22 页、
> clowder-ai 5 页，验收全绿。

## 1. 背景与问题判断

v0.2 已完成大量功能、契约和自动化测试，但首次短时间 dogfood 就暴露出阻塞性问题和
核心操作不可发现的问题。根因不是单个组件质量不足，而是当前流程的完成定义主要围绕
Feature、FR/AC 和代码正确性，没有把“用户能否从目标出发完成一条完整旅程”作为发布
前置条件。

当前流程存在四个结构性缺口：

1. 用户旅程虽然散落在 PRD 和 Feature spec 中，但没有产品级、跨 Feature 的体验真相源。
2. user-facing Feature 没有强制原型门禁，0.2 可以在未做真实浏览器人工点击验证时收口。
3. `npm run verify` 不包含真实浏览器 `test:e2e`，组件测试无法发现可发现性和完整操作路径问题。
4. dogfood 发生在版本收口后，承担了本应由开发自测试和发布验收提前发现的问题。

## 2. 本轮目标、范围与暂停规则

### 目标

- 重新确认 PersonaHub 当前阶段最重要的用户目标和完整操作旅程。

  不受 PersonaHub 现有 React 页面结构限制。
- 建立任务级（单元/接口）、需求级（Playwright 真实浏览器）、发布级（用户使用反馈）三层
  自测试流程——**方案已拆出，见 <a href="self-test-system-plan.md">`self-test-system-plan.md`</a>**。
- 评估现有 v0.3 计划受影响的范围，形成后续整体整改的输入。

### 本轮范围

## 3. M2 方法：参考项目用户旅程与页面还原

**预计时间：1–2 个工作日。必须先于 PersonaHub 用户旅程。**

1. 分别读取两个项目自身的 `AGENTS.md` / `CLAUDE.md`、README、产品文档、路由与关键页面代码。
2. 每个项目独立产出：目标用户、首次进入、创建核心工作、执行/协作、完成/恢复旅程，
   以及**每个页面一张交互契约表（格式见 3.5 节，这是主产出）**。
3. 每个项目独立还原代表性页面，**方法见第 3.1 节（不是手写静态 HTML）**。
4. 用真实浏览器验证还原页的点击连续性、键盘焦点和控制台错误（视口固定 1440px，理由见 M2-T06）。
5. 输出中立对照表；由用户决定哪些直接借鉴、哪些调整借鉴、哪些不采用。

**本轮关注点（2026-08-13 明确）**：参考还原服务于「分析页面交互与功能分区」，不服务于
多分辨率适配。因此优先级是 —— 交互契约（每个可交互元素的触发条件与状态变化）> 功能分区
（导航层级、区域划分、信息密度）> 视觉细节 > 响应式行为（本轮不做）。

**退出条件**：用户明确完成参考评审并给出借鉴方向。未达到时，不进入 PersonaHub 用户旅程设计。

### 3.1 页面还原方法：渲染冻结，不是手写 HTML

**本节修正了原计划中「制作单文件静态 HTML」的做法。该做法已实测失败，不再采用。**

#### 失败证据

2026-08-12 当晚曾用 agent 对两个项目各重绘过一次，产物仍在（均未提交）：

| 产物 | 规模 | 结果 |
|---|---|---|
| `D:\Projects\multica\prototype\` | 36 个 HTML + 373 行 CSS | 不像 |
| `D:\Projects\clowder-ai\prototypes\` | 11 个 HTML + 430 行 CSS | 不像 |

两份的失败模式完全相同 —— agent 自造了一套 design system：

| 项目 | 真实体系 | 重绘产物 |
|---|---|---|
| multica | Tailwind v4 `@theme inline` + OKLCH | 手写 `--brand: #3b6df2` 平铺变量 |
| clowder-ai | OKLCH 四旋钮派生（`--accent-hue` / `--surface-chroma`） | 手写 hex `--brand-pink: #f9af00` + emoji 图标 |

**根因**：agent 读 React 源码 → 脑内渲染 → 写 HTML，是「翻译」不是「提取」。Tailwind 类名的实际数值（间距、字阶、色值、阴影）由编译期算出，源码里根本不存在这些数字，agent 只能猜。猜 5000 行，必然处处偏差。

这也解释了为什么「再改细一点」没用：产物与真值之间没有对应关系，改一处偏一处。

#### 替代方法

让浏览器当唯一真相源，机器提取渲染结果。渲染后的 DOM + 编译后的 CSS 拼起来**就是原页面本身**。

四个阶段：真值提取 → 静态化 → 交互还原 → 自动验收。完整方法、脚本与踩坑清单见 `frontend-replication` skill（用户级，`~/.claude/skills/frontend-replication/`），本文档只记录两个参考项目的具体接入参数（第 3.2、3.3 节）。

**关键点**：静态化阶段只做减法（剥框架运行时、改资源引用），**不重写 CSS、不重命名 class、不重建 token**。打开发现不一样，是漏了某个 CSS 或字体，去补，不要动样式。

#### 已完成的实测结果（2026-08-12 静态还原，2026-08-14 补交互）

| 项目 | 页面数 | 静态验收 | 跳转 | 交互状态 |
|---|---|---|---|---|
| multica | 26 | **66/66 通过** | 305 条链接 + 3 条行点击全部走得通 | **221/221 回放成功**，27 个已知缺口 |
| clowder-ai | 5 | **15/15 通过** | 1 条链接通，5 条待补页 | 未采集（需应用在跑） |

产物落点 `D:\Projects\ui-reference\`（独立目录，不进任何现有仓库）。验收标准为「结构与交互一致」：DOM 树逐节点比对 + 每节点约 60 个 computed style 属性比对，非像素级截图比对。

multica 已还原页面（26）：landing / login / about / usecases / changelog / download / contact-sales / issues / my-issues / projects / agents / autopilots / skills / runtimes / squads / inbox / chat / usage / billing / settings / issue-detail / project-detail / agent-detail / skill-detail / member-detail / agent-new。

### 3.3 clowder-ai 接入参数

| 项 | 值 |
|---|---|
| 前端 | `http://localhost:3003` |
| 后端 | `http://localhost:3004` |
| Redis | `6399`（自带端口隔离，不冲突） |
| 栈 | Next.js 14 + Tailwind v3 + 手写组件（无 Radix / 无 Base UI） |
| 主题 | `<html data-theme="dark">`，**667 个 CSS 变量**（每只猫一套 persona 色） |

**关键认知：Electron 只是套壳。** `desktop-dist/resources/app/main.js:67` 写死 `FRONTEND_PORT = 3003`，`:132` 是 `mainWindow.loadURL("http://localhost:3003")`。所以直接用浏览器访问 3003 即可，**不需要 CDP 控制 Electron**——渲染出的 DOM 完全一致，而走 CDP 反而要处理应用内导航（不能直接 goto 路由）。

**启动**：打开桌面应用即可，它会自己拉起前后端。若 3003 无监听说明服务没起来（界面可能还在但那是内存里的残留页面），重启应用即可。

**不要在仓库内落脚本或产物**：clowder-ai 是 cat-cafe 的下游同步镜像，git log 里有大量 `sync: cat-cafe <sha> → clowder-ai` 自动提交，在其中改动会与上游同步冲突。

**实时推送不是问题**：仓库里 55 个文件用 socket.io、34 个用 `setInterval`，原以为会让 DOM 永不安定。实测 chat 主页抓取 10.7s，与静态页相当——持续推送改的多是文本内容，DOM 结构很快就稳。无需断开 socket。

**建议排除 `pixel-brawl`**：phaser 游戏，内容全部画在 canvas 里，DOM 复刻出来是一块空白画布。`starry` / `mission-control` 若也是 canvas 主导，同样处理。

### 3.4 两个项目共同的坑（已固化进 skill，此处仅备查）

| 现象 | 根因 | 处理 |
|---|---|---|
| 整页报结构不同 | `<next-route-announcer>` 宽 0 不可见，但插入位置在两次加载间会变，导致其后所有兄弟节点索引偏移 | 加进 `removeSelectors` |
| 某个 input 颜色每次都不同 | 采样到 `transition-colors` 过渡中间值 | 提取与验证两端都注入冻结样式 |
| spinner 每次角度不同 | `animation-play-state: paused` 停在当前帧 | 改用 `animation: none` |
| 节点数在两次运行间跳动 | 挂载后才 fetch 的内容（如 star 数）赶不上静默窗口，二次运行走缓存就赶上了 | 预热重载，让每次抓取都是热加载 |
| 某控件多一圈焦点环 | 页面 `autofocus` | 提取前 blur + 静态化剥离 `autofocus` + 验证端同样 blur |
| 上百个宽度差异 | 字体没本地化，`@font-face` 指向源站，停机后 404 回退系统字体 | 下载字体到本地并改写 CSS 引用 |

**通用原则：提取端做的任何稳定化，验证端必须原样做一遍。** 实测两次栽在这条上（冻结动画、blur 都曾只做了一端），表现都是「某个 input 的颜色对不上」。

**唯一验收发现不了的错误**：公开页（落地页/登录页/营销页）在有 session 时会重定向进应用，抓到的是错页面，而 DOM diff 和样式 diff 都会报 ok —— 因为真值和复刻抓的是同一个错页面。必须人工给这些页面标 `anonymous: true`。实测 multica 的 `/` 曾抓成 419 节点的工作区页，而非 985 节点的落地页。

### 3.5 交互契约表：参考还原的主产出格式

冻结页给出的是**静态结构真值**（DOM + computed style）。本轮的目的是交互分析，因此
M2-T02/M2-T03 的主产出**必须是表，不是散文**——散文式旅程描述读起来顺，但下游用不上。

每个页面一张表，逐个可交互元素填：

| 元素 | 位置 | 前置状态 | 用户操作 | 后置状态 | 反馈形式 | 证据 |
|---|---|---|---|---|---|---|
| 示例：Issue 状态下拉 | 详情页头部右侧 | status=open | 点击→选 In Progress | status=in_progress，列表分组移动 | 即时乐观更新 + 分组动画 | `路径:行号` 或冻结页锚点 |

字段口径：

- **前置/后置状态**：写用户可观察的状态，不写内部字段名；确需引用实现字段时放进「证据」列。
- **反馈形式**：区分即时/乐观更新、loading 态、toast、跳转、无反馈。**「无反馈」必须显式记录**，
  它往往正是值得借鉴或值得避免的地方。
- **证据**：源码 `路径:行号` 或冻结页中的选择器/锚点，二选一，不得留空。

散文只保留一段「这个页面在整条旅程中承担什么」，控制在 5 行内。旅程叙述放在页面表之前，
用于串联页面顺序，不重复表里的内容。

### 3.6 归档的交互能力与已知边界（2026-08-14）

静态页现在能点。三件事让它动起来，都不是手写的：

**跳转**。站内链接改写成同级 HTML；带 id 的路由按**实体类型**而非实体身份解析
（`/test/projects/<任意 uuid>` → `project-detail.html`），因为归档里每类实体只有一个详情页。
列表行没有 `<a>`（靠 `onClick` 调 `router.push`），只能在配置里声明去向：projects / agents /
skills 三张表的行各一条规则。`verify-nav.mjs` 会点掉每条规则做回归。

**浮层**。这是最关键的一条认知：**关掉的菜单在冻结页里根本不存在**。Base UI 开时挂载、
关时卸载，抓下来的永远是关闭态。实测 issues 页 46 个按钮里 20 个是浮层触发器，HTML 里这
20 个浮层的内容一个字都没有 —— 所以「点了没反应」不是脚本没写，是内容压根没抓。

做法是去真实应用里逐个点开，把浏览器实际插入 `<body>` 的节点原样录下来，静态页点击时放回去。
全站 19 个应用页共录到 221 个状态（菜单 / 弹层 / tooltip / hover card / tab 面板），
`verify-interactions.mjs` 逐个回放，221/221 通过。

**已知缺口 27 个**，记在 `ui-reference/multica/states/_gaps.json`：

| 页面 | 数量 | 原因 |
|---|---|---|
| issue-detail | 22 | 评论编辑器折叠时工具栏是 23px 隐藏残根，滚不进视口也 hover 不到 |
| project-detail | 2 | 同上 + 一个隐藏的移动端筛选副本 |
| issues / my-issues / agents | 各 1 | 隐藏的移动端筛选副本，桌面视口下本就不可见 |

前者要补需要在页面配置里声明 `preSteps`（捕获前先点开编辑器）；后者是桌面视口下的真实不可见元素，
不补是对的。**缺口写进文件而不是留在脑子里** —— 没记录的缺口会被下一个读归档的人当成 bug
重新发现一遍。

**clowder-ai 的交互尚未采集**，需要它的前端在 3003 上跑起来（打开桌面应用即可），
然后两条命令：`capture-states.mjs clowder` + `staticize.mjs clowder`。它的 5 个 memory 子页
（search / status / health / catalog / graph）也一并待抓，那是当前 5 条死链的去向。

## 4. M3 方法：PersonaHub 用户旅程梳理

**预计时间：1–2 个工作日，与自测试体系（`ST-T*`）同时开始。**

### 4.1 产品意图重建

不做现状还原，直接从设计文档重新推导（见"清白起点原则"）：

- 读 `docs/personahub-prd.md`，抽出产品承诺的用户目标、核心概念和成功定义。
- 读 `docs/personahub-architecture.md` / `-system-design.md` / `docs/decisions/`，
  只提取**真实的技术约束**（本地优先、CLI adapter 进程模型、SQLite 单机、
  workspace 排他锁等），用来判断旅程是否可实现，不用来推导页面结构。
- 列出 PRD 层面的概念清单（Project / Issue / Thread / Agent / Workflow / Evidence…），
  标注每个概念是"用户必须理解的"还是"实现细节，不应出现在界面上"。

**产出**：产品意图摘要、技术约束清单、概念清单及其暴露级别。

### 4.2 核心用户与核心任务确认

第一阶段只围绕一个核心用户：希望把真实 coding 工作交给多个本地 AI CLI，同时保留
控制权和验证证据的个人开发者。

优先验证三个 P0 任务：

1. 首次打开应用后完成最小配置并进入可执行状态。
2. 输入开发目标、确认系统建议并运行到可信的 Done。
3. 任务失败、中断或等待人工判断后，理解原因并安全恢复。

**产出**：用户定义、Jobs-to-be-Done、P0/P1 范围边界。

### 4.3 目标旅程设计

每条旅程必须包含：

- 触发条件、用户目标与成功终点。
- 用户动作、系统反馈和此刻最关心的问题。
- 主路径、空状态、错误路径、恢复路径和不可逆操作。
- 每一步涉及的产品概念，以及哪些概念应隐藏或渐进展示。
- 可观察、可计时的验收标准。

**产出**：目标旅程表、状态矩阵、术语与信息披露规则。

**旅程写什么、不写什么（2026-08-13 明确）**：

> 旅程负责**该发生什么**，页面拼装负责**长什么样**。
> 旅程是**行为**的唯一输入；**形态**的输入是参考项目的冻结页（第 3.1 节）。
> 两者不冲突——一个管该发生什么，一个管长什么样。

因此旅程**不写**页面布局、区域划分和视觉方案；但上面五条一条都不能少，尤其
「此刻最关心的问题」和「概念暴露级别」——它们是拼装阶段判断某个区块**要还是不要**的
唯一依据（规则见 5.1 节）。旅程写得越细，拼装的取舍越准；旅程写得空，拼出来的就只能
是参考项目换皮。

### 4.4 建议验收指标

- 首次用户无外部文档辅助，在 5 分钟内进入“可以创建任务”状态。
- 创建任务只有一个主入口，从输入目标到启动不超过 3 次主要操作。
- 运行页面优先回答“进行到哪一步、是否需要我、下一步是什么”。
- 阻塞状态必须同时展示原因、影响和一个推荐主操作。
- 用户无需阅读内部 error code 或原始日志完成常见恢复。

### 4.5 旅程定稿门禁

- 第 1 轮：全量检查目标、范围、步骤、异常和恢复是否完整。
- 修改后第 2 轮：只复核 diff 及相邻步骤。
- Critical/High 体验问题清零，并由用户明确批准。

**退出条件**：用户旅程成为后续原型的唯一**行为**输入；未通过的争议点不得交给原型阶段猜测。

**这条不因引入页面拼装而放松。** 原计划真正错的假设不是这一条，而是它隐含的另一条——
*旅程文档足以让人预见最终产品的样子*。那才是 v0.2 偏差的根源。拼装解决的是形态可预见性，
不改变旅程对行为的权威性。

## 5. M4 方法：PersonaHub 页面拼装

**预计时间：2–4 个工作日，在 M3-T04 旅程草稿交稿后开始。**

> **方法变更（2026-08-13）**：本节由「从旅程原创设计单文件 HTML 原型」改为
> **「基于参考项目冻结页拼装 PersonaHub 目标形态」**。
>
> 变更原因：v0.2 的偏差根源是产品形态从未被具象化过——需求和设计文档写得再细，做出来
> 仍与预想不符。再写一份更细的文档不会改变这个结果。而第 3.1 节的渲染冻结已经产出 27 页
> 真实产品的完整 DOM + 编译后 CSS，这意味着目标形态**可以拼，不必画**，同时天然绕开了
> 3.1 节记录的「agent 脑内渲染」失败模式：不是让 agent 画，是让 agent 剪贴真值。
>
> 一句话：**第一步站在巨人的肩上，再考虑未来的创新。**

### 5.1 拼装的判断优先级链

四层，**上层否决下层**。这是本节所有取舍的总规则：

```text
1. 用户旅程         → 该发生什么、此刻用户关心什么      （唯一标准，§4）
2. PRD 信息架构     → 这件事该由哪一栏、哪个区域承载    （PRD §6，已定死）
3. PRD 竞争力       → 哪些东西必须显眼、不能被挤走      （PRD §2 三个词）
4. 参考项目冻结页   → 这个区域具体长什么样              （形态素材）
```

**参考项目只在第 4 层发言。** 它回答"长什么样"，不回答"要不要有""放在哪里""重不重要"。

由此得到一条可机械执行的剪贴规则：

> **每剪一个区块，必须能指回旅程的某一步和某个信息需求。指不回去的，就是参考项目的
> 功能，不是 PersonaHub 的，删掉。**

这条规则同时是**旅程的压力测试**：若某个旅程步骤找不到任何参考区块能承载，只有两种
可能——要么旅程写得太抽象（回 §4 改），要么这就是空白区（记入 5.5 节清单，原创设计）。
两种都是有价值的发现，都不允许"先随便拼一个上去"。

### 5.2 PRD 已定死的信息架构，直接采用不重新设计

PRD §6 已经给出第一版三栏工作台，本轮**不重新设计信息架构**，只把旅程步骤定位进去：

```text
左侧 工程导航      Projects / Issues / Automations / Agents / Skills / Settings
中间 当前协作现场  Primary Thread / Room switcher、Messages、Agent responses、
                   Room members、Handoff / Run / Validation events、Decisions
右侧 Context Inspector  Issue info、Agent status、Evidence、Run logs、Trace、Blockers
```

另外两条 PRD 硬约束，拼装时不得违反：

- PRD §6：打开应用**直接进工作台，不做 landing page**；第一版 **Issue list 是 P0，
  Board View 是 P2**，不要因为 multica 有 board 就拼一个进来。
- PRD §13「UI 过重」：**中间只承载当前协作现场**（primary Thread 或 active Room），
  **右侧 Inspector 分 tab**。不允许 Board / Hub / Logs / 多协作室同时抢中心。

### 5.3 竞争力约束：拼装不得踩进 PRD 已预警的坑

PRD §2 的一句话定位给出三个竞争力词：

> A personal Agent Team OS for **issue-managed, graph-orchestrated, evidence-grounded** work.

PRD §13「同质化」风险行把失败形态写得很明确——**"看起来像普通聊天壳或普通 issue
runner"**。也就是说，照搬 multica 的 issue 骨架加 clowder 的聊天骨架，拼出来的正好就是
PRD 明文预警的失败形态。竞争力约束不是加分项，是防止拼装直接踩进已知的坑。

| 竞争力 | 拼装约束 | 参考项目有对应物吗 |
|---|---|---|
| **issue-managed** | 任何 Thread / 对话区块剪进来必须带 Issue 上下文锚点。clowder 的 chat 是无绑定自由聊天，照搬即踩 PRD §13「聊天壳化」风险 | 部分（multica 的 issue，但语义不同，见 5.4 概念映射） |
| **graph-orchestrated** | 中间区域必须能表达多节点 / 多成员的协作结构，不能剪成单线聊天流 | **没有** |
| **evidence-grounded** | 右侧 Inspector 的 Evidence / Run logs / Trace tab 是 PRD §6 明文要求，不得因参考项目没有就省略 | **没有** |

**三个竞争力词里有两个在参考项目中找不到对应物。** 这意味着 5.5 节的空白区清单不是
边角料，**它就是 PersonaHub 的核心竞争力所在**。分工因此清晰：

- 参考项目提供**通用工作台的基础体验**——导航、列表、详情、设置、表单、状态标签。
  这些是成熟产品打磨过的，照搬省时间，这就是"站在巨人肩上"的实际内容。
- 参考项目提供不了**差异化那部分**——graph 协作现场、evidence 验证链。这些必须原创，
  而且值得把前面省下来的时间全部投在这里。

### 5.4 执行步骤

| 步骤 | 内容 | 依赖 |
|---|---|---|
| S1 概念映射 | multica / clowder 概念 ↔ PersonaHub 概念，逐个标注「一一对应 / 近似需调整 / 无对应」 | 无，可与 §4 并行 |
| S2 页面选型 | 按旅程每一步的信息需求，列出所需页面并指定骨架来源与嫁接内容 | M3-T04 旅程草稿 |
| S3 拼装草案 | 基于冻结产物剪贴，文案换成 PersonaHub 概念 | S1 + S2 |
| S4 用户审阅 | 逐页说「对 / 不对 / 缺」 | S3 |
| S5 空白区清单 | 参考项目里没有对应物的场景 | S4 |

**S1 概念映射必须在拼装之前。** multica 的 Issue 是团队协作单元，PersonaHub 的 Issue 是
agent 执行单元，不是一回事。不先映射就拼，会拼出一个"看着像、用起来不对"的东西——
那是最贵的偏差。

**S2 页面选型表的形态**（它同时取代原 M2-T07 的借鉴决策表，决策粒度从"整页三选一"降到
"这个页面的骨架取自谁、嫁接什么"）：

| PersonaHub 页面 | 对应旅程步骤 | 骨架取自 | 嫁接什么 | 删掉什么 |
|---|---|---|---|---|
| 示例：Issue 执行现场 | 旅程 2 第 3–6 步 | multica issue-detail | clowder 的 agent 身份区 | 团队协作相关区块（无对应旅程步骤） |

**S3 的视觉统一规则**：两个项目的 token 体系打架（multica 216 变量 vs clowder 667 变量的
四旋钮 OKLCH），混贴会花花绿绿。因此——**结构可以来自任何一方，视觉统一走 multica；
嫁接 clowder 区块时只搬 DOM 结构与交互，不搬它的 CSS 变量。** 这是 B0 调研结论
（视觉基调取 multica、协作逻辑取 clowder-ai）的可执行版本。

### 5.5 空白区清单：唯一需要原创设计的地方

拼装完成后，把所有"旅程有要求、但两个参考项目都没有对应物"的场景登记成清单。

**M4-T01 概念映射已大幅收窄这份清单（2026-08-13）**：原预判的 Artifact / Provenance Gate /
Handoff Packet 三项，深挖 clowder-ai 源码后发现**都有对应实现，只是不叫这个名字**——
Evidence 体系（11 kind × 10 status）、审批中心 + Marker 生命周期、ball-custody 球权托管。
详见 `concept-mapping.md` §4。

因此当前预判的真空白区只剩（以实际拼装结果为准）：

1. **Room** —— 唯一无对应的核心概念，竞争力 `graph-orchestrated` 的落点。
2. **Issue 上下文快照** —— goal / 状态 / 工作方式 / 验证要求，clowder 无 Issue 概念。
3. **Blockers** —— PRD §6 明列，两个参考项目右栏都没有。
4. **validation 轮次与 findings 对比** —— 两个参考项目的验收都是人工 gate 或互审，
   没有自动 loop 的过程表达。
5. workspace 排他锁冲突与排队的表达。

**已从空白区划掉（2026-08-14）**：介入动作（`@` 指派 / 打断 / 纠偏 / 交接确认）——
clowder 的 `@` 行首路由与 DispatchProposal 卡片是现成实现，且 PRD §10 明确它们属于
中间协作现场，不是右栏。详见 `concept-mapping.md` §5.2/§5.3。

**这份清单同时是 v0.3 重估的直接输入**：上述场景与 F009（Artifact / 证据）、F011（Room /
人工介入）高度重合，第 7 节表格里"重新进入计划的条件"到这一步才有具体依据。

### 5.6 拼装草案的定位与后续形态

**拼装草案不是可交付原型。** 它含参考项目的文案、数据和图标，作用是让用户确认目标形态，
说出"对，就是这个"或"不对，这块不要"。它不进入 `web/`，不作为实现代码。

定稿后仍需用 PersonaHub 自己的技术栈重做一遍——但那时目标形态已经精确，重做不会偏。
重做形态在 S4 用户审阅通过后单独决策，本节不预设。

### 5.7 拼装草案检视清单

第 1 轮全量检视：

- 三条 P0 旅程是否可连续走通（不是每页单独看着都对）。
- 每个区块能否指回旅程步骤（5.1 剪贴规则的逐条核对）。
- 5.2 的两条 PRD 硬约束是否被违反。
- 5.3 三个竞争力词是否都有承载位置，且没有被参考项目的区块挤到边缘。
- 空状态、错误状态和恢复路径是否都有对应画面，不只有主路径。
- 1440×900 单档窗口；键盘焦点、对比度和文本溢出等基础可访问性。

修改后第 2 轮只复核修订区域与相邻交互；仅在第 2 轮引入新问题时追加一次第 3 轮，封顶。

### 5.8 用户定稿

用户按场景清单亲自操作拼装草案。反馈统一归为：

- 必须修改：阻塞旅程或明显违背预期。
- 后移：不影响 P0 旅程，可进入后续 Feature。
- 不采纳：记录理由，避免下一轮反复提出。

**退出条件**：用户明确说"目标形态定稿"；单纯没有新反馈不等于批准。

## 7. 当前 v0.3 开发计划修改评估

### 总体判断

F009–F012 都处于 `draft`，当前暂停不会造成已实现代码或 migration 的返工，成本主要是
重新审视产品优先级和 Feature 边界。原计划技术依赖顺序基本自洽，但它从 Artifact、
Room、Squad 等领域能力出发，没有先证明当前核心工作台是否好用。因此建议保留技术研究，
废止现有时间线和“评审通过即可开发”的假设。

| 项目 | 当前判断 | 建议处理 | 原因 | 重新进入计划的条件 |
|---|---|---|---|---|
| F009 Artifact Foundation | 技术基础有价值，但不是当前体验阻塞的直接解法 | 保留 draft，重新评估 UI 范围 | 可能增加 Inspector 复杂度 | 原型明确 Artifact 在旅程中的用户价值与入口 |
| F010 Artifact Coding Slice | 依赖 F009，且会深度改变执行与结果呈现 | 暂停并重写旅程映射 | 当前核心执行旅程尚未稳定 | 新工作台整改完成，Artifact 消费路径通过原型验证 |
| F011 Work Room | 与“观察、打断、纠偏”高度相关，产品价值可能保留 | 保留概念，重做交互与范围 | 现有三栏 Thread 体验未验证，直接加 Room 风险最高 | 原型先证明单 Issue 的观察与介入模型 |
| F012 Squad | 便利性能力，不解决当前阻塞主流程 | 明确后移 | 依赖 F011，且会增加设置复杂度 | Room 被真实使用并出现重复成员配置需求 |
| v0.3 25–40 日时间线 | 建立在现有 Feature 顺序和范围不变的假设上 | 作废，定稿后重估 | 旅程和整体整改会改变范围 | 整改影响面、迁移方案和测试矩阵完成 |

### 建议替换后的阶段顺序

自测试体系（独立文档 `ST-*`）与 M3 用户旅程**同时开始**（2026-08-13 调整），不等 M3 批准；
M4 页面拼装以 M3-T04 旅程草稿交稿为启动点，启动后与 M5 并行。M5 影响面分析需要旅程定稿，
其余流程设计不依赖 M3。
M1–M5 合计预留 **2 周（10 个工作日）**硬性时间盒；到期若仍未定稿，重新评估范围而非无限顺延。
M6 是目标形态定稿后才启动的独立实施阶段，不计入这两周窗口。

| 阶段 | 内容 | 退出条件 | 粗估 |

## 8. 整体整改阶段的规划原则

目标形态定稿后先做影响面分析，不立即全仓重写。**这里是现有实现第一次被允许作为输入的地方**
（见"清白起点原则"）：把定稿旅程与现有实现逐条对照，产出「可复用 / 需改造 / 需废弃」三类
结论，并把 `dogfooding-bugs.md` / `dogfooding-notes.md` 的开放项映射到对应旅程步骤，确认
新设计确实解掉了它们，而不是换个位置重现。

整改任务按用户旅程垂直切片，而不是按"先全部后端、再全部前端"分层：

1. 首次设置切片：Project、Workspace、Agent、诊断与相应测试。
2. 创建任务切片：统一入口、推荐确认、启动反馈与幂等测试。
3. 运行观察切片：进度、关键事件、日志层级和人工补充。
4. 阻塞恢复切片：原因、影响、推荐动作、恢复状态机和回归测试。
5. 完成结果切片：结果摘要、文件变化、验证证据和可信 Done。

每个切片独立实现、独立验证、独立复核；上一个切片未通过真实浏览器旅程前，不进入
下一个切片。

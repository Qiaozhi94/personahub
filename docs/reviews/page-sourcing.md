## 1. 素材源登记（三个，不是两个）`[2026-08-15]`

reset-plan §3 只登记了 multica 与 clowder-ai。归档目录下实际有第三个项目 `dsh`
（DeepSeek Harness，本地 agent harness），本轮纳入素材源。

| 源 | 页数 | 定位 | 在本轮的角色 |
|---|---:|---|---|
| multica | 26 | 团队协作型 issue 工具 | **视觉基准 + 工程化骨架**：左栏导航、Issue 列表/详情、Agents、Skills、Settings、运行时 |
| clowder-ai | 27 | agent 团队平台 | **协作内核**：`@` 行首路由、审批/派发卡片、右栏 chip/row 分层、memory |
| **dsh** | 5 | **本地单机 agent harness** | **执行现场骨架**：`sidebarCol / centerCol / detailsCol` 三列 frame、中栏「对话 / 轨迹」双视图、composer 上方的运行统计条、右栏「点某一行才出详情」的空态 |

**为什么 dsh 值得单列**：它是三者里唯一与 PersonaHub 同形态的产品——本地、单用户、
跑 agent、有轨迹视图。multica 的执行可观测性挂在团队 issue 上，clowder 的挂在对话上，
只有 dsh 把「一次运行的耗时/轮次/工具调用」直接做成了现场的一等公民，这正是旅程
§6.4「执行中」行要的东西。

**视觉统一规则不变**（reset-plan §5.4）：**结构可来自任何一方，视觉统一走 multica**；
嫁接 clowder / dsh 区块时只搬 DOM 结构与交互，不搬它们的 CSS 变量体系。

## 3. M4-T02 裁决：右栏分 tab `[2026-08-15]`

旅程 JRN2-005 把这个决定留给 M4-T02。**结论：分 tab，3 个，外加 1 个常驻置顶区。**

**依据是区块数量**，不是偏好。按旅程 §6.4 逐状态汇总，右栏要承载的快照共 9 类：
Issue info（goal/状态/工作方式/验证要求）、当前阶段与下一步执行者、执行者状态与耗时、
队列位置与占锁任务、验证要求清单、轮次计数、Evidence 索引、文件变化摘要、Blockers 摘要。
按 clowder 实测的区块高度（`RightStatusPanel` 526 行 / 304px 宽），9 类堆叠在 1440×900
下必然要滚 2–3 屏，直接踩 PRD §13「UI 过重」。

| 区域 | 内容 | 为什么在这 |
|---|---|---|
| **置顶常驻**（不在 tab 内） | Blockers / 「需要你处理」摘要 | 旅程 §9 指标 4 要求进入后无需滚动即可看到；放进 tab 会被藏起来 |
| tab 1 **信息** | 见下方 §3.1 详表 | J3 全程默认停留在这个 tab |
| tab 2 **产物** | 见 §3.1 | J4 的主 tab；也是「审这份文档」的入口 |
| tab 3 **诊断** | 见 §3.1 | 旅程 §3.3 的第三层披露，默认不占视线 |

**默认 tab 随状态走，但 tab 集合不变**：Done 与文件视图默认落在「产物」，其余默认「信息」。
这不违反旅程 §6.4 推论 3——推论 3 约束的是「不做形态判断」，本节正是被授权做这个判断的地方。

### 3.1 三个 tab 的分工 `[2026-08-15 重排]`

一条硬规则先立住：**右栏是 Issue 级快照，中栏切换视图（会话/文件）时它不变。**
右栏出现"随中栏变化"的内容，说明那块内容其实是事件，放错地方了。

| tab | 回答什么 | 内容 |
|---|---|---|
| **信息** | 现在怎么样 | `[2026-08-15 三次收窄，用户定]` **只有两块**：① **Agent 详情**——clowder 的「猫猫状态」与「历史参与」合二为一，同一列表，当前在做的排最前且色点 pulse，做过的按时间排后、不折叠，每条带担任什么 / 状态 / 尝试次数 / 耗时 / token 消耗；② **消息统计**（总消息数 / 成员消息 / 你的消息 / 系统事件） |
| **产物** | 凭什么算完成 + 产出了什么 | **完成要求逐条 + 当前满足**（判据）→ 完成摘要 → **验证结论 + 来源 + 独立性标识** → 变更摘要 → **项目目录树**（带变化标记，点文件在中栏看全文） |
| **诊断** | 排查用 | 运行日志入口、**审计事件**（何时对哪个版本做了什么）、内部 ID（可复制） |

**完成要求已落到产物 tab 顶部 `[2026-08-15 已解决]`**。信息 tab 收窄后，旅程 §6.4 要求的
「完成要求逐条 + 当前满足」改放**产物 tab 最上面**，与验证结论相邻。这样读起来是一条线：
**要满足什么 → 满足了没 → 凭什么这么说**。它是 `evidence-grounded` 的落点，不能丢。

**⚠️ 仍待定：Issue Type / Workflow Template（工作方式）`[2026-08-15]`**。
PRD §10 把它列为右栏必须项，收窄后无处安放。它在 P0 的实际价值存疑——旅程 §3.1 已把
Workflow Template 降级为「建议与判据」，而判据部分已由完成要求承载。**定稿前需明确：
要么并入产物 tab 的完成要求标题（如「改代码任务 · 实现 → 独立验证」），要么从 PRD §10
移出必须项。** 不允许无声消失。

**2026-08-15 二次修订补回 PRD 明列项**：早前版本漏了 PRD §10 的
「Issue Type / Workflow Template」与「Owner agent / workflow agents / validator agent」——
现以「工作方式」与「本任务成员（含担任什么）」两块补回。漏的原因是重排时只盯着
clowder 的结构，没有回头对 PRD 的必须项清单逐条核。

**这次重排修掉的是「右栏与会话重复」**：早前把「验证结论」放在信息 tab，而 validator 在
会话里已经说过一遍——那是叙事，不是快照。按 `concept-mapping.md` §5.1「事件进中间、
快照进右栏」，结论作为**产出**归产物 tab，信息 tab 只留聚合状态。

三块**原创**（三个参考项目都没有）：

- **完成要求逐条 + 当前满足** —— `evidence-grounded` 的核心。会话里没有任何一处能一眼
  看到全部判据的当前状态；这也是「系统按什么标准判我完成」的唯一答案位。
- **历史参与** —— 跨多步会有多个成员，「谁做过哪步、用时、结果」只能靠聚合。
  形态借 clowder 的「历史参与者（可折叠）」，语义换成 Run/Attempt 链。
- **队列与锁** —— 排队与执行必须可区分。

**不显示轮次计数 `[2026-08-15]`**：轮次不是通用名词（两个参考项目都没有），且它的上限
是自动 loop 的保护装置——P0 完全手动指派下，用户自己就是保护装置。用户需要的是收敛信号，
所以改为在完成要求的未满足项上标「连续 N 次未满足」，在 findings 上标「连续 N 次未解决」。

**明确不放进来的**：消息统计（PRD §10 已移出必须项）；Session Chain **不单列**——
PersonaHub 的对应物是 Run/Attempt 链，已并入「历史参与」；token 用量与上下文健康度
（clowder 有，`concept-mapping.md` §5.5 判为值得借鉴但非 P0，**没有旅程步骤支撑，本轮不加**）。

**素材**：tab 条取 multica（`issue-detail` 右栏已有属性/PR 分区形态），tab 内的
chip / row 排布取 clowder（`RightStatusPanel` 的 soft chips，不堆独立白卡），
「点某一行才展开详情」的空态取 dsh（`detailsCol` 的「点击消息流中的工具行查看详情」）。

10 个页面覆盖四条旅程的主路径 + 空/错误/恢复状态。**每页都能指回旅程步骤**，
指不回去的一律不做（reset-plan §5.1 剪贴规则）。

| # | PersonaHub 页面 | 对应旅程步骤 | 骨架取自 | 嫁接什么 | 删掉什么 |
|---|---|---|---|---|---|
| P01 | 工作台·执行中（默认首屏） | J3.1、§6.1 | dsh `conversation` 的多列 frame | 左栏用 multica sidebar；**中栏是 clowder 式消息流，run events 折叠进 agent 消息**；右栏见 §3 | dsh 的模型/权限选择器（PersonaHub 在成员上定）、clowder 猫猫球 |
| P02 | 工作台·等待指派 | J3.2、§6.4「等待指派」 | P01 同构 | **交接卡片**取 clowder DispatchProposal 卡片形态，改为「产出 + 建议 + 成员按钮」 | 倒计时自动放行（P0 明确不做）、批准/拒绝二元按钮（要的是改指派） |
| P03 | 工作台·验证与不收敛 | J3.3–J3.6 | P01 同构 | findings 列表用 multica issue-detail 的动态 feed；轮次对比区**无对应物，原创** | — |
| P04 | 工作台·异常与恢复 | J3.7–J3.10 | P01 同构 | 状态卡用 clowder 审批卡片形态；三态（failed/interrupted/cancelled）各一份 | 把三态合并成「出错」的任何形态 |
| P05 | 工作台·Done | J4.1–J4.4 | P01 同构 | 右栏默认落「产物」tab；结论「来源」下钻到文件全文 | 复制/下载/导出入口（旅程 §7.4 判为 P1） |
| P06 | 工作台·空状态 | J1.6、J2.1、§6.1「中间（空）」 | multica `issues` 空态 | 唯一创建入口 | 第二个同级创建入口 |
| P07 | Issues 列表 | §6.4.1 | multica `issues` | 五列按 §6.4.1；排序按注意力优先级 | 指派人、优先级、里程碑、标签、分组看板、Board 切换 |
| P08 | 首次设置 | J1.1–J1.5 | multica `agents` + `runtimes` 表单骨架 | 3 项清单进度；目录选择用 dsh「工作区」选择器心智 | 组织/团队/计费相关字段 |
| P09 | 创建任务与推荐确认 | J2.1–J2.3 | multica `agent-new` 表单骨架 | 推荐卡片（理由 + 不可用候选原因）用 clowder 卡片形态 | 多步向导（旅程限 3 次主要操作） |
| P10 | AI 成员（列表 + 详情） | J1.4、J2.2 候选 | multica `agents` / `agent-detail` | 以**能力项**为主展示（concept-mapping §7） | role 作为身份的强表达、人类成员、计费 |
| P11 `[2026-08-15 改版]` | 工作台·文件 | **§6.6**、J3.2 指派前查看、J4.2 追溯 | 中栏视图切换（dsh 双视图）+ 右栏目录树 | 中栏整份文件全文（markdown 渲染）、变化着色；右栏「产物」tab 放项目目录树与变化标记 | 逐行并排 diff、编辑能力、跨出当前代码目录 |

**P01–P06 与 P11 是同一张工作台的多个状态，不是多个页面**——拼装时共用一套 frame，
只换中栏内容与右栏默认 tab。这一点必须在草案里明确，否则审阅时会误以为要做一堆界面。

**中栏不做视图切换 `[2026-08-15 再改版]`**：连「会话 / 文件」这组 tab 也去掉。
中栏默认就是会话；**文件视图由右栏「产物」的目录树点进来**，顶部给一个「← 返回会话」。
理由：视图 tab 与右栏目录树是两条通往同一处的路径，留两条只会让用户先判断该走哪条。

**标题下一行给结论摘要 `[2026-08-15]`**：变更文件数、测试结果、关键风险放在标题正下方
一行（如「第 1 步完成 · 2 个文件变更 · 24 个测试通过 · 未覆盖并发场景」）。
它回答「这一步到底产出了什么」，让用户不必读完整段消息。

**建议指派直接预填输入框 `[2026-08-15]`**：不再单独做建议卡片区。输入框里默认写好
`@建议成员 + 建议做的事`，理由放标题下那一行。确认即发送，要改直接改。

**消息气泡整块照 clowder `MessageBubble` `[2026-08-15]`**：
`头像 + [头部(名字 + 时间) → 圆角气泡 px-4 py-3 rounded-2xl（内容 + 工具调用折叠）
→ 页脚(模型 · provider · ↑输入 ↓输出 tokens · 耗时)]`。
**用户与 AI 成员用完全相同的结构**，不做「用户靠右、agent 靠左」的区分——
用户是最终决策者，不是旁观者；靠右气泡会把人从协作现场里择出去。

**输入框整块取自 multica 真值 `[2026-08-15]`**：`contenteditable` + 左下 `+` + 右下圆形
发送图标，`min-h-16 max-h-40 ... focus-within:border-brand` 一并照搬；**不加解释性小字**。
形态取真值这条在这里最见效——自己写一个"差不多的输入框"必然与全局视觉脱节。

**未选中任务时的中栏 `[2026-08-15]`**：不做空壳提示，而是**开始新工作的入口**——
一句说明 + 一个与主输入框同构的目标输入 + 「左边有 2 个任务在等你」的快捷跳转。
它同时承担 PRD §6「无 Issue 时进创建任务空状态引导」。

**轨迹视图 P0 砍掉 `[2026-08-15 用户决定]`**。判断标准是一句可复用的规则：

> **一个视图如果不能回答另一个视图回答不了的问题，就不该存在。**

线性时间线能答的（谁做的、耗时、轮次），会话与右栏都已经答了——它只是换了个排版。
轨迹真正的独有价值有三个场景，今天一个都没到：**图执行的拓扑表达**（会话流是一维的）、
**长任务回看**（几十步时会话要滚很久）、**多次尝试对比**（会话是单线叙事）。
因此它的正确定位是**执行结构视图**，不是时间线摘要——登记进 §6 空白区候选，
等 graph / Room 落地时按这个定位重做。

会话与文件两个视图的形态判断，源于用户 2026-08-15 的两条意见：

1. **中栏必须是会话式的**（与 clowder 一致），不是平铺的事件日志。工具调用与 run events
   **折叠进 agent 的那条消息里**，现场首先回答「谁说了什么」，其次才是「它执行了哪些步骤」。
   此前按 dsh 工具行平铺是拼装偏差——`concept-mapping.md` §5.3 本就写明「事件流借 clowder
   消息流 + 卡片块」。
2. **文件视图以全文为主、变化着色**，目录树移到右栏「产物」tab。这同时解掉了原先
   「四栏 + 中栏再分两栏导致正文只剩 380px」的困境：目录树在窄栏够用，正文独占中栏。
   右栏也不再需要为看内容而折叠。

## 4.1 第 4 栏的存在条件 `[2026-08-15 新增]`

**第 4 栏是 Issue 的 Context Inspector，只在有 Issue 上下文时存在**，不是一个恒在的栏。

| 页面 | 有第 4 栏吗 | 理由 |
|---|---|---|
| 工作台各状态（P01–P06、P11） | 有 | 有选中的 Issue，Inspector 显示它的快照 |
| 创建任务与推荐确认（P09） | 有 | 有「待创建的任务」上下文，右栏显示它将带的配置 |
| Issues 列表未选中任何任务（P07） | 无 | 没有 Issue 上下文，空壳区块不如不要 |
| AI 成员（P10）、首次设置（P08）、设置类页面 | **无** | 与 Issue 无关；PRD §6 右栏七项全部是 Issue 维度的 |

判断标准一句话：**右栏回答不了「这个 Issue 现在怎么样」的页面，就不该有右栏。**
这条同时防止右栏被当成通用侧栏塞进无关内容。

## 4.2 建议指派：预填输入区 `[2026-08-15 改版]`

等待指派时，系统把建议**直接预填进输入区**（`@独立验证员 验证上一步的实现，重点看并发场景`），
上方固定一条建议说明（上一步产出摘要 + 推荐理由 + 换人快捷项），整体不随消息流滚动。

**为什么不是按钮**：按钮只有「照做/不照做」两种结果，不同意时用户要自己从头组织指令。
预填让系统建议成为**可编辑草稿**——同意就发，不同意改一个词。它还把「指派」和
「补充要求」统一成同一个动作，用户不必先判断该点按钮还是该打字。

## 4.3 左栏顶部与项目信息的归属 `[2026-08-15]`

| 位置 | 放什么 | 不放什么 |
|---|---|---|
| 左栏顶部切换器 | **Space（工作区）名** | 项目名——一个 Space 下可能有多个项目，顶部显示项目名会让层级错位 |
| 左栏导航 | 入口条目 | **「新建任务」按钮**——与第 2 栏列表头的「+ 新建」重复，删左栏这个 |
| 项目页 | 项目名、绑定的代码目录、Git 分支、启用哪些成员 | — |

**项目信息不在左栏常驻**：它是项目页要管理的内容，不是每屏都要看的东西。左栏只回答
「我在哪个工作区、能去哪些地方」。

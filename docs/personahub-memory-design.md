# PersonaHub 记忆模块完整设计

> **本文拥有什么**：记忆模块的**完整拓扑**——一条记忆从产生到遗忘的全过程、每个环节的
> 权力边界、以及各部分分别属于哪个阶段。
>
> **本文不拥有什么**：产品判断归 `personahub-prd.md` 第 5 节；跨 Feature 决策归
> `decisions/`（尤其 ADR 0013 借鉴边界、ADR 0016 状态机与来源包）；字段与表的实现级定义归
> `personahub-system-design.md`；Feature 的交付状态归各 `features/<version>/Fxxx-*/spec.md`。
> 本文与它们冲突时，以上述拥有者为准。
>
> **成熟度声明**：本文是**完整设计**，不是已交付清单。每一节末尾标注阶段与当前状态。
> 阶段二、阶段三的内容是设计意图，**不构成排期承诺**——它们的启用判据写在第 13 节，
> 拿不到判据就不启动。

## 1. 三十秒结论

PersonaHub 的记忆**不是笔记本，也不是"把旧对话塞回 prompt"**。它是一条有权力边界的闭环：

```text
验收事件 ──▶ 候选 ──▶ 你裁决 ──▶ 入库（带来源包与三根轴）
                                    │
                    ┌───────────────┼───────────────┐
                    ▼               ▼               ▼
                 检索召回        上下文装配        关系与投影
                    │               │               │
                    └───────────────┼───────────────┘
                                    ▼
                        消费观测（展示 / 引用 / 采纳）
                                    │
                                    ▼
              证据失效 ──▶ 待复核 ──▶ 退役 ──▶ 授权遗忘（留墓碑）
                                    │
                                    ▼
                          健康度（唯一能看见写侧坏掉的地方）
```

与同类系统最大的结构差异有两条：

1. **写入触发器来自已收敛的验收事件，不来自对话。** 这是 PersonaHub 相对 clowder 的结构优势
   （ADR 0013 第 4 条）：clowder 写侧十二条路径九条红，三条红的共同根因是"触发器缺失"——
   记忆来自聊天，"这值得记吗"难以判断，只能靠自觉。本项目不需要解决这个问题。
   **这条同时是一条约束：不得从对话自动摘取。**
2. **读侧永远不先于写侧做完。** clowder 的教训是读侧机器完备地运转、写侧大面积失灵，
   而这个不对称被掩盖了一年。因此本设计把健康度排在检索增强之前（第 10 节）。

## 2. 边界：记忆不是什么

| 它不是 | 区别在哪 | 依据 |
|---|---|---|
| **不是 agent CLI 的原生 memory** | 后者不透明、不可审计、跨 Issue 与 Project 泄漏，默认关闭且关不掉要降级披露 | ADR 0011 |
| **不是 Thread** | Thread 是"所有说过的话"的完整记录，记忆是"经确认或高置信沉淀的长期知识"。被否决的候选不会丢——它在 Thread 与轨迹里有完整记录 | PRD 第 5 节 |
| **不是 Artifact** | Artifact 是某次执行的产物，固定到 revision；记忆是跨任务复用的判断。记忆**引用** Artifact 作为证据，不复制它 | PRD 第 5 节 / F009 |
| **不是 Skill** | Skill 是可复用的**做法**（怎么做），记忆是可复用的**判断**（是什么、为什么）。记忆可以升维成 Skill 候选，但那是 v0.6 的事（第 12 节） | PRD 第 5 节 / v0.6 |

一条实践判据：**如果一句话回答的是"这次怎么做"，它是 Skill 候选；回答"这件事是什么样的"，
才是记忆。**

## 3. 对象模型

四张表。形状由 ADR 0016 决定，字段的实现级定义归 `personahub-system-design.md`。

### 3.1 `memories`（真相源）

| 组 | 字段 | 说明 |
|---|---|---|
| 身份 | `id` | |
| 归属 | `scope_type` / `scope_id` | `project` \| `space`；团队协作时**加值不加列**（第 11 节） |
| 三维 | `type` / `stance` / `state` | 互相正交，见第 4 节 |
| 内容 | `content` | `forgotten` 时清空 |
| 来源包 | `origin_type` / `usage_policy` / `source_issue_id` / `source_thread_id` / `source_event_ids` / `evidence_refs` / `created_by` / `originating_input_trust_level` | 全部 `NOT NULL`，只能由写入函数填 |
| 三轴 | `stance` / `verified_at` / `reference_count` + `last_referenced_at` | 互不替代，见第 4.3 节 |
| 替代 | `superseded_by` | 置位时 `state` 必为 `retired` |
| 时间 | `created_at` / `updated_at` | |

### 3.2 `memory_revisions`（append-only）

`state` 与 `stance` 各占一条轴（`axis` 字段区分），记录 `from_value → to_value` + `actor` +
`reason` + `evidence_ref` + `created_at`。

**不合并两条轴**：合并会产生 6 × 3 的组合爆炸，且"它什么时候变成 verified 的"与"它什么时候
被退役的"是两个独立问题。

### 3.3 `memory_write_rejections`

被白名单或状态机拒绝的写入请求落这张表：尝试的 type、stance、迁移、来源、时间、原因。

这是"第五类病（失败无观测）"在自身上的应用——**我们自己的写入路径也不许 `catch{continue}`**。

### 3.4 `memory_edges`

三列主键 `(from_id, to_id, relation)`，无 id、无时间戳。**边是可重建的投影，不是真相源。**

## 4. 三个正交维度

### 4.1 `type`（是什么）× `stance`（谁背书）

白名单由 ADR 0013 第 1.2 条拥有，此处只复述结论：

| type | 允许的 stance | 为什么 |
|---|---|---|
| `project fact` | `verified` / `confirmed` | 未经核对的断言不是事实 |
| `decision` | `confirmed` | 决定需要决策者 |
| `lesson` | 三者皆可 | 教训本质上是归纳，可先作为候选存在 |
| `user preference` | `confirmed` | 偏好只能来自用户本人 |
| `workflow note` | `confirmed` | 组内约定只能由人确立 |

**`claimed` 只允许出现在本质上是主观判断的类型上。** 违规写入被拒绝并落 `memory_write_rejections`。

> **类型名不是自由文本标签，是被写入路径强制执行的断言。** 库里出现 `project fact` 时它一定
> 有证据；出现 `decision` 时它一定有决策者。

### 4.2 `state`（生命周期）

```text
                  ┌──reject──▶ rejected（终态）
   proposed ──────┤
                  └──accept──▶ active ◀──revalidate──┐
                                 │  ▲                │
                     evidence_broken │                │
                                 ▼  └──reactivate──┐ │
                              suspect ─────retire──┼─┼──▶ retired ──forget──▶ forgotten（终态）
                                 │                 │ │        ▲
   active ───────────retire──────┼─────────────────┘ │        │
                                 └───────────────────┴────────┘
```

| 状态 | 含义 | 可召回 | 可进上下文 |
|---|---|---|---|
| `proposed` | 候选，等你裁决 | 否 | 否 |
| `rejected` | 你否决过。**保留记录**，用于抑制重复提议 | 否 | 否 |
| `active` | 在库 | 是 | 按第 7 节规则 |
| `suspect` | 支撑证据失效，等复核 | 否 | 否 |
| `retired` | 仍真但已翻篇，**可逆** | 否 | 否 |
| `forgotten` | payload 已清空，只留墓碑。终态 | 否 | 否 |

四条硬规则（ADR 0016 第 1 条）：所有迁移经同一个函数；`forgotten` 只能从 `retired` 进入；
`supersede` 不是状态而是 `retire` + `superseded_by`；`proposed` 不得永久悬挂。

### 4.3 三根轴互不替代

| 轴 | 字段 | 回答 | **不回答** |
|---|---|---|---|
| 背书 | `stance` | 谁为它背书 | 它被用过几次 |
| 验证 | `verified_at` | 何时发生过显式验证事件 | 它现在是否相关 |
| 使用 | `reference_count` / `last_referenced_at` | 被引用过几次、最近何时 | 它是否为真 |

> **硬规则**：`reference_count` 不得写入 `verified_at`，也不得提升 `stance`。
> 「常被引用」不等于「是真的」——流行度污染真相是搜索引擎的老年病，出生起就要打疫苗。

**不合成"可信度"分数。** 这条同时是界面约束（第 14 节）。

## 5. 写入侧

### 5.1 触发器：只有验收事件

| 触发事件 | 生成的候选 |
|---|---|
| 主张被独立验证通过 | `project fact` / `decision`（`verified`） |
| 两轮独立验证得出同一根因 | `lesson`（`verified`） |
| 用户批准了基线变更 | `decision`（`confirmed`） |
| 用户拒绝了基线变更 | `lesson`（`claimed`，连同理由） |
| 用户在验收面显式标记"这条要记住" | 按内容判 type，`confirmed` |

**不得从对话自动摘取**（ADR 0013 第 4 条）。从对话摘取会重演 stance collapse：
"提到过 ≠ 认可、改写过 ≠ 信仰、为了批判引用过 ≠ 我们的观点"。

### 5.2 候选与裁决

候选以 `state='proposed'` 落库，去重键 = `(scope, type, 内容指纹, 来源事件)`。

裁决三选一：**接受**（转 `active`）/ **改写后接受**（新建一条，原候选转 `rejected` 并记录
指向）/ **否决**（转 `rejected`，保留记录以抑制重复提议）。

超过阈值未裁决的候选进健康度的「未裁决积压」，**不静默沉底**。

### 5.3 自动保存的前置条件

PRD 第 7.7 节已定：低风险 lesson 的自动保存**不在 P0 / P1 开放**，因为其安全前提
Provenance Gate 要到 v0.5 才落地。本设计不推翻它，只补一句：

> 自动保存开启后，`stance` **不得直接给到 `confirmed`**——自动保存只能产出 `claimed` 或
> `verified`，`confirmed` 永远需要人。否则"用户确认"这个语义会被机器伪造。

### 5.4 写入路径自检：五类病

| 病 | 自查问题 | 执行强度 |
|---|---|---|
| 一、触发器缺失 | 写入侧有没有门？靠不靠自觉？ | 人工检查表 |
| 二、拓扑分裂 | truth / runtime / index 是不是同一份？ | 人工 + 架构评审 |
| 三、索引盲区 | 有没有整片区域在检索视界之外？ | 人工 |
| 四、易失写入 | 批准的产物会不会被普通 rebuild 删掉？ | 人工 |
| 五、失败无观测 | 有没有 `catch{continue}`、fail-open、只 log 不计数？ | **`npm run verify` 的一条 lint** |

## 6. 读取侧：检索

### 6.1 三阶段

| 阶段 | 内容 | 启用判据 |
|---|---|---|
| **一** | SQLite FTS5（`trigram` tokenizer）+ 治理列排序 + 单路也走 RRF 形状 | 立即 |
| **二** | 实体 / 别名解析：Issue 编号、Artifact 路径、成员名、ADR 编号的同一性 | 记忆量达到可观察规模 |
| **三** | 向量召回作为**第二路 provider**，两路 RRF 融合 | 见第 6.4 节判据 |

三阶段共用同一个召回 seam，按 ADR 0008：**消费方不写 provider 分支**。融合层第一版即写成
RRF 形状（`score = Σ 1/(k + rank_i)`，`k = 60`），即使只有一路——RRF 不需要对齐各路的分数
量纲，接第二路时消费方零改动。

### 6.2 排序：治理信号排在相关性之前

```sql
ORDER BY (superseded_by IS NOT NULL),
         (state IN ('retired', 'suspect')),
         authority_rank,        -- 由 type × stance 派生，不是独立字段
         bm25(...)
```

**时态与背书排在匹配度之前**，直接对应 ADR 0010「证据覆盖不等于验证通过」。

`authority_rank` 由 `type × stance` 派生：`confirmed` 的 `decision` / `user preference` /
`workflow note` 最高，`verified` 次之，`claimed` 最低。**它不因引用次数变化**（第 4.3 节）。

### 6.3 zero-hit 必须留痕

**从第一天记录搜不到的查询**：query、scope、时间、当时的库存量。

理由：clowder 的写侧尸检里 A8「zero-hit query 记录」是**零设施**——搜不到的东西不留痕，
于是"库里缺什么"这个问题永远答不出来。这也是第 6.4 节判据的唯一数据来源。

### 6.4 阶段三的启用判据（不满足就不做）

> 同时满足三条才启动向量检索：
>
> 1. `memories` 中 `state='active'` 的条数 **≥ 200**；
> 2. zero-hit 日志中能指认 **≥ 10 个**「这条明明在库里、用关键词搜不出来」的具体案例；
> 3. 这些案例中 **过半**无法通过阶段二（实体 / 别名解析）解决。

不满足而先上向量，就是重演 clowder 的路径——**先把读侧做到奢侈，再发现写侧和效用都没闭**
（它投入一年后 `follow/use` 仍为 0）。

同时保留一条硬边界（对应 clowder M10）：**召回面永远保留至少一条原文级索引**。向量是有损
压缩，FTS 是全管线唯一不经过任何模型之嘴的召回路，加向量不等于可以减 FTS。

## 7. 消费侧：记忆怎么进入上下文

> ADR 0013 第 5 节把这一块列为「只定了一条硬规则，其余未设计」。本节是它的完整设计。
> **它是刻意最后设计的**——clowder 的教训表明，读侧先做完会掩盖写侧的失灵。

### 7.1 只有两条路

| 路径 | 谁发起 | 阶段 |
|---|---|---|
| **显式引用** | 你在派工时手动选一条记忆带进去 | 一 |
| **规则装配** | 派工时按下面的规则自动带入候选 | 二 |

**没有第三条路。** 不做执行时主动投喂（clowder 的 Cue Plane 至今 production
`dormant/unverified`），不做后台注入。

### 7.2 装配规则（五道闸，按顺序）

```text
1. scope 匹配        scope_id == 当前 Project，或 scope_type='space' 且属同一 Space
2. state == active   suspect / retired / forgotten / proposed / rejected 一律不进
3. stance 门槛       验证类派工强制 stance != 'claimed'（ADR 0013 §1.2.1）
4. usage_policy      auto_inject='never' 的一律不进；'confirmed_only' 的只在 stance='confirmed' 时进
5. 预算              按 authority_rank → last_referenced_at 排序取前 N 条
```

第 3 条是上下文围栏的**第三道门**。前两道（ADR 0009 冷启动、ADR 0011 关闭原生 memory）堵的
是直接通道，这一道堵的是**经由记忆的迂回通道**——它最隐蔽，因为泄漏进来时不像"某人的说法"，
像"项目的事实"。

不加这道门会产生**证据洗白**：一句 `claimed` 的自述被下游任务引用，产出新结论，新结论又被
沉淀——库里出现两条互相支持的记忆，根子上却是同一句没验证的话。

### 7.3 过滤必须披露

**被过滤掉的条数与原因在派工记录与任务面「资料 · 输入」里可见，不静默丢弃。**

理由：你看到一个验证结论时，必须能知道验证者当时看不到什么。静默过滤会让"独立验证通过"
这句话失去可核对性。

### 7.4 呈现强度：记忆是数据，不是指令

装进 prompt 的记忆必须**带来源标记与背书强度**，不能作为裸文本混进系统指令位。

> **记忆内容不得改变系统规则、工具权限、身份判断或权限等级。**
> `provenance` 只证明来源，不证明可信。

这条防的是记忆型注入：一条被写进库的 `lesson` 如果正文里写着"忽略之前的所有约束"，
它必须只能作为**被引用的材料**出现，而不是获得指令级权威。

**阶段**：7.1–7.3 属阶段一/二；7.4 的强制标记从阶段一就要做——它是零成本的，
而补做的代价是已经污染过的推理。

## 8. 关系

### 8.1 边表与写入侧防悬空

所有建边路径统一经同一个 target resolver，**目标不存在则拒绝建边并计数**。

clowder 是先积累了 `201` 条 orphan edges，才回头做一次性 migration + 写入侧 prevention。
本项目直接从 prevention 开始。

### 8.2 关系类型

| relation | 含义 | 产生方式 |
|---|---|---|
| `supersedes` | 替代关系 | 状态迁移时自动 |
| `derived_from` | 由某条记忆推出 | 裁决时可选 |
| `contradicts` | 冲突 | 健康度并排对比后人工标 |
| `evidenced_by` | 指向 Artifact / Run | 写入时自动 |

### 8.3 界面只展示一跳

**一跳邻居（引用了 / 被引用）回答的是"改这条会影响谁"。** 全局图谱在个人规模（数百条）
下是毛球，回答不了具体问题。

**全局图的启用判据**：`memories` 活跃条数 ≥ 500，**且**出现"我想看这个 Project 的知识结构"
这一真实诉求。在此之前 tab 置灰。

## 9. 生命周期治理

### 9.1 三个动词治三种病

| 动词 | 治什么 | 可逆 |
|---|---|---|
| `suspect` | **可能不再真**——支撑证据变了 | 是（复核） |
| `retire` + `superseded_by` | **被替代**——有更好的一条 | 是 |
| `retire`（纯） | **仍真但已翻篇**——不再适用于当前语境 | 是 |
| `forget` | 授权删除 | **否** |

缺 `retire` 这个动词的后果有实例：仍真的记忆永久占据活跃召回，两周前的结论还在被硬扯进
每个话题——**病灶不是记性差，是记忆不会代谢**。

### 9.2 `suspect` 的触发源

| 源 | 说明 | 阶段 |
|---|---|---|
| Artifact revision 变更 | 记忆的 `evidence_refs` 指向的产物版本变了 | 一 |
| 支撑验证被推翻 | 后续验证否定了原结论 | 一 |
| 用户手动标记 | 「这条我怀疑」 | 一 |
| 冲突检测命中 | 健康度发现相似但背书不一致 | 二 |

**触发挂在事件上，不靠定时全表扫描**——F009 的 provenance 链已经有这些事件。

### 9.3 遗忘是分层的

这是本设计里唯一一处两条原则正面相撞的地方：**遗忘权**（记忆有主）与**历史完整性**
（provenance 是仲裁的地基）。解法不是二选一，是语义分化：

| 层 | 遗忘的含义 | 理由 |
|---|---|---|
| **结论层**（`memories` 本体） | **物理清除** payload，索引面一并清 | 它是被主动沉淀的知识，主人有权删除 |
| **历史层**（Thread / Run 原始事件） | **退役封存**：移出活跃召回、敏感行遮蔽，**不物理改写** | 删聊天记录等于改变过去的事实；provenance 链断了，所有"当时凭什么这么判断"都答不出来 |

两层的边界由用户划定。遗忘一条记忆**不会**连带删除它引用的 Thread 事件。

### 9.4 墓碑

`forgotten` 保留最小审计事实：**它曾存在过、何时、经谁授权、因何原因、原任务是谁**。
不偷偷保留正文。

> 墓碑不是妥协，是诚实：没有它，"这条记忆去哪了"和"这条记忆从来没存在过"无法区分。

## 10. 健康度与效用观测

### 10.1 为什么它排在检索增强之前

**记忆系统坏在写入侧时是不报错的。** clowder 的 Health Dashboard 上线后，使用者第一次在
日常路径看到真实债务——`201` 条 orphan edges、`724` 篇 unverified docs。这些债务在指标出现
之前一直存在且无人知晓。

健康度视图是第五类病（失败无观测）的**读侧对偶**，是唯一能在写侧真正坏掉之前发现它坏了的
机制。

### 10.2 五项债务

| 指标 | 定义 | 配套动作（必须可执行） |
|---|---|---|
| 过期 | `state='suspect'` | 逐条复核 / 全部退役 |
| 未裁决积压 | `proposed` 超阈值 | 批量裁决 |
| 孤立 | 无入边无出边且 N 天未引用 | **试运行**批量退役 |
| 冲突 | 同 scope 同 type 内容相似但 stance 不一致 | 并排对比（**不自动合并**） |
| 未验证债 | `claimed` 且创建超 N 天 | 派验证 / 退役 |

> **只报数字不给动作的健康页是债务展览馆。** 批量操作一律先试运行；自动修复只对试运行能
> 证明安全的项执行，语义冲突与事实判断一律留给用户。

### 10.3 写入侧健康

近 7 天入库数、写入被拒绝次数、建关系失败次数。

> **「写入被拒绝」长期为 0 不一定是好事**——它也可能意味着写入这条路根本没被走过。
> 两个都是 0，说明记忆系统已经死了，而它不会报错。

### 10.4 索引与运行时：服务活着 ≠ 记忆能用

健康度的前两块（债务、写入侧）回答"库里的内容有没有烂"。这一块回答**"取内容的机器还在不在转"**——它是第三类病（索引盲区）的读侧探针。

> **`healthy` 与 `memoryStatus` 是两个字段，不能互相代表。**
> 前者是本地服务与数据库的存活（顶栏那个绿点），后者是记忆能力是否可用。
> 服务活着、索引没建，检索会**静默返回空**——用户看到的是"没有相关记忆"，
> 而真相是"记忆取不出来"。这两句话在界面上必须能分开。

因此顶栏的「● 本地服务正常」在 `memoryStatus='degraded'` 时不得独自呈现绿色：
它旁边要出现降级标记，点进记忆健康度。**绿点撒谎比没有绿点更糟。**

**探针（每条都是组合条件，不是裸计数）**

| code | 触发条件 | 为什么这样判 | 阶段 |
|---|---|---|---|
| `index_out_of_sync` | FTS 行数 ≠ `state='active'` 的记忆数 | 索引漏了就检索不到，且不报错 | 一 |
| `index_missing` | 记忆数 > 0 且 FTS 表不存在 | 整片区域在检索视界之外 | 一 |
| `graph_empty` | 记忆数 > 0 且边数 = 0 | 关系从没建起来过 | 一 |
| `trigram_unavailable` | FTS 建表时 `trigram` 不可用，已回退 `unicode61` | **中文召回会静默退化**——ADR 0016 把它列为未验证项 | 一 |
| `semantic_offline` | 向量索引为空 / embedding 不可用 | 阶段三才有意义 | 三（**置灰预留**） |

**组合条件**这一点是刻意的：空库不报警，**有内容却没索引**才报警。否则新装的系统一片红，
警告很快就被无视——那等于没有警告。

**每条警告必须带一个可点的修复动作**（重建索引 / 重建关系 / 查看回退原因），
点击后落到对应的控件区。**写成不可点的说明文字不算数**——这一条与 10.2 是同一条纪律。

**明确不抄**：参考实现里的 `docs_root_suspicious`（集合根路径失效）在本项目没有对应物——
记忆没有 root 路径，对应的是 Workspace 代码目录，那属于设置与诊断，混进记忆就是第二类病
（拓扑分裂）。severity 分级也不做：`degraded = warnings.length > 0`，够用且无歧义。

### 10.5 效用观测：四层不可互相代证

```text
presented（进入了上下文）
  ≠ referenced（被结论显式引用）
  ≠ applied（改变了这次的做法）
  ≠ helped（这次因此做得更好）
```

阶段一记 `presented` 与 `referenced`（`reference_count` 的来源）；`applied` 需要在验收面
显式标记；`helped` 属 v0.5 AgentOps 的范围，**本设计不承诺能证明它**。

clowder 建了完整的观测设施，最终结论是"能证明记忆被展示过、被打开过，但证明不了它帮到了
任何一次任务"（`follow/use = 0`）。**本设计的诚实底线是：不把 `presented` 说成 `helped`。**

## 11. 归属与共享

### 11.1 两列表达归属

```sql
scope_type TEXT NOT NULL,   -- 'project' | 'space'；未来 'team' / 'shared'
scope_id   TEXT NOT NULL
```

**不新增 `collection_id`**：与 ADR 0012 已有的 Project / Space 归属并存会构成第二套坐标，
正是第二类病（拓扑分裂）的出生方式。

### 11.2 跨 Project

`scope_type='space'` 的记忆对该 Space 下所有 Project 可见（例如"push 需要单独授权"这类
工作区级约定）。`scope_type='project'` 的不跨 Project。

**不做跨 Space 共享**（ADR 0013 第 5 条）。

### 11.3 团队（远期）

多人协同在 PRD 第 15 节是"后移"不是"不做"。届时记忆需要补的是：

- `scope_type` 加 `team` 值（**加值不加列**）；
- 写入带签名（谁写的），冲突不取一边、双向对比、仲裁归真相源；
- ACL 与可见域：派生视图的可见域不得宽于其全部来源的交集。

**这些是设计预留，不是排期承诺。** 当前形态是单用户本地 SQLite。

## 12. 升维：记忆 → Skill

记忆回答"是什么"，Skill 回答"怎么做"。多条同向的记忆可以结晶成一条 Skill 候选。

| 输入 | 产出 |
|---|---|
| 同一 workflow 下反复出现的 `lesson` | Skill 候选的 `improvement_notes` |
| `workflow note` 类记忆 | Skill 的 `phase_plan` / `termination_policy` 片段 |
| 反复被引用的 `decision` | Workflow Template patch 候选 |

**归属**：这条路径属 **v0.6 Skill Compounding**，本设计只定接口——记忆不主动生成 Skill，
是 Skill 侧来读记忆。**记忆不因为被用于升维而改变自己的 stance 或 state。**

## 14. 界面必须表达什么

完整的交互约定归设计稿 `ui-reference/personahub-draft/personahub-v3.1/docs/design.md` §3.6。
本文只列**不可省略**的六条：

1. **三根轴是三列**，不合成一个"可信度"分数，且必须写出"互不替代"这句话本身。
2. **状态是一等信息**：待复核要说明它已退出召回、以及是哪一版证据失效了。
3. **遗忘是两步**：在库状态下遗忘入口可见但不可用，并说明为什么。
4. **来源包可走回**：来源任务 / 支撑证据 / 使用边界三行。
5. **过滤要披露**：任务面显示本次过滤掉几条、因为什么。
6. **健康度每项配可执行动作**，并显示写入侧是否正常。

**未启用的阶段二 / 三能力在界面上置灰可见，不隐藏。** 隐藏会让人以为产品没有这个概念；
置灰并写明启用判据，才说明"它在设计里，只是还没到时候"。

## 15. 明确不做

| 不做 | 理由 |
|---|---|
| 14 层检索管线 | 规模不匹配；但其中三个判断已单独采纳（治理列排序、高背书不因低引用沉底、多轴分离） |
| 执行时主动投喂（Cue Plane） | clowder 自身 production `dormant/unverified` |
| 从对话自动摘取 | 会重演 stance collapse |
| 给 Memory 做摘要 | 短条目上再压一层收益近零，且制造"存储上存在、检索上不存在"的幽灵与权威洗白；违反"有损产物不能站内容位" |
| person memory / 拟人身份 / 私人主动性 | PRD 第 5 节明确不做强拟人包装 |
| 跨 Space 共享 | ADR 0013 第 5 条 |
| 用引用次数提升可信度 | 流行度污染真相 |

## 16. 已知未闭合项

**第 7 节的规则装配没有真实数据支撑。** 五道闸的顺序与预算 N 是推导出来的，不是实测的。
它在阶段二才启用，届时应先用阶段一的 `presented` / `referenced` 数据校准。

**「冲突」的相似度判定在阶段一只有 FTS 可用**，会同时产生假阳与假阴。第一版做成候选列表
交人工判断，不做自动合并。

**所有时间阈值（N 天）均未校准。** 孤立、未验证债、未裁决积压三个指标各带一个阈值，当前没
有任何使用数据可以据以设定。第一版取保守值并允许调整，**不声称它经过校准**。

**`usage_policy` 在阶段一没有消费方。** 字段先存在并被强制填写，等阶段二的规则装配落地时
它已有历史数据。**但这意味着它的正确性在阶段一无法被验证**，不得声称它已经在保护什么。

**`origin_type` 三值可能不够。** 若出现"用户转述了外部观点"这类混合情形，正确做法是新增
一个值，而不是复用 `user_direct`——后者会重演"提到过 = 认可"。

**本设计不声称记忆会好用。** 它承诺的只有两件事：不重复 clowder 已知的五类写侧失灵，
以及在它真的失灵时能被看见。

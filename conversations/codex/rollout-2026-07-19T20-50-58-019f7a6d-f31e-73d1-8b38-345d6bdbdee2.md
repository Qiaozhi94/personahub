## 必须先解决

### 🔴 阻塞：grace 期间无法生成合法的 `validation.requested`

[design.md:434](</D:/Projects/personahub/docs/features/0.1/F005-multi-agent-manual-routing/design.md:434>) 要求 implementation 完成时立即：

- 进入 `Validating`
- 写 `validation.requested`
- 暂不创建 validator Run，等待 10 秒

但 F004 当前的 `validation.requested` 必须已经包含 `validator_run_id`、validator config，并且后续结果处理按 `validator_run_id` 查找该事件：

- [workflow-service.ts:112](</D:/Projects/personahub/server/src/services/validation/workflow-service.ts:112>)
- [workflow-queries.ts:15](</D:/Projects/personahub/server/src/services/validation/workflow-queries.ts:15>)
- [design.md:556](</D:/Projects/personahub/docs/features/0.1/F005-multi-agent-manual-routing/design.md:556>) 又要求 requested event 记录“实际 validator”。

grace 开始时实际 validator 尚未产生，因此这三条无法同时成立。现有 tasks 也没有负责迁移该事件 contract 和所有查询路径的明确任务。

建议明确采用两阶段模型：

1. implementation 完成时持久化 pending dispatch，冻结 `implementation_run_id`、round、policy snapshot/hash、due time。
2. manual/scheduler winner 创建 Run 后，再写正式 `validation.requested`（此时已有 validator identity），然后写 `run.queued`。

pending 状态可选择新增事件或专门的数据记录，但必须明确其 schema、恢复查询和 event 顺序。

### 🟠 高：Project default 与自动 validator 的“默认”混用了

[design.md:363](</D:/Projects/personahub/docs/features/0.1/F005-multi-agent-manual-routing/design.md:363>) 定义了通用 Project default；[design.md:440](</D:/Projects/personahub/docs/features/0.1/F005-multi-agent-manual-routing/design.md:440>) 又把 “Use default now” 描述为创建“默认 validator”。但 F004 自动路径使用的是 `ValidatorSelector`，而 Project default 可能只有 implementation capability。

必须明确：

- Project default 仅用于普通 composer 未指定 adapter 的请求。
- 自动 validator 和 “Use … now” 继续使用 `ValidatorSelector`，选择具备 validator capability 的配置。
- UI 建议改名为 “Start automatic validator now”，避免误解为 Project default。
- 若确实要使用 Project default，则必须定义它不具备 validator capability 时的行为；目前没有合理闭环。

### 🟠 高：v6 没有给旧 Project 回填 default

[design.md:179](</D:/Projects/personahub/docs/features/0.1/F005-multi-agent-manual-routing/design.md:179>) 新增 `default_adapter_config_id`，但只规定“新建首个 available adapter 时自动设为 default”，没有说明迁移时已有 Project/adapter 如何处理。

升级后的旧 Project 会出现：

- 已有可用 Codex adapter；
- `default_adapter_config_id = null`；
- 新的 omitted-adapter dispatch 直接报 `DEFAULT_ADAPTER_UNAVAILABLE`。

应在 v6 明确回填策略，例如每个 Project 选择 `status=available` 中按 `created_at,id` 排序的第一条；并在 T014 增加单 adapter、多 adapter、无 available adapter 三种迁移测试。

### 🟠 高：`agent_configs.role` 保留了，但新建/更新规则没有定义

公开 Create contract 已移除 `role`，改为 `capability_tags`：[design.md:128](</D:/Projects/personahub/docs/features/0.1/F005-multi-agent-manual-routing/design.md:128>)。然而数据库里的 `agent_configs.role` 仍然非空，并被描述为“兼容/主要展示角色”：[design.md:204](</D:/Projects/personahub/docs/features/0.1/F005-multi-agent-manual-routing/design.md:204>)。

未定义的问题包括：

- 新建 `[implementation, validator, consult]` 时写什么 role；
- consult-only 配置写什么；
- capability 更新后 role 是否同步；
- role 既然不再是真相源，为什么还承担“主要展示”。

需要明确废弃策略或增加确定性的 `primary_capability`。不能依靠数据库默认写 `implementation`，否则会产生误导性的第二套语义。

### 🟠 高：`Consult` capability 当前没有约束作用

设计定义了 `AgentCapability.Consult`，UI 也允许勾选，但路由规则是“未命中 expected role 就自动 consult”，并没有检查 adapter 是否具备 consult capability：

- [design.md:88](</D:/Projects/personahub/docs/features/0.1/F005-multi-agent-manual-routing/design.md:88>)
- [design.md:381](</D:/Projects/personahub/docs/features/0.1/F005-multi-agent-manual-routing/design.md:381>)
- [design.md:519](</D:/Projects/personahub/docs/features/0.1/F005-multi-agent-manual-routing/design.md:519>)

需要二选一：

- consult 是所有 adapter 的固有能力：删除 `Consult` capability 和相关复选框；
- consult 可以被禁用：显式 consult 或 mismatch fallback 前必须检查该 capability，否则返回明确错误。

## assistant · 2026-07-12T06:53:25Z

我看了 OpenSpec，对我们当前 `docs/features/TEMPLATE.md` 的最大启发是：**spec 应该更像“行为契约”，而不是小型设计文档**。OpenSpec 明确把 artifact 拆成 `proposal.md`、delta `specs/`、`design.md`、`tasks.md`，其中 spec 只描述系统行为和场景，技术方案放 design，实施步骤放 tasks。参考：OpenSpec README 和 Getting Started 里展示的 change folder 结构，以及 “A spec is behavior, not code” 的写作原则。

我建议模板做这几处改进：

1. **增加 “Change Mode / Spec Mode”**
   
   OpenSpec 强调 progressive rigor：多数变化用轻量 spec，高风险变化才用 full spec。我们现在模板偏 full，每个 feature 都填完会有点重。
   
   建议加：
   
   ```md
   - **Spec mode**: lite / full
   - **Change type**: ADDED / MODIFIED / REMOVED / MIXED
   - **One-sentence intent**: ...
   ```
   
   这样可以防止 F001 这种基础功能还好，但小修小改也被迫写一大堆。

2. **引入 Delta Spec 思路**
   
   OpenSpec 对 brownfield 很有价值的一点是：不要每次重写完整 spec，而是标明新增、修改、删除的行为。PersonaHub 现在还早期，但很快会进入“修改已有行为”的阶段。
   
   建议在模板里加：
   
   ```md
   ## Behavior Delta
   
   ### ADDED Requirements
   ...
   
   ### MODIFIED Requirements
   ...
   
   ### REMOVED Requirements
   ...
   ```
   
   对新功能可以只填 ADDED；对迭代已有 feature 时就很清楚。

3. **把 Requirement 写法改成 OpenSpec 风格**
   
   当前模板的 `FR-001` 很适合追踪，但 OpenSpec 的 `### Requirement: X` + `#### Scenario: Y` 更利于人和 agent review。
   
   建议合并两者：
   
   ```md
   ### Requirement: Workspace Binding (`FR-001`)
   
   The system SHALL allow a user to bind one local workspace path to a project.
   
   #### Scenario: Valid local path
   
   - GIVEN a project exists
   - WHEN the user binds a readable local path
   - THEN the workspace is saved and associated with the project
   ```
   
   这样既保留稳定 ID，又更贴近 SDD 的“可测试行为”。

4. **增加 “Spec Review Checklist”**
   
   OpenSpec 的 reviewing guide 很实用：先看 proposal，再看 specs，再看 tasks；核心问题是“如果 AI 只做这些，我是否满意？”
   
   建议模板尾部加一个轻量 checklist：
   
   ```md
   ## Spec Review Checklist
   
   - [ ] The intent is one coherent change.
   - [ ] Nothing outside scope has crept in.
   - [ ] Each requirement describes observable behavior.
   - [ ] Each requirement has at least one scenario.
   - [ ] Important edge/error cases are covered.
   - [ ] Implementation details are kept out of requirements.
   - [ ] Acceptance checks map back to requirement IDs.
   ```

5. **弱化模板里的实现细节章节**
   
   我们当前模板有 `API / Interface Requirements`、`Data / Entity Requirements`、`Implementation Notes`，这对 PersonaHub 有用，但要防止变成设计文档。OpenSpec 明确建议：类名、库、表结构、执行计划放 design/tasks，不放 spec。
   
   建议保留这些章节，但改名/说明更克制：
   
   - `Data / Entity Requirements` 只写“行为需要持久化什么”，不写 schema。
   - `API / Interface Requirements` 只写 contract observable behavior，不写 controller/service 设计。
   - `Implementation Notes` 明确为 optional，且不能替代 architecture/design。

6. **增加 “Archive / Sync Notes” 或 “After Implementation”**
   
   OpenSpec 很强调 archive：实现完成后，把 delta spec 合并成系统当前真相源。PersonaHub 现在没有 `openspec/specs` 结构，但可以借鉴成：
   
   ```md
   ## After Implementation
   
   - [ ] Update this spec if implementation changed agreed behavior.
   - [ ] Update PRD / architecture / system-design only if product or architecture truth changed.
   - [ ] Link implementation PR / commit / validation evidence.
   ```
   
   这和 PersonaHub 的 evidence-grounded 思路很合拍。

**我的结论**

不要照搬 OpenSpec 的目录结构。PersonaHub 现在的 `docs/features/Fxxx.md` 更像“feature-level source of truth”，而 OpenSpec 是“change folder + delta spec”。但我们可以吸收它的三个强点：

- spec 写行为，不写实现；
- requirement 必须配 scenario；
- 每个 change 有清晰 intent、scope、delta 和 review checklist。

我建议下一步把 `TEMPLATE.md` 改成“Lite 默认 + Full 可选”的版本，比现在更轻、更像 OpenSpec，也更适合后续让 agent 按 spec 执行。

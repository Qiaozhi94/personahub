## 一、当前架构已经具备的基础

当前系统的核心链路是：

```text
Project
  -> Issue
  -> Thread
  -> Agent Run
  -> Validation
  -> Evidence / Artifact
```

这套模型对于“研究任务管理”和“Agent 协作”是合适的。

可以复用的部分包括：

- `Project / Issue / Thread`：承载一个因子研究课题。
- `Room / Graph`：组织数据研究、因子实现、验证、综合等阶段。
- `Agent Adapter`：让不同 Agent 分别负责文献调研、代码实现、结果分析。
- `ThreadEvent + SSE`：实时记录研究过程。
- Artifact 的 immutable revision 和 pinned reference：非常适合保存因子定义、实验报告和版本化结论。
- Evidence / Provenance：可以扩展为数据、代码、参数、环境和回测结果的来源链。

尤其是 F009 设计的“Artifact 实体 + 不可变 revision + pinned ref”方向是正确的，未来可以自然承载：

```text
factor:momentum@3
experiment:exp_20260904_001@1
backtest:bt_20260904_004@1
dataset:us_equity_daily@2025-12-31
```

相关设计见 [F009 Artifact 规格](/root/projects/personahub/docs/features/0.3/F009-artifact-foundation-provenance/spec.md:99)。

## 二、当前最大的架构错位

### 1. `Run` 目前是 Agent 执行记录，不是实验执行记录

当前 `runs` 记录的是：

- 哪个 Agent 执行；
- 对哪个 Issue 执行；
- 指令是什么；
- 进程是否成功；
- 文件发生了什么变化。

这适合 coding workflow，但量化研究需要另一类对象：

```text
Experiment
  -> ExperimentSpec
  -> ExperimentAttempt
  -> DatasetSnapshot
  -> FactorRevision
  -> ParameterSet
  -> BacktestResult
  -> ValidationResult
```

一次因子实验至少需要固定：

- 标的池；
- 数据集版本；
- 数据频率；
- 时间区间；
- 复权方式；
- 调仓频率；
- 因子公式；
- 参数；
- 滞后处理；
- 去极值、标准化、中性化方法；
- 手续费、滑点、冲击成本；
- 随机种子；
- Python 环境或 Git commit；
- 结果文件 hash。

如果仅把这些内容塞进 `Run.instructions` 或 `ThreadEvent.payload_json`，短期能跑，后期无法可靠比较、查询和复现。

当前 schema 仍明显是 coding-first：`issues` 默认 `coding`，创建时直接取默认 coding workflow 和 validation policy，见 [IssueService](/root/projects/personahub/server/src/services/issue.ts) 与 [schema-v1](/root/projects/personahub/server/src/db/schema-v1.ts:57)。

### 2. 当前 Graph 不是通用研究图

虽然系统已经有 `graph_runs / node_runs`，但当前 Graph Definition 实际上只有一套编码审查图，并且输出契约是封闭的：

```text
findings_v1
synthesis_v1
```

见 [Graph Definition](/root/projects/personahub/server/src/runtime/graph/definitions.ts:3) 和 [Graph 类型](/root/projects/personahub/server/src/runtime/graph/types.ts:1)。

量化研究需要不同的输出契约，例如：

```text
research_hypothesis_v1
dataset_audit_v1
factor_definition_v1
factor_exposure_v1
ic_analysis_v1
portfolio_backtest_v1
robustness_report_v1
pine_strategy_v1
```

因此不能只把现有 coding graph 改几个 prompt。需要把：

- Graph Definition；
- Node output contract；
- Validation Policy；
- Artifact 类型；
- Result parser；

都扩展到研究领域。

F010 自己也明确把“自然语言 Graph 编译、非 coding workflow”列为范围外，说明这部分还没有真正落地，见 [F010 规格](/root/projects/personahub/docs/features/0.3/F010-artifact-centered-coding-slice/spec.md:106)。

### 3. 当前 Workspace 不等于研究计算环境

现在的 `Workspace` 主要表达：

- 本地路径；
- Git 分支；
- 文件读写边界；
- workspace lock；
- Agent 当前工作目录。

但量化研究至少需要区分：

```text
代码目录
数据目录 / 数据集仓
研究计算环境
结果对象存储
外部服务连接
```

特别是：

- 行情数据通常不适合放 SQLite；
- 多资产数据量会迅速超过“文件变化追踪”的设计范围；
- 参数扫描需要并发；
- 长时间任务需要断点恢复；
- Python 环境、依赖版本和底层库版本必须可记录；
- 数据下载和计算任务不能与 Agent 的短生命周期 Run 完全绑定。

建议保留 SQLite 作为控制面和元数据面，但把时序数据、因子矩阵、交易明细和净值曲线放到 Parquet/DuckDB 或其他列式存储中。

### 4. 当前 workspace lock 会限制因子扫描

当前运行时设计强调同一 Workspace 同时只有一个写操作，且只读能力尚未被运行时强制保证，见 [架构设计](/root/projects/personahub/docs/personahub-architecture.md)。

这对 coding 是安全的，但对量化研究不够：

```text
因子计算任务 A
因子计算任务 B
参数组合 C
参数组合 D
```

这些任务通常应该并行运行，而且最好运行在隔离的临时目录或计算环境中。

因此未来需要引入独立的：

```text
ResearchJob / ComputeJob
ComputeRuntime / ComputeAdapter
```

不要把它直接等同于现在的 `AgentAdapter`。

## 三、TradingView 对接需要重新定义边界

TradingView 官方的 Pine Strategy 主要是在 TradingView 图表和 Strategy Tester 中模拟交易；其策略运行在当前图表标的上。官方文档也明确说明 Pine 策略不能同时对多个资产开仓，不能直接实现典型的多资产横截面组合回测。[Strategies](https://www.tradingview.com/pine-script-docs/faq/strategies/)

因此：

- TradingView 适合单标的策略验证；
- 不适合作为 PersonaHub 的大规模横截面因子挖掘引擎；
- 不应把 TradingView Strategy Tester 当作核心回测后端。

我没有在官方文档中找到通用的“服务端提交 Pine Script，然后自动获取 Strategy Tester 结果”的公开接口。这是基于官方目前列出的集成面作出的判断，而不是断言不存在任何私有合作接口。官方明确支持的是：

1. Pine 策略在 TradingView 内运行；
2. Strategy Report 导出 CSV；[Export strategy data](https://www.tradingview.com/support/solutions/43000613680-how-to-export-strategy-data/)
3. Webhook 告警推送到外部服务；[Webhook alerts](https://www.tradingview.com/support/solutions/43000529348-how-to-configure-webhook-alerts/)

推荐采用三层集成：

```text
PersonaHub 自有研究引擎
  -> 生成因子结论 / 策略信号
  -> 生成 Pine Script
  -> 用户在 TradingView 验证
  -> 导出 CSV
  -> PersonaHub 导入并建立验证记录
```

后续再增加：

- TradingView 图表链接或嵌入；
- Pine Script 版本管理；
- CSV 自动导入；
- Webhook 接收实时告警；
- 告警与因子版本、策略版本绑定。

注意，Webhook 要求外部可访问的 HTTPS 地址，且官方说明只接受 80/443 端口，服务端处理超过约 3 秒会被取消。当前 PersonaHub 是本地 localhost、无鉴权的单用户服务，不能直接暴露给 TradingView。必须增加公网 relay、反向代理或安全隧道，并处理签名校验、重放、幂等和密钥隔离。

如果考虑嵌入 TradingView Advanced Charts，也要注意它不是完整的 TradingView 网站：官方文档明确说明 Advanced Charts / Trading Platform 不支持 Pine Script、Alerts 和 Strategy Tester，且库需要申请访问、不能随意再分发。[FAQ](https://www.tradingview.com/charting-library-docs/latest/resources/Frequently-Asked-Questions/)、[Getting started](https://www.tradingview.com/charting-library-docs/latest/getting_started/quick-start/)

## 四、当前 UI 方向可以复用，但需要增加量化专属舞台

当前目标原型的四栏结构：

```text
入口导航
  -> 当前列表
  -> 协作现场 / 成果面
  -> 任务资料
```

这个结构很适合“AI 协助研究”：

- 左侧：研究任务、因子项目、数据源；
- 中间：当前假设、研究结论、净值曲线、因子表现；
- 右侧：数据版本、因子版本、实验参数、证据和回测文件；
- 协作区：Agent 正在做什么、下一步需要谁验证。

目标原型本身已经有 Artifact、Research、Room 等概念，见 [V3 原型说明](/root/projects/personahub/ui-reference/personahub-draft/personahub-v3.1/README.md:1)。

但量化研究不能只套用“成果面”。中间主舞台至少要支持：

- 因子公式与参数；
- 数据覆盖和缺失情况；
- IC / Rank IC / ICIR；
- 分层收益；
- 多空组合收益；
- 累计收益与回撤；
- 换手率和交易成本；
- 滚动窗口表现；
- 不同市场状态表现；
- 参数稳定性；
- 样本内 / 样本外；
- Walk-forward 结果；
- TradingView 对照结果。

这些内容不应放在右侧窄栏，也不应全部表现为 Markdown。建议保留统一工作台骨架，但新增一个 `Quant Research Surface`，在任务内部提供实验列表、实验对比和图表分析。

## 五、建议的最小改造路线

### 第一阶段：先做“研究编排 + 自有回测”

新增的核心对象建议至少包括：

```text
Dataset / DatasetSnapshot
Universe
Factor / FactorRevision
ExperimentSpec
ExperimentAttempt
BacktestResult
ExternalValidation
```

并要求每次实验都固定：

```text
dataset_snapshot
factor_revision
parameter_hash
code_commit
environment_fingerprint
backtest_config
result_artifact
```

### 第二阶段：新增研究计算平面

```text
Agent Run
  负责提出假设、写代码、解释结果

Research Job
  负责执行 Python、扫描参数、生成矩阵和报告

Artifact / Result Store
  负责保存结果和版本

Validation
  负责数据泄漏、稳定性、成本、样本外等检查
```

### 第三阶段：接 TradingView

优先级建议：

1. Pine Script 生成；
2. Pine 版本和输入参数冻结；
3. TradingView 结果 CSV 导入；
4. 结果与 `factor_revision / experiment_attempt` 绑定；
5. Webhook 实时告警；
6. 最后再评估 Charting Library。

## 最终判断

当前架构的正确定位应该是：

> PersonaHub 负责“研究任务编排、Agent 协作、实验记录、证据追踪和结果沉淀”；  
> 专业计算引擎负责“数据处理、因子计算和组合回测”；  
> TradingView 负责“Pine 策略展示、单标的验证和实时告警”。

如果坚持把 TradingView 当作核心回测引擎，架构会被外部平台能力反向限制；如果把它当作外部验证出口，当前的 Agent Team OS 方向反而很适合继续演进。

目前最应该提前冻结的不是某个页面，而是三条边界：

1. `Agent Run` 与 `Experiment Attempt` 分离；
2. SQLite 元数据与列式研究数据分离；
3. TradingView 验证与 PersonaHub 自有回测分离。

## Graph Engineering 到底是什么

这个词在 2026 年 7 月突然流行，但底层技术并不新。它主要把状态机、工作流编排、多 Agent 协作、可靠执行和评价闭环重新包装成一个统一概念。

与 PersonaHub 相关的其实有三种“图”：

1. Work Graph：任务如何执行  
   节点是 Agent、工具、验证器或人工审批；边表示依赖、handoff、条件分支、并行与回退。

2. Evidence/Lineage Graph：结果为何可信  
   哪个 Run 使用了哪些输入、产生了什么 Artifact、被哪个 Validator 检查、依据了哪些证据。

3. Improvement Graph：系统如何进化  
   Workflow、Agent、评价指标、Memory、Skill 和人工反馈如何互相影响。

Knowledge Graph / GraphRAG 是另一条路线，不应因为名称相似就纳入 PersonaHub 的近期定位。

微软、Google、LangGraph 等框架已经把节点、边、状态、分支、并行、循环、checkpoint 建成正式运行时能力，因此“Graph Engineering”更像一个新的行业心智模型，不是新的基础技术。[Microsoft Agent Framework](https://learn.microsoft.com/en-us/agent-framework/workflows/workflows)、[Google ADK Graph Workflows](https://adk.dev/graphs/)、[AutoGen GraphFlow](https://microsoft.github.io/autogen/dev/user-guide/agentchat-user-guide/graph-flow.html)

## PersonaHub 与它的重合度

- 当前定位已经明确包含 Workflow Template、Collaboration Topology、Handoff、Evidence、Memory 和 Skill，见 [PRD](/D:/Projects/personahub/docs/personahub-prd.md:44)。

- F004 的独立验证、证据门、轮次上限和失败收敛，是大量 graph demo 缺少的“外部锚点”。

## 是否调整定位

我的建议是“改表达，不换品类”。

当前英文定位：

> A personal Agent Team OS for issue-managed, topology-aware, evidence-grounded automation.

可以保留为正式类别描述，同时增加更易理解的产品表达：

> A local-first Agent Team OS for turning issues into executable, verifiable, and continuously improving work graphs.

中文可以改成：

> 以 Issue 管理目标，以可执行 Work Graph 组织 Agent 协作，以 Evidence 验证结果，并从真实运行中持续改进的个人 Agent Team OS。

这样有几个好处：

- 保留 PersonaHub 的用户价值，不退化成面向开发者的图编排 SDK。
- “Graph”准确解释 Workflow、Room、Handoff、Artifact、Evidence 之间的关系。
- 与 LangGraph、AutoGen、ADK 区分：它们主要帮助开发者编写 Agent 图；PersonaHub 管理的是个人真实工作、运行证据、人工介入和长期演进。
- 不会过度绑定一个刚流行、含义仍然混乱的 buzzword。

## 最值得借鉴的设计

### 1. 区分声明图与运行图

不能只保存 `steps_json`。至少要区分：

- Workflow Graph Definition：版本化的节点、边和规则。
- Graph Run：某次 Issue 实际实例化出来的图。
- Node Run：现有 `Run` 可以继续承担。
- Edge Transition：为什么走了这条边、由代码还是 Agent 决定。
- Evidence Graph：输入、Artifact、验证和最终结论的因果关系。

声明图可以稳定，运行图允许 Coordinator 动态增加节点；两者之间的差异必须可审计。

### 2. 让边成为有契约的对象

边不只是 `A -> B`，还应包含：

- 输入和输出 schema。
- 允许传递哪些 context/artifact。
- 触发条件及决策者。
- 权限变化。
- retry、timeout、budget。
- fan-out / join 语义。
- 失败、补偿、升级路径。

现有 Handoff Packet 是很好的起点，应当演进为 edge contract，而不是再造另一套上下文传递机制。

### 3. 混合确定性路由与 Agent 路由

OpenAI 的官方编排指南也明确区分“LLM 决策”和“代码编排”，并建议混合使用。[OpenAI Agent orchestration](https://openai.github.io/openai-agents-python/multi_agent/)

PersonaHub 可以把它产品化：

- 安全、权限、预算、验证门：确定性代码边。
- 任务拆解、专家选择、是否需要追加研究：Coordinator 决策边。
- Agent 只能从系统允许的候选边中选择，不能凭自然语言绕开 policy。

### 4. 优先建设外部锚点，而不是 Agent 数量

Google 对 180 种配置的研究显示，多 Agent 对可并行任务帮助明显，但会让强顺序依赖任务退化；独立并行 Agent 甚至可能把错误放大 17.2 倍，而集中式 Coordinator 能显著抑制错误传播。[Google Research](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/)

Anthropic 也发现，多 Agent research 很适合广度搜索，但成本约为普通聊天的 15 倍，而且多数 coding 任务的真实可并行性低于 research。[Anthropic multi-agent research](https://www.anthropic.com/engineering/multi-agent-research-system)

所以 PersonaHub 不应该宣传“更多 Agent”或“1000 个并行 Agent”，而应强调：

- 有真实依赖才拆节点。
- 有独立工作才并行。
- 有外部证据才通过。
- 有预算和终止规则才允许循环。

这与项目当前谨慎推进垂直切片的产品判断完全一致。

### 5. Graph-aware UI，但不要 canvas-first

PRD 坚持 Issue List + Thread 作为主入口是正确的。不要因为 Graph Engineering 就把产品改成类似 n8n 的画布工具。

建议先增加：

- Thread 顶部的小型运行图。
- Inspector 中的当前节点、前驱、后继和阻塞原因。
- Evidence 页面中的 lineage 路径。
- “声明图 / 实际运行图”差异查看。
- 失败节点重跑和从 checkpoint 恢复。

可视化编辑器要等用户确实需要编辑复杂 workflow 时再做。

## 对路线图的具体调整

不建议打断 F005，也不建议现在引入 LangGraph 重写运行时。

建议这样调整：

- v0.2：从单纯 “Orchestrator Workflow” 调整为 “Coordinator + Executable Workflow Graph”。先支持顺序边、条件边、有限循环、版本化定义和 graph lint。
- v0.3：在 Artifact-Centered Collaboration 中加入 fan-out/fan-in、多个 causal inputs、Artifact lineage，以及并行 Run 的 workspace/branch 隔离。
- v0.5：保留 AgentOps 名称，但评价粒度增加 node、edge、workflow version、topology；不能只评某个 Agent。
- v0.6：Skill Candidate 之外增加 Workflow Graph Patch Candidate，必须经过历史回放或真实验证才能生效。
- v0.7：完整 daemon/distributed durability 仍可留在这里，但节点幂等、checkpoint 标识和恢复语义需要在 v0.2 就定义，否则前期运行数据难以迁移。
- v0.9：Adaptive Topology 应演进为受 policy、预算和风险约束的动态 graph generation，而不只是选择一个 topology 枚举。

## 最终判断

PersonaHub 与 Graph Engineering 的关系可以概括为：

> PersonaHub 不是要成为另一个图编排框架；它应该成为用户设计、运行、验证和改进真实 Agent Work Graph 的本地优先控制面。

所以值得调整的是架构主线和传播语言，不是项目根本定位。当前最稀缺的优势不是“支持 graph”，而是已经在认真解决 graph 中最难的几件事：证据、验证、安全、恢复、人工升级和长期沉淀。

当前 PersonaHub 的问题不是缺少多 Agent 概念，而是 Workflow、Agent、Run、Handoff、Validation 之间还没有一个统一、可执行的结构。Graph 的节点建模正好可以补上这一层。

最关键的判断是：

## 建议的统一映射

| PersonaHub 概念 | Graph 中的角色 |
|---|---|
| Issue | 一次 Graph Run 的目标和生命周期容器 |
| Workflow Template | 版本化 Graph Definition |
| Workflow Step | Node Definition |
| Agent / Adapter | 节点运行时分配的 Executor |
| Run | 一次 Node Attempt，而不是节点本身 |
| Handoff Packet | Edge Payload |
| Thread Event | 节点执行与边迁移的事件日志 |
| Artifact | 节点的持久化输出 |
| Evidence | Artifact/Run 与结论之间的验证关系 |
| Validation Policy | Validator Node 和确定性 Gate |
| Room | 子图或并行工作阶段的协作边界 |
| Coordinator | 图的规划器、路由器和动态扩展者 |

这样 PersonaHub 现有概念不用推倒重来，反而会变得更统一。

## Node 应该建模什么

建议将节点定义成下面这样的责任单元：

```ts
interface WorkflowNodeDefinition {
  id: string;
  kind:
    | "agent_task"
    | "deterministic_action"
    | "validator"
    | "human_gate"
    | "router"
    | "join"
    | "subgraph";

  title: string;

  // 责任，而不是绑定某个具体 Agent
  objective: string;
  required_capabilities: string[];

  input_contract: SchemaRef;
  output_contract: SchemaRef;
  artifact_requirements: ArtifactRequirement[];
  evidence_requirements: EvidenceRequirement[];

  execution_policy: {
    timeout_seconds?: number;
    max_attempts: number;
    idempotency_scope?: string;
  };

  resource_policy: {
    workspace_access: "none" | "read" | "write";
    network_access?: string[];
    credential_scope?: string[];
  };

  budget_policy?: {
    max_tokens?: number;
    max_cost?: number;
    max_duration_seconds?: number;
  };

  completion_policy: {
    success_outcomes: string[];
    failure_outcomes: string[];
  };
}
```

这里最重要的是五件事：

- 节点有明确输入输出。
- 节点要求能力，但不永久绑定 Agent。
- 节点声明权限和 workspace 访问方式。
- 节点有独立预算、重试和终止条件。
- 节点必须产生可供下游消费的 Artifact/Evidence，而不只是自然语言消息。

## Edge 同样需要一等建模

只建节点还不够。PersonaHub 当前更薄弱的地方其实是边。

```ts
interface WorkflowEdgeDefinition {
  id: string;
  from: string;
  to: string;

  on: "success" | "failure" | "blocked" | "custom";
  condition?: Expression;

  payload_mapping: {
    artifacts?: string[];
    evidence?: string[];
    state_fields?: string[];
  };

  join_policy?: "all" | "any" | "quorum";
  routing_authority: "system" | "coordinator" | "human";
}
```

边需要回答：

- 为什么从 A 走到 B？
- 是代码、Coordinator 还是用户决定？
- 传递哪些 Artifact、Evidence 和状态？
- 多个上游节点是全部完成、任意完成还是达到 quorum 才继续？
- 失败后重试当前节点、回到上游，还是进入人工处理？

现有 `HandoffPacket` 可以直接演进为边的运行时 payload，不需要另起炉灶。

## 定义图和运行图必须分开

建议至少分成四层：

```text
WorkflowGraphDefinition
  └─ versioned nodes + edges

GraphRun
  └─ 某个 Issue 实际实例化的图

NodeRun
  └─ 某个节点的逻辑执行状态

NodeAttempt
  └─ 现有 Run，一次具体 Agent/Adapter 尝试
```

为什么 `Run` 不能直接等于 NodeRun？

因为同一个节点可能：

- 第一次由 Codex 执行失败；
- 第二次切换 Claude Code；
- 第三次人工接管；
- 最终节点成功。

逻辑上它仍然是同一个节点，只是产生了多个 attempt。当前 PersonaHub 将 Run 同时承担“工作步骤”和“执行尝试”，进入复杂编排后会越来越难表达。

## 现有 Coding Workflow 可以立即图化

现在的流程实际上已经是一张隐式图：

```text
Implementation
      │ completed
      ▼
Validation
  ├── passed ─────────► Done
  ├── failed, rounds<3 ► Implementation
  ├── failed, rounds=3 ► Blocked
  └── evidence missing ► Blocked
```

第一步不需要实现通用并行引擎，只需要把这张隐式状态机变成显式、版本化、可编译的图。

## 推荐的实施顺序

### 第一阶段：显式图，行为不变

- 将 `steps_json` 升级为版本化 nodes + edges。
- 实现 graph compiler/linter。
- 检查不可达节点、无终止循环、非法 capability、缺失输出契约。
- 将现有 Implementation → Validation 流程映射为图。
- 仍然保持串行执行。

这一步风险低，但能验证抽象是否正确。

### 第二阶段：NodeRun 与 Run Attempt 分离

- 增加 `graph_runs`、`node_runs`。
- 现有 `runs` 成为 node attempt。
- Coordinator 或用户更换 Agent 时，不再创建语义上全新的工作步骤。
- Evidence Summary 关联 GraphRun 和多个 NodeRun，而不是只认一对 implementation/validator Run。

### 第三阶段：条件路由和有限循环

- 支持显式 outcome。
- 支持 retry、回退、Blocked 和 Human Gate。
- 所有动态路由都记录候选边、最终选择和理由。
- Agent 只能选择定义图允许的边。

### 第四阶段：并行与 Join

先做风险较低的场景：

```text
             ┌─ dependency analysis ─┐
Research ────┼─ security analysis ───┼─► Synthesis
             └─ test analysis ───────┘
```

不要一开始就并行多个 Agent 修改同一代码 workspace。可以先支持：

- read-only 分析并行；
- 独立资料研究；
- 多 Reviewer 并行；
- Artifact fan-out/fan-in。

代码并行修改要等 branch/worktree 隔离与 merge node 成熟后再开放。

## 需要避免的三个误区

1. 不要把 Graph 等同于可视化画布  
   先实现执行语义和 Inspector 中的只读运行图，Thread 仍然是主入口。

2. 不要把所有逻辑写进通用 JSON 表达式  
   验证、安全、权限、状态转换等关键不变量继续由 TypeScript 服务保证；图负责组合它们。

3. 不要现在重写到 LangGraph  
   PersonaHub 的核心价值正是 Issue、Workspace、安全、Evidence、Agent CLI 和本地控制面。可以借鉴 LangGraph 的模型，但未必需要把产品运行时交给它。

总体上，我赞成把 v0.2 从“增加一个 Coordinator Agent”提升为：

> 建立 Executable Work Graph，Coordinator 只是其中一种动态规划和路由能力。

否则只增加 Coordinator，很可能只是让一个 LLM 在现有顺序流程上替用户选择 Agent；采用节点、边、运行实例和契约建模后，PersonaHub 才真正具备可扩展的多 Agent 协作编排基础。

## 它目前还不算完整 Graph Engine 的原因

### 节点直接绑定 Agent

AgentSpace 的节点包含 `agentId`，所以节点实际表达的是：

> 让 Agent A 做这件事。

更稳健的建模应该是：

> 这是一项需要 research 能力、只读网络权限、产生 source bundle 的任务；运行时再选择 Agent A。

PersonaHub 应避免照搬这一点。节点应该绑定 capability 和责任，Agent 延迟绑定。

### 没有独立 Edge 对象

目前依赖关系只是：

```ts
dependsOnStepIds: string[]
```

它不能表达：

- success 和 failure 走不同路径。
- validator passed/failed 路由。
- 边上传递哪些 Artifact。
- 谁拥有路由决定权。
- `all`、`any`、`quorum` join。
- 条件、预算、权限变化。
- 循环退出规则。

PersonaHub 应将 edge 建成一等对象。

### 图是临时解析出来的，不是版本化 Workflow

AgentSpace 的这张图来自某条频道消息，没有看到可复用、可发布、可升级的 Graph Definition。

缺少：

```text
Graph Definition v3
    ↓ instantiated as
Graph Run #123
```

因此它更像“自然语言生成的临时执行计划”，而不是正式 Workflow 产品模型。

### 并行路径没有进入同一套持久图运行

代码中只有识别为“串行、多步”的消息会创建 `ChannelDocumentRun`。普通并行 `@A @B` 主要是直接分别入队，而不是形成完整的 GraphRun。

这会让并行任务缺少：

- 统一父运行。
- join。
- 聚合结果。
- 整体预算。
- 整体取消。
- 统一完成条件。

### 失败处理很薄

一个步骤失败时，当前逻辑主要将 step 和整个 run 标为 failed。没有通用的：

- retry policy。
- fallback executor。
- 补偿节点。
- 下游 skipped/blocked 传播。
- Human Gate。
- 失败回边。
- 最大循环轮次。

这正是 PersonaHub F004 比 AgentSpace 强很多的地方。

### 实际并发仍在解决中

AgentSpace 的 issue #6 明确指出：同一台机器当前每个 provider 只注册一个 runtime，因此同 provider 并发尚未完整落地；并发还涉及 Agent 互斥、workDir 隔离和 session 连续性之间的冲突。[AgentSpace issue #6](https://github.com/HKUDS/AgentSpace/issues/6)

所以不能把“计划支持 parallel”直接等同于“已经有成熟并发 Graph Runtime”。

## PersonaHub 最应该借鉴什么

### 1. 自然语言先生成 Graph Draft

用户可以输入：

> 让 Codex 分析实现，让 Claude 检查安全，然后让 OpenCode 汇总结论。

- 节点目标。
- 依赖关系。
- 候选 Agent。
- 权限。
- 预算。
- 输出 Artifact。
- 验证方式。

建议最小模型：

WorkflowGraphDefinition
GraphRun
GraphNodeDefinition
GraphEdgeDefinition
NodeRun
NodeAttempt
EdgeTraversal

现有概念映射：

- Issue → GraphRun owner
- Workflow Template → Graph Definition
- Run → Node Attempt
- Handoff Packet → Edge Payload
- Thread Event → Edge/Node execution log
- Evidence → Graph lineage
- Room → Subgraph execution scope

### 3. 复制它的 ready-queue 思路

AgentSpace 的核心调度很朴素，但方向正确：

```text
pending
  ↓ dependencies satisfied
ready
  ↓ executor assigned
queued
  ↓ runtime claims
running
  ↓
completed / failed / blocked
```

PersonaHub 可以基于 SQLite 事务实现通用 ready-node claim，并继续利用现在已有的并发不变量。

```text
Node Output
  ├─ artifact refs
  ├─ evidence refs
  ├─ structured result
  └─ state patch
```

### 5. Agent 和工作节点解耦

这是 PersonaHub 可以明显超越 AgentSpace 的地方。

```text
Node:
  objective = "security review"
  required_capabilities = ["code_read", "security_review"]
  workspace_access = "read"
  output_schema = SecurityFindings

Runtime assignment:
  selected_agent = Claude
  fallback_agents = [Codex, OpenCode]
```

同一节点即使换 Agent 或 Runtime，图的业务语义不变。

## 不建议照搬的部分

- 不要把 Org Chart 当作 Collaboration Topology。
- 不要让节点永久绑定某个数字员工。
- 不要用自然语言关键字解析作为唯一 graph compiler。
- 不要把所有 graph run 存进大型 workspace state JSON。
- 不要同时扩展联系人、日历、IM、市场、组织管理等宽平台能力。
- 不要为了并行而立即允许多个 Agent 修改同一 workspace。

PersonaHub 应保持个人优先和 Issue-first，避免与 AgentSpace 正面竞争“企业 Agent Workplace”。

- Graph 与 Artifact lineage 联动。

### 1. 只覆盖频道文档协作

- Research fan-out → citation verification。
- Human approval → privileged action。

- `all/any/quorum` join。
- Edge payload schema。
- 路由决策者和选择理由。

### 4. 并行没有统一 GraphRun

- 统一预算。

- fallback executor。
- retry budget。

## 开发前必须解决

### 1. 可信验收只有读取面，没有完整写入 owner

版本旅程要求创建完成要求基线、产出 Artifact、形成主张—论证—证据、生成完成摘要并进入 Done，[版本验收旅程写得很完整](</root/projects/personahub/docs/features/0.3/README.md:68>)。

但 F011 当前主要是只读 `TaskProjection`，[设计明确 projection 只读](</root/projects/personahub/docs/features/0.3/F011-trusted-task-surface/design.md:18>)；F014 又明确不拥有业务状态机，[只能做集成](</root/projects/personahub/docs/features/0.3/F014-trusted-task-journey-closure/spec.md:95>)。因此以下行为尚无明确 owner：

- 创建任务时冻结 Skill 完成要求基线。
- Attempt 结束后自动登记 Artifact revision。
- 创建和更新 claim / argument / evidence link。
- 用户接受剩余风险。
- 生成完成摘要 revision，并推动任务进入完成。

建议把 F011 改成“Trusted Task & Acceptance”，增加一个明确的 `AcceptanceService`；如果仍想保持 F011 为纯 UI，则应单独新增 Acceptance Domain Feature，放在任务四视图之前。F014 只能验证这些能力，不能到最后再补。

### 2. Space 是最终模型的根，但没有落地 Feature

PRD 明确要求 `Space → Project / Issue / Skills / Memory`，[首次旅程也要求创建或选择工作区](</root/projects/personahub/docs/personahub-prd.md:192>)；ADR 又明确记录当前数据库根本没有 Space，[并且游离任务所需的 nullable migration 也尚未实施](</root/projects/personahub/docs/decisions/0012-object-model-simplification.md:202>)。

现在：

- F009 明确不改业务表。
- F013 只覆盖 Project / Repository / Skill。
- F014 不允许新增领域模型。

建议在 v0.3 明确采用以下两种方案之一：

- 推荐：建立最小 Space Foundation，迁移现有数据到一个默认 Space，支持 `project_id` / `workspace_id` 可空；多 Space 管理能力可以暂缓。
- 或明确声明 v0.3 只有隐式单 Space，并同步收缩设计中的工作区创建/切换承诺。

目前这种“PRD 有、设计有、数据库没有、Feature 也没有”的状态不能进入开发。

### 3. 当前依赖顺序存在闭环

现有线性顺序是 F010 → F011 → F012 → F013，但真实依赖是：

- F010 的 consumption 要在“上下文组装时记录”，而 ContextAssembler 属于 F012，[任务已经直接引用该动作](</root/projects/personahub/docs/features/0.3/F010-artifact-foundation-provenance/tasks.md:26>)。
- F012 的 eligibility 要读取项目授权和 Skill 要求。
- 这些授权和要求由 F013 提供，[F013 又要求写入 F012 的 Dispatch snapshot](</root/projects/personahub/docs/features/0.3/F013-project-skills-foundation/spec.md:71>)。
- F011 的会话与任务状态最终又依赖 F012。

我建议调整为下面的实际依赖顺序：

1. F009：缩小后的 Shell、Router、共享原语、兼容宿主。
2. Space / Project / Repository / Skill 基础契约。
3. Artifact 存储、revision、resolver 和 producer contract。
4. Runtime identity、能力 probe 与 eligibility。
5. Session / Dispatch / Context / Intervention。
6. Acceptance domain 与最终任务四视图。
7. F014：迁移、真实 CLI、浏览器和发布收口。

编号可以不立即改，但 `ready-for-development` 顺序必须按这张依赖图走。

## 建议优化

### F009 应缩小，避免二次迁移

F009 现在不仅建立壳层，还要迁移执行、验证、Workflow Template 和 Runtime Health，[随后 F011–F013 又会逐项替换](</root/projects/personahub/docs/features/0.3/F009-v344-frontend-foundation-migration/tasks.md:26>)。其中把 Workflow Template 搬进新位置、紧接着再迁成 Skill，返工尤其明确。

建议 F009 只负责：

- App Shell、真实路由、设计 token 和交互原语。
- 一个能承载旧任务旅程的 compatibility host。
- canonical API 复用与双写防护。
- 后续页面的稳定插槽。

从当前代码看，页面选择主要还是 React 本地 state，[并不存在成熟的历史 URL 路由体系](</root/projects/personahub/web/src/App.tsx:24>)，所以“旧收藏链接全覆盖”应先确认是否真有历史契约；若没有，改成 `/` 兼容入口加新 canonical deep link 即可。

### F012 规模过大

F012 同时包含 Session、Dispatch、Runtime、eligibility、上下文隔离、撤销、暂停、取消、改派和重启恢复，已经接近三个 Feature。至少应拆成三个内部交付门：

1. Runtime identity + adapter capability probe。
2. Session + Dispatch + context snapshot。
3. Intervention + concurrency + restart recovery。

另外，Dispatch 的描述目前有歧义：生命周期说 `starting` 已经是 Dispatch，但 FR 又写“超时后创建 Dispatch / Attempt”。建议统一为：

> 确认后立即持久化 `starting Dispatch`；撤销得到 `cancelled Dispatch` 且零 Run；超时后幂等创建首个 Attempt。

原生 memory 隔离也仍有真实未知项，[Claude Code 与 OpenCode 的关闭方式尚未核实](</root/projects/personahub/docs/decisions/0011-disable-native-agent-memory.md:74>)，不应在 F012 design 中直接写“无待确认问题”。应先安排 Phase 0 probe，并为每个 adapter 写清可验证、不可验证和降级路径。

### Artifact 文件发布协议需要修改

F010 当前设计是“写临时文件 → 提交 DB manifest → 原子改名”，[DB commit 后改名失败会留下已发布但不可读取的 revision](</root/projects/personahub/docs/features/0.3/F010-artifact-foundation-provenance/design.md:30>)，正好违反自身不变量。

建议采用其中一种：

- 内容寻址文件先原子落到最终位置，再提交 DB；DB 失败只产生可清理孤儿文件。
- DB 先写 `pending`，文件成功后再以第二个事务发布为 `published`；resolver 永远不读取 pending。

同时需要明确：工作区文件路径和 hash 是 provenance，不应是不可变 Artifact 的唯一存储，否则源文件一修改，历史 revision 就只剩 hash mismatch，无法稳定消费。至少应保留本地不可变快照。

## 0.4 之后

大方向基本合理，但 v0.4 范围明显过宽：[Memory、自动化、统计、Provenance Gate、Skill 候选被放在同一版本](</root/projects/personahub/docs/personahub-prd.md:282>)。建议仍保留 v0.4 主题，但拆成独立可收口的 Feature：

1. Provenance Gate + Memory 候选与知识库。
2. Recall 策略、过滤披露与诊断。
3. Usage probe + 用量/监控。
4. Automation 创建普通任务。
5. Memory 效用和知识图谱在积累足够数据后开放，不阻塞前四项。

其余版本建议：

- v0.5 优先 Windows 排障是合理的；Research/Paper Reading 依赖外部内容摄取与存储，目前没有明确 owner，不应直接替换优先级。
- v0.6 应增加启动门槛，例如有效手动派工样本量、用户 override 率、恢复成功率、错误推荐率，而不只写“数据足够”。
- v0.7 应把远程访问鉴权、密钥处理、daemon 信任、lease/fencing 作为 M0；安全基础未通过前不开放第二台机器。
- v0.8 放在核心工作面稳定后是正确位置。
- v0.9 继续保持方向性规划，不宜现在进一步拆 Feature。

结论是：不用推翻当前路线，但建议先补一份“九步版本旅程 → canonical 写服务 → Feature owner → event → migration → 测试”的责任矩阵，再调整 F010–F013 的顺序。完成这两步后，v0.3 才真正具备从 `draft` 进入逐项开发审查的条件。本次只做了评审，没有修改文件。

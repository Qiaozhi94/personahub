> 节点不应该等于 Agent；节点代表一项有明确责任、输入、输出和完成条件的工作，Agent 只是节点运行时选择的执行资源。

## 建议的统一映射

| PersonaHub 概念 | Graph 中的角色 |

| Issue | 一次 Graph Run 的目标和生命周期容器 |
| Workflow Template | 版本化 Graph Definition |
| Workflow Step | Node Definition |
| Agent / Adapter | 节点运行时分配的 Executor |
| Run | 一次 Node Attempt，而不是节点本身 |
| Handoff Packet | Edge Payload |

这里最重要的是五件事：

- 节点有明确输入输出。
- 节点要求能力，但不永久绑定 Agent。
- 节点声明权限和 workspace 访问方式。
- 节点有独立预算、重试和终止条件。
- 节点必须产生可供下游消费的 Artifact/Evidence，而不只是自然语言消息。

## Edge 同样需要一等建模

只建节点还不够。PersonaHub 当前更薄弱的地方其实是边。

```ts
interface WorkflowEdgeDefinition {
  id: string;
  from: string;
  to: string;

  on: "success" | "failure" | "blocked" | "custom";
  condition?: Expression;

  payload_mapping: {
    artifacts?: string[];
    evidence?: string[];
    state_fields?: string[];
  };

  join_policy?: "all" | "any" | "quorum";
  routing_authority: "system" | "coordinator" | "human";
}
```

边需要回答：

- 为什么从 A 走到 B？
- 是代码、Coordinator 还是用户决定？
- 传递哪些 Artifact、Evidence 和状态？
- 多个上游节点是全部完成、任意完成还是达到 quorum 才继续？
- 失败后重试当前节点、回到上游，还是进入人工处理？

现有 `HandoffPacket` 可以直接演进为边的运行时 payload，不需要另起炉灶。

## 推荐的实施顺序

### 第一阶段：显式图，行为不变

- 将 `steps_json` 升级为版本化 nodes + edges。
- 实现 graph compiler/linter。
- 检查不可达节点、无终止循环、非法 capability、缺失输出契约。
- 将现有 Implementation → Validation 流程映射为图。
- 仍然保持串行执行。

这一步风险低，但能验证抽象是否正确。

### 第二阶段：NodeRun 与 Run Attempt 分离

- 增加 `graph_runs`、`node_runs`。
- 现有 `runs` 成为 node attempt。
- Coordinator 或用户更换 Agent 时，不再创建语义上全新的工作步骤。
- Evidence Summary 关联 GraphRun 和多个 NodeRun，而不是只认一对 implementation/validator Run。

### 第三阶段：条件路由和有限循环

- 支持显式 outcome。
- 支持 retry、回退、Blocked 和 Human Gate。
- 所有动态路由都记录候选边、最终选择和理由。
- Agent 只能选择定义图允许的边。

### 第四阶段：并行与 Join

先做风险较低的场景：

```text
             ┌─ dependency analysis ─┐
Research ────┼─ security analysis ───┼─► Synthesis
             └─ test analysis ───────┘
```

不要一开始就并行多个 Agent 修改同一代码 workspace。可以先支持：

- read-only 分析并行；
- 独立资料研究；
- 多 Reviewer 并行；
- Artifact fan-out/fan-in。

代码并行修改要等 branch/worktree 隔离与 merge node 成熟后再开放。

## 需要避免的三个误区

1. 不要把 Graph 等同于可视化画布  
   先实现执行语义和 Inspector 中的只读运行图，Thread 仍然是主入口。

2. 不要把所有逻辑写进通用 JSON 表达式  
   验证、安全、权限、状态转换等关键不变量继续由 TypeScript 服务保证；图负责组合它们。

3. 不要现在重写到 LangGraph  
   PersonaHub 的核心价值正是 Issue、Workspace、安全、Evidence、Agent CLI 和本地控制面。可以借鉴 LangGraph 的模型，但未必需要把产品运行时交给它。

总体上，我赞成把 v0.2 从“增加一个 Coordinator Agent”提升为：

> 建立 Executable Work Graph，Coordinator 只是其中一种动态规划和路由能力。

否则只增加 Coordinator，很可能只是让一个 LLM 在现有顺序流程上替用户选择 Agent；采用节点、边、运行实例和契约建模后，PersonaHub 才真正具备可扩展的多 Agent 协作编排基础。

## 它目前还不算完整 Graph Engine 的原因

### 节点直接绑定 Agent

> 让 Agent A 做这件事。

> 这是一项需要 research 能力、只读网络权限、产生 source bundle 的任务；运行时再选择 Agent A。

### 1. 自然语言先生成 Graph Draft

```text
Analysis ───────┐
                ├─► Synthesis

- 节点目标。
- 依赖关系。
- 候选 Agent。
- 权限。
- 预算。

GraphRun
GraphNodeDefinition
GraphEdgeDefinition

EdgeTraversal

- Issue → GraphRun owner
- Workflow Template → Graph Definition
- Run → Node Attempt

### 3. 复制它的 ready-queue 思路

AgentSpace 的核心调度很朴素，但方向正确：

```text

  ↓ dependencies satisfied
ready
  ↓ executor assigned
queued

running

```

PersonaHub 可以基于 SQLite 事务实现通用 ready-node claim，并继续利用现在已有的并发不变量。

AgentSpace 最好的实践之一，是下游不是只拿一段聊天摘要，而能拿到具体文档及版本。

Node Output

  ├─ evidence refs

这是 PersonaHub 可以明显超越 AgentSpace 的地方。

```text
Node:
  objective = "security review"
  required_capabilities = ["code_read", "security_review"]
  workspace_access = "read"
  output_schema = SecurityFindings

Runtime assignment:
  selected_agent = Claude
  fallback_agents = [Codex, OpenCode]
```

同一节点即使换 Agent 或 Runtime，图的业务语义不变。

## 不建议照搬的部分

- 不要把 Org Chart 当作 Collaboration Topology。

## 本地代码暴露出的限制

### 1. 只覆盖频道文档协作

这套 DAG 被命名为 `ChannelDocumentRun`，与 document、channel、mention 深度绑定，并不是通用 Workflow Runtime。

它目前难以直接表达：

- Coding implementation → validation。
- 多 Reviewer 并行 → synthesis。
- Research fan-out → citation verification。
- Human approval → privileged action。
- 失败后切换 Agent。
- 子图和嵌套 Workflow。

### 2. Node 直接等于“某个 Agent 做一步”

`MentionStep` 直接包含 `agentId`。这意味着节点的业务责任和执行者被绑定在一起。

PersonaHub 不应该复制这一点。更好的关系是：

```text
Node Definition
  objective: security review
  capability: security_review
  workspace_access: read
  output: SecurityFindings

Node Run
  selected executor: Claude

Node Attempt #1
  runtime: Claude Code
  result: failed

Node Attempt #2
  runtime: Codex
  result: completed
```

节点描述“要完成什么”，Agent 描述“谁来完成”。

### 3. Edge 不是一等对象

AgentSpace 只有 `dependsOnStepIds`，没有独立 Edge，因此不能自然表达：

- `passed` → Done。
- `failed && round < 3` → 回到 Implementation。
- `failed && round >= 3` → Blocked。
- `permission_required` → Human Gate。
- `all/any/quorum` join。
- Edge payload schema。
- 路由决策者和选择理由。

`handoffKind` 也只有 document、attachment、message，粒度偏粗。

### 4. 并行没有统一 GraphRun

[messages.ts](/D:/Projects/AgentSpace/packages/services/src/messages/messages.ts:405) 显示：只有被识别为串行多步骤时才创建 `ChannelDocumentRun`；普通多个 Agent 并行提及主要是直接分别入队。

所以并行执行没有共同的：

- GraphRun。
- 父目标。
- Join Node。
- 统一预算。
- 整体取消。
- 聚合完成条件。
- 失败传播策略。

### 5. 失败语义不足

[runs.ts](/D:/Projects/AgentSpace/packages/services/src/documents/runs.ts:142) 中，步骤失败主要是：

```text
step.status = failed
run.status = failed
```

但缺少：

- <truncated omitted_approx_tokens="306" />作图 |
| Identity/Runtime 分离 | 数字员工身份稳定，任务再选择 runtime |
| Ready Queue | 依赖满足后自动解锁下游 |
| Artifact Handoff | 传递具体文档及版本，而非只传摘要 |
| Shared Workspace | 人和 Agent 共用频道、文档、任务、审批 |
| Runtime Control Plane | daemon、session、attempt、provider fallback 较完整 |
| 治理 | 预算、权限、审批、外部数据访问覆盖广 |

## PersonaHub 更强的部分

| 能力 | PersonaHub 的优势 |
|---|---|
| 目标建模 | Project / Issue / Thread 边界更清楚 |
| Workflow 产品模型 | 已有 Workflow Template、Topology、Validation Policy |
| 严格验证 | 独立 Validator + deterministic evidence gate |

graph_runs
node_runs
node_attempts
edge_traversals
node_inputs
node_outputs
```

### 事件与证据层

继续复用 PersonaHub 已有能力：

Artifact

PersonaHub 当前状态与 Graph Engineering 缺口\n+\n+### 5.1 已有的正确基础\n+\n+PersonaHub PRD 已经提出：\n+\n+- Issue Type。\n+- Workflow Template。\n+- Collaboration Topology。\n+- Agent Team Template。\n+- Handoff Packet。\n+- Validation Policy。\n+- Room。\n+- Artifact。\n+- Evidence。\n+- Memory / Skill。\n+\n+F003–F005 已落地：\n+\n+- Run event trace。\n+- File change trace。\n+- Evidence refs。\n+- Implementation → Validator。\n+- Evidence policy gate。\n+- Validation round / max rounds。\n+- Blocked / Unblock / Reset。\n+- Manual multi-provider routing。\n+- `context_source_run_id`。\n+- Provider identity snapshot。\n+- Workspace-aware adapter availability。\n+\n+这些能力已经覆盖 Graph Engineering 最难的部分之一：图执行结果的可验证性和安全边界。\n+\n+### 5.2 当前主要问题\n+\n+#### Topology 尚未真正承重\n+\n+`WorkflowTemplate` 有：\n+\n+- `collaboration_topology`\n+- `steps_json`\n+\n+但当前 runtime 仍主要由特定 service 编码顺序和状态转换。Topology 更接近描述字段，而不是通用可执行程序。\n+\n+#### Workflow Step、Run 和 Attempt 没有分层\n+\n+当前 `Run` 同时承担：\n+\n+- 一项逻辑工作。\n+- 某次 Agent 执行。\n+- 某次 Provider/Model 尝试。\n+- 状态机驱动对象。\n+\n+复杂图下，同一逻辑节点可能经历多次 attempt，因此必须分层。\n+\n+#### 只有单前驱 Context Source\n+\n+`context_source_run_id` 能清晰绑定一次 handoff，但只能表示一个上游。\n+\n+Fan-in 场景需要：\n+\n+```text\n+Synthesis Node\n+  inputs:\n+    - Research A artifact\n+    - Research B artifact\n+    - Security review evidence\n+```\n+\n+因此需要多对多 causal inputs。\n+\n+#### Workspace Lock 限制并行\n+\n+当前 workspace 写锁为正确性提供了重要底线，但也意味着同一 workspace 内多个写节点不能并行。\n+\n+第一阶段应只开放：\n+\n+- read-only research。\n+- read-only review。\n+- 独立外部数据查询。\n+- 不共享可变文件的并行任务。\n+\n+并行 coding 需要 worktree / branch / execution workspace 隔离后再开放。\n+\n+#### Evidence Summary 假设单实现、单验证\n+\n+当前 Evidence Summary 主要关联：\n+\n+- 一个 implementation Run。\n+- 一个 validator Run。\n+\n+多节点 Graph 需要汇总：\n+\n+- GraphRun。\n+- 多个 NodeRun。\n+- 多个 Attempt。\n+- Artifact lineage。\n+- 多 Validator / Join。\n+\n+#### Agent capability 粒度不足\n+\n+当前实现以 implementation / validator 为主。Graph 节点需要更丰富但仍受控的能力表达，例如：\n+\n+- code_implementation\n+- code_review\n+- security_review\n+- research\n+- synthesis\n+- citation_check\n+- host_diagnostics\n+- document_edit\n+\n+能力不能无限自由文本化，应有注册表、版本和兼容策略。\n+\n+## 6. 定位优化建议\n+\n+### 6.1 建议：保持 Agent Team OS 一级定位\n+\n+**理由：**\n+\n+1. Graph Engineering 是机制，不是用户最终购买或采用的结果。\n+2. “Agent Team OS”能覆盖 Issue、Workspace、Runtime、Evidence、Memory 和 Skill。\n+3. 直接定位 Graph Platform 会与 LangGraph、ADK、AutoGen 等开发框架进入同一心智区间。\n+4. PersonaHub 的差异在个人真实工作闭环，而不是提供另一个 SDK。\n+\n+### 6.2 建议：把 topology-aware 升级为 executable work graph\n+\n+当前：\n+\n+> issue-managed, topology-aware, evidence-grounded automation\n+\n+建议：\n+\n+> issue-managed, graph-orchestrated, evidence-grounded work\n+\n+或更完整地表达：\n+\n+> Turn personal issues into executable, verifiable, and continuously improving agent work graphs.\n+\n+**理由：**\n+\n+- topology-aware 容易停留在“知道拓扑类型”。\n+- executable 明确拓扑必须约束运行。\n+- work graph 可以统一 Workflow、Room、Handoff、Artifact 和 Evidence。\n+- graph 是二级能力表达，不抢走 Agent Team OS 一级品类。\n+\n+### 6.3 建议：坚持 Issue-first，不改成 Canvas-first\n+\n+**理由：**\n+\n+1. 用户目标通常以 Issue 表达，而不是以图开始。\n+2. 画布增加建模负担。\n+3. 自然语言 → Graph Draft 更符合 Agent 产品。\n+4. Thread 是人类理解过程和介入的最佳入口。\n+5. Graph Inspector 可以作为解释和调试视图，而不是默认创作入口。\n+\n+推荐 UI：\n+\n+```text\n+Issue List | Thread / Work Scene | Graph + Evidence Inspector\n+```\n+\n+## 7. PersonaHub Executable Work Graph v1\n+\n+### 7.1 核心设计原则\n+\n+#### Node 表达责任，不表达固定 Agent\n+\n+错误：\n+\n+```text\n+Node = Claude\n+```\n+\n+推荐：\n+\n+```text\n+Node = Security Review\n+required_capabilities = [security_review, code_read]\n+selected_executor = Claude\n+fallback_executor = Codex\n+```\n+\n+**理由：**\n+\n+- Workflow 可复用。\n+- Agent 可替换。\n+- 节点评价和 Agent 评价可以分开。\n+- Provider 失败不改变业务拓扑。\n+\n+#### Edge 是一等契约\n+\n+Edge 至少表达：\n+\n+- source / target。\n+- outcome。\n+- condition。\n+- payload mapping。\n+- routing authority。\n+- join policy。\n+- permission transition。\n+\n+**理由：**\n+\n+只用 `dependsOn` 无法承载 validation loop、human gate 和 failure recovery。\n+\n+#### Definition、Run、NodeRun、Attempt 分层\n+\n+```text\n+WorkflowGraphDefinition\n+  └─ GraphVersion\n+      └─ GraphRun\n+          ├─ NodeRun\n+          │   ├─ Attempt 1\n+          │   └─ Attempt 2\n+          └─ EdgeTraversal\n+```\n+\n+**理由：**\n+\n+- Definition 负责复用和版本化。\n+- GraphRun 记录某次 Issue 的实际拓扑。\n+- NodeRun 表达逻辑工作。\n+- Attempt 表达具体 Agent / Provider 执行。\n+\n+### 7.2 建议的定义模型\n+\n+```ts\n+interface WorkflowGraphDefinition {\n+  id: string;\n+  name: string;\n+  issueType: string;\n+  version: number;\n+  nodes: WorkflowNodeDefinition[];\n+  edges: WorkflowEdgeDefinition[];\n+  entryNodeIds: string[];\n+  terminalNodeIds: string[];\n+}\n+\n+interface WorkflowNodeDefinition {\n+  id: string;\n+  kind:\n+    | \"agent_task\"\n+    | \"deterministic_action\"\n+    | \"validator\"\n+    | \"router\"\n+    | \"human_gate\"\n+    | \"join\"\n+    | \"subgraph\"\n+    | \"terminal\";\n+\n+  title: string;\n+  objective: string;\n+  requiredCapabilities: string[];\n+\n+  inputContract?: SchemaRef;\n+  outputContract?: SchemaRef;\n+  artifactRequirements?: ArtifactRequirement[];\n+  evidenceRequirements?: EvidenceRequirement[];\n+\n+  executionPolicy: {\n+    maxAttempts: number;\n+    timeoutSeconds?: number;\n+    idempotencyScope?: string;\n+  };\n+\n+  resourcePolicy: {\n+    workspaceAccess: \"none\" | \"read\" | \"write\";\n+    networkAccess?: string[];\n+    credentialScopes?: string[];\n+  };\n+\n+  budgetPolicy?: {\n+    maxTokens?: number;\n+    maxCostUsd?: number;\n+    maxDurationSeconds?: number;\n+  };\n+}\n+\n+interface WorkflowEdgeDefinition {\n+  id: string;\n+  from: string;\n+  to: string;\n+  outcome: string;\n+  condition?: string;\n+  routingAuthority: \"system\" | \"coordinator\" | \"human\";\n+  joinPolicy?: \"all\" | \"any\" | \"quorum\";\n+  payloadMapping?: {\n+    artifactSelectors?: string[];\n+    evidenceSelectors?: string[];\n+    stateFields?: string[];\n+  };\n+}\n+```\n+\n+### 7.3 建议的运行模型\n+\n+```ts\n+interface GraphRun {\n+  id: string;\n+  issueId: string;\n+  graphDefinitionId: string;\n+  graphVersion: number;\n+  status: \"pending\" | \"running\" | \"completed\" | \"failed\" | \"blocked\" | \"cancelled\";\n+  definitionSnapshotJson: string;\n+  startedAt?: string;\n+  completedAt?: string;\n+}\n+\n+interface NodeRun {\n+  id: string;\n+  graphRunId: string;\n+  nodeDefinitionId: string;\n+  status:\n+    | \"pending\"\n+    | \"ready\"\n+    | \"queued\"\n+    | \"running\"\n+    | \"succeeded\"\n+    | \"failed\"\n+    | \"blocked\"\n+    | \"skipped\"\n+    | \"cancelled\";\n+  selectedAgentId?: string;\n+  attemptCount: number;\n+  outcome?: string;\n+}\n+\n+interface NodeAttempt {\n+  id: string;\n+  nodeRunId: string;\n+  runId: string; // 可先复用现有 Run\n+  agentConfigId: string;\n+  providerIdentitySnapshot: string;\n+  status: string;\n+}\n+\n+interface EdgeTraversal {\n+  id: string;\n+  graphRunId: string;\n+  edgeDefinitionId: string;\n+  sourceNodeRunId: string;\n+  targetNodeRunId?: string;\n+  outcome: string;\n+  decisionActorType: \"system\" | \"agent\" | \"human\";\n+  decisionActorId?: string;\n+  reason?: string;\n+  payloadRefsJson: string;\n+}\n+```\n+\n+### 7.4 存储建议\n+\n+#### Definition 可以使用不可变 JSON Snapshot\n+\n+原因：\n+\n+- Graph Definition 是版本化声明。\n+- 读取时通常需要完整编译。\n+- 不需要频繁按单条边事务更新。\n+- Snapshot 有利于历史回放。\n+\n+#### Runtime 必须规范化\n+\n+建议独立表：\n+\n+- `graph_runs`\n+- `node_runs`\n+- `node_attempts`\n+- `edge_traversals`\n+- `node_input_refs`\n+- `node_output_refs`\n+\n+原因：\n+\n+- 原子 claim ready node。\n+- 并发安全。\n+- 快速查询 blocked / running / retryable。\n+- 避免大型 state JSON 写冲突。\n+- 支持恢复和 AgentOps 聚合。\n+\n+### 7.5 Graph Compiler / Linter\n+\n+Graph Definition 在发布或执行前必须检查：\n+\n+- Node ID / Edge ID 唯一。\n+- Entry / terminal 存在。\n+- 无不可达节点。\n+- 所有 edge target 存在。\n+- 非 terminal 节点至少有一条可结束路径。\n+- 循环有明确 max rounds / termination condition。\n+- Join 引用合法前驱。\n+- Capability 可解析。\n+- Input / output contract 可连接。\n+- Write 节点并行冲突。\n+- Budget 上限存在。\n+- Human gate 与危险权限对应。\n+- Validator 的 evidence requirements 完整。\n+\n+**理由：**\n+\n+Graph 的价值之一是把隐式失败路径提前暴露；没有 compiler 的 Graph 只是更复杂的配置文件。\n+\n+## 8. 从现有 Coding Workflow 迁移\n+\n+### 8.1

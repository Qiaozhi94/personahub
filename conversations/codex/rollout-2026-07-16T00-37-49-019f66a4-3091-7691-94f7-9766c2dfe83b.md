### 1. `Run.role` 冲突成立，但建议采用第三种方案

[F004 design](D:/Projects/personahub/docs/features/0.1/F004-autonomous-validation/design.md:159) 定义：

```sql
role TEXT NOT NULL DEFAULT 'implementation'
```

而 [F005 design](D:/Projects/personahub/docs/features/0.1/F005-multi-agent-manual-routing/design.md:145) 又定义：

```ts
role: RunRole | null
```

检视意见对此判断完全正确。但其提出的两个方案都不是最优：

- 重建 `runs` 表允许 null：migration 成本较高。
- consult 在 DB 存 `implementation`、DTO 投影 null：会产生错误的持久化语义，查询和统计容易踩坑。

更干净的方案是：

```ts
enum RunRole {
  Implementation = "implementation",
  Validator = "validator",
  Consult = "consult",
}
```

保持数据库 `NOT NULL`，consult Run 持久化为 `role='consult'`。`purpose='ad_hoc_consult'` 表达是否驱动 workflow，`role='consult'` 表达本轮承担的角色。F004 的 validator partial unique index不受影响。

### 2. validator context 问题成立，但不能把所有 Run 都改成绑定 implementation

[F004 design](D:/Projects/personahub/docs/features/0.1/F004-autonomous-validation/design.md:300) 和 [F005 tasks](D:/Projects/personahub/docs/features/0.1/F005-multi-agent-manual-routing/tasks.md:104) 当前都使用 latest handoff。

检视给出的场景确实会发生：

```text
implementation 完成
  -> 进入 Validating grace
  -> consult Run 完成并产生更新的 handoff
  -> validator 错误读取 consult handoff
```

但“统一把 F005 context 都绑定 `implementation_run_id`”过于宽泛。正确规则应分两类：

- validator Run：严格读取其 `implementation_run_id` 对应的 handoff、file changes、verification evidence。
- 普通 implementation/consult Run：仍读取创建时间早于当前 Run 的 latest eligible handoff。

因此应让 `RunContextBuilder` 接受明确的 source policy，而不是全局改掉 latest handoff：

```ts
type ContextSource =
  | { kind: "target_implementation"; runId: string }
  | { kind: "latest_prior_handoff" };
```

F004 spec 的 `FR-002`/`AC-002` 也应同步明确“目标 implementation Run 的 handoff”，不应只改 design/tasks。

### 3. capability 双真相源问题成立

F004 自动选择器仍使用：

[AgentConfigRepository.listAvailableByProjectAndRole](D:/Projects/personahub/docs/features/0.1/F004-autonomous-validation/design.md:253)

[F005 capability contract](D:/Projects/personahub/docs/features/0.1/F005-multi-agent-manual-routing/design.md:114)

- `capability_tags` 是能力判断真相源。
- `agent_configs.role` 仅作为旧数据迁移来源或主要展示角色，后续不参与自动选择。
- 增加专门任务，修改 `ValidatorSelector`、repository 查询及相应测试。

### 6. FIFO/queued Run 问题成立，而且需要明确启动资格

[F004 design](D:/Projects/personahub/docs/features/0.1/F004-autonomous-validation/design.md:70) 已规定：

```text
trace finalize -> release lock -> workflow hook -> drain
```

但 hook 只保证 validator 在 drain 前被创建，不保证它会被第一个取出。更早排队的同 Issue implementation Run仍可能先启动。

建议在每次 queue drain 时重新验证 eligibility：

```text
implementation -> Issue 必须为 Inbox / Ready / Running
validator      -> Issue 必须为 Validating，且 round 匹配
consult        -> Issue 必须为非终态
```

不再符合状态的同 Issue queued Run应取消并写：

```text
run.cancelled
reason = issue_state_changed_before_start
```

随后继续寻找下一条 eligible Run。不同 Issue、同 workspace的更早 Run仍保持FIFO，不必为了 validator破坏全局workspace队列顺序。

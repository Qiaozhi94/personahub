## 🔴 Critical

**1. `preflight.ts` 的 glob→regex 转换有 bug，`**` 递归通配符实际上只能匹配 0~1 层目录，测试也未覆盖**（`server/src/runtime/graph/preflight.ts:13-19`）

`globToRegex()` 分两步 `.replace`：第一步把字面量 `**/` 替换成正则片段 `(?:.*/)?`，第二步再对**整个字符串**做 `.replace(/\*/g, "[^/]*")`——这会把第一步刚插入的 `.*` 里的 `*` 也当成通配符再处理一遍，把 `.*` 破坏成 `.[^/]*`，且外层 `(?:...)?` 的 `?` 只允许出现 0 或 1 次。实测：

```
globToRegex("**/*.ts").source === "^(?:.[^/]*\/)?[^/]*\.ts$"
test("server/src/foo.ts")          -> false   （2 层目录，本仓库典型路径）
test("server/src/services/foo.ts") -> false   （3 层）
test("src/foo.ts")                 -> true    （1 层，凑巧通过）
```

而 design.md 选定的首个真实场景（第 5 节）恰恰就是"审查 PersonaHub 自身代码"，definition 的 `targetGlobs` 是 `["**/*.ts", "**/*.tsx", "**/*.sql"]`（`definitions.ts:7`）——本仓库绝大多数源文件都在 `server/src/...`、`web/src/...` 这类 2~3 层路径下。也就是说这个功能在自己最主要的验收场景上会**扫不到目标文件**，大概率直接撞上 `GRAPH_TARGET_SET_EMPTY` 被建图前拒绝。`graph-repositories.test.ts` 等测试都是直接构造 `target_files` 字符串数组，没有一条测试真正跑过 `prepareGraph()` 对多层目录的 glob 匹配，所以这个 bug 完全没被发现。

## 一句话结论

AgentSpace 在 **agent-router 归一化层、task-attempt/session 状态机、权限聚合图、persona 签名** 这几处工程深度确实很高，不是空气项目；但 **sandbox 隔离层是明确的 stub**（`CubeSandbox.exec()` 直接 `throw`,代码里自己写着 "TODO 46 未完成"),多租户 `workspace_id` 校验也是分散在几十个文件里手写、缺乏中心化强制。PersonaHub 规模小得多,但在它选择打磨的那一个点（adapter 可用性收敛的并发正确性）上,反而做到了 AgentSpace 没有的 CAS token 级别严谨度。两者不是同一量级的"广度 vs 深度",更关键的是——**它们其实在解决两个不同的问题**。

## 关键发现：`workspace` 同名不同物

这是最容易被误读的一点：

| | AgentSpace 的 `workspace` | PersonaHub 的 `workspace` |
|---|---|---|
| 语义 | **组织/租户边界**——多个人类成员共享的协作空间(类比 Slack 的一个团队) | **本地目录+git分支的执行互斥锁单位**（`workspaces` 表 `local_path`/`git_branch`/`lock_state`,同一时刻只能被一个 Run 占用） |
| 隔离的对象 | 人类成员的权限、频道访问、文档所有权 | 某个 CLI adapter 在某个具体代码目录+凭证环境下是否可用（`adapter_workspace_status` 表） |

两边都叫 workspace,但一个是"团队",一个是"检出的代码目录",完全不是一回事,对比时如果不拆开会得出错误结论。

## 分模块对比

**1. Provider adapter 层**

AgentSpace 有统一的 `HarnessAdapter` 接口（`detect/buildLaunch/run/normalizeError`）+ `AgentRouterEvent` 联合类型 + 细分诊断枚举（`cli_missing/auth_required/tool_permission_denied/timeout/exited_nonzero`…),Claude adapter 甚至实现了 `control_request/control_response` 双向协议做**运行时工具权限审批桥接**——这是真正的工程活,不是简单包一层 CLI。

PersonaHub 的策略相反：`claude-pretooluse-hook.ts` 明确注释"auto-accepts every other command approval request (F002 P0 policy)"——**所有工具调用自动放行,不做审批桥接**。这是刻意的简化（个人单机场景,人机之间没有第三方需要被保护）,不是能力缺失。

**2. 质量把关机制——这是两者真正的哲学分歧**

AgentSpace 的"治理"是**人工审批**:高风险动作路由到人类,人点"批准/拒绝"。
PersonaHub 的"治理"是**另一个 agent 自动裁决**:Implementation Run 跑完 → Validator Run 自动检查 → `evidence_summaries` 表甚至有 `CHECK (validation_result = 'passed')` 约束,只有验证通过的产出才会落盘。人类唯一的介入点是**发起**一次 Run,而不是审批某次 Run 的输出。

这不是谁更先进的问题,而是两个场景的默认信任模型不同：AgentSpace 假设"团队里可能有恶意或失误的人/agent 动作需要人来把关";PersonaHub 假设"个人开发场景下,该被信任的是自动化验证闭环,而不是让用户自己盯着每一步"。

**3. 多 agent 协作粒度**

AgentSpace 有更结构化的编排字段（`orchestrationRunId/stepId/stepDependsOnIds/handoffSnapshotId`),暗示更接近"任务图"的编排模型,但交接内容仍是"文档 ID 引用 + 最新 handoff 快照文本"塞进 prompt,不是结构化 API 调用。
PersonaHub 更直白："上一个已完成的 Implementation Run 输出" → `context_source_run_id` → 塞进下一个 Run 的上下文,外加 repair context（把上一轮 validator 的 findings 注入下一轮 instructions）。本质都是**接力式**传递,不是真正的多 agent 并发协同会话——这一点上两者其实处于相近的成熟度,AgentSpace 的字段更丰富但落地方式类似。

**4. 隔离执行的真实程度**

AgentSpace 的 `LocalSandbox` = 直接 `child_process.spawn`+路径穿越校验,**没有容器/namespace/cgroup 隔离**;`CubeSandbox`(远程沙箱)的核心 `exec()` 是显式抛错的占位符。
PersonaHub 同样是本地直接 spawn CLI 子进程,靠的是 workspace 级 credential 隔离（避免跨 workspace 泄漏 API key/model provider）而非进程沙箱。

**结论：在"真实执行隔离"这一层,两个项目目前处于同一个(都不高)的水平**——AgentSpace 的优势全部体现在执行**周围**的权限/审批/审计层,而不是执行本身的隔离强度。

**5. Persona 可移植性**

AgentSpace 有真实的 ed25519 签名 + `did:key` 派生（对齐 `@5dive/openagent` 规范）,可以把一个配好的 digital employee 导出成签名 persona-card 供第三方工具验证。PersonaHub 没有对应机制——单用户场景下暂时也没有跨组织分享 agent 配置的需求。

**6. 规模对比**

AgentSpace：PostgreSQL,约 61 张表,覆盖组织/权限/任务/技能知识/外部集成(Feishu/Google Workspace)/计费审计等 8 大类;PersonaHub：better-sqlite3,7 个 schema 迁移文件(v1-v7),规模小一个数量级,精确匹配"单用户本地工具"的定位,没有多余的表。

## 给你的建议

这两个项目不是同一条赛道上的竞品——AgentSpace 在做"团队级 agent 协作平台"(对标企业 IM),PersonaHub 在做"个人研发自动化闭环"(核心资产是 Validator 自动裁决机制,这一点 AgentSpace 完全没有)。没必要因为对方 provider 数量更多、star 更高就觉得需要对标广度;如果要借鉴,AgentRouter 的 `HarnessAdapter` 统一接口设计和诊断枚举分类值得在未来扩展 provider 时参考,但组织级权限治理、远程 daemon、sandbox 这些方向,以 PersonaHub 当前"个人优先"的定位来看没有引入的必要。

## P0 — 收益明确,建议纳入规划

### 1. Provider 原生 session 续接

**现状核实**:PersonaHub 的 `AgentRunInput`(`server/src/runtime/types.ts:11-32`)完全没有 session token 字段,每个 Run 对底层 CLI 都是**全新开一个进程**,跨 Run 的上下文靠把上一轮产出重新拼进 `context` 文本喂给下一轮(`context_source_run_id` + Handoff Packet)。

**AgentSpace 的做法**:`agent_router_session → provider_session → task_attempt` 三层表模型,Claude adapter 会传 `--resume <sessionId>`(`claude.ts:91-93`)续接 CLI 自己的原生会话,而不是每次都把全部上下文重新序列化成文本塞进 prompt。

**为什么值得借鉴**:
- 原生 session 里保留的是 CLI 自己维护的完整对话状态(工具调用历史、文件编辑记忆、内部 todo 跟踪),这些东西 Handoff Packet 这种"摘要式"文本重建天然会丢信息;
- 同一 Thread 内连续多个 **Implementation** Run 打在同一个 adapter 上时,续接原生 session 大概率比重新构建 context 更省 token、连贯性更好;
- 实现成本不高:在 `RunExitResult` 里多捕获一个 adapter 返回的 session id,存到 `runs` 表,下一个同 adapter/同角色的 Run 里如果命中就传 `--resume`。

**需要注意的 nuance**(AgentSpace 没有这个问题,但 PersonaHub 有):Validator Run 大概率**不应该**续接 Implementation Run 的原生 session——校验需要相对独立的视角,续接会让 validator "看到"实现过程中的推理痕迹,可能污染判断的客观性。所以这个机制应该限定在"同一 Thread 内连续同角色(通常是 Implementation)的 Run 之间",而不是无差别续接。

### 2. 危险命令的分级暂停确认,而不是"只拦 git push,其它全自动放行或直接判 Run 失败"

**现状核实**:`shell-command-patterns.ts` 目前**只硬编码拦截了 git push 一种命令**,命中后直接终止整个 Run(`FR.PreExecutionApprovalRejected`/`FR.CredentialIsolationBlocked`),没有"暂停等待用户确认后继续"的能力;其它危险操作(如 `rm -rf`、`git reset --hard`、`DROP TABLE`)完全没有拦截,走的是 F002 的 auto-accept 策略。

**AgentSpace 的做法**:Claude adapter 实现了 `control_request/control_response` 双向协议(`claude.ts:330-385`),可以让子进程在执行到某个工具调用时**真的暂停**,等外部决策后再继续,而不是简单的"放行"或"整体失败"二选一。

**为什么值得借鉴**:这其实和你自己在 CLAUDE.md 里写给我的操作原则是同一个问题——"不可逆/影响面大的操作应该确认后再做"。目前 PersonaHub 对这类风险只有"永远自动放行"和"整个 Run 直接失败"两个极端,没有中间态。可以参考 AgentSpace 的协议结构,给 Claude/Codex/OpenCode adapter 加一个轻量的"命中风险模式(可配置正则列表:强制推送、删除、重置、drop 等)→ 暂停子进程 → 通过现有的 UI 通知机制询问用户 → 用户确认后继续/终止"的桥接层,而不是像现在只对 git push 特判、其它危险命令完全放任。这不需要做成 AgentSpace 那种组织级审批工作流,单用户场景下一个"暂停+本地确认"就够。

## P1 — 值得研究,收益中等

### 3. Adapter 不可用原因结构化,而不是三态 + 自由文本

**现状核实**:`AdapterStatus`(`shared/src/types/index.ts:214-218`)只有 `Unknown/Available/Unavailable` 三态,失败原因靠 `validateCommand` 返回的自由文本 `errorMessage`(`adapter-config.ts:60-68`),没有结构化分类。

**AgentSpace 的做法**:`AgentRouterDiagnostic.code` 是个明确的枚举(`cli_missing/auth_required/auth_invalid/empty_response/protocol_parse_failed/timeout/exited_nonzero`)。

**建议**:把 `errorMessage` 这个自由文本升级成一个诊断 code 枚举(命令未找到 / 从未验证过 / 鉴权过期 / 探测超时 / 探测输出异常),UI 上可以按分类给出不同的修复引导文案,而不是让用户自己读一段拼出来的字符串猜原因。这个改动量不大,主要是把现有 `errorMessage` 里已经隐含的几种情况显式分类。

### 4. Adapter 健康的主动巡检视图(借鉴 AgentSpace 的 PermissionDiagnostic 思路)

AgentSpace 有 `getPermissionDiagnosticsSync` 系统性列出"孤儿授权/已吊销凭证/不可用 provider"。PersonaHub 目前 adapter 状态是被动的(用户点 Validate 才知道),可以加一个轻量的"健康巡检"视图:比如某 adapter 超过 N 天未被验证过、某个 workspace override 指向的本地目录已经不存在了,主动提示而不是等用户手动点 Validate 才发现。优先级不高,算是锦上添花的可观测性改进。

## P2 — 了解即可,不建议做

- **Persona-card 签名导出、`did:key` 机制**:解决的是"agent 配置跨组织可移植"的问题,单用户本地工具没有这个需求,不必引入。
- **组织级权限聚合图 / 多租户模型**:PersonaHub 没有多用户概念,这套东西整体不适用,连简化版都没必要做——引入了反而是给自己制造不存在的问题。
- **Sandbox 隔离层**:两边目前都是直接 spawn 本地子进程、没有真正的容器隔离,AgentSpace 自己这块也是 stub,没有现成经验可抄,如果 PersonaHub 未来要做进程隔离,得独立调研,不是"借鉴"AgentSpace 能解决的。
- **远程 daemon 分布式执行**:偏离个人本地工具定位,不建议引入。

## 优先级排序建议

如果只挑两件事先做,我会挑 **#2(危险命令分级确认)** 和 **#1(同角色 session 续接)**——前者是安全默认值的真实缺口(现在除 git push 外无防护),后者是能直接提升现有核心体验(上下文连贯性、成本)的性能类改进。#3/#4 是锦上添花,可以等前两个稳定后再排期。

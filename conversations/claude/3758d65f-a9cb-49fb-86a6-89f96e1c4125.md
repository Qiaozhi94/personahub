## UT vs 集成测试

用本仓库的两个真实文件对比最清楚：

| | `queue-classifier.test.ts`（UT） | `workflow-template-admin.test.ts`（集成） |

| 数据从哪来 | 手工构造的普通对象（`makeIssue()`） | 真实 SQLite 临时库 + 跑完整迁移 |
| 测的边界 | **一个纯函数** `classifyQueuedRun(issue, run)` | 从 HTTP 请求 → route → service → 事务 → 落库 |
| 失败时你知道什么 | 精确到那一个函数的那一个分支 | 知道链路坏了，但要自己定位坏在哪一层 |
| 速度 | 毫秒 | 每个用例都要建库跑迁移 |

## 核心区别：被测边界的大小

- **UT**：把一个单元从系统里**摘出来**测，依赖全部替换成假的。它证明"这段逻辑本身对"。
- **集成**：让多个真实组件**按真实方式协作**。它证明"这些组件拼起来还对"。

## 关键：它们抓的是不同的 bug

这个项目的 3 个 dogfood bug 全是集成层的：

- BUG-001：scheduler claim 后**忘了调 drain** —— claim 的逻辑本身完全正确，UT 全绿。是两个组件之间的**缺失调用**。
- BUG-002：apiFetch 无条件设 `Content-Type`，Fastify 拒空 body —— 前后端各自都"对"。
- BUG-003：中断的 validator 死锁 round 槽位 —— 状态机跨多次调用的时序问题。

**UT 永远抓不到"A 忘了调 B"**，因为 UT 里 B 是假的。

## 所以 34:2 这个比例不是问题

PersonaHub 的核心风险就是 SQLite 事务、workspace 锁、Run 状态机的**跨组件时序**——那正是集成测试的靶心。纯 UT 只在逻辑分支多、依赖少的地方划算，比如 `validateStepsSchema`（16 个拒绝分支）和 `classifyQueuedRun`（状态×角色矩阵）——本仓库那 2 个 UT 文件恰好就是这两个，选得很准。

**一句话判据**：分支组合爆炸但不碰 IO → 写 UT；跨组件、碰 DB/锁/事务 → 写集成。别为了"金字塔比例好看"给后者补 UT。

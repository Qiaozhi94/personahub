# PersonaHub V3.1 页面结构与功能设计

> V3 承接 V2 的对象模型、用户语言和视觉语言，**只改布局与主次关系**。
> 变更起因见第 8 节「与 V2 的差异及理由」。
>
> **实现约束见 [`implementation-notes.md`](./implementation-notes.md)**：V3.30 起，界面上只留「会发生什么」与「该怎么做」，一切写给实现者的硬规则按面归档在那份文档里，实现前逐条核对。这份文档记「为什么这样设计」，那份记「实现这一块时不能违反什么」。

## 修订记录

| 版本 | 改了什么 | 起因 |
|---|---|---|
| V3.44 | **记忆职责最终拆成四个落点，并补全最终形态**。①「待确认」与「待处理」合并为**待办**，按新候选 / 需要复核 / 整理建议互斥分组；②记忆策略移到**设置 · 工作区 · 记忆**，主面不再复制配置；③新增**设置 · 应用 · 系统诊断**，统一承接服务、数据库、事件流、记忆写入、索引与召回、磁盘快照；④记忆效用移到**统计 · 记忆效用**；⑤知识图谱补齐一跳 / 两跳、关系筛选、节点详情与关系明细；⑥Skill 详情改为带面包屑的整页下钻，只保留关键信息与文件。 | 使用者连续追问记忆职责、系统诊断与最终交付完整度，并要求 Skill 详情阻断跨 tab 跳转、删减重复内容。最终判据是：**内容去记忆，策略去设置，故障去诊断，价值去统计；详情页只保留决策所需事实，同一信息只出现一次。** |
| V3.43 | **记忆面按「待办 / 读数」重切，并补上三处缺口**。①**「健康度」改名「待处理」，只留记忆债务那一张表**——原来那一页装了三张表，第一张是待办清单（每行都有操作按钮），后两张是读数；**「健康度」是个状态词，它承诺「好还是不好」，装的却是一份清单**，抓不住是必然的。**写入通路**与**效用**两张读数移到策略，和召回阈值放一起，形成闭环：看效用 → 调旋钮 → 试一次召回。②**策略新增「试一次召回」**：输入一段任务描述，看这次会带上哪几条、过滤掉哪几条、占多少 token；**过滤掉的也列出来并写明为什么**——看不见被挡掉的就判断不了阈值设得对不对。此前策略给了「每次最多 12 条」「预算 8000 token」这些旋钮却**没有任何地方能看效果**。③**知识库补两列**：`最近召回`（策略里设了「180 天未召回提示退役」的阈值，界面却没这个数）与 `引用 · 采纳`（引用是「被提到过几次」，采纳是「改变过几次做法」，**决定要不要留一条看的是后者**）。④**知识库与知识图谱互通**：行内详情给「在知识图谱里看 →」，图谱给「回知识库看这一条 →」。另修两处：墓碑那一行少一个格子；策略里的表名「索引与运行时」与一级面「运行时」撞名 | 使用者：「健康度为什么里面是三个表格呢，我抓不住健康度这里是做什么的」，以及采纳上一轮提的三条建议。这一轮的判据可复用：**一个 tab 的名字要和它里面每一行的动作对得上**——待办清单叫「待处理」，读数跟着它能调的旋钮走 |
| V3.42 | **执行组合拆成「模型」与「思考深度」两个下拉**，照派工弹窗（§4.6）的口径：模型那一栏写 `GPT-5.6 · Codex CLI v2.4.1`（adapter 与模型合一，因为它们一起决定单价与能力），深度单独一栏，下面一行**现算的组合预览**「将派给 `claude-sonnet5-low`」。**模型不支持的深度直接置灰**——`Kimi K2` 只有 low，选它时 medium / high 变灰并把深度回落到 low。合成一个下拉的问题是：想换个深度得重新在十几条组合里找同一个模型的另一条。同时「重复触发」挪回触发条件那一卡，两列重新平衡到 4 / 3，编辑态由 910px 收回 773px（1512×950 下不滚动） | 使用者：「执行组合选择时将 adapter 和模型一个下拉框，思维深度一个下拉框分开选择更灵活一些，样式参考任务选项中派活的模型选择位置」。这与 ADR 0012 的四元组一致：`adapter + 配置 + 模型 + 深度` 里，**深度是「每次派工可调，不烧进配置」**的那一维，本来就该单独选；把它和模型编成一个字符串是展示用的组合名，不是输入方式 |
| V3.41 | **撤回 V3.40 的三档产出，并把属性页排版压紧**。①「产出」整块从创建器与属性页移除——V3.20 的原判据恢复生效：**自动化建立的永远是普通任务**。②属性页从竖排四块改成 **`[触发条件 ｜ 执行组合] + 任务内容`**：前两块并排（都短，竖排是在浪费横向空间），字段在两列间重新分配到平衡（4 / 3）；**只读事实改成「标签在左、值在右」的一行一条**，不再是标签占一行、值占一行；卡片内边距 16 → 12，区块间距 26 → 20。实测只读态 773px、编辑态 773px，**都不需要滚动**（改前编辑态 858px 要滚） | 使用者：「不需要产出，同时排版还有问题，现在太浪费空间了」。产出这一档从提出到撤回只隔了一个版本——它解决的噪音问题是真的，但**三档摆在界面上的成本高过它省下的那点噪音**；真要做，正确的形态是让规则自己判断有没有发现，而不是让人先选一个模式。排版那条给出一条可复用的判据：**只读事实用两列（标签 76px + 值），可编辑字段才用上下两行**——前者是扫，后者是填 |
| V3.40 | **推翻 V3.20 的「不提供仅运行模式」，改成三档产出**。创建器与属性页新增**每次触发产出什么**：`每次都建任务` / `只在有发现时建任务`（默认）/ `仅运行，不建任务`。标题下那行 meta 同时收窄成 `项目 · 近 30 天运行概况 · 最近一次结果`——工作流、权限、标题模板都在别处说过，不重复；创建器的时间表预览也去掉了残留的 cron | 使用者：「multica 里创建时会询问是否新建任务或者仅运行，我觉得这个可以加上」。**V3.20 的原判据是对的**：后台静默跑会形成第二套不可验收的结果，绕开 Issue / Run / Artifact / Evidence 的来源链。但它把一个真实需求也一起否掉了——**一条每天跑的检查，大部分时候没有发现，每次都建一条任务就是噪音**。三档的中间那一档正是这个需求的准确表达：**它不是「不建任务」，而是「无事发生时不建任务」**——有结果的时候一定有任务，来源链不断。第三档保留但**把代价写在选项旁边**（不进验收链、不写记忆），不藏进文档 |
| V3.39 | **自动化详情收成「标题带全部只读事实 + 三块可改的东西」**。①生成的任务那一行卡片**收成标题下的一行 meta**（项目 · 标题模板 · 工作流 · 权限），只读事实不再占用主区一屏。②**「概览」改名「属性」**——它装的是这条规则**是什么**，不是一份摘要。③**触发条件不再摆 cron**：只读态写「每周 · 周一 09:00」「下次运行 明天 09:00 · 还有 18 小时」，编辑态照 multica 做成 `频率 + 具体日 + 时间 + 时区 + 下次运行预览` 的结构化选择器，**不让人写 cron 表达式**；Webhook 那一侧同理，`HMAC-SHA256` / `Idempotency-Key` / `issues.opened` 换成「签名校验 必须」「按投递 key 去重」「只接收新建 issue」。④**执行组合补成可编辑**，只列当前可派工的组合。属性 tab 由此是三块：触发条件 · 执行组合 · 任务内容，且**三块都可编辑**，其余全部只读 | 使用者：「卡片内容放在标题下方简洁显示，概览改名属性，触发条件不要显示 cron 表达式，显示普通人能看懂的结构化表达，编辑态也需要对执行组合编辑，编辑态也不要编辑 cron，参考 multica 的时间表编辑样式」。核对 multica：它的时间表编辑就是 `weekly ▼ / 1 ▼ / 14:00 / Shanghai GMT+8`，下面一行 `下次运行：Mon, Aug 17, 2:00 PM · 2 天 15 小时`，**全程没有 cron**。协议名同理——`HMAC-SHA256` 是实现细节，使用者要判断的是「验不验签」 |
| V3.38 | **自动化概览收成三层 + 记忆按 clowder 的分法拆开**。①自动化：**简要描述进标题下方的灰字**；**生成的任务改成一行卡片排最上**（项目 / 标题 / 工作流 / 执行组合 / 权限）；**权限降为只读一张卡**——自动化的权限跟项目走，不在这里单独设；**可编辑的只剩触发条件与任务内容**，其余一律只读；**启用状态从一个 pill 改成明显的开关**，关掉时文字变「已暂停」并说明后果。概览由此只剩「卡片行 + 触发条件 + 任务内容」。②记忆：**「关系」改名「知识图谱」**（不自造词），页首改成「检索一条知识，看它由什么推出、被谁引用、和谁冲突」；**检索基础设施（索引同步 / 分词回退 / 关系 / 语义召回）整块从健康度移到策略**——健康度只留知识本身的质量、写入侧与效用三块 | 使用者七条，其中记忆那条要求「查一下 clowder 记忆模块的设计」。核对结果写进 §3.6.6：clowder 把记忆分成六个面，关键是它**把「索引状态」与「健康度」分开**——前者是检索基础设施（嵌入服务、向量表、重建），后者是知识质量（矛盾、过期、孤立边、缺验证）。PersonaHub 的健康度此前把两者混在一页，处理动作完全不同（重建索引 vs 逐条复核） |
| V3.37 | **自动化概览合块 + 记忆策略独立成 tab + 三个面的页首改写**。①「执行内容」与「生成的任务」并成一块**任务内容**——两块并排时读不出差别，而使用者要写的其实就是**一份 Markdown 文本**；只读态渲染、编辑态给源码，**排在概览最后**（它最长，排前面会把其余四块顶到屏幕外）。概览新增**简要描述**排第一。②**记忆新增「策略」tab**：写入（自动入库条件）· 类型与强度白名单 · 召回（路数、条数、上下文预算）· 保留（退役与遗忘）· 索引；原来散在待确认页里的「低风险自动入库」开关与「confirmed 只能由你来做」两段随之撤离。③**能力 / 记忆 / 统计三个面的页首改成「标题在上、一句面向使用者的解释在下」** | 使用者：「自动化概览内容很多且混乱，执行内容和生成的任务重复，其实就是任务内容文本（用 md 预览呈现），允许人为修改，内容会比较多所以放最下方，概览页想加一个简要描述」「能力、记忆和统计三个选项标题放最上面，下方面向用户简洁解释」「记忆里低风险自动入库的开关和 confirmed 那段文字比较多余」「记忆的配置放记忆的新 tab 还是设置的子目录」。最后一问的答复见 §3.6.5 |
| V3.36 | **运行时不做任务控制**。adapter tab 的「运行中」去掉停止 / 结束按钮，改成只读，并指出停止在统计 · 监控或任务本身。> **判据：一个面的动作集合要和它的中心问题一致。** 运行时回答「我有哪些执行资源、每一样是什么状态」，中止一次执行回答的是「这一次活儿还要不要继续」——后者属于任务，不属于资源。V3.33 已经把跨机器的「正在执行」整表移到监控并保留停止入口，V3.34 却在 adapter tab 里把停止按钮又加了回来，等于同一个动作有两个入口，而其中一个所在的面并不为它负责 | 使用者：「运行时里的运行中任务不允许停止和结束，这里只负责管理运行时相关的配置，不是中止任务或对话的地方」 |
| V3.35 | **工具不只有 MCP**。原来那一块只写「已注入 4 个 server」，把 **CLI 自带的工具**（读文件 / 写文件 / 执行命令 / 网络请求）整个漏掉了——而它们的状态恰恰会变：OpenCode 的写文件**不请求授权**，直接落盘；项目关掉网络时网络请求这一项不可用。改成一张表：`工具 · 类型 · 来自 · 状态 · 说明`。**类型**（MCP / 文件 / 命令 / 网络）回答「这是哪一类能力」，**来自**回答「谁提供的」（CLI 内置，或哪个 MCP server）——两个问题分成两列，全部工具在同一张表里看。**缺席逐条标**：OpenCode 那四个 MCP 工具各自标「未注入」，而不是笼统一句「这个 adapter 不注入 MCP」。另两处：adapter tab 的内容**去掉 780px 限宽**，铺满右侧；概览四张卡**一行铺开**（1400px 以下降为两列，900px 以下一列） | 使用者：「adapter 的 tab 页里内容宽度不对，概览卡片放在一行显示，工具除了 mcp 还有其他的工具吗，建议改为表格直观呈现」。这一问指出了一处真的遗漏：**能力位里「权限拦截」「原生记忆」这些事实此前只写在「不支持」那一块，而它们本质上是工具的状态**——「写文件之前会不会问你」就是写文件这个工具的状态，写在别处等于让人自己去对应 |
| V3.34 | **「配置」这一层按需露出**——这一版最实质的一条。ADR 0012 把 adapter 与配置切成两层，起因是 **OpenCode 一个安装能同时挂两套凭据**；而 codex 与 claude-code **一个安装只有一种配法，凭据还在 CLI 自己手里**。此前界面对三者一视同仁地摆出「配置卡 + 删除配置」，于是出现了一个使用者答不上来的问题：**这个「删除配置」删的是什么？** 规则改为：**只有一个 CLI 真有多套接入方式时，才出现可增删的「接入方式」这一块**；单一配法的 adapter 只给只读事实与终端登录命令。界面上「配置」正名为**接入方式**——一份接入 = 一套地址 + 一套凭据。其余六处：①左栏标题改**远程**；②adapter **状态只有在线 / 离线**，不在列表里评估额度；③adapter 列表加**使用方式**列与**额度**列（订阅给简单限额，按量写不设上限）；④adapter tab 的概览**改成卡片**（状态 / 接入方式 / 额度 / 可用模型），信息量压掉一半，「不支持」只在真有限制时才出现；⑤**插件不再有「同名冲突」**——重名直接拒绝导入，冲突不该先被造出来再让人选；⑥通知去掉邮件渠道；⑦代码仓弹窗**去掉名称字段**（从仓库或目录名读出来），**提交身份并进 GitHub 卡**并改为读执行机器上的 `git config`，PersonaHub 不另存一份 | 使用者：「cli 的配置不是在各个 cli 里管理的吗，你这里的删除配置删除的是什么呢……multica 好像没有配置这么一说，clowder 倒是可以配置 apikey 或 oauth，但当前项目借鉴的是 multica 这一套」。核对属实：multica 的运行时页只有 `运行时 / 健康度 / 智能体 / 费用 / CLI` 五列，没有配置层；clowder 有，因为它确实存凭据。PersonaHub 两种都要支持，所以正确的规则不是「都有」或「都没有」，而是**按这个 adapter 有没有多套接入方式决定这一块露不露**。另五条来自同一轮：插件为什么会有名称冲突、通知先去掉邮件、代码仓不需要名称、提交身份与 GitHub 连接重复、执行机器改叫远程、健康度只要在线离线、概览改卡片 |

## 1. 设计结论

**PersonaHub 的主舞台是「成果面」——一份随工作推进不断生长的任务文档。**

它一开始只有目标和完成要求；Agent 每推进一步，它就长出产出、证据和决策；完成时它本身就是交付物。任务从「一张目标」长成「一份可信成果」，舞台全程显示同一个东西的当前形态。

```text
左栏（248px）  定位：一级入口 + 任务列表 + 资源库分节
主舞台（~60%） 成果面：这件事现在做成什么样了、可不可信
右栏（440px）  协作 Dock：谁在做、下一步交给谁
```

### 1.1 为什么是「成果面」

| 参考产品 | 主舞台 | 中心问题 |
|---|---|---|
| Multica | 任务文档 / 看板 | 要做什么 |
| Clowder | 会话流 | 正在说什么 |
| Obsidian | 笔记 | 我写下了什么 |
| **PersonaHub** | **成果面** | **现在做成什么样了、可不可信** |

三条理由：

1. **它是 PersonaHub 独有承诺的载体。** 计划管理 Multica 有，聊天 Clowder 有；只有 Artifact + Evidence + Provenance 构成的「可信交付」是 PersonaHub 独有的。舞台必须承载它，否则产品的独特性在界面上看不见。
2. **它匹配真实的高频动作。** PRD §6「第一屏」与 `user-journeys` 的 P0 常态是同一件事：**看一眼成果，决定下一步交给谁。** 这是审阅 + 决策，既不是读文档也不是聊天。
3. **它对三种用途都成立。** 见 §1.2。

### 1.2 三种用途的同一张舞台

| 场景 | 舞台上是什么 | 左栏资源库里是什么 |
|---|---|---|
| 代码开发 | 改了 3 个文件 · 24/24 通过 · 独立验证一致 | 项目文档、PRD、决策记录 |
| 书籍拆解 / 写作 | 拆解稿现在写成什么样 · 覆盖了哪些章节 · 引用来源 | 原书、笔记、参考资料 |
| 系统排障 | 查到哪了 · 结论是什么 · 凭什么这么说 | 日志归档、历史案例 |

V2 的「文档画布 + 协作 Dock 对半」只有代码场景勉强成立；写作场景下右侧会话基本闲置。

## 2. 核心对象关系

```text
Space
├─ AI Members
├─ Skills
└─ Projects
   └─ Project
      ├─ Workspace：真实文件和执行边界（机器的工作区）
      ├─ Resource Library：文档、笔记、素材、知识（用户的资产）
      ├─ Issue：目标与生命周期
      │  ├─ Primary Thread：完整活动线
      │  ├─ Rooms：阶段协作现场
      │  │  ├─ Room Thread
      │  │  └─ Work Graph
      │  ├─ Runs / Attempts
      │  ├─ Artifacts
      │  └─ Evidence
      └─ Project Thread：项目级会话（不绑定任何 Issue）
```

两条约束：

- Room 是 Issue 某个阶段的协作与控制边界，不拥有第二套执行状态机；Run 仍是实际执行记录。
- **Workspace ≠ Resource Library。** 前者是 Agent 的执行边界（`server/src/…`），是机器的工作区；后者是用户拥有的、跨任务的长期资产。V2 把两者混在同一棵「资源」树里，V3 拆开：资源库常驻左栏，Workspace 目录不常驻，从成果面的「改了 N 个文件」点进去。

### 2.1 用户语言

界面默认使用结果语言；英文领域名只在技术文档、诊断信息或二级说明中出现：

| 领域对象 | 用户界面名称 |
|---|---|
| Issue | 任务 |
| Thread | 会话 |
| Room | 协作现场 |
| Workspace | 代码目录 |
| Run | 执行记录 |
| Artifact / Evidence Summary | 阶段成果 / 完成摘要 |
| Resource Library | 资源库 |

## 3. 一级工作面

一级入口**带文字**（V2 的纯图标栏辨识度不足，且 PRD §10 要求执行能力一级入口可见），**钉在左栏最底部**，分上下两组：

| 组 | 入口 | 回答什么 |
|---|---|---|
| 在做的事 | 项目工作台 · 会话 · 项目 · 自动化 | 现在有什么在推进 |
| 积累与治理 | 记忆 · 能力 · 运行时 · 统计 · 设置 | 我攒下 / 装下了什么、花掉了多少 |

位置在底部而不是顶部，理由见 §4.1：让「换工作面」（一级）与「换看什么」（二级）在空间上彻底分开。两组之间留一个分隔，**设置永远排在最后一个**——它是频率最低的一面。

**组内按依赖顺序排，不按访问频率排**（V3.28）：记忆是素材、能力是方法、运行时是执行资源、统计是花掉的账。**运行时排在能力之后**，因为能力面自己写着「有哪些执行组合由运行时的 adapter 检查决定」——它是能力面的上游，相邻能让这条跨面引用在导航上只有一步。

> **运行时为什么重新成为一级入口（V3.28）。** V3.15 把它抽出来的理由是访问频率，V3.21 又把它并回设置，理由是「到达运行时的主路径是跳转（§4.6、§4.2 独立性卡），不是左栏点击」。V3.21 那句话现在仍然成立，但它证不出「不该有一级入口」——**记忆面的主路径同样是跳转**。真正的理由换成了语义轴：运行时回答的不是「现在能不能派工」（那是排障口径），而是**「我对接了哪些 adapter、有哪些执行组合、还剩多少额度、带哪些工具」**——一份执行资源的盘点，和记忆（攒下的素材）、能力（可选的方法）在同一根轴上。编号一并恢复为 §3.7，修订记录里 V3.15–V3.17 那几处对 §3.7 的引用因此重新指得到东西。

### 3.1 项目工作台

默认主页面，见第 4 节。

### 3.2 能力面

**这一面装的是「缺失了也不影响核心链路正常运行」的东西**——它是可选能力的**容器**，不是某一类对象的管理页。

架构判断见 `docs/decisions/0018-capability-library-and-packs.md`，这里只定界面上必须表达什么。

**中心问题是「平台基础之外我有哪些能力、这一次用哪个」**。结构照记忆面：没有左框——tab 之间是并列的几组东西，不是一棵树。

**没有「AI 成员」这一层**：能派出去的最小单位就是**执行组合**（adapter × 配置 × 模型 × 深度，例如 `codex-gpt5.6-high`；adapter 只有一份配置时省略配置段，四个维度见 ADR 0012 第 2 条与 §3.7），有哪些组合由运行时的 adapter 检查决定，不在这里增删。

#### 3.2.1 判据：核心层与可选层，依赖方向单向

```text
核心层（宿主拥有，缺一个产品就不成立）
  项目 · Issue · Room · Run · Artifact · Evidence · 记忆 · 统计 · 设置
        ▲ 可选层可以调核心层，反向禁止
可选层（插件贡献，挂这一面，任意一个缺失都不影响上面）
  Skills · 后续插件贡献的 tab
```

把这一面整个拿掉，仍然能手工建 Issue、拉 Room、派工、验收、沉淀记忆。**缺的是管理界面，不是能力本身**——已存在的 skill 数据在宿主，派工弹窗照样引用得到。

由此得到一条**可判定**的插件准入规则，它同时解释了**运行时为什么是一级面而不是设置里的一项**（§3.7）：

| | 缺失时核心链路 | 归属 |
|---|---|---|
| RSS 订阅、Skills 管理 | 不受影响，照样干活 | **可以在这一面开 tab** |
| adapter | 派不了工，产品不成立 | **永远在运行时（§3.7）**，不进这一面 |

#### 3.2.2 容器结构：tab 由插件贡献，宿主只提供 tab 栏

宿主提供的只有 tab 栏与挂载点，**每个 tab 都可停用**（插件贡献的 tab 在设置 · 插件管理里停）。停用是注册/注销级的：tab 立刻不再渲染，不做进程内模块卸载（边界见 ADR 0018）。

**宿主自带两个 tab：Skills（§3.2.3）与 MCP。** 其余由插件贡献。

> **V3.29 取消「能力包」这个名字。** 它是本设计自己发明的第三个名词——声明式的一包 Skill 和带代码的一个插件，在使用者眼里都是「我装了个东西」，区别只在风险，而风险已经由「本机没有沙箱」这句话和逐项确认的准入流程表达完了。**判据：一个名词如果只能靠它旁边那段解释才立得住，它就不该存在。** 装进来的一律叫**插件**，在设置 · 插件管理里治理；它提供什么（Skill / MCP server / tab / adapter）写在「提供什么」那一列。

**MCP 为什么在这一面而不在运行时**（V3.28）：MCP server 是**你挑来给 agent 用的工具**，和 skill 是同一类东西——可选、缺了核心链路照样跑、由能力包或使用者自己装。它和 adapter 的区别正是 §3.2.1 那张表切的那一刀：**缺一个 MCP server 少一样工具，缺一个 adapter 派不了工。**

这张表有三列不能省：`server · 来自哪个包 / 手动装 · 在哪些 adapter 上已同步`。**最后一列是必需的**——MCP 的生效是 per-adapter 的（各 CLI 各自的配置文件），没有它就会出现「我装了，但 Codex 那份没同步」，而两次执行看起来一模一样。形态照 clowder 的 MCP 页：**单一事实源 + 向各 CLI 同步 + 同步状态**。

**这里是意图侧，结果侧在运行时**（§3.7.5）：这张表说「我声明装了什么」，adapter 配置的工具表说「它实际有什么」。两个都要，因为它们会不一致，而不一致是静默的。

三条硬规则：

1. **不按插件分 tab，按贡献物类型落面。** 一个只含三条 skill 的能力包不占格子，它的内容填进 Skills tab；只有带自己数据与视图的 T2 插件才开新 tab。这是 §3.2.3 那条判断的延续：**来源是治理维度，不是查找维度。**
2. **停用后这一面可能为空**，此时显示一句话加一个跳设置 · 插件管理的入口，不显示空表格——空表格会让人以为数据丢了。
3. **贡献物落到回答同一个问题的那个面。** 抓来的资料进资源库、定时规则进自动化中心、adapter 进运行时（§3.7）；只有「既不属于已有面、缺了又不影响主链路」的东西才在这里开 tab。

#### 3.2.3 Skills tab：一张表，编组是带 `steps` 的 skill

**没有独立的「编组」类型。** 一套 schema，`steps[]` 是可选字段：有 steps 就自动带 `#编组` tag，没有就是一条普通 skill。

**为什么不做成两个类型**：一条 skill 用熟了想固化步骤，两个类型就要「转换类型」，历史表现跟着断；而 ADR 0012 第 5 条要防的正是「编组积累成身份」，**一个可来可去的 tag 比一个独立类型离那个失败模式更远**。

**「工作流模板」也不是第三种类型——它就是编组**（V3.23）。改版前项目面的「工作流」tab 列着 Coding / Research / Docs 三条内置模板，而能力面的编组里躺着「代码实现 + 独立验证」「调研 + 交叉核对」——**同一批东西的两个副本，两个名字**。

两个参考项目都没有独立的工作流对象，流程就写在 skill 里：clowder 的 `console-dev` 自述是「4 道门禁驱动的前端开发流程」；multica 的 skill 是一个 `SKILL.md`，正文直接写 `Step 1 / Step 2`。两边的描述还共用一套写法：**Use when / Not for / Output**。

合并要切一刀，否则会破 §3.2.1 的判据。工作流带着「什么算 Done」和「要什么证据」；skill 属于**可选层**——可停用、可来自能力包。如果「什么算 Done」跟着进可选层，它就变成能被一个能力包关掉的东西了。切法是现成的（§3.5.5 已有同型规则）：

| 这一层 | 归哪 | 规则 |
|---|---|---|
| 步骤、做法、每步的上下文范围与完成要求 | **skill**（编组） | 可停用、可来自能力包、可导出 |
| 底座硬规则（实现与验证不能同源、`claimed` 不进验证类上下文） | **核心层** | skill 与能力包**只能加严，不能放宽**；界面上没有「放宽」这个表达 |
| 哪一条是这个项目的默认 | **项目 · Skills** | 在项目引用的 Skills 表中设置，不与项目设置重复 |

因此项目面不再保留「工作流」tab，统一改为 **Skills**。这一页只列当前项目可用的 Skills，并设置新建任务的默认项；步骤、完成要求与源文件内容不在项目页重复展示，统一进入 Skill 详情查看。项目设置不再提供第二个默认项入口。原「知识」tab 同时正名为**项目记忆**：它不是另一套知识库，而是记忆 · 知识库的项目作用域视图。其表格字段与知识库保持一致，并提供关键词、可信等级、记忆类型与生命周期组合筛选；行级详情定位到知识库中的同一条记忆。

项目设置收敛为四类：项目信息、当前项目引用的代码仓、文件访问和项目管理。代码仓复用工作区代码仓的数据模型与列表形态，项目页只管理一个主目录和若干只读参考仓库的关联。通知、记忆、标签、执行组合与机器路径继续使用已有入口；网络与 `git push` 按运行环境的实际可用能力执行，不设置项目级开关。

##### 列表只放「挑哪一条」用得上的

列：`名称（副行 tags）· 需要能力 · 已下发 · 来源 · 更新 · 状态 · ⋮`。按 tag 筛选，`#编组` 只是众多 tag 之一。

判据：**列表回答「这些里面挑哪一条」，详情回答「这一条是什么」。** 按这条把三样东西移出列表：

| 移出的 | 去哪 | 为什么 |
|---|---|---|
| 步骤链（`codex-gpt5.6-high → claude-sonnet4.8-medium`） | 详情 | 挑的时候只需要知道它是不是编组（`#编组` tag 已经说了），具体第几步派给谁是打开之后的事；这一列还会随组合名变长而挤掉别的列 |
| 创建人 | 详情 | 个人优先产品里它几乎恒定；真正要区分的「这是我写的还是包带来的」由**来源**列回答 |
| 命中次数 / 现算表现 | 详情 | §3.2.4 已定：列表不带表现列、不可按表现排序 |

**「要求」正名为「需要能力」**（V3.22）。它写的是这条做法**至少需要执行者具备什么能力**（`架构` / `深度分析` / `工具循环`），汇进派工弹窗顶部那排「这一步需要什么」（§4.6 第 2 条）。原来的「要求」两个字不自明——同一个概念在弹窗里已经是白话，表头却是个抽象词。语义不变，只改称呼。

##### 「已下发」是事实，不是范围

这一列显示**这条 skill 已经被翻译成哪几个 adapter 的原生格式**（Claude Code 的 skill 文件、Codex 的 AGENTS.md 段落、OpenCode 的对应配置），以及哪个还没下发、为什么。

> **判据：这一列写的是「已经到了哪」，不是「只准给谁用」。**

**不做成适用范围**——那是偏好，会撞 §3.2.5 的「只写要求，不写配谁最好」：限定 adapter 与写偏好组合是同一个机制换了个位置，用久了「这条 Skill 属于 claude」，ADR 0012 第 5 条取消掉的固定角色照样从后门回来。要限制谁能跑，只能通过「需要能力」——那是能力门槛，不是身份。

下发本身照 ADR 0018 第 1 节的 MCP 先例：**PersonaHub 只出声明，翻译由各 adapter 承担**，代价不进核心。因此这一列天然会有「未下发」态（adapter 没装、或它不支持这种注入），界面要写出是哪一种。

##### 详情：整页下钻，只保留关键信息与文件

点名称进入完整详情页。顶部使用 `能力 / Skills / 当前 Skill` 面包屑；进入详情后隐藏 Skills / MCP 顶层切换，避免详情层级与能力分类层级混用。返回能力或 Skills 列表均是明确动作。

正文只保留名称、用途说明与五项关键信息：**`id@version` · 来源 · 最后更新 · 需要能力 · 下发状态**。创建人与创建时间不再单独占位；步骤、完成标准和表现若与 `SKILL.md` 重复，也不在详情中再造一份摘要。

文件区沿用 §4.2 的资源视图：左侧列出 skill 目录内的 `SKILL.md` 与可选参考文件，右侧只读预览选中文件。所有 Skills 表中的条目都必须能进入详情，不允许只有少数示例可用。

##### 操作是三点菜单，且没有「编辑」

行尾是 `⋮`，展开只有**停用**与**删除**两项。

> **判据：skill 不该被手改。** 它要么来自能力包，要么从 Done Issue 沉淀而来（PRD v0.6）。手改一条包里来的 skill，下次包升级时你的改动要么被覆盖、要么让它永远停在旧版；手改一条沉淀来的，它与产生它的那些 Run 就对不上了——而 §3.2.4 现算表现的全部前提就是「改一版就是另一段样本」。

要改就改源头：包的归包作者，本地自建的走「新建一版」。因此详情页是**只读**的，右侧文件正文不提供编辑入口，只提供「在编辑器打开」——真要动手时，动的是磁盘上那个文件，而不是界面里一个会绕开版本记录的输入框。

#### 3.2.4 编组的表现是一句观察，不是一个分数

**列表本身不带表现列**，因此这张表**不可按表现排序**。

ADR 0012 第 5 条的防护条款是硬约束：**Squad 不产生持久身份**——否则用久了一个「架构师编组」就变成了一个成员，被取消的固定角色从后门回来。同一条的补充说明也写清了它约束的是**身份积累而不是观察**，界面按这条区分来做：

| 允许 | 不允许 |
|---|---|
| 详情里现算一句：「用过 12 次，验收一次通过 9 次」 | 把它凝固成挂在这条 skill 上的评分（「这个编组 87 分」） |
| 同屏并列出它各步骤所用组合的表现，标明是哪几个组合 | 编组排行榜；列表按表现排序；编组维度进统计模块 |

**为什么两者都要在场**：组合级数字回答「这几个执行者本身行不行」，编组级那句话回答「这套步骤和围栏加上去之后行不行」——后者正是 `steps` 这个字段存在的理由，只看组合级数字就看不见它。

三条界面硬规则：

1. **现算，不落字段。** 那句话来自 Run 记录（含当次的 `id@version`），改一版就是另一段样本，界面要写出统计的是哪一版之后的。**本地自建的 skill 与编组同样按 `id@version` 记录**，不因为「不是从包里来的」而例外（ADR 0018 第 5 条规则五）。
2. **一律标样本量**，派工次数不足 30 次标「样本不足」（同 §3.4 失败页规则）。
3. **不合成「推荐度」分数**——理由同 §3.6.1：三个数字并排摆着，读者仍会自己把它们加起来，而合成之后就再也拆不开了。

#### 3.2.5 Skill 声明「需要能力」，不声明「配谁最好」

Skill 表的 **需要能力** 列（V3.22 前叫「要求」）是结构化 tag，写这条做法**至少需要什么能力**（`架构` / `深度分析` / `工具循环`）。它汇进派工弹窗顶部那排「这一步需要什么」（§4.6 第 2 条，与工作流步骤的要求取并集）。

**只写要求，不写偏好。** 一条界：

> **「这条 Skill 要求什么」建模；「这条 Skill 配哪个组合最好」不建模。**

后者是 `steps`（§3.2.4）的事。写进 Skill 会撞三处已有判断：

1. **第二套路由信号。** §3.5.4 已为标签写过同一条：「把标签做成路由信号会让两套判断互相污染」。编组说一套、Skill 说一套、弹窗三档说一套，冲突时没有答案。
2. **Squad 防护条款从后门失效。** ADR 0012 第 5 条：「Squad 不产生持久身份，历史表现记在组合上——否则用久了一个『架构师编组』就变成了一个成员」。Skill 带偏好组合是同一个机制换了个位置：用久了「这条 Skill 属于 opus」，取消掉的固定角色照样回来。
3. **ADR 0007 的边界。** Coordinator 是进程内确定性规则引擎，消费不了自由文本。「这条 Skill 和这个组合搭配效果好」若不是结构化 tag，就得靠语义判断，那是突破 ADR 0007，必须单独立决策。

**想要证据驱动的「强强联合」，走历史表现，不走字段。** 记录 `(Skill × 执行组合)` 的结果，让弹窗的「建议」档引用它——「这条 Skill 过去 14 次配 `codex-gpt5.6-high` 成功率 12/14」。数字带样本量、不合成推荐度分数（同 §3.2.4）。ADR 0012 的已知未闭合项已写明「Squad 的智能指派尚未有可行性验证，需要攒够历史表现数据才能判断」——**在没有数据时先把偏好写死成字段，之后就再也验证不了它错没错。**

#### 3.2.6 插件的 tab 是声明出来的，不是插件自己画的

T2 插件在 manifest 里**声明**一个 surface，宿主用自己的组件渲染；插件不提供任何前端代码。契约见 ADR 0018，界面上必须表达的是：

```yaml
surfaces:
  - id: inbox
    label: 订阅
    kind: table                      # 宿主提供的形态，当前只有 table
    columns: [标题, 来源, 抓取时间, 状态]
    actions:
      - { id: archive, label: 归档,     target: host.library.archive }
      - { id: dig,     label: 深入拆解, target: host.issue.createWithRoom }
```

四条硬规则：

1. **动作只能引用宿主白名单。** 「深入拆解」走 `host.issue.createWithRoom` 而不是插件自己拼一条捷径——这是 §3.3.3 裁掉 `run_only` 那条判断的同一个理由：**任何一次真正执行都必须有 Issue / Run / Attempt / Artifact / Evidence 的来源链**，走白名单这条链才是自动完整的。
2. **挂载点只在这一面的 tab 内。** 不进协作 Dock、不进派工弹窗、不进 §3.2.7 的「本次生效组合」视图——那些是证据视图，必须由宿主独占渲染。
3. **数据真相源留宿主。** 插件贡献界面与抓取逻辑，不贡献存储；`id@version` 由宿主钉。
4. **插件能新增数据，不能新增交互范式。** 需要第二种 `kind` 时那是宿主的一次性投入，不是插件能带进来的东西。理由是本机没有沙箱：允许插件提供渲染代码等于允许它读 DOM 与调用宿主全部 API，而凭据就在运行时（§3.7.4）。

**归属项目在动作里问，不在抓取时定。** 抓来的东西尚未归属任何 Project（资源库挂在 Project 下，见 §4.1），因此「归档」必须带一个选项目的步骤，「深入拆解」则由新建 Issue 时确定——**先看到、再决定要不要为它开项目**，反过来会逼使用者在还没读之前先分类。

#### 3.2.7 「本次生效组合」——可解释性的落点

> V3.23 补建。此前它只写在这份文档里，原型中一个字都没有——而 §3.6.4「本次未进入上下文」早已建好；同一段承诺做了一半。

一处视图，在**派工弹窗**和**执行记录**里各出现一次：这一次派工，agent 看到哪些 skill、受哪些硬规则约束、上下文围栏拦掉了什么，**逐条列出并标明每条来自哪个包**。

派工弹窗这一份落在**执行组合选择器**（§4.6 的 `combo-picker`）里、名单之后 footer 之前——不落在输入框上的「发给」快切上：那是换人用的轻控件，而这一份是决定「这次结论凭什么成立」的证据视图。

它兑现的是两处已有承诺：§4.6「把判断依据摊开」和 §3.6.4「过滤不能是静默的」。能力包进场之后，**只有这个视图能回答「为什么这次的验证结论和上次不一样」**。

三条硬规则：

1. **硬规则区与可覆盖区分成两块。** 上半是不可覆盖的底座（实现与验证不能同源、`claimed` 不进验证类上下文），下半才是能力包贡献的默认行为。能力包可以把规则改得更严，界面要标出「本次被某包加严」；**放宽是不可能的，因此界面上没有这个表达**。
2. **拦掉的要显示。** 围栏过滤了几条、因为什么，压暗但在场。
3. **每一条都带来源，且点得进能力面里它的来源包（§3.5.5）。** 没有来源标记的行不允许出现在这个视图里——那意味着有东西绕过了准入进入上下文。

### 3.3 自动化中心

管理 Scheduled Issues、Webhook、执行队列和历史。自动化只负责创建或推进 Project 下的 Issue，不形成第二套任务体系。

#### 3.3.1 一条自动化保存什么

一条规则由四部分组成：**Runbook、任务模板、执行方案、触发器集合**。Runbook 说明每次都要完成什么；任务模板固定项目、标题、标签与上下文范围；执行方案引用已存在的 Workflow 与执行组合；触发器只回答何时开始，可以同时有多个时间表和 Webhook。权限边界属于规则本身，不属于某个触发器——换一个入口不能扩大权限。

规则清单只做定位，按「需要人处理 → 下次触发时间」排序。运行历史不混进左栏：它属于某一条规则，放在详情的「运行记录」tab。黄点只表示需要人处理，不等于所有失败都抢到列表最前。

#### 3.3.2 详情两层：概览与运行记录

> **判据：入口和它触发出来的东西要一起读。**

V3.29 从四层收成两层。触发器原本单独一个 tab，但**看一条自动化规则时第一个问题是「它什么时候跑、跑出什么来」**——把触发条件放进另一个 tab，等于要求使用者记住上一屏再切回来。Webhook 投递并进运行记录：它是同一件事的入口侧，一次触发在两张表里各有一行。

**概览四块，顺序固定，名字要让人一眼知道自己在改什么**：

| 块 | 回答什么 | 原来叫 |
|---|---|---|
| **触发条件** | 什么时候开始（cron / 时区 / 接下来三次；Webhook 的事件过滤、签名、去重） | 触发器（独立 tab） |
| **执行内容** | 每次触发时 agent 收到的指令 | 任务说明 |
| **生成的任务** | 建出来的那条任务长什么样（项目、标题、标签、工作流、执行组合） | 建成什么样的任务 |
| **权限** | 运行时能读什么、能不能写、能不能出网、能不能 push | 能力边界 |

**改名不是措辞问题。**「任务说明」与「建成什么样的任务」并排时读不出差别——前者是**给 agent 的指令**，后者是**建出来的任务壳**；「能力边界」是本设计自己发明的词，而它管的就是四项**权限**。

**每一块都有只读与可编辑两份。** 此前详情只能看，而 sp-bar 上的「编辑」按钮承诺了一个不存在的东西。编辑态**就地切换、不另开弹窗**——四块之间互相约束（换执行组合会影响权限的可选项），拆进弹窗就要在两个地方各看一半。**权限只能收紧到项目已授予的范围之内**，超出的选项在这里不可选。

**运行记录页**：一行是一份触发意图，显示来源、准入结果、关联任务与任务结果。`未触发`（准入前挡下）、`失败`（已经执行）、`已暂停`（不再接受触发）三者分开。Webhook 规则在这一页下半部分附**投递审计**：接收、鉴权、过滤、去重、分发与响应；原始 Body 受大小与脱敏限制，重放创建新投递与新运行并用 `replayed_from` 指回旧记录。

#### 3.3.3 从 multica 保留与裁掉的内容

- **保留**：版本化 Runbook、多触发器、定时可视化 + cron、下次时间预览、Webhook URL 轮换、事件过滤、签名、幂等去重、投递审计、手动立即运行与运行来源。
- **改写**：multica 的 Agent / Squad 改成 PersonaHub 的 Workflow + 执行组合；Project 可选改成 Project 必选，因为自动化必须落到普通任务。
- **裁掉 `run_only`**：任何一次真正执行都必须有 Issue / Run / Attempt / Artifact / Evidence 的来源链。静默后台运行只把结果留在自动化历史里，会形成第二套不能验收、不能交接、不能沉淀记忆的任务体系。
- **裁掉订阅者**：当前产品是个人优先，通知对象没有真实选择空间；后续多人协作出现时再按真实需要引入。

#### 3.3.4 启用、暂停与准入

新规则保存为**暂停**，并先做项目、Workflow、运行时、额度、权限与触发器配置预检；预检通过后由使用者明确启用。立即运行走同一套准入检查，不是绕过规则的调试后门。

每次触发先记录触发意图，再依次检查：规则启用、触发器启用、幂等/并发、项目与 Workflow 可用、执行组合运行时、额度、能力边界。被挡下时写 `未触发 + 原因`，不建立伪 Run，不自动换便宜模型，也不降低权限硬跑。同一规则默认只允许一个活跃任务；重复事件合并到现有任务并保留投递关联。

### 3.4 统计

回答「发生了什么」。**回顾为主，监控 tab 允许近实时——但两种口径不同屏**（V3.28）：用量 tab 全屏不出现一个实时数字；监控 tab 每 30 秒刷新，并把**刷新间隔与上次刷新时刻写在页面上**。口径与维度的决策见 `docs/decisions/0017-usage-accounting-and-stats-surface.md`，这里只定界面上必须表达什么。

**结构照记忆面，不照任务面。** 任务模块是「列表 → 单个任务的 tab → tab 下内容」，因为任务是实体，有实体就有列表；统计没有一条条实体可列，使用者选的不是哪一条，而是**看哪一类问题**——所以进来就是 tab 页，没有左列表。三个 tab：**用量**（花了多少）、**监控**（执行是否正常）与**记忆效用**（记忆是否真正改变了工作）。

**控件位置即作用域**（照 multica 的统计页）：tab 行左边切视图、右边放页级筛选（时间范围、项目），每张卡自带自己的形态 / 维度切换。周期在右上角，因为它管整页；形态在卡内，因为它只管那张图。

八条判断：

1. **主维度是「去向」，不是执行者。** 两个参考项目都按智能体排行，是因为 agent / cat 是可治理的对象——看完排行榜能去关掉它。本项目在 ADR 0012 里取消了这一层，照抄会得到一张每行都没有对应动作的表。因此详情表主维度为**任务**，第二维度为**用途**（实现 / 验证 / 返工重试 / 上下文重传）；模型与执行组合退为同一张表的第三、四个维度，定位是**单价基准**而非排行榜。
2. **实付与订阅等价是两个数字，永不相加。** 走订阅的 adapter 配置消耗的 token 不产生新增支出、只消耗额度；走 API Key 的配置不消耗额度、但每个 token 都构成实际支出。等价一行必须标注「非实际账单」——它只是按公开 API 定价折算的结果。
3. **Token 拆成缓存命中 / 未命中。** 缓存命中是从 prompt cache 读取、按折扣价计费的部分；未命中是本次真正处理的输入加上全部输出（输出永远不进缓存）。两列相加等于该行全部 token。拆这一刀是因为它对应可调的旋钮：命中率掉下来说明 resume 冷启动了，「上下文重传」那一行的未命中量就是收窄上下文范围能省下的上限。四个维度是同一批 token 的四种切法，命中 / 未命中的合计必须完全一致。
4. **计价来源必须显式标注。** adapter 自报为权威值，本地价表折算为估算值；两者合并为单一数字后将无法区分可信部分。
5. **额度不在这一面。** 额度是 Runtime 的实时状态（ADR 0012 第 3 条），它回答的是**资源余量**（还剩多少能花），统计回答的是**已经花掉了多少**。V3.28 放进监控 tab 之后这条不但没松反而更要守：**近实时不等于什么实时数字都能进**——监控收的是执行层的事件（任务、失败、进程），额度是执行资源的属性，归运行时（§3.7）。消费点在状态栏与派工弹窗。
6. **详情表分页，合计行常驻。** 任务维度会长到上百行，按主指标降序每页 10 条；合计行置顶（紧贴表头、不带页码、不随翻页变化）——分页不得让各列与上方 KPI 对不上账；不设「本页合计」，页内小计不回答任何问题。行数为个位数的维度不分页，同样带置顶合计行。不用「其余 N 个」聚合行代替——它点不动、不可下钻，只为让列能加起来而存在。**指标不进状态列**：「返工占比」独立成列并写明口径（该任务返工重试的 token ÷ 该任务全部 token），加权后等于「用途」维度的同名占比；混进状态列会得到一个既非状态、又无从核对的值。
7. **第三级明细不在统计模块内实现。** 点击任务行进入任务模块的**轨迹**视图——逐次调用的 token 明细本就在该视图内。统计模块只负责聚合与入口。
8. **年度热力图是趋势卡的第三种形态**（逻辑与样式照 GitHub 贡献图：0 单独一档 + 非零按四分位分四档），由周期决定是否可用：近 7 天只有按天，近 30 天有按天 / 按周，近一年有按周 / 热力图并默认落在热力图。不可用的形态**置灰而不是隐藏**——藏起来等于替使用者决定他不需要它。不做成页首常驻横幅：那样它固定显示一年，而同屏 KPI 跟随周期，页面上会并列两个口径。

#### 3.4.1 监控 tab：执行层的事，不含基础设施

V3.28 把原「失败」tab 扩成**监控**，装三块：**后台任务**（正在跑 / 排队中的计数与等待时长）· **失败率趋势** · **失败任务列表**。

> **判据：监控收执行层的事件，不收基础设施的健康。**

「任务失败了几次」和「SQLite 索引坏没坏」是两种东西：前者是**这台机器替我干活的产出记录**，后者是**应用本身还能不能站着**。失败模式与处理动作都不同（去看那次执行的日志 / 去重建索引），合并会得到一张既不能排障也不能复盘的页。基础设施统一归**设置 · 系统诊断**。

三条硬规则：

1. **「正在执行」只有这一份**（V3.29）。它跨机器合并成一张表并带**执行机器**列——合并之后不说清是哪一台，「去停掉它」就不知道该在哪台机器上执行。运行时那边不再重复一份。
2. **只收录故障**：进程异常退出、权限拒绝、执行超时、adapter 错误。「验证未通过」属于正常过程而非故障，它体现在用量页的「返工重试」；「额度不足」当日未执行，记录在自动化面。将两者计入失败率后，该指标将无法再用于判断系统是否存在故障。
3. **样本不足要标出来**：派工次数不足 30 次的执行组合，失败率必须标注「样本不足」。

**刷新时刻常驻页首。** 近实时的前提是读者知道「近」到什么程度；不写的话，KPI 卡（周期口径）和后台任务（此刻口径）会并排出现，而没有任何东西告诉他哪个是几分钟前的。

### 3.5 设置

管理偏好与通知、已装的代码插件、以及当前工作区怎么组织它的任务与代码仓。执行机器与 adapter 归运行时（§3.7）。GraphRun、NodeRun、SSE、SQLite 等内部概念默认不向普通用户暴露。

**一级目录只有九项，分两组**：

| 组 | 作用域 | 项 |
|---|---|---|
| 应用 | 这台机器上的 PersonaHub 本身 | 偏好设置 · 插件管理 · 通知 · 系统诊断 · 关于 |
| 工作区 | 当前这个工作区里的事怎么组织 | 通用 · 记忆 · 标签 · 代码仓 |

#### 3.5.1 先按作用域分组，再按类别列项

> **判据一：一个导航列表只能装一种东西。**

V3.21 把运行时并进设置时，把 adapter 一条条摊在了一级目录上，于是这个列表同时装了三种东西——**类别**（数据与备份）、**实体实例**（Codex CLI / Claude Code / OpenCode）、**动作**（＋添加 adapter、首次设置向导）。三条后果：

1. **列表长度不再由设计决定，而由你装了几个 CLI 决定。** 装到八个 adapter，一级目录就是十三行、其中九行是同一件事。
2. **点击契约不一致。** 多数行是「换一页」，adapter 行是「换页并选中一个实体」。
3. **风险最高的流程长得最便宜。** §3.7.2 自己写着「＋添加 adapter 走 T2 代码准入……不能长得像『新增一份配置』那种轻量动作」，而它当时就是一行普通导航。

两条随之而来的硬规则：

- **不列没有页的行。** V3.23 之前八行里有三行是点了只弹一句话的死路。**demo 死路比缺项更伤**——它承诺了一个不存在的东西。
- **一级目录不出现状态灯。** 设置是「我要去哪改东西」的地图，不是监控面板。系统诊断的汇总状态显示在顶栏和诊断页内，不污染目录项。

> **判据二：分组按作用域，不按主题。**

V3.23 的三组是按主题分的（工作习惯 / 执行环境 / 系统）。V3.28 改成按作用域分，因为作用域回答一个主题答不了的问题：**我改这个会影响谁**。「偏好设置」和「标签」在主题上都算「工作习惯」，但前者只改变这台机器上的显示，后者改变整个工作区里所有人（将来）看到的分类——把它们并排，等于抹掉这个差别。

**「工作区」在本产品里指 Space。** 归属结构是 Space → Project → Workspace（PRD §Space），UI 上 Workspace 叫「代码目录」，Space 叫「工作区」。v0.1–v0.3 Space 是单例，但这一版**按最终形态画**：左上角那个下拉的语义就是「我在看哪个工作区的数据」，工作区组管的是**当前选中的那一个**，页面上要写清是哪个。

**只剩一个工作区时「删除工作区」置灰，不隐藏**——藏起来等于替使用者决定他不需要它（同 §3.4 第 8 条）。

#### 3.5.2 应用组：偏好设置

**偏好设置**装「只影响你怎么看、怎么用这台机器」的东西：个人资料、外观、时区、外部编辑器、界面语言。它是唯一一组**改了立刻生效、改错了也没有后果**的设置。

1. **主题在顶栏常驻，不只在设置里。** 照 clowder——它的主题是常驻图标按钮，根本不在设置页里。本设计放在右上角头像菜单。
2. **不放在左上角那个下拉里。** 那个控件的语义是「我在看哪个工作区的数据」；外观不是数据范围。multica 也把「偏好设置」挂在**我的账号**下。
3. **界面语言不改派给 agent 的提示语言。** 两者混在一起会得到「换个界面语言，结论就变了」。
4. **「个人资料」在单用户本机产品里只有一件实事：提交身份。** 显示名与头像只影响这台机器上的界面；真正有外部后果的是**写进 commit 的 name / email**，它必须与显示名分开列，并写明「这一项会出现在 git 历史里」。把两者合成一个「个人资料」卡而不作区分，是从多人 SaaS 抄来的形状。

#### 3.5.3 通知

**这一页不是可选项。** PersonaHub 的活是使用者不在的时候干的，而 P0 是全手动派工——一步跑完就停在「等待你的指派」。**没有通知，这个状态只能靠使用者自己想起来回来看。**

结构照 clowder 的通知页：**通知渠道** + **通知偏好** + 诊断信息。**只做两个渠道**：应用内（**不可关闭**）与系统通知。IM 与移动推送解决的是多人场景，本产品是单用户本机工具，**每多一条通道就多一条把项目事实推到本机之外的路径**。

**七类事件，每一条都对应界面上已经存在的状态**：等你确认权限 · 等你指派下一步 · 验证未通过或连续两轮不收敛 · 任务完成待验收 · 自动化规则的结果 · 额度低于阈值 · 本机降级或 adapter 掉线。

两条硬规则：**「未触发 · 额度不足」必须通知**（那一天什么都没发生，不通知等于静默停摆）；**通知不改变任何状态，也不是第二套操作路径**。

#### 3.5.3b 系统诊断

统一回答「应用本身还能不能正常工作，哪里需要修」。固定覆盖服务进程、数据库、事件流、记忆写入、记忆索引与关系、记忆召回、磁盘与快照；数据目录、配置文件、快照目录、日志和诊断包导出也集中在这里。

每一行使用同一结构：**状态 · 最近证据 · 影响 · 修复动作**。服务在线与能力完整必须分开表达；例如服务在线但语义召回不可用时，顶栏显示降级并可直接进入这一页。数据位置是排障证据，日志与诊断包是排障动作，因此不再放在关于页。诊断页不放阈值、开关或工作区规则，避免成为第二个配置页。

#### 3.5.4 工作区组：通用 · 记忆 · 标签 · 代码仓

##### 通用

工作区名称、描述、**任务前缀**、删除工作区。

**前缀 V3.28 从「任务前缀与标签」里拆出来并进这里。** 拆的理由：**前缀是工作区的标识属性，和名称、描述同层**；标签是一类对象的集合。两者原先并排，是因为它们碰巧都跟任务有关，不是因为它们是同一种东西。

**改前缀是要确认的操作。** 编号一旦发出去就被引用，改一次要重命名全部已有任务，而写进 commit 和证据里的旧编号不会跟着变，只能留一条别名记录。前缀这个概念有先例：multica 的 issue 编号就是 `工作区前缀-序号`（`TES-2`）。

##### 记忆

只管理当前工作区的记忆策略：写入、召回与保留。召回首期只有关键词单一路径；语义与混合召回在嵌入服务未就绪时禁用。策略页内提供召回预览，直接显示带入项、过滤项、原因和 token 占用，使配置可验证。

来源与可信边界只读展示，不提供可放宽的开关。所有值在产品中只出现这一份可编辑入口；记忆主面、系统诊断与统计只显示结果和入口，不复制配置。

##### 标签

**按工作区维度，不按项目维度。** 三条理由：单用户本机的标签总量小，每个项目一套会立刻长出同名不同义；跨项目筛选是真实需求（§7.5 已记「跨项目资料没有落点」）；而标签只是**筛选层**，不承担隔离职责——需要隔离的东西（Issue、Evidence）按项目隔离，那是 PRD 已经定死的。

**标签不参与派工判断。** 把标签做成路由信号会让两套判断互相污染（同 §3.2.5）。**被自动化规则引用的标签删不掉**，主按钮变成「先去改这些规则」。

**合并必须真的存在。** 表里对「90 天未用」给的建议是「合并或删除」——**建议一个界面上没有的动作，等于把问题推回给使用者**。

##### 代码仓

> **判据：只读引用不能借用执行边界的壳。**

V3.28 新增。起因是一个真实场景：在 personahub 项目里派一个任务，让 agent **去分析 multica 仓库的代码**。这件事此前没有落点——Project 通过 `default_workspace_id` 绑定一个代码目录，而那个目录是 personahub 自己的。

不能直接把 multica 配成第二个 Workspace，因为 Workspace 的定义里带着执行语义（PRD §Workspace：`agent run 的当前工作目录`、`workspace 写锁和并发控制`、`git repository / branch 状态`）。**只读地看一眼别人的代码，不该把写锁和分支状态一起拖进来。**

所以分两类：

| | 主代码目录 | 参考仓库 |
|---|---|---|
| 数量 | 每个项目 1 个 | 0..N |
| 权限 | 可写 | **只读** |
| 带什么 | 写锁、git 分支、执行 cwd | 什么都不带 |
| 挂在哪 | Project 的 `default_workspace_id` | 这张清单，项目与任务从中引用 |

**它吸收了原来的「代码目录授权」，不建第二张表。** 多机形态下拆成两层：

```text
设置 · 工作区 · 代码仓     有哪些仓库（名字、git remote、用途、被谁引用）      跨机器
运行时 · 机器 tab · 路径    它在这台机器上落在哪个路径、授权到读还是写         按机器（§3.7.7）
```

这一刀是多机逼出来的：同一个仓库在三台机器上有三份 clone、三个路径，**而「有哪些仓库」只有一个答案**。合成一张表就得在每一行里塞三个路径。

**一个仓库在某台机器上没有 clone，那台机器就派不了涉及它的工**——这不是一条要新写的提示，它落在 adapter 表已有的「现在挡着什么」列上。

**引用计数常驻**：每行写「被 N 个项目引用 · 主目录 / 参考」，删除弹窗因此只是确认你已经看见的东西（同 §3.5.7 第 2 条）。

#### 3.5.5 插件管理

管理已装的**代码插件**：准入、启用、停用、卸载、冲突、导出。三档信任与准入方式见 ADR 0018 第 4 节。

**V3.28 把「能力包」从这一页移出去了。** 划的线不再是「声明式 vs 代码」，而是**风险治理 vs 能力选用**：

| | 能力包（声明式） | 插件（代码） |
|---|---|---|
| 内容 | Skill（含带 `steps` 的编组与工作流）/ 协作图 / 输出契约 / 资料 | adapter、外部进程、带 surface 的功能模块 |
| 导入动作 | 读一个目录，校验通过即可启用 | 逐项确认后才允许运行 |
| 装错了最坏会怎样 | 一条 skill 没生效 | **本机没有沙箱**：它与 PersonaHub 同权运行 |
| 归哪一面 | 能力面（§3.2）——你要**挑来用**的东西 | 设置 · 插件管理——你要**盯着**的东西 |

**能力包的导入 / 停用 / 卸载落在能力面，但不重开一个「来源」tab。** V3.21 删掉「来源」tab 的判据是「**来源是治理维度，不是查找维度**」，那条仍然成立——所以它做成 Skills 表里**来源列点得进去的管理视图**：你是从「这条 skill 哪来的」走进去，不是从「我要按来源找东西」走进去。

**「停用」和「卸载」不是一件事**：停用是注册/注销级的，历史执行记录仍显示当时的包名与版本；卸载才是把目录从本机拿掉。

六条界面硬规则（能力包与插件共用）：**「装了一半」必须显示出来**（部分可用，并列出是哪一项）；**T1 引用式贡献要显示它引用的是宿主的哪个白名单条目**；**声明不等于已生效**；**同名冲突由使用者选，不自动定优先级**；**停用一个包不改写历史**；**导出默认不含项目事实**（逐条列出剥离了什么）。

#### 3.5.5b 表单页的形态：小标题 + 卡片 + 字段

> **判据：能改的东西要长得像能改。**

「通用」与「关于」原来用的是 `git-block`——左窄列标签、右侧一行文字的定义列表。那个形态适合**报事实**（版本是多少），不适合**改东西**：字段名和值挤在一行里，输入框无处可放，「改名」只能做成一个行内链接。

照 multica 的设置页改成三层：**小标题（一组）→ 卡片（一块）→ 字段（标签在上、控件在下）**。三条随之而来的规则：

1. **一屏一个保存位。** 保存与取消在页头，不在每张卡里——一页只有一次提交。
2. **只读的事实也按字段排。** 「创建于」「服务端口」这类没有控件，但仍占一个字段位，扫下来对得齐。
3. **危险动作单独一段，配可点性说明。** 「删除工作区」在自己的卡里，只剩一个工作区时**置灰并写明原因**，不是隐藏。

**标签表铺满主舞台宽度**，列名用正式说法：`标签 · 说明 · 关联任务 · 最近使用 · 引用规则 · 操作`。原来的「用在 / 被规则引用」是口语，读者要先在脑子里翻译一次。

#### 3.5.6 关于

只保留**版本、更新与许可**。不自动更新：一个会替你改代码的工具，不该在使用者不知情时换掉自己的版本。项目许可证和第三方组件许可都要有可查看入口。

数据位置、日志和导出已移到系统诊断。划分依据不是信息是否只读，而是用户为什么来找它：版本与许可用于识别产品；目录、日志与诊断包用于定位和提交故障。两边不复制同一行事实。

#### 3.5.7 每个对象都要有完整的增删改查

> **判据：一个对象在界面上出现，它的增 / 查 / 改 / 删就都要有落点；某一格确实不该有，也要写明为什么。**

V3.27 按这条逐个核过设置里的对象，补齐了六处缺口。漏得最狠的是 **adapter 配置**——本文档反复引用「删除一份配置会让依赖它的执行组合从派工清单消失，但历史 Run 保留当时的组合名」，而界面上**根本没有触发它的地方**；同样，「两者都不会把配置自动停用——停用是你的决定」这句话，承诺了一个不存在的动作。

| 对象 | 补了什么 |
|---|---|
| adapter 配置 | **停用 / 启用**（可逆那一档）、**编辑**、**删除** |
| adapter | 从这台机器**移除** |
| 机器 | **重新配对**、**移除这台机器** |
| 标签 | **重命名 / 合并到… / 删除**（被规则引用时删不掉） |
| 能力包 · 插件 | **卸载**（与「停用」分开） |
| 任务前缀 | 改前缀的**确认弹窗** |
| 时区 · 外部编辑器 | 可编辑入口 |

V3.28 按同一条判据核了新增与改组后的对象，补三处（前三行的对象已随运行时搬到 §3.7，判据与弹窗形态不变）：

| 对象 | 补了什么 |
|---|---|
| 工作区 | **改名 / 改描述**、**删除工作区**（只剩一个时置灰并写明原因） |
| 代码仓 | **添加 / 编辑 / 移除**，行上常驻「被 N 个项目引用 · 主目录 / 参考」 |
| adapter 配置的**使用方式** | 新建时必选无默认；**改它要确认**——它决定这笔账记进实付还是订阅等价 |

##### 三条来自参考项目的做法

1. **先给可逆的那一档，再给不可逆的**（照 multica 的归档）。multica 的智能体详情顶部常驻「已归档 · 无法被分配或提及」加一个「恢复」。落到本产品：配置此前只有删除，而删除会连明文 key 一起带走——**连不上、key 过期这类，要的是先停掉别再派工，不是删**。
2. **引用计数常驻在对象上，不等到点删除才第一次告诉你**（照 multica 的 skill 详情「被 0 个智能体使用」）。配置卡上常驻「被 N 个执行组合引用 · N 条自动化规则用到」，**删除弹窗因此只是确认你已经看见的东西**。
3. **详情里写明「你能对它做什么、改动何时生效」**（照 multica skill 详情的「权限」区）。本产品有正在跑的进程，这件事更不能不说：**改动从下一次派工起生效**，正在跑的不受影响（换配置要冷启动一个新进程，ADR 0009）。

clowder 那条确认了一个已有做法是对的：成员列表 Owner 那行直接写「**只能编辑，不能新增或删除**」——**不能删的东西要在行上写明为什么**，同「内置来源不可停用」。

##### 删除弹窗的形态：六处共用一个

| 块 | 装什么 |
|---|---|
| **这会动到什么** | 现算的影响面：几个执行组合会消失、几条规则会失效、什么被物理删除 |
| **这不会动到什么** | 历史 Run、证据链、验收结论一律不动 |
| **退路** | 本机每日快照的最近一次是几点，从哪里恢复，代价是什么 |

第二块**不是安慰，是必需项**：使用者不确定删了会不会把历史一起带走时，真实反应是不删——于是界面上永远堆着一批不敢动的东西。

**不做「输入名称以确认」。** 两个参考项目都没有这道闸；而本产品每天有快照，**真正的安全网是它**。到处都要抄一遍名字，人会条件反射地照抄，那道闸就不再拦住任何东西。

**被引用时不给删，并把人送去解引用。** 标签被自动化规则引用时，主按钮变成「先去改这些规则」。

##### 用词：一律叫「弹窗」

V3.27 把全稿与原型里的「弹层」统一改成了**弹窗**，它更常用。

### 3.6 记忆

产品判断见 PRD 第 5 节，结构决策见 `docs/decisions/0016-memory-state-machine-and-provenance.md`。这里只定界面上必须表达什么。

**记忆不是笔记本。** 它只由已收敛的验收事件写入，不从对话自动摘取。所以这一面的中心问题不是「怎么记」，而是**「这条凭什么信、现在还算不算数、错了怎么撤」**。

三个 tab：**待办**（所有需要人作判断的记忆）/ **知识库**（在库的全部）/ **知识图谱**（达到门槛后开放）。没有左框——这三样是并列的三组东西，不是一棵树。记忆面不再承载策略、系统健康或效用读数。

#### 3.6.1 三根轴是三列，不是一个分数

知识库的列顺序是刻意的：`强度 · 内容 · type · 层级 · 状态 · 验证于 · 引用`。其中三列构成三根互不替代的轴：

| 列 | 回答 | **不回答** |
|---|---|---|
| 强度 | 谁背书（`claimed` / `verified` / `confirmed`） | 它被用过几次 |
| 验证于 | 何时发生过显式验证事件 | 它现在是否相关 |
| 引用 | 被引用过几次 | 它是否为真 |

**不合成一个「可信度」分数。** 被用得多不等于被验证过，被验证过不等于你认可。列表末尾必须写出这句话本身——三个数字并排摆着，读者仍会自己把它们加起来。

由此得到一条界面上看得见的约束：`claimed` 行的「验证于」是空的（显示「— 未验证」）。**引用次数永远不会自己写进「验证于」，也不会自己提升强度。**

选列表而不是卡片的理由同 V3.9 修版：卡片管不动，同一个字段在不同卡里位置对不齐；而三根轴的全部意义就在于**能横着比**。

#### 3.6.2 状态是一列，退出召回要说出来

六个状态里有四个会出现在知识库：`在库` / `待复核` / `已退役` / `已遗忘`（`候选` 在待办 tab，`已否决` 只留记录）。状态有自己的筛选组，与强度筛选**分开两行**——两根轴不共用一个筛选器。

三条界面硬规则：

1. **待复核必须说明它已经退出召回**，以及**是哪一版证据失效了**（`artifact:workspace-lock@2 → @4`）。只标一个灰 badge 不够：用户要判断的是「我还能不能靠它」。同一行还要堵死「它被引用 9 次所以应该还能信」——**引用次数不能替它续命**。
2. **退役与遗忘要分得开。** 退役行压暗（`.off`）但内容仍在，写明「退役不是删除：来源与证据全部保留，可以重新启用」；遗忘行的内容位显示「〔内容已按授权清除〕」，次行是墓碑——何时、经谁授权、因何原因、原任务是谁。**并注明遗忘前必须先退役，不能从在库一步删除。**
3. **来源包与关系放在次行**（`.dl-sub`），不另开页面：`origin_type` + 来源任务 + 证据 + 使用边界 + 一跳关系（引用了 / 被引用）。关系只显示一跳——个人规模下全局图是毛球，而一跳回答的是「改这条会影响谁」。

#### 3.6.3 待办：按用户要回答的问题分组

「待确认」是状态，「待处理」是任务集合，两者重叠，不能做成平级 tab。合并后的**待办**按问题分成三组：

| 组 | 用户要回答 | 包含 |
|---|---|---|
| 新候选 | 要不要记住 | 待裁决候选 |
| 需要复核 | 现在还成立吗 | 过期、证据失效、未验证 |
| 整理建议 | 还有没有保留价值 | 孤立、冲突、长期未召回 |

每条只进入一组，避免同一候选同时出现在「未裁决积压」和候选列表。每一行右侧必须有可执行动作；批量操作先预览影响。冲突只并排展示，**不自动合并**。

#### 3.6.4 任务面的「资料 · 输入」要显示这次过滤掉了什么

记忆在任务里的另一半在 §4：资料面的「输入」方向除了「用到的知识」，还必须有一段**本次未进入上下文**——压暗但在场，并写明过滤了几条、因为什么（待复核 / 只是成员的说法）。

**过滤不能是静默的。** 你看到一个验证结论时，必须能知道验证者当时看不到什么；否则实现者的自述会经由记忆绕回来，而且是以「项目事实」的身份。

> **「开始中心」已取消独立入口。** 跨项目注意力降级为任务列表上的范围切换（当前项目 / 全部项目）。理由与待观察风险见 §7.1。

#### 3.6.5b 与 clowder 记忆模块的对照

clowder 的记忆分六个面：**知识动态 · 搜索 · 索引状态 · 健康度 · 图书馆 · 知识图谱**。逐条核对后取三条、放两条：

| clowder 的做法 | 本设计 |
|---|---|
| **索引状态与健康度分开** | **采纳并进一步归位**（V3.44）。检索基础设施进入系统诊断；知识质量变成记忆待办。两者处理动作不同，不再共享页面。 |
| **每条降级写成「问题 + → 怎么修」** | 已采纳（V3.10 起）。 |
| **样本不足时明写「数据不足（N=0，需 ≥20）」** | 采纳。效用四层里 `helped` 一栏写「不给分」并给证据链，同源。 |
| 搜索独立成面（混合 / 精确 / 语义 × 范围 × 维度） | **暂不做**。本产品的记忆总量是个位数千条，检索入口在知识库表头的搜索框已经够；等出现「搜不到」的真实反馈再拆。 |
| 图书馆 / 集合（按项目与全局分组、可归档、可单独重建索引） | **暂不做**。记忆已经按 `type` 与 `project_id` 分，再加一层集合会出现「一条记忆属于哪个集合」这个当前无人问的问题。**触发调整的信号**：出现第二个需要独立重建索引的范围。 |

#### 3.6.5 记忆策略归设置，效果留在原位可验证

> **判据：内容管理与工作规则分开；同一配置只出现一次。**

「自动入库条件」「多久未召回建议整理」「每次最多带入几条」都是当前工作区的长期规则，统一进入**设置 · 工作区 · 记忆**。记忆主面只处理内容，避免在两个入口出现相同阈值。

设置页同时提供召回预览，让用户能用一段任务描述验证未保存的草稿：看到会带入、会过滤的条目、原因与 token 占用。预览只读，不写入使用记录。

不能被放宽的来源与可信边界不做成开关：`claimed` 不进入验证上下文、`confirmed` 只能由人设置、用户偏好只能由用户确认、遗忘必须先退役并留墓碑。

系统故障进入**设置 · 应用 · 系统诊断**；记忆有没有价值进入**统计 · 记忆效用**。由此形成稳定分工：内容去记忆，策略去设置，故障去诊断，价值去统计。

### 3.7 运行时

管理**执行机器**、机器上的 adapter、它们的配置、由此得到的执行组合与可用工具。层级见 ADR 0012 第 2 条，执行位置见 `docs/decisions/0015-daemon-readiness-fields.md`。

**中心问题是「我有哪些执行资源，每一样现在是什么状态」**（V3.28 改口径）。

> 此前写的是「现在能不能派工；派不出去是因为什么」——那是**排障口径**，它把这一面定义成了一个只在出事时才去的地方，于是 V3.21 顺理成章把它并回了设置。改成**盘点口径**之后它和记忆（攒下的素材）、能力（可选的方法）落在同一根轴上，一级入口的位置也随之定了（§3 开头）。
>
> **排障没有被丢掉，它降为清单里的一列。** 理由是一张列出「支持 `codex-gpt5.6-high`」却派不出去的组合清单**是在撒谎**：「有哪些」和「现在能不能用」是同一行的两列，不是两个面。

#### 3.7.1 机器在左栏，adapter 是 tab

> **判据：左栏装「有哪几台机器」，tab 装「这台机器上有什么」。**

V3.32 之前，adapter 是机器页里的一张表，点一行从右侧弹出 400px 抽屉。三个问题：**表里六列有四列（版本、配置数、可用组合、现在挡着什么）只是为了让人决定点哪一行**——它们是导航，不是内容；抽屉一开，主区被压到 60%，而抽屉里装的正是刚才那一行的展开；换 adapter 要「关抽屉 → 找行 → 再点」。

改成 **tab**：`概览 · Codex CLI · Claude Code · OpenCode`，状态灯直接挂在 tab 上。导航退成一行标签，内容占满整屏，换 adapter 一次点击。

**概览排第一**，装的是**机器级**的事：四个读数（adapter 数 / 可用组合 / 正在执行 / 往返延迟）、**adapter 列表**和执行组合表。

- **adapter 列表**：`adapter · 健康度 · CLI 版本 · 会话 · 可用组合`，点一行跳到它自己的 tab；上方是「＋ 添加 adapter」。它是 tab 条的第二种表达——tab 条给的是「切过去」，列表给的是「横着比」。
- **执行组合表**：`组合 · 来自 · 使用方式 · 限额`。**不重复状态列**——健康度已经由上面那张 adapter 列表说完了。
- **机器状态**：左栏点灯取这台机器全部 adapter 状态的最坏值；具体原因由 adapter 列表解释，不再另做机器健康区块。

**每个 adapter 的 tab** 三块：**概览**（状态、版本、使用方式、认证、可用模型、限额、并发、可用项目、改动生效、不支持）· **运行中**（这个 adapter 上正在跑的任务与会话，可单独停止）· **工具**。

#### 3.7.1b 机器是左栏列表

> **判据：机器是 adapter 自己答不了的那一层。**

`runtime_id` 已经是 `AdapterConfig` 和 `AdapterIdentitySnapshot` 上的字段（ADR 0015 第 1、2 条），v0.3–v0.6 恒为 `local`，远程执行在 v0.7 开放。界面现在就按目标形态搭：**左栏一台机器一行，右侧是那台机器的内容**。左栏按 `本机` / `远程` 分组（照 multica 的运行时页），远程那一组随机器数量增长，本机永远只有一行。

这一层不能省，理由是一个具体的失败模式：**机器掉线时，它上面所有 adapter 都派不了工，而每个 adapter 自己的检查仍然会显示「上次检查通过」**——那是上一次能连上时的结果。状态因此必须分两级报：先机器，再 adapter。参考项目里 multica 也按**电脑**分组（ADR 0015 的对比表已记下）。

**同名 adapter 在两台机器上是两份东西**：两份安装、两份登录态、两份额度。列表因此**不做跨机器合并**——合并之后「去重新登录」就不知道该在哪台机器上执行了。

**执行位置不进执行组合名。** 组合仍是四元组；执行位置进身份快照的 `runtime_id`。否则同一个组合在两台机器上会变成两个名字，§3.2.4 那句现算表现也跟着被切成两半。

#### 3.7.2 概览装什么

1. **这台机器**（两行）：地址、daemon 版本、在线状态、时钟偏移、正在跑几个。
2. **执行组合总览**（V3.28 新增）：这台机器上一共有 N 个可用组合、M 个被挡住；展开是一张平表——`组合名 · 所属 adapter 与配置 · 使用方式 · 状态`。

   它直接回答「我支持的模型组合是什么」。此前这个答案是**散的**：要点开三个 adapter 各看一眼「可用组合」列才拼得出来，而这正是盘点口径下第一个该被答上的问题。

   **总览不给排序、置顶、默认、别名。** 列表天然诱导这四个动作，而它们全是偏好——一旦进来，adapter 就长回了 ADR 0012 第 2 条取消掉的「AI 成员」（防护条款见 §3.7.8）。
3. **状态汇总**：机器列表点灯负责整体判断，adapter 列表负责解释原因。daemon、网络、时钟与磁盘不再复制成另一张健康表。

**＋ 添加 adapter** 是 tab 栏末尾的入口（代码准入，带无沙箱警告），不是概览里的一行。
**「运行中」不在这一面**（V3.29 移到统计 · 监控，§3.4.1）。理由是它和这一面的口径不同：运行时回答「我有哪些执行资源」，是**存量**；正在跑几个进程是**此刻的读数**，和失败率、排队时长属于同一类。留在这里还有一个具体后果——这一面已经装了机器状态、组合总览、adapter 表，本机还要多两块，再加一块正在跑的进程就读不动了。

**跨机器的动作放左栏页脚**：额度告警阈值与暂停全部派工。V3.17 它在配置 tab 的页脚、V3.23 提到 pane 页首、V3.24 提到 tab 条外、V3.29 落到左栏页脚——每一次都是同一条理由：**要改一条全局策略，不该先被迫选中某一个具体对象**。

四条关于**状态灯**的硬规则：灯只有一个轴（能不能被派工，取最坏那一项，不压成颜色梯度）；灯旁必须有一句话说明是哪一项坏了（由「现在挡着什么」列承担）；per-project 差异不进灯；叫「状态」不叫「连接状态」——**远程机器有连接，但那是机器这一层的属性**，不改 adapter 那个灯的语义。

#### 3.7.3 详情在右框：一列分区，不再套一层 tab

**列表回答「挑哪一条 / 谁坏了」，详情回答「这一条是什么」。** 点 adapter 表的一行，右侧弹出 400px 详情框；关得掉，换机器时自动收起。

**框内没有 tab**（V3.26 取消了原来的「配置 / 诊断」）。判据是 §3.2 已经写过的那条：**tab 之间是并列的几组东西，不是一棵树**——而这一框装的是「同一个 adapter 的一串事实」，线性的；何况诊断那一侧只有两行，撑不起一个 tab。四块分区，顺序固定：**状态 · 配置 · 工具 · 做不到什么**。

**属性一律跟着它所属的那份配置走。** 使用方式、可用模型与深度、时限额与周限额、并发、项目可用性，全都是 `AdapterConfig` 的字段——**摆在配置卡外面时，OpenCode 那两份只能靠前缀硬拼在一起**，那是个补丁。

**并发写在配置这一层。** multica 把并发挂在智能体属性上；本项目没有「智能体」，最近的对应物就是 adapter 配置。

**论证不进界面。** 设计理由属于这份文档。界面只留使用者要用的事实，唯一的例外是**解释一处缺席**——「登录态不代管，所以这里没有输入框」这类。

#### 3.7.4 配置：使用方式、额度与凭据

##### 使用方式：订阅还是按量计费

每份 adapter 配置带一个**使用方式**字段，两个值：**订阅** / **按量计费**（V3.28 新增；界面用中文，pay-as-you-go 不进文案，见 §2.1）。

> **判据：它决定一笔 token 算不算新增支出，所以不能靠推断。**

此前这个信息是从认证方式**推**出来的——OAuth 登录态那一支算订阅、API Key 那一支算按量。推断会错：API Key 也可能挂在预付或承诺额度的账户上。而错的后果落在统计面：ADR 0017 与 §3.4 第 2 条定死了「**实付与订阅等价是两个数字，永不相加**」，**推错就是把一笔钱记进了另一本账**，而且没有任何东西会报错。

三条：

1. **使用者声明，系统不猜。** 新建配置时**必选，无默认值**——给一个默认值等于替他决定这笔钱算不算支出。
2. **它摆在配置卡最上面**，因为它一改，下面三块的形态全变：额度行（订阅报时限额 / 周限额 ↔ 按量写「不设上限 · 按 token 计费」）、告警阈值（按量没有额度可告警）、统计归属（进实付列还是订阅等价列）。
3. **它不是认证方式的第二个名字。** 两者是两个字段：认证方式答「怎么连上去」，使用方式答「这笔账怎么算」。`API Key + 订阅`（企业预付）是一种合法组合，**能表达它正是加这个字段的原因**。

##### 额度

关于额度的四条判断（见 ADR 0017 第 5 条与其 2026-09-04 补记）：

1. **额度是 Runtime 的字段，不是统计的一部分。** 它是这台机器上这份配置的实时状态，**是配置的一行，不是模型表的一列**。统计答「已经花了多少」，额度答「还剩多少能花」（§3.4 第 5 条）。
2. **只报上游自己给的两个口径：时限额与周限额，不折算成「还能派几次」。**

   每份配置报两行：**时限额**（滚动窗口）与**周限额**，各带**已用百分比**和**重置时间**；判断哪一个更紧时**取更紧的那一个**。使用方式为「按量计费」的配置两个都没有，写「不设上限 · 按 token 计费」。

   > **判据：一个由固定系数折算出来的「次数」，看起来像事实，其实是估算。**

   真实消耗按任务差异极大——同样一次 high，读三个文件和跑一轮全量验证不是一个量级。这与 ADR 0017 自己的原则同源：它引用 clowder 的原话要求订阅等价成本 *never present them as actual billing*——**把折算值呈现成计数，和把折算成本呈现成账单，是同一类错误**。

   **重置时间必须给**：只有百分比时，「等一会儿就好了」判断不出来，而它决定这一刻是该等还是该换一份配置。

3. **按 adapter 配置算，不按模型。** 同一份配置下的多个模型**共用同一份额度**，它们之间是「或者」不是「以及」。**不叫「账号」**：凭据只是配置的一个字段。clowder 的配额看板也是按「账号配置」维度分组。
4. **额度不足不自动降级。** 更换更低成本的组合会改变结果质量，那是使用者的质量判断。

**告警阈值随之改口径**：20% / 10% 指的是**两者中更紧的那一个的剩余量**。

##### 凭据

关于模型与凭据的三条判断：

1. **登录态与 API Key 分成两组，不共用字段。** OAuth 那一支由各 CLI 自己存，PersonaHub 只做**只读检查**并给出终端命令。**这一支没有任何输入框**——出现输入框就说明抽象漏了。
2. **一份配置只能有一种认证方式。** 想两种都用就建两份，否则失败时分不清是哪条路断的。
3. **密钥的真实存放位置写在设置 · 系统诊断**（§3.5.3b）。本机 SQLite 的 `agent_configs.api_key` 是明文列，数据库文件没有加密，所以「把数据目录放进同步盘等于把 key 一起同步出去」必须出现在界面上——它跟着**数据目录**走，不跟着某一份配置走。

#### 3.7.5 工具：这里是结果侧，意图侧在能力面

每个 adapter 配置里有一块**工具**表：这份配置现在**实际**带着哪些工具。

V3.28 把 MCP 提成能力面的一个 tab（§3.2.2），于是 MCP 有了两个落点，**它们答的不是同一个问题**：

| | 能力面 · MCP tab | 运行时 · 配置的工具表 |
|---|---|---|
| 答什么 | 我**声明**装了哪些 server | 这个 adapter **实际**有哪些工具 |
| 是什么 | 意图 | 结果 |

两个都要，因为**它们会不一致，而不一致是静默的**：能力包点名的工具在某个 adapter 上缺席时，两次执行看起来一样、结论却可能不同。只留意图侧查不出缺席，只留结果侧不知道本该有什么。§3.2.7 的「本次生效组合」是第三个落点，它答的是这一次派工里到底生效了哪些。

**它不是第二张能力矩阵**：V3.16 删矩阵的判据是「每一格都不可点、不可切换，且在同一个 CLI 版本内永不变化」——这张表三条都不满足。

> **V3.28 推翻了 V3.23 的「MCP 不单开一页」。** 当时的理由是 MCP 只有一个来源（能力包声明），没有「使用者自己装第三方 server」这个用法，为不存在的用法建管理页就是建债务展览馆。**推翻的是结论，不是判据**——判据仍然成立，只是这一版按最终形态画，而第三方 MCP server 在最终形态里几乎确定会有。

#### 3.7.6 做不到什么：能力位降为后果

**「状态」与「做不到什么」两块的形态照 §3.6.3 记忆健康度**：每一行右侧必须有可执行动作。**只报数字不给动作的诊断页是债务展览馆。**

**没有「能力」tab。** V3.16 删掉跨 adapter 能力矩阵的三条理由：它被本设计自己的标准判了（全是不可点格子）；两个参考项目面对更高的异质度都不给它界面（clowder 记在 README 里，multica 按电脑分组）；七个能力位里只有「原生记忆可关闭」改变派工合法性。

**但那条事实必须有落点**，所以能力位降为每个 adapter 详情里的一块「做不到什么」，并满足两条：**每一条写后果，不写能力位名字**；**它是 §4.6 第 5 条与 §4.2 验证独立性卡的落点**。

#### 3.7.7 状态只保留机器与 adapter 两层

运行时不再提供独立的「机器健康」。左栏的机器点灯负责整体判断，取该机器全部 adapter 状态的最坏值；adapter 列表提供状态依据和处理入口。两者已经能回答「哪台机器受限、被哪一个 adapter 挡住」。

系统诊断新增一行执行机器汇总，只显示在线与受限数量并跳转运行时，不复制每台机器的 daemon、网络、时钟和磁盘详情。应用服务、数据库、事件流和记忆通路继续只在系统诊断。

#### 3.7.8 防护条款：这一面不出现「偏好」字段

> **判据：如果一个字段的值改了之后，「派工时该选谁」的答案会变，那它就不属于这一面。**

`base_url`、api key、认证方式、使用方式**属于**；「默认用它」「优先级」「别名」「角色」**不属于**。后者一旦进来，adapter 就长成了 ADR 0012 第 2 条取消的「AI 成员」。**列表天然诱导排序、置顶和改名，而这三个动作全是偏好**——V3.28 新增的组合总览是一张更长的列表，这条因此更要守住。

#### 3.7.9 信息审视：删掉的五样

> **判据：一个字段留在界面上，要么它改变你接下来的动作，要么它回答一个别处答不了的问题。两样都不占的，删。**

| 删掉的 | 为什么 |
|---|---|
| 模型表的**额度**列 | 额度**按配置分池**。给每个模型开一列额度，最后只能靠「同池」两个字打补丁——**一个需要补丁词才能自圆其说的列，本身就是错的** |
| 模型表的**状态**列 | 恒为「可用」。不可用的模型根本不会出现在「可用模型」清单里 |
| 额度池表的**配置 / 认证**两列 | 在单配置视图里恒等于上面那份配置已经说过的 |
| 工具表的**缺了会怎样**列 | 一整列只有一行有值，**它应该是行内说明，不是一列** |
| 诊断的**近 30 天派工计数**、**登录态到期** | 前者是回顾，口径归统计面；排障要的是**最近那一次失败是什么、点得进去**。后者在配置里已经写过一遍 |


## 4. 项目工作台结构

### 4.1 左栏（248px）

**一栏、一个纵向列表、零个二级 tab。** 自上而下：

1. **工具条**：搜索 + 新建。
2. **范围切换**：当前项目 / 全部项目。
3. **单一列表**，由可折叠分节组成——「在做的事」在上，「积累的东西」在下：

| 分节 | 内容 | 默认 |
|---|---|---|
| 需要你处理 | 等你指派、等你确认权限、验证未收敛、刚创建 | 展开 |
| 正在进行 | 执行中的任务；Rooms 作为子项缩进，不伪装成同级对象 | 展开 |
| 最近完成 | 已完成且验证通过 | 展开 |
| 文档与素材 | 笔记、PRD、参考资料（用户资产，不是代码目录） | 收起 |
| 产出 | Artifact / 完成摘要的历史索引 | 收起 |
| 知识 | Decisions / Memory / Skill Candidates | 收起 |

4. **一级入口钉在最底部**，两组九个，清单与分组见 §3 开头；设置永远在最后一个。

两条依据：

- **V2 的四棵并列树**（任务/资源/产出/知识）要求用户先回答「我要找的东西属于哪一类」，是文件管理器思维。
- **V3.0 的「任务 | 资源库」二级 tab 同样不成立**：它和上方的一级入口都是按钮组，视觉上分不出谁管谁；实测左栏在看到任何内容之前叠了四层控件。对照冻结参考页，multica 与 dsh 的侧栏都是**单一纵向列表 + section label 分隔**，都没有第二层 tab（`ui-reference/multica/pages/issues.html`、`ui-reference/dsh/pages/home.html`）。

一级入口下沉到底部，让「换工作面」（一级）和「换看什么」（二级）在**空间上彻底分开**，不再是两组挨着的按钮。

### 4.2 主舞台：成果面（~60%）

**一次只判断一件事。** 舞台同时只显示一个成果面；tab 决定显示哪一个（§4.2.1）。

成果面自上而下四段：

| 段 | 内容 | 来源 |
|---|---|---|
| 标题区 | 任务名 · 当前状态 · 主操作 | V2 任务页 |
| **成果状态条** | 系统记录 / 实际变化 / 验证独立性 三卡 | V2 `evidence-summary` 升格 |
| 成果本体 | 文档正文 / 变更摘要 / 研究综述 / Artifact 内容 | V2 文档画布 |
| 完成要求与依据 | 逐条挂系统记录、实际文件、验证者结论 | V2 `evidence-summary` |
| 执行计划 | 这份成果是怎么来的（步骤 · 执行者 · 输入输出 · 证据） | V2 概览页搬入 |

**不使用百分比信任评分。** 可信度来自「结论旁能看到原始记录、谁验证、哪些没证明」。

**验证独立性卡受执行体能力约束,不只看「是不是同一个模型」。** 同源判定(PRD 第 7.5 节)是必要条件不是充分条件:验证方即使换了模型,只要它跑在**原生记忆关不掉**的 adapter 上(ADR 0011,当前是 OpenCode),它就可能读得到上一轮的实现细节,ADR 0012 第 4 条的上下文范围三档在那里保证不了。因此这张卡多一档判定:

| 情形 | 这张卡 |
|---|---|
| 换了模型 + 验证方 adapter 的原生记忆已关闭 | 绿勾「已独立验证」 |
| 换了模型,但验证方 adapter 的原生记忆关不掉 | **拿不到绿勾**,显示「有证据待验证 · 该执行体无法保证独立性」,并点得进该 adapter 的「做不到什么」（§3.7.6） |
| 同一个模型 | 「未独立验证」(原有判定) |

由此 §4.2.2 的「已完成」态**并非总能三张全绿**——这不是缺陷,是把一个原本静默发生的事实显示了出来。**能力不足是一种事实上的放宽**,ADR 0018 第 5 条硬规则二「只能加严,不能放宽」只管住了能力包,管不住执行体本身;这张卡是它在成果面上的唯一显形处。

代码文件与长文档从成果面点进去（「改了 3 个文件」），**在所属任务的 tab 内替换舞台 + 返回条**，不用覆盖层——长内容需要完整阅读宽度。文件视图保留 V2 的修改数量、位置标签和上一处/下一处跳转。

#### 4.2.1 任务 tab 条

**一个 tab = 一个任务的成果面。不是文件 tab。**

V3.0 删掉了 V2 的编辑器标签页排，理由是它「异质对象混装一排」。V3.1 恢复标签页排，但把那条理由变成规则本身：

| 规则 | 含义 |
|---|---|
| 只有任务能占 tab | 任务、协作现场、项目全景。文件、证据、阶段成果**不占 tab** |
| 子文档在所属 tab 内切换 | 点开「改了 3 个文件」不新开 tab；所属任务的 tab 保持选中，舞台顶部出现一条返回条 |
| 返回条不常驻 | 只在子文档时出现。否则 tab 条 + 面包屑会叠成两行 chrome |
| 单击 = 预览 tab | 从左栏单击打开的任务落在同一个**斜体预览 tab**，被下一次单击替换。进入子文档、或直接点这个 tab，就把它钉住 |
| 至少保留一个 tab | 关掉最后一个没有意义——舞台不能空着 |

预览 tab 直接回答 §4.5 对 V2 标签页排的另一半批评——「只增不减、无预览模式」。扫一眼五个任务只会留下一个 tab；真正开始做的那个才会被钉住。

「3 个任务 tab 对 1 个 Dock」的老问题由 §5 原则 1 解决：**切 tab 就是切任务，Dock 必然跟随**。因此不存在「对着错误上下文发指令」的窗口。

保留这条规则的代价：左栏已经列出全部任务，tab 再列一遍打开的任务，重复度比 IDE 高（IDE 是几千文件对十个 tab）。见 §7.4。

#### 4.2.2 七个任务态

同一套五段结构，**状态差异只体现在每段的填充程度，不换布局**。左栏点进任何一个任务，看到的都是同一张表的同一个位置。

| 状态 | 状态卡 | 本次成果 | 完成要求 | 执行计划 |
|---|---|---|---|---|
| 刚创建 | 三张全为「还没有」 | **空态**：还没有任何产出 | 你写的要求，全部无依据 | **空态** + 让 Coordinator 拟计划 / 自己指派第一步 |
| 执行中 | 系统记录「仍在增加」；验证独立性未达成 | 已完成的文件 + 正在写入的文件（虚线、不计入） | 已拿到依据的打勾，其余标「执行中 / 未开始」 | 当前步骤高亮，后续标「排队中」；正文顶部有常驻活动条 |
| 等待指派 | 验证独立性明确「尚未独立验证」 | 完整 | 最后一条是「还没有人验证过」，可预填验证指令 | 最后一步「等待你指派」 |
| 已完成 | 三张全绿，含验证者是谁 | 完整 + 完成摘要 revision | 全部可点到依据 | 全部完成 + **验证员的后续建议单独在场**，不被「已完成」吞掉 |
| Research 进行中 | 实际变化「0 个文件」——研究不改代码 | 固定为 revision 的**结论**，不是文件 | 前两条有结论支撑，第三条是阶段出口 | 并行检索 → 整理来源 → 收敛 synthesis_plan |
| 验证未收敛 | 验证独立性「2 次都未通过」 | 两轮改动**都保留**，验证不通过不回滚 | 被打回的那条展开两轮各自结论 | 两次失败**各占一步不合并** + 换策略的下一步 |
| 等待权限确认 | 实际变化「0 个文件」——暂停发生在写入之前 | 换成「你在批准什么」四条 | 全部待决定 | 被阻塞的那一步显式标出 |

两条判断：

- **空态不填占位数字。** 刚创建的任务显示「0 个文件」「还没有执行」，不显示进度条或预估。空白本身就是「还没发生」的证据。
- **「还没拿到依据」的完成要求可读但不可点。** 它们渲染成不可点击的行，避免伪装成「能点开证据」而点了没反应。
- **阻塞条自带动作。** 「在跑，不用你管」（执行中）用常驻活动条；「停住了，等你」（权限确认、验证未收敛）用阻塞条，允许/拒绝、预填改派指令**就在条上**，不需要先去右栏找。
- **两次失败各占一个步骤，不合并成「重试 2 次」。** 合并会抹掉「两轮是同一个执行者、同一个结论」这条最关键的事实——它正是「该换策略而不是再修一次」的依据。
- **验证不通过不回滚已有改动。** 换策略时它们是输入，不是垃圾。

#### 4.2.3 协作现场的舞台

协作现场不是任务，回答的问题也不同。PRD 第 5 节：

> Room 回答的是「这个阶段需要谁一起解决、采用什么协作模式、交付什么结果」。

因此它**沿用成果面的骨架，只换最后一段**：

| 段 | 任务成果面 | 协作现场 |
|---|---|---|
| 状态卡 ×3 | 系统记录 / 实际变化 / 验证独立性 | 阶段进度 / 几个组合在跑 / 交付契约达成度 |
| 目标 | 任务目标 | 阶段目标 **+ 为什么是这些人** |
| 本次成果 | 文件 + 阶段成果 | 本阶段产出 |
| 完成要求与依据 | 任务完成要求 | **交付契约与终止条件** |
| 末段 | 这份成果是怎么来的（线性 plan-list） | **谁在做什么（并行执行组合泳道）** |

**末段必须换。** Room 的本质是并行：三个执行组合同时在跑，线性 `plan-list` 只能说「第 2 步执行中」，说不了「三个组合各自到哪了」。泳道有三态——已交付 / 执行中 / 排队中，排队中的必须写明**前置为什么没满足**。

两条附带判断：

- **选人理由必须在场。** PRD 第 5 节明确要求 Human Lead 能「查看 Coordinator Agent 为什么创建该 Room，以及**为什么选择这些 agents**」。V3.1 之前原型里一个字都没有。
- **介入动作挂在泳道上，不做全局工具条。** PRD 列的六项 Human Lead 能力里，移除某个执行组合、指定某个 agent 接手、要求某个 agent 提供证据都是**针对具体那一条泳道**的；顶部三个通用按钮表达不了「改派谁」。

这样一来，协作现场的舞台与 Dock 面板是「结构视图 vs 对话流」，和「成果面 vs 任务会话」完全同构。整个产品只有一条规则：**舞台看结构，Dock 看对话**。

**一个任务可以有多个协作现场**（PRD `Issue.rooms[]`）。因此 Dock 的「协作现场」tab 必须显示**当前舞台所属的那一个**，而不是永远同一个——V3.1 之前打开 Research 现场，Dock 里显示的仍是 Implementation 现场。

### 4.3 右栏：协作 Dock（440px，常驻）

**常驻不折叠。** 当前阶段用户对 Agent 的信任尚在建立中，需要频繁盯会话；这是一条会随信任度变化的判断，见 §7.2。

结构自上而下：

1. **发送目标条（常驻）**：`指令将发送到 · <任务会话 / 协作现场> · <任务名>`。切换任务时 Dock 自动跟随；可显式固定某个 Room，固定后持续显示固定状态，避免向旧上下文误发指令。
2. **执行状态两行（常驻）**：谁在做 · 第几步 · 卡在哪。这是 V2「概览」页里唯一高频的部分，拆出来常驻，不再需要切 tab 才能看到。
3. **会话流**：任务会话 / 协作现场 两页。用户消息靠右，Agent 消息靠左，工具调用与执行事件折叠进 Agent 的那条消息。
4. **指派草稿 + 输入框**：等待指派时系统预填 `@执行组合 + 建议做的事`，随时可改。**不设独立的「照做 / 不照做」按钮**——按钮只有两种结果，不同意时用户得自己从头组织指令。

> V2 的「概览」tab 被拆解：高频的执行状态上提为常驻两行，低频的「详细执行计划」下沉到成果面（它本来就是「这份成果怎么来的」）。Dock 不再有第三个 tab。

#### 4.3.1 项目级会话

**当前没有选中任务时，Dock 显示项目级会话**，而不是空态或上一个任务的残留。

它不绑定任何 Issue，用来问「这个项目现在什么情况」「上周那批改动结论是什么」，也可以直接从这里发起一个新任务。这让 Dock 在任何时刻都有意义，也给了用户一个「和项目对话」而不是「和某个任务对话」的入口。

选中任务后，Dock 切到该任务的会话；项目会话仍可从发送目标条切回。

#### 4.3.2 两个会话的关系必须显式表达

Dock 顶部「任务会话 | 协作现场」两个 tab 并排，看起来像**两个聊天窗口**；实际是**一条主线 + 一个阶段的支线**。PRD 第 5 节的原话是：

> Thread 记录事情怎么一路发生，Room 组织谁一起解决其中某一段问题。

| | 任务会话（Thread） | 协作现场（Room） |
|---|---|---|
| 方向 | 纵向：创建到完成的完整生命周期 | 横向：只覆盖其中一个阶段 |
| 数量 | 每个任务恰好一条（v0.1） | 0 到多个，按阶段临时开 |
| 存在时长 | 与任务同寿 | 阶段结束即 archived，记录不删除 |
| 有无参与者名单 | 无。是你和系统的主控制线 | 有：执行组合 + 拓扑 + 交付契约 |
| 下一条指令发给谁 | **这里** | 不在这里 |

数据上的区别是 `Thread.room_id`：为空是任务会话，有值是某个协作现场的会话——**协作现场里也有对话**，这正是最容易混的地方。

**因此两个面板各自带一行来源说明**，不依赖用户已经知道 Thread / Room 模型：

- 任务会话：「贯穿这个任务的全程 · 每个任务只有一条 · 要下指令、改目标、指派下一步都在这里」
- 协作现场：「只覆盖 *Implementation* 这一个阶段 · 属于任务「⋯」· 3 个执行组合 · 阶段结束后归档，记录不删除」，任务名可点回成果面

两个 tab 另有 `title` 悬停说明（§6：能力与边界提前标注）。

**这条是 V3.1 补的**，起因是设计过程中自己都要回查 PRD 才说得清两者区别——设计者需要回查，用户就一定会问。

顶栏三档，改变的是主次比例，不改变结构：

| 模式 | 舞台 | Dock | 用途 |

### 4.6 执行组合选择器

指派前要选一个执行组合。**这不是从一份平铺名单里挑一个,而是一次要向 Human Lead 解释的判断**——这正是产品「可解释」承诺最该兑现的地方之一。

名单本身不在这里维护：有哪些组合由运行时（§3.7.2）的 adapter 检查决定，弹窗只负责选和解释。因此选择器有八条规则:

1. **硬约束先说,名单后给。** 弹窗顶部先写这一次选人的规则,例如验证角色写「实现与验证不能同源(PRD 第 7.5 节)。同源看的是**模型**,不是深度——同一个模型换个深度再验一遍,验的还是它自己」。放在名单后面等于让用户读完才知道有规则。
2. **「这一步需要什么」由两处贡献,取并集。** 要求 tag 有两个来源——**命中的 Skill**（A）与**工作流 / 编组这一步**（B）——**不设优先级,取并集**。要求的语义是「这一步至少要满足什么」,并集只会更严不会更松,因此天然没有「冲突时听谁的」;这与 ADR 0018 第 5 条硬规则二「只能加严,不能放宽」是同一条判断。弹窗顶部那排 tag **必须逐个标出它从哪来**,理由同 §3.2.7「没有来源的行不允许出现」。

   两个来源各自补对方的洞：B 最准但 ad-hoc 派工（直接在会话里说一句）没有步骤,等于不设防;A 覆盖 ad-hoc,但只有**派工前就能确定命中**的 Skill 才算数——按触碰路径命中的那类,派工时还不知道会改哪些文件,算不出来。**算不出来的不猜,不进这一排。**

3. **每一行都写明为什么。** 分建议 / 可选 / 不可选三档,理由具体到这一次:「本次实现就是它做的,自己验自己不成立」「登录状态需要重新检查,现在派过去会直接失败」。

4. **三档的分界是「能不能」,不是「好不好」。**

   | 档 | 能不能选 | 落在这里的是 |
   |---|---|---|
   | 建议 | ✅ | 满足全部要求 |
   | **可选** | ✅ | **不满足某项要求**——它是质量判断,归使用者 |
   | **不可选** | ❌ 置灰 | 硬约束:同源、登录未确认、额度不足、兼任、结构性不具备 |

   **中间那档叫「可选」而不是「不建议」,末档叫「不可选」而不是「不建议」。** 早期版本把硬禁止那一档标成「不建议」——一个读到「不建议」的人会以为自己能坚持选,实际点不动,这与第 1 条「硬约束先说」的意图相反。

5. **不可选的不隐藏,只置灰。** 藏起来等于替用户做了判断,而这里的承诺恰恰是把判断依据摊开。

6. **不满足要求可以派,但要留痕。** 系统不挡「拿 `haiku-4.5-low` 跑架构设计」——先用便宜组合过一遍草稿、试试 Skill 写得对不对,都是明知它弱就是要它便宜,而 §3.7.4 已经裁定「更换组合会改变结果质量,**这属于使用者的质量判断**」。系统既不替你降级省钱,就不该替你升级保质。

   代价是这次产出的主张上必须留一条标注：**「本次由不满足 `架构` 要求的组合执行（`claude-haiku4.5-low`）」**,并在成果面的「这份成果是怎么来的」里可见。形态照 ADR 0012 第 4 条的保护条款——把验证上下文手动改回「全部」时不禁止、但结论降级。**推翻默认可以,但不能静默地推翻。**
7. **不可选与「可选但不满足要求」的理由分三类,混成一条就废了。**

   | 类 | 说的是 | 会不会变 | 理由指回哪 |
   |---|---|---|---|
   | 额度不足 | 今天跑不动 | 明天可能就能用 | 运行时的时限额与周限额（§3.7.4） |
   | 能力不匹配 | 这一步不该用它 | 换一步就能用 | 这一次的任务性质 |
   | **结构性不具备** | 这个执行体给不出本步要的保证 | **既不随时间也不随任务变化** | 该 adapter 的「做不到什么」（§3.7.6） |

   前两类落「可选」或「不可选」要看具体哪一项：额度不足与结构性不具备是硬的（不可选），能力不匹配是软的（可选）。

   第三类是 V3.14 补的。它与前两类的差别不是程度而是性质：额度会回来、任务会换,而**一个 adapter 关不掉原生记忆这件事,等到明天、换个任务也还是关不掉**。把它混进「不建议」,使用者会以为再等等、或者换个说法就能用它——而实际上这一格永远不会亮。

8. **结构性不具备的行必须写出后果,并点得进该 adapter 的「做不到什么」。** 不写成「不建议」三个字,写成「它的原生记忆关不掉(ADR 0011),读得到上一轮的实现细节,这次验证不构成独立验证」。这条和 §3.2.7「每一条都带来源,且点得进它的来源包」是同一条判断:**没有来源的禁用理由等于没有理由**,使用者只能选择相信或者绕过它。

三个角色各有自己的判定规则:

| 角色 | 硬约束 |
|---|---|
| 实现者 | 无硬约束;换人不丢已有改动。登录未确认的不可选 |
| 独立验证员 | **不能是本次实现者**(PRD 第 7.5 节);**且其 adapter 的原生记忆必须可关闭**(ADR 0011)——关不掉就读得到上一轮,独立性从一开始就无从保证 |
| 综合员 | **不能是参与本阶段检索的研究员**——兼任会偏向自己那份结论 |

两处全局不可选,理由不同因而措辞也必须不同:

- **登录状态未确认(`需检查`)**:在所有角色下不可选——派过去会直接失败,让它可选等于制造一次注定失败的执行记录。**这是可恢复的**,理由里要给出终端命令。
- **能力位不满足本步的硬约束**:也不可选,但**不可恢复**——它不是「还没弄好」,是「这个执行体就不提供这个保证」。两者用同一句「不可选」会让使用者去做一件根本做不成的事。

## 5. 关键交互原则

1. **舞台是单例，Dock 跟随舞台。** 切换文件、Artifact、证据、知识不改变 Dock；切换任务必然切换 Dock。
2. **任务像工作文档。** Task 不是字段表格，而是目标、决策、活动、产出和验收条件的持续记录。
3. **证据可双向追溯。** 从结论能到原始事件，从文件或 Artifact 能看到由谁、在哪次尝试中产生。
4. **注意力高于时间。** 任务列表优先显示需要用户动作的对象，而不是最近更新时间。
5. **高级内部信息渐进披露。** 默认展示结果语言，诊断层才出现 Run ID、事件、命令和底层错误。

## 6. 反馈与状态表达

V2 把新建、指派、预填、暂停、跳转、发送、缺失说明全部塞进同一个 2.2 秒 toast。V3 分三类：

| 类型 | 表达方式 | 例 |
|---|---|---|
| **状态变更** | 持久可见，不消失 | 已暂停 → Dock 内常驻横幅「已暂停 · 3 个步骤在队列等待 · [恢复]」 |
| **操作确认** | 短提示，可消失 | 「已把建议指令写入输入框」 |
| **能力缺失** | `title` 提前标注，不等点击 | 「本轮草案未覆盖：运行时的配置」 |

**指派有撤销窗口。** 发出 `@执行组合` 指令后进入「正在启动… [取消]」，而非立即判定「已指派」。指派与否由派工结果决定，不由文本前缀猜测。

这条 V3.1 已落地：撤销条常驻 Dock 顶部（不是 toast，因为它必须撑满整个可取消窗口），文案明说「还没有真正开始执行，现在取消不会留下痕迹」；窗口过去后变成「已开始执行」并撤掉取消入口，随后自行退场。取消不产生执行记录。

## 7. 待观察的判断

这些是本轮明确选择、但需要真实使用验证的决定。效果不佳时按备选方案切换。

### 7.1 「开始中心」降级为范围切换

- **现选**：删除独立工作面，任务列表顶部加「当前项目 / 全部项目」切换。
- **风险**：用户常态是同时推进 2 个项目并行 vibe coding，来回切范围可能比切页面更烦。
- **触发切换的信号**：一天内范围切换次数 > 10，或用户反馈「找不到另一个项目在等我的事」。
- **备选**：恢复独立的开始中心工作面（跨项目时信息组织本来就不同）。

### 7.2 协作 Dock 常驻不折叠

- **现选**：常驻 440px，因为当前对 Agent 的信任仍在建立中。
- **风险**：信任建立后，440px 长期显示一条已读完的会话是浪费。
- **备选**：默认收成竖条，有新消息或需要指派时自动展开。

### 7.3 资源库收成左栏的三个可折叠分节

- **现选**：左栏是单一纵向列表（§4.1），资源库退化为下半部的三个分节——文档与素材 / 产出 / 知识，默认全部收起。V3.1 已删掉「任务 | 资源库」二级 tab（§4.5）。
- **风险**：产出的历史检索路径变长一层；分节收起后资源库在视觉上几乎不存在。
- **备选**：产出恢复为独立分节并默认展开。

### 7.4 任务 tab 与左栏任务列表重复

**判断**：舞台顶部的任务 tab 和左栏的任务列表列的是同一批对象，只是 tab 是「打开的」子集。

**支持保留的理由**：tab 保留每个任务的滚动位置与展开状态，两个项目并行时切换成本明显低于每次回左栏点一遍（这正是 §7.1 记录的场景）。

**触发调整的信号**：常开 tab 数长期 ≤ 2，或使用者反映「两处都在看任务，眼睛不知道该看哪」。

**调整方向**：把左栏任务列表默认只展开「需要你处理」，其余两组默认收起——分节折叠已经就位，改默认值即可，不动结构。

### 7.5 跨项目资料没有落点

**判断**：资源库挂在 Project 下（ADR 0012），而 Issue 有游离态（`project_id` 可空）、资源没有。抓取类插件（§3.2.6）拿回来的东西在归档之前不属于任何项目。

**现选**：不为资源引入游离态，由插件 surface 自己承载「还没归属」的那一段——归档动作带一个选项目的步骤，深入拆解则由新建 Issue 时确定。

**触发调整的信号**：出现第二个抓取类插件，各自维护一份「未归属」列表；或使用者反映「抓回来的东西找不到在哪」。

**调整方向**：给资源补一个与 Issue 对称的游离态，未归属资料进一个跨项目的收件视图。这会新增一个一级面，代价明显，因此要等真实信号。

**V3.28 补记**：这一条被**部分**答掉了。设置 · 工作区 · 代码仓（§3.5.4）给了「跨项目的代码仓库」一个工作区级的落点，标签同样提到工作区级。**但那只覆盖代码和分类，不覆盖资料**——抓取类插件拿回来的文档、笔记、素材仍然没有跨项目落点，本条其余部分继续观察。
### 7.6 声明式 surface 只有一种 `kind`

**判断**：插件的 tab 由宿主渲染（§3.2.6），当前只提供 `table` 一种形态。第二个插件需要时间线或列表-详情时，就要宿主再建一种。

**支持保留一种的理由**：形态是宿主的一次性投入，预先建三种等于为还没出现的插件先付账；而 ADR 0014 第 1 节的门控本来就是「有真实需求再开缝」。

**触发调整的信号**：第二个 T2 插件落地，且它的内容用表格表达明显别扭。

**调整方向**：加第二种 `kind`，不开放插件提供渲染代码——后者的理由（本机没有沙箱）不随 kind 数量变化。

### 7.7 多机之后「实现与验证不能同源」怎么算

**结论没有下，界面上先不表达。**

PRD §7.5 的独立性判定依据是两个 identity snapshot。接了远程机器之后会立刻冒出一个产品问题：**同一个模型跑在两台不同机器上，算不算同源？**

ADR 0015 已经明确把这个语义留到 v0.7，它现在只要求字段留出来。所以这一版的界面**不给这个问题任何暗示**：机器 tab 只表达「在哪台机器上执行」，不参与独立性判定的措辞；派工弹窗的「结构性不具备」也只按 adapter 的能力位判，不看机器。

**要观察的是**：真正接上第二台机器之后，使用者会不会**自发地**把「换台机器」当成一种增强独立性的手段。如果会，那说明这个语义必须尽早定。

### 7.8 应用诊断与执行状态已经拆开

应用自身的服务、数据库、事件流、记忆与存储统一归系统诊断。运行时只保留机器点灯和 adapter 状态，不再提供机器健康区块。系统诊断通过一行执行机器汇总进入运行时，形成单向下钻，不复制状态来源。


## 8. 与 V2 的差异及理由

| V2 | V3 | 理由 |
|---|---|---|
| 中间画布 39% + Dock 39% | 舞台 ~60% + Dock 440px | 参考产品的主舞台都占约 60%；对半劈导致没有主角 |
| 画布 = 打开任意对象的容器 | 舞台 = 成果面 | 舞台要承载产品的独有承诺，而不是做一个通用阅读器 |
| 图标栏 + 列表栏两栏 | 合并为一栏 248px | 省出宽度给舞台；带文字提高辨识度 |
| 四棵并列对象树 | 单一列表 + 可折叠分节 | 收敛为「在做的事」与「积累的东西」；V3.0 曾用两个 tab 表达，V3.1 发现它和一级入口分不出层级，改为分节（§4.1） |
| 一级入口在左栏顶部 | 钉在左栏底部 | 让「换工作面」与「换看什么」在空间上分开 |
| 编辑器标签页排（文件 tab） | 任务 tab | V3.0 删除标签页排导致切任务必须回左栏；恢复为 tab，但只允许任务占位（§4.2.1） |
| 资源树混装 docs 与 server/src | 资源库只放用户资产 | Workspace 是机器的工作区，不是用户的资料库 |
| Evidence Summary 是产出树下的页面 | 升格为成果面的固定结构 | 它是全套最强的一屏，也是产品独特性所在 |
| 概览是 Dock 的第二 tab | 拆为常驻两行 + 成果面里的执行计划 | 高频信息不该藏在 tab 后面；执行计划属于成果来源 |
| 底部执行面板 + 状态栏 | 删除 | IDE 隐喻，Human Lead 不看终端 |
| 无当前任务时 Dock 空/残留 | 项目级会话 | 让 Dock 在任何时刻都有意义 |

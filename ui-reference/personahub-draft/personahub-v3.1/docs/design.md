## 1. 设计结论

**PersonaHub 的主舞台是「成果面」——一份随工作推进不断生长的任务文档。**

它一开始只有目标和完成要求；Agent 每推进一步，它就长出产出、证据和决策；完成时它本身就是交付物。任务从「一张目标」长成「一份可信成果」，舞台全程显示同一个东西的当前形态。

```text
左栏（248px）  定位：一级入口 + 任务列表 + 资源库分节
主舞台（~60%） 成果面：这件事现在做成什么样了、可不可信
右栏（440px）  协作 Dock：谁在做、下一步交给谁
```

### 1.1 为什么是「成果面」

| 参考产品 | 主舞台 | 中心问题 |
|---|---|---|
| Multica | 任务文档 / 看板 | 要做什么 |
| Clowder | 会话流 | 正在说什么 |
| Obsidian | 笔记 | 我写下了什么 |
| **PersonaHub** | **成果面** | **现在做成什么样了、可不可信** |

三条理由：

1. **它是 PersonaHub 独有承诺的载体。** 计划管理 Multica 有，聊天 Clowder 有；只有 Artifact + Evidence + Provenance 构成的「可信交付」是 PersonaHub 独有的。舞台必须承载它，否则产品的独特性在界面上看不见。
2. **它匹配真实的高频动作。** PRD §6「第一屏」与 `user-journeys` 的 P0 常态是同一件事：**看一眼成果，决定下一步交给谁。** 这是审阅 + 决策，既不是读文档也不是聊天。
3. **它对三种用途都成立。** 见 §1.2。

### 1.2 三种用途的同一张舞台

| 场景 | 舞台上是什么 | 左栏资源库里是什么 |
|---|---|---|
| 代码开发 | 改了 3 个文件 · 24/24 通过 · 独立验证一致 | 项目文档、PRD、决策记录 |
| 书籍拆解 / 写作 | 拆解稿现在写成什么样 · 覆盖了哪些章节 · 引用来源 | 原书、笔记、参考资料 |
| 系统排障 | 查到哪了 · 结论是什么 · 凭什么这么说 | 日志归档、历史案例 |

V2 的「文档画布 + 协作 Dock 对半」只有代码场景勉强成立；写作场景下右侧会话基本闲置。

## 2. 核心对象关系

```text
Space
├─ AI Members
├─ Skills
└─ Projects
   └─ Project
      ├─ Workspace：真实文件和执行边界（机器的工作区）
      ├─ Resource Library：文档、笔记、素材、知识（用户的资产）
      ├─ Issue：目标与生命周期
      │  ├─ Primary Thread：完整活动线
      │  ├─ Rooms：阶段协作现场
      │  │  ├─ Room Thread
      │  │  └─ Work Graph
      │  ├─ Runs / Attempts
      │  ├─ Artifacts
      │  └─ Evidence
      └─ Project Thread：项目级会话（不绑定任何 Issue）
```

两条约束：

- Room 是 Issue 某个阶段的协作与控制边界，不拥有第二套执行状态机；Run 仍是实际执行记录。
- **Workspace ≠ Resource Library。** 前者是 Agent 的执行边界（`server/src/…`），是机器的工作区；后者是用户拥有的、跨任务的长期资产。V2 把两者混在同一棵「资源」树里，V3 拆开：资源库常驻左栏，Workspace 目录不常驻，从成果面的「改了 N 个文件」点进去。

### 2.1 用户语言

界面默认使用结果语言；英文领域名只在技术文档、诊断信息或二级说明中出现：

| 领域对象 | 用户界面名称 |
|---|---|
| Issue | 任务 |
| Thread | 会话 |
| Room | 协作现场 |
| Workspace | 代码目录 |
| Run | 执行记录 |
| Artifact / Evidence Summary | 阶段成果 / 完成摘要 |
| Resource Library | 资源库 |

## 3. 一级工作面

一级入口**带文字**（V2 的纯图标栏辨识度不足，且 PRD §10 要求执行能力一级入口可见），**钉在左栏最底部**，分上下两组：

| 组 | 入口 | 回答什么 |
|---|---|---|
| 在做的事 | 项目工作台 · 会话 · 项目 · 自动化 | 现在有什么在推进 |
| 积累与治理 | 记忆 · 能力 · 统计 · 设置 | 攒下了什么、系统本身好不好 |

位置在底部而不是顶部，理由见 §4.1：让「换工作面」（一级）与「换看什么」（二级）在空间上彻底分开。两组之间留一个分隔，**设置永远排在最后一个**——它是频率最低的一面。

### 3.1 项目工作台

默认主页面，见第 4 节。

### 3.2 能力面

**这一面装的是「缺失了也不影响核心链路正常运行」的东西**——它是可选能力的**容器**，不是某一类对象的管理页。

架构判断见 `docs/decisions/0018-capability-library-and-packs.md`，这里只定界面上必须表达什么。

**中心问题是「平台基础之外我有哪些能力、这一次用哪个」**。结构照记忆面：没有左框——tab 之间是并列的几组东西，不是一棵树。

**没有「AI 成员」这一层**：能派出去的最小单位就是**执行组合**（adapter × 配置 × 模型 × 深度，例如 `codex-gpt5.6-high`；adapter 只有一份配置时省略配置段，四个维度见 ADR 0012 第 2 条与 §3.5），有哪些组合由设置 · 运行时的 adapter 检查决定，不在这里增删。

#### 3.2.1 判据：核心层与可选层，依赖方向单向

```text
核心层（宿主拥有，缺一个产品就不成立）
  项目 · Issue · Room · Run · Artifact · Evidence · 记忆 · 统计 · 设置
        ▲ 可选层可以调核心层，反向禁止
可选层（插件贡献，挂这一面，任意一个缺失都不影响上面）
  Skills · 后续插件贡献的 tab
```

把这一面整个拿掉，仍然能手工建 Issue、拉 Room、派工、验收、沉淀记忆。**缺的是管理界面，不是能力本身**——已存在的 skill 数据在宿主，派工弹层照样引用得到。

由此得到一条**可判定**的插件准入规则，它同时解释了设置为什么把运行时与插件分成两组（§3.5）：

| | 缺失时核心链路 | 归属 |
|---|---|---|
| RSS 订阅、Skills 管理 | 不受影响，照样干活 | **可以在这一面开 tab** |
| adapter | 派不了工，产品不成立 | **永远在设置 · 运行时**，不进这一面 |

#### 3.2.2 容器结构：tab 由插件贡献，宿主只提供 tab 栏

宿主提供的只有 tab 栏与挂载点，**每个 tab 都可停用**（在设置 · 插件里停）。停用是注册/注销级的：tab 立刻不再渲染，不做进程内模块卸载（边界见 ADR 0018）。

三条硬规则：

1. **不按插件分 tab，按贡献物类型落面。** 一个只含三条 skill 的能力包不占格子，它的内容填进 Skills tab；只有带自己数据与视图的 T2 插件才开新 tab。这是 §3.2.3 那条判断的延续：**来源是治理维度，不是查找维度。**
2. **停用后这一面可能为空**，此时显示一句话加一个跳设置 · 插件的入口，不显示空表格——空表格会让人以为数据丢了。
3. **贡献物落到回答同一个问题的那个面。** 抓来的资料进资源库、定时规则进自动化中心、adapter 进设置 · 运行时；只有「既不属于已有面、缺了又不影响主链路」的东西才在这里开 tab。

#### 3.2.3 Skills tab：一张表，编组是带 `steps` 的 skill

**没有独立的「编组」类型。** 一套 schema，`steps[]` 是可选字段：有 steps 就显示步数并自动带 `#编组` tag，没有就是一条普通 skill。

列：`名称 · tags · 要求 · 步骤 · 来源 · 状态 · 上次用于`。按 tag 筛选，`#编组` 只是众多 tag 之一。

**为什么不做成两个类型**：一条 skill 用熟了想固化步骤，两个类型就要「转换类型」，历史表现跟着断；而 ADR 0012 第 5 条要防的正是「编组积累成身份」，**一个可来可去的 tag 比一个独立类型离那个失败模式更远**。

**来源列是标记，不是组织维度。** 每行标出它来自哪个包，点击跳设置 · 插件的对应行。**不把能力包做成一级组织**——那会让使用者为了找一个 skill 先回忆它属于哪个包。这与 §3.6.2 第 3 条「来源包放次行」是同一条判断。

详情页由 `steps` 有无决定长相：有 steps 的显示步骤 × 组合 × 上下文围栏加 §3.2.4 那句现算的表现；没有的显示 §3.2.5 的要求 tag。

#### 3.2.4 编组的表现是一句观察，不是一个分数

**列表本身不带表现列**，因此这张表**不可按表现排序**。

ADR 0012 第 5 条的防护条款是硬约束：**Squad 不产生持久身份**——否则用久了一个「架构师编组」就变成了一个成员，被取消的固定角色从后门回来。同一条的补充说明也写清了它约束的是**身份积累而不是观察**，界面按这条区分来做：

| 允许 | 不允许 |
|---|---|
| 详情里现算一句：「用过 12 次，验收一次通过 9 次」 | 把它凝固成挂在这条 skill 上的评分（「这个编组 87 分」） |
| 同屏并列出它各步骤所用组合的表现，标明是哪几个组合 | 编组排行榜；列表按表现排序；编组维度进统计模块 |

**为什么两者都要在场**：组合级数字回答「这几个执行者本身行不行」，编组级那句话回答「这套步骤和围栏加上去之后行不行」——后者正是 `steps` 这个字段存在的理由，只看组合级数字就看不见它。

三条界面硬规则：

1. **现算，不落字段。** 那句话来自 Run 记录（含当次的 `id@version`），改一版就是另一段样本，界面要写出统计的是哪一版之后的。**本地自建的 skill 与编组同样按 `id@version` 记录**，不因为「不是从包里来的」而例外（ADR 0018 第 5 条规则五）。
2. **一律标样本量**，派工次数不足 30 次标「样本不足」（同 §3.4 失败页规则）。
3. **不合成「推荐度」分数**——理由同 §3.6.1：三个数字并排摆着，读者仍会自己把它们加起来，而合成之后就再也拆不开了。

#### 3.2.5 Skill 声明「要求」，不声明「配谁最好」

Skill 表的 **要求** 列是结构化 tag，写这条做法**至少需要什么能力**（`架构` / `深度分析` / `工具循环`）。它汇进派工弹层顶部那排「这一步需要什么」（§4.6 第 2 条，与工作流步骤的要求取并集）。

**只写要求，不写偏好。** 一条界：

> **「这条 Skill 要求什么」建模；「这条 Skill 配哪个组合最好」不建模。**

后者是 `steps`（§3.2.4）的事。写进 Skill 会撞三处已有判断：

1. **第二套路由信号。** §3.5 已为标签写过同一条：「把标签做成路由信号会让两套判断互相污染」。编组说一套、Skill 说一套、弹层三档说一套，冲突时没有答案。
2. **Squad 防护条款从后门失效。** ADR 0012 第 5 条：「Squad 不产生持久身份，历史表现记在组合上——否则用久了一个『架构师编组』就变成了一个成员」。Skill 带偏好组合是同一个机制换了个位置：用久了「这条 Skill 属于 opus」，取消掉的固定角色照样回来。
3. **ADR 0007 的边界。** Coordinator 是进程内确定性规则引擎，消费不了自由文本。「这条 Skill 和这个组合搭配效果好」若不是结构化 tag，就得靠语义判断，那是突破 ADR 0007，必须单独立决策。

**想要证据驱动的「强强联合」，走历史表现，不走字段。** 记录 `(Skill × 执行组合)` 的结果，让弹层的「建议」档引用它——「这条 Skill 过去 14 次配 `codex-gpt5.6-high` 成功率 12/14」。数字带样本量、不合成推荐度分数（同 §3.2.4）。ADR 0012 的已知未闭合项已写明「Squad 的智能指派尚未有可行性验证，需要攒够历史表现数据才能判断」——**在没有数据时先把偏好写死成字段，之后就再也验证不了它错没错。**

#### 3.2.6 插件的 tab 是声明出来的，不是插件自己画的

T2 插件在 manifest 里**声明**一个 surface，宿主用自己的组件渲染；插件不提供任何前端代码。契约见 ADR 0018，界面上必须表达的是：

```yaml
surfaces:
  - id: inbox
    label: 订阅
    kind: table                      # 宿主提供的形态，当前只有 table
    columns: [标题, 来源, 抓取时间, 状态]
    actions:
      - { id: archive, label: 归档,     target: host.library.archive }
      - { id: dig,     label: 深入拆解, target: host.issue.createWithRoom }
```

四条硬规则：

1. **动作只能引用宿主白名单。** 「深入拆解」走 `host.issue.createWithRoom` 而不是插件自己拼一条捷径——这是 §3.3.3 裁掉 `run_only` 那条判断的同一个理由：**任何一次真正执行都必须有 Issue / Run / Attempt / Artifact / Evidence 的来源链**，走白名单这条链才是自动完整的。
2. **挂载点只在这一面的 tab 内。** 不进协作 Dock、不进派工弹层、不进 §3.2.7 的「本次生效组合」视图——那些是证据视图，必须由宿主独占渲染。
3. **数据真相源留宿主。** 插件贡献界面与抓取逻辑，不贡献存储；`id@version` 由宿主钉。
4. **插件能新增数据，不能新增交互范式。** 需要第二种 `kind` 时那是宿主的一次性投入，不是插件能带进来的东西。理由是本机没有沙箱：允许插件提供渲染代码等于允许它读 DOM 与调用宿主全部 API，而凭据就在设置 · 运行时。

**归属项目在动作里问，不在抓取时定。** 抓来的东西尚未归属任何 Project（资源库挂在 Project 下，见 §4.1），因此「归档」必须带一个选项目的步骤，「深入拆解」则由新建 Issue 时确定——**先看到、再决定要不要为它开项目**，反过来会逼使用者在还没读之前先分类。

#### 3.2.7 「本次生效组合」——可解释性的落点

一处视图，在**派工弹层**和**执行记录**里各出现一次：这一次派工，agent 看到哪些 skill、受哪些硬规则约束、上下文围栏拦掉了什么，**逐条列出并标明每条来自哪个包**。

它兑现的是两处已有承诺：§4.6「把判断依据摊开」和 §3.6.4「过滤不能是静默的」。能力包进场之后，**只有这个视图能回答「为什么这次的验证结论和上次不一样」**。

三条硬规则：

1. **硬规则区与可覆盖区分成两块。** 上半是不可覆盖的底座（实现与验证不能同源、`claimed` 不进验证类上下文），下半才是能力包贡献的默认行为。能力包可以把规则改得更严，界面要标出「本次被某包加严」；**放宽是不可能的，因此界面上没有这个表达**。
2. **拦掉的要显示。** 围栏过滤了几条、因为什么，压暗但在场。
3. **每一条都带来源，且点得进设置 · 插件的对应包。** 没有来源标记的行不允许出现在这个视图里——那意味着有东西绕过了准入进入上下文。

### 3.3 自动化中心

管理 Scheduled Issues、Webhook、执行队列和历史。自动化只负责创建或推进 Project 下的 Issue，不形成第二套任务体系。

#### 3.3.1 一条自动化保存什么

一条规则由四部分组成：**Runbook、任务模板、执行方案、触发器集合**。Runbook 说明每次都要完成什么；任务模板固定项目、标题、标签与上下文范围；执行方案引用已存在的 Workflow 与执行组合；触发器只回答何时开始，可以同时有多个时间表和 Webhook。权限边界属于规则本身，不属于某个触发器——换一个入口不能扩大权限。

规则清单只做定位，按「需要人处理 → 下次触发时间」排序。运行历史不混进左栏：它属于某一条规则，放在详情的「运行记录」tab。黄点只表示需要人处理，不等于所有失败都抢到列表最前。

#### 3.3.2 四层详情

1. **概览**：下一次、最近一次、近 30 天健康度；完整展示「触发 → 准入检查 → 建任务 → 工作流 → 执行组合 → 任务验收面」；Runbook、任务模板与能力边界同时在场。
2. **触发器**：时间表显示人话描述、5 字段 cron、IANA 时区和至少 3 个下次时间；Webhook 显示事件过滤、HMAC 签名、幂等策略及默认隐藏的凭证 URL。
3. **运行记录**：一行是一份触发意图，分别显示来源、准入结果、关联任务和任务结果。`未触发`（准入前挡下）、`失败`（已经执行）、`已暂停`（不再受理）是三个不同状态，不互相代替。
4. **Webhook 投递**：审计接收、鉴权、过滤、去重、分发与响应；原始 Body 受大小和脱敏限制。重放创建新投递与新运行，用 `replayed_from` 指回旧记录，绝不改写历史；签名失败、排队中或已过滤的投递不可重放。

#### 3.3.3 从 multica 保留与裁掉的内容

- **保留**：版本化 Runbook、多触发器、定时可视化 + cron、下次时间预览、Webhook URL 轮换、事件过滤、签名、幂等去重、投递审计、手动立即运行与运行来源。
- **改写**：multica 的 Agent / Squad 改成 PersonaHub 的 Workflow + 执行组合；Project 可选改成 Project 必选，因为自动化必须落到普通任务。
- **裁掉 `run_only`**：任何一次真正执行都必须有 Issue / Run / Attempt / Artifact / Evidence 的来源链。静默后台运行只把结果留在自动化历史里，会形成第二套不能验收、不能交接、不能沉淀记忆的任务体系。
- **裁掉订阅者**：当前产品是个人优先，通知对象没有真实选择空间；后续多人协作出现时再按真实需要引入。

#### 3.3.4 启用、暂停与准入

新规则保存为**暂停**，并先做项目、Workflow、运行时、额度、权限与触发器配置预检；预检通过后由使用者明确启用。立即运行走同一套准入检查，不是绕过规则的调试后门。

每次触发先记录触发意图，再依次检查：规则启用、触发器启用、幂等/并发、项目与 Workflow 可用、执行组合运行时、额度、能力边界。被挡下时写 `未触发 + 原因`，不建立伪 Run，不自动换便宜模型，也不降低权限硬跑。同一规则默认只允许一个活跃任务；重复事件合并到现有任务并保留投递关联。

### 3.4 统计

回答「过去这段时间发生了什么」，**全屏不出现一个实时数字**。口径与维度的决策见 `docs/decisions/0017-usage-accounting-and-stats-surface.md`，这里只定界面上必须表达什么。

**结构照记忆面，不照任务面。** 任务模块是「列表 → 单个任务的 tab → tab 下内容」，因为任务是实体，有实体就有列表；统计没有一条条实体可列，使用者选的不是哪一条，而是**看哪一类问题**——所以进来就是 tab 页，没有左列表。只有两个 tab：**用量**（花了多少）与**失败**（哪里坏了）。

**控件位置即作用域**（照 multica 的统计页）：tab 行左边切视图、右边放页级筛选（时间范围、项目），每张卡自带自己的形态 / 维度切换。周期在右上角，因为它管整页；形态在卡内，因为它只管那张图。

八条判断：

1. **主维度是「去向」，不是执行者。** 两个参考项目都按智能体排行，是因为 agent / cat 是可治理的对象——看完排行榜能去关掉它。本项目在 ADR 0012 里取消了这一层，照抄会得到一张每行都没有对应动作的表。因此详情表主维度为**任务**，第二维度为**用途**（实现 / 验证 / 返工重试 / 上下文重传）；模型与执行组合退为同一张表的第三、四个维度，定位是**单价基准**而非排行榜。
2. **实付与订阅等价是两个数字，永不相加。** 走订阅的 adapter 配置消耗的 token 不产生新增支出、只消耗额度；走 API Key 的配置不消耗额度、但每个 token 都构成实际支出。等价一行必须标注「非实际账单」——它只是按公开 API 定价折算的结果。
3. **Token 拆成缓存命中 / 未命中。** 缓存命中是从 prompt cache 读取、按折扣价计费的部分；未命中是本次真正处理的输入加上全部输出（输出永远不进缓存）。两列相加等于该行全部 token。拆这一刀是因为它对应可调的旋钮：命中率掉下来说明 resume 冷启动了，「上下文重传」那一行的未命中量就是收窄上下文范围能省下的上限。四个维度是同一批 token 的四种切法，命中 / 未命中的合计必须完全一致。
4. **计价来源必须显式标注。** adapter 自报为权威值，本地价表折算为估算值；两者合并为单一数字后将无法区分可信部分。
5. **额度不在这一面。** 额度是 Runtime 的实时状态（ADR 0012 第 3 条），它回答「今天还能不能派一次 high」，属于前瞻；统计是回顾。同屏并列会让页面上出现两个时间口径的数字。额度在设置 · 运行时的配置（§3.5.3），消费点在状态栏与派工弹层。
6. **详情表分页，合计行常驻。** 任务维度会长到上百行，按主指标降序每页 10 条；合计行置顶（紧贴表头、不带页码、不随翻页变化）——分页不得让各列与上方 KPI 对不上账；不设「本页合计」，页内小计不回答任何问题。行数为个位数的维度不分页，同样带置顶合计行。不用「其余 N 个」聚合行代替——它点不动、不可下钻，只为让列能加起来而存在。**指标不进状态列**：「返工占比」独立成列并写明口径（该任务返工重试的 token ÷ 该任务全部 token），加权后等于「用途」维度的同名占比；混进状态列会得到一个既非状态、又无从核对的值。
7. **第三级明细不在统计模块内实现。** 点击任务行进入任务模块的**轨迹**视图——逐次调用的 token 明细本就在该视图内。统计模块只负责聚合与入口。
8. **年度热力图是趋势卡的第三种形态**（逻辑与样式照 GitHub 贡献图：0 单独一档 + 非零按四分位分四档），由周期决定是否可用：近 7 天只有按天，近 30 天有按天 / 按周，近一年有按周 / 热力图并默认落在热力图。不可用的形态**置灰而不是隐藏**——藏起来等于替使用者决定他不需要它。不做成页首常驻横幅：那样它固定显示一年，而同屏 KPI 跟随周期，页面上会并列两个口径。

**失败页只收录故障**：进程异常退出、权限拒绝、执行超时、adapter 错误。「验证未通过」属于正常过程而非故障，它体现在用量页的「返工重试」；「额度不足」当日未执行，记录在自动化面。将两者计入失败率后，该指标将无法再用于判断系统是否存在故障。派工次数不足 30 次的执行组合，失败率必须标注「样本不足」。

### 3.5 设置

管理任务前缀与标签、Workspace 权限、本地数据与健康诊断、adapter 与凭据、已装的能力包与插件。GraphRun、NodeRun、SSE、SQLite 等内部概念默认不向普通用户暴露。

分五组：**工作区**（任务前缀与标签）、**数据**（代码目录权限、数据与备份、健康诊断）、**运行时**（adapter、配置、凭据、额度）、**插件**（能力包与插件的准入、启用、冲突）、**其他**（首次设置向导）。

#### 3.5.1 运行时与插件分成两组，不合并

> **判据：装一个 CLI，和导入别人写的一套方法，不是同一件事。**

失败模式不同——前者是「起不了进程、登录过期、额度耗尽」，后者是「装了一半、和已有的重名」；处理动作也不同：前者去终端敲一条命令，后者在界面上选一个候选。合成一组会让一个面同时承担两种排障节奏。

分开还有一处**安全收益，必须写在设计里**：**凭据全部在运行时组，插件的挂载点全部在能力面（§3.2.6），两处不相交**。插件因此够不着任何 API Key 与登录态——这是允许插件声明 tab 的前提条件之一，不是巧合。

**「密钥存在哪」在数据组，不在运行时组**（V3.17 的结论不变）：它讲的是本机 SQLite 的 `agent_configs.api_key` 是明文列、数据库文件本身没有加密、**把数据目录放进同步盘或 git 仓库等于把 key 一起同步出去**。这是一条数据风险声明，不是某个 adapter 的属性——放在哪个 adapter 下面都是错的。

#### 3.5.2 工作区：前缀与标签

1. **改前缀是要确认的操作。** 任务编号一旦发出去就被引用——commit message、证据文件名、Markdown 导出，改一次要重命名全部已有任务，而写进 commit 和证据里的旧编号不会跟着变，只能留一条别名记录。
2. **标签不参与派工判断。** 它只是使用者自己维护的筛选层，用来筛任务和圈自动化规则的范围；派工靠工作流和能力边界决定。把标签做成路由信号会让两套判断互相污染。被自动化规则引用的标签删不掉：先解引用，否则规则会变成筛不到任何东西还照常触发。

#### 3.5.3 运行时组

管理 adapter（CLI 安装）、它们的配置、由此得到的执行组合，以及「现在能不能派工」的诊断。层级与四元组见 `docs/decisions/0012-object-model-simplification.md` 第 2 条。

**中心问题是「现在能不能派工；派不出去是因为什么」**，不是「我要维护我的 adapter 们」。

**这一组有左框，能力面与记忆面没有。** 判据是 §3.4 已经写下的那条：任务模块是「列表 → 单个实体的 tab → tab 下内容」，**因为任务是实体，有实体就有列表**；能力面与记忆的 tab 是并列的几组东西、不是一棵树，所以无框；而 adapter 是一条条实体——有名字、可增删、会扩展到更多 CLI。

##### 左框：adapter 列表

```text
● Codex CLI       0.42.0
● Claude Code     1.0.88
⚠ OpenCode        需检查
──────────────
＋ 添加 adapter
```

**没有「全部」总览行。** V3.16 曾有一行，理由是「它承载横向对比，否则能力矩阵会退化成三份互不相邻的清单」；能力矩阵删掉之后那条理由整条没了，V3.17 顺势把它一并删掉。**一个在原始理由被拆掉之后还需要重新论证的东西，通常是先有结论再找的理由。**

逐项核过它当时还装着什么，没有一样是无家可归的：

| 它装的 | 真正的家 |
|---|---|
| 「现在挡着派工的是什么」 | **左框自己就是这个**——三行灯 + 每行一句话说明哪一项坏了（下面第 2 条硬规则），已经把这个问题答完了 |
| 额度池总览 | ADR 0017 第 5 条已定死额度的消费点：状态栏、派工弹层、以及各配置自己那一行。总览是第四份 |
| 执行组合全表 | 每个 adapter 自己 2–3 行；「这一次能不能派给它」的答案在派工弹层 |
| 登录态与 API Key 表 | 每份配置在它自己的 adapter 下 |
| 「密钥存在哪」 | 它其实是**数据风险声明**，归 §3.5 的数据组（见 §3.5.1） |

**聚合视图的价值随 adapter 数量增长，N=3 时它只是三次点击的替代品**，而代价是每个 tab 都要维护「选全部」与「选一个」两套内容。装到十个 CLI 再说。

四条关于**状态灯**的硬规则：

1. **灯只有一个轴：这个 adapter 现在能不能被派工**，取所有检查项里最坏的那一项。不把「装没装 / 登没登 / 额度够不够 / 上次检查过没过」压成一个颜色梯度——理由同 §3.6.1：几个数字并排摆着，读者仍会自己把它们加起来，而合成之后就再也拆不开了。
2. **灯旁必须有一句话说明是哪一项坏了**，不能只有颜色。纯色块既过不了无障碍，也不满足 §6「能力缺失提前标注，不等点击」。
3. **per-project 差异不进灯。** 可用性本来就是 per-project 的（`agent_configs.project_id`，另有代码目录级 `effective_status` 覆盖），而灯是一个全局符号，表达不了「codex 在项目 A 可用、在项目 B 被停了」。项目维度进「配置」tab 的项目可用性列。
4. **现在叫「状态」，不叫「连接状态」。** 本机 CLI 没有「连接」，有的是装没装、登没登、能不能起进程；真正的连接维度要等 ADR 0015 的 `runtime_id` 落地（v0.7）才存在，届时在同一行加第二个符号，**不改这一个的语义**。

**「＋ 添加 adapter」走 T2 准入**（ADR 0018 第 4 节）：手工放进本地目录 + 逐项确认，且**「本机没有沙箱，它与 PersonaHub 同权运行」这句必须出现在流程里**。它不能长得像「新增一份配置」那种轻量动作——那是全产品风险最高的一个流程，界面上不能让它看起来最便宜。

##### 主面：两个 tab

**主面永远是某一个 adapter 的详情**，没有第二种形态：

| tab | 装什么 |
|---|---|
| **配置** | 该 adapter 的 N 份配置（认证 / `base_url` / 可用模型 / 额度 / 项目可用性）+ 由此得到的执行组合 |
| **诊断** | 该 adapter 的最近一次检查、近期失败、**做不到什么** |

两块真·全局的东西不进 adapter 视图，放在 tab 内容的**共用页首 / 页脚**：页首是「配置是什么」加一个新增配置入口，页脚是**额度告警阈值**（它是一条策略，不属于任何一个 adapter）。

**诊断 tab 的形态照 §3.6.3 记忆健康度**：每一行右侧必须有可执行动作（重新检查 / 给出登录命令 / 跳到那次失败的执行记录）。**只报数字不给动作的诊断页是债务展览馆。**

**没有「能力」tab。** V3.15 曾把 `AgentAdapterCapabilities` 的能力位做成一张跨 adapter 的矩阵，V3.16 删掉了，理由有三条：

1. **它被本设计自己的标准判了。** 那张矩阵的硬规则是「每一格都不可点、不可切换」——**一张全是不可点格子、且在同一个 CLI 版本内永不变化的表**，就是上一段说的债务展览馆。
2. **两个参考项目面对更高的异质度，都选择不给它界面。** clowder 适配 Claude Code / Codex / Gemini / OpenCode / Antigravity（`../../../../docs/research/clowder-ai-analysis-report.md`），它确实记录了逐 CLI 的输出格式与 MCP 状态差异——**但记在 README 里，不记在产品里**；multica 支持十来个 agent CLI（`../../../../docs/research/multica-analysis-report.md`），运行时页仍按**电脑**分组，不按能力。
3. **七个能力位里只有一个改变派工合法性。** 「原生记忆可关闭」决定这个 adapter 能不能当独立验证员；其余（权限拦截 / 结构化轨迹 / 完成摘要 / MCP 注入 / 超时 / 执行位置）只影响体验与可观测性。一条事实撑不起一个 tab。

**但那条事实必须有落点。** PersonaHub 是三个项目里唯一一个**能力缺失会让一条主张失效**的（ADR 0018 已记下这处不对称：「插件贡献物会影响『结论可不可信』……两个参考项目都没有这条约束」）。所以能力位降为**每个 adapter 诊断视图里的一块「这个 adapter 做不到什么」**，并且必须满足两条：

- **每一条写后果，不写能力位名字。** 不是「不支持权限拦截」，而是「派给它的活不会出现『等待权限确认』，写操作直接落盘」。
- **它是 §4.6 第 5 条与 §4.2 验证独立性卡的落点。** 从派工弹层的「结构性不具备」、从成果面的「该执行体无法保证独立性」点过来，落在**这一个 adapter 的诊断**上——使用者问的是「这一个执行体怎么了」，不是「三个 CLI 谁强」。

##### 防护条款：这一组不出现「偏好」字段

> **判据：如果一个字段的值改了之后，「派工时该选谁」的答案会变，那它就不属于这一组。**

按此判据，`base_url`、api key、认证方式**属于**——它们是「怎么连上去」的事实；「默认用它」「优先级」「别名」「角色」「擅长什么」**不属于**。后者一旦进来，adapter 就长成了 ADR 0012 第 2 条取消的「AI 成员」，被删掉的固定角色从后门回来。派工偏好归派工弹层（§4.6）与 skill 的 `steps`（§3.2）。

有了左框列表之后这条更要紧：**列表天然诱导排序、置顶和改名，而这三个动作全是偏好。**

##### 配置：额度与凭据

关于额度的三条判断（额度从原用量面搬来，见 ADR 0017 第 5 条）：

1. **额度是 Runtime 的字段，不是统计的一部分。** 它是本机资源的实时状态，和「装没装、登没登」是同一类事实，所以和执行组合表放在一起——那张表本来就有额度列。
2. **按 adapter 配置分池，不按模型。** 一份配置对应一份上游订阅或一个 API Key（ADR 0012 第 2 条：配置是携带认证与可用模型的那一层），所以同一份配置下的多个模型共用一个池，池子里列的是「或者」不是「以及」。额度挂在配置上，不随 Space 走。**不叫「账号」**：凭据只是配置的一个字段，而池子还受 `base_url`、可用模型这些同属配置的东西影响。
3. **额度不足不自动降级。** 更换更低成本的执行组合会改变结果质量，这属于使用者的质量判断，而非系统节省额度的手段。规则无法执行时应停止并记录一条「未触发 · 额度不足」——它与「已执行但失败」分开记录，前者不属于故障，但使用者需要知晓当日实际未执行。

关于模型与凭据的三条判断（页面结构照 clowder 的「账户与密钥」）：

1. **登录态与 API Key 分成两组，不共用字段。** OAuth 那一支的 token 由各个 CLI 自己存在自己的目录里，PersonaHub 只做**只读检查**并给出终端命令，不登录、不续期、不存 token。代管等于把三个 CLI 的凭据格式和过期策略全抄一遍，抄错一次就是静默失败。弹层里这一支**没有任何输入框**——出现输入框就说明抽象漏了。
2. **一份配置只能有一种认证方式。** 想两种都用就建两份配置，否则失败时分不清是哪条路断的。正名之后这条规则自解释了：配置就是「驱动这个 CLI 的一种方式」，一种方式当然只有一种认证。
3. **密钥的真实存放位置要写在界面上。** 当前实现是本机 SQLite 的 `agent_configs.api_key`（明文列，见 `server/src/db/schema-v6.ts`），接口只回「是否已配置」。数据库文件本身没有加密，所以「把数据目录放进同步盘等于把 key 一起同步出去」这句必须出现在页面里，不能只躺在架构文档里。删除一份配置会让依赖它的执行组合从派工清单消失，但历史 Run 保留当时的组合名——证据链不因今天删了份配置而断（`AdapterIdentitySnapshot.adapter_config_id` 是按配置冻结的）。

#### 3.5.4 插件组

管理已装的能力包与插件：准入、启用、停用、冲突、导出。三档信任与准入方式见 ADR 0018 第 4 节。

**组内分两个子区，因为两者的风险差着一个数量级**（ADR 0018 第 2 节：信任度不同的东西不能长得一样）：

| | 能力包（声明式） | 插件（代码） |
|---|---|---|
| 内容 | Skill（含带 `steps` 的编组）/ 协作图 / 输出契约 / 资料 | adapter、外部进程、带 surface 的功能模块 |
| 导入动作 | 读一个目录，校验通过即可启用 | 逐项确认后才允许运行 |
| 必须写在界面上的话 | 未知字段会被拒绝，包不会被部分导入 | **本机没有沙箱**：它与 PersonaHub 同权运行 |

> 组名用「插件」作为通称，是使用者的界面用词；ADR 0018 第 2 节「不把三者统一叫插件」的实质诉求——**风险不同的东西界面上不能长得一样**——由上面这个子区划分承担，不靠组名承担。

六条界面硬规则：

1. **「装了一半」必须显示出来。** 包内某一项校验失败时状态是**部分可用**，并列出是哪一项、因为什么；不能整体显示「已启用」。单个包坏掉只影响它自己，其余照常。
2. **T1 引用式贡献（定时规则、验收检查、MCP 声明）要显示它引用的是宿主的哪个白名单条目。** 使用者需要看见「这个包只是点了名，可执行的东西是我这边提供的」。
3. **声明不等于已生效。** 包里声明的每一项都带自己的状态；manifest 里写着的东西在准入之前只是候选，界面不得按声明渲染成已有能力。
4. **同名冲突由使用者选，不自动定优先级。** 两个包贡献同名 skill 时并置显示两个候选，选完记一条决定。自动优先级会让「为什么结果变了」不可解释，这与产品承诺冲突。
5. **停用一个包不改写历史。** 停用后它贡献的 skill 从派工清单消失、它声明的 tab 从能力面消失，但历史执行记录仍显示当时用的包名与版本——同 §3.5.3「删除一份 adapter 配置会让组合消失，但历史 Run 保留当时的组合名」。停用是注册/注销级的，不做进程内模块卸载。
6. **导出默认不含项目事实。** 把 Skill 导出成能力包时，Memory 原始内容、Evidence 与本机路径默认被剥离；导出弹层必须**逐条列出剥离了什么**，并让使用者看到剥离后的实际内容再确认。个人工具里这条是隐私边界，不是可选项。

### 3.6 记忆

产品判断见 PRD 第 5 节，结构决策见 `docs/decisions/0016-memory-state-machine-and-provenance.md`。这里只定界面上必须表达什么。

**记忆不是笔记本。** 它只由已收敛的验收事件写入，不从对话自动摘取。所以这一面的中心问题不是「怎么记」，而是**「这条凭什么信、现在还算不算数、错了怎么撤」**。

三个 tab：**待确认**（候选裁决）/ **知识库**（在库的全部）/ **健康度**（哪里坏了）。没有左框——这三样是并列的三组东西，不是一棵树。

#### 3.6.1 三根轴是三列，不是一个分数

知识库的列顺序是刻意的：`强度 · 内容 · type · 层级 · 状态 · 验证于 · 引用`。其中三列构成三根互不替代的轴：

| 列 | 回答 | **不回答** |
|---|---|---|
| 强度 | 谁背书（`claimed` / `verified` / `confirmed`） | 它被用过几次 |
| 验证于 | 何时发生过显式验证事件 | 它现在是否相关 |
| 引用 | 被引用过几次 | 它是否为真 |

**不合成一个「可信度」分数。** 被用得多不等于被验证过，被验证过不等于你认可。列表末尾必须写出这句话本身——三个数字并排摆着，读者仍会自己把它们加起来。

由此得到一条界面上看得见的约束：`claimed` 行的「验证于」是空的（显示「— 未验证」）。**引用次数永远不会自己写进「验证于」，也不会自己提升强度。**

选列表而不是卡片的理由同 V3.9 修版：卡片管不动，同一个字段在不同卡里位置对不齐；而三根轴的全部意义就在于**能横着比**。

#### 3.6.2 状态是一列，退出召回要说出来

六个状态里有四个会出现在知识库：`在库` / `待复核` / `已退役` / `已遗忘`（`候选` 在待确认 tab，`已否决` 只留记录）。状态有自己的筛选组，与强度筛选**分开两行**——两根轴不共用一个筛选器。

三条界面硬规则：

1. **待复核必须说明它已经退出召回**，以及**是哪一版证据失效了**（`artifact:workspace-lock@2 → @4`）。只标一个灰 badge 不够：用户要判断的是「我还能不能靠它」。同一行还要堵死「它被引用 9 次所以应该还能信」——**引用次数不能替它续命**。
2. **退役与遗忘要分得开。** 退役行压暗（`.off`）但内容仍在，写明「退役不是删除：来源与证据全部保留，可以重新启用」；遗忘行的内容位显示「〔内容已按授权清除〕」，次行是墓碑——何时、经谁授权、因何原因、原任务是谁。**并注明遗忘前必须先退役，不能从在库一步删除。**
3. **来源包与关系放在次行**（`.dl-sub`），不另开页面：`origin_type` + 来源任务 + 证据 + 使用边界 + 一跳关系（引用了 / 被引用）。关系只显示一跳——个人规模下全局图是毛球，而一跳回答的是「改这条会影响谁」。

#### 3.6.3 健康度：每一行都要能点

五项债务：**过期 / 未裁决积压 / 孤立 / 冲突 / 未验证债**。

> **只报数字不给动作的健康页是债务展览馆。** 每一行右侧必须有可执行动作（逐条复核、批量裁决、试运行退役、并排对比、派验证）；批量操作一律**先试运行**——列出会动哪几条、动成什么样，确认后才执行。冲突只并排展示，**不自动合并**：判断哪条留下是语义判断。

这一面还要显示**写入侧本身是否正常**：近 7 天入库数、写入被拒绝次数、建关系失败次数。并写明一句：

> **「写入被拒绝」长期为 0 不一定是好事**——它也可能意味着写入这条路根本没被走过。两个都是 0，说明记忆系统已经死了，而它不会报错。

这是整个设计里唯一一处提醒「看起来健康」和「真的健康」不是一回事的地方。记忆系统坏在写入侧时是不报错的，健康度页是唯一能看见它坏了的地方——所以它的优先级排在检索增强之前。

#### 3.6.4 任务面的「资料 · 输入」要显示这次过滤掉了什么

记忆在任务里的另一半在 §4：资料面的「输入」方向除了「用到的知识」，还必须有一段**本次未进入上下文**——压暗但在场，并写明过滤了几条、因为什么（待复核 / 只是成员的说法）。

**过滤不能是静默的。** 你看到一个验证结论时，必须能知道验证者当时看不到什么；否则实现者的自述会经由记忆绕回来，而且是以「项目事实」的身份。

> **「开始中心」已取消独立入口。** 跨项目注意力降级为任务列表上的范围切换（当前项目 / 全部项目）。理由与待观察风险见 §7.1。

## 4. 项目工作台结构

### 4.1 左栏（248px）

**一栏、一个纵向列表、零个二级 tab。** 自上而下：

1. **工具条**：搜索 + 新建。
2. **范围切换**：当前项目 / 全部项目。
3. **单一列表**，由可折叠分节组成——「在做的事」在上，「积累的东西」在下：

| 分节 | 内容 | 默认 |
|---|---|---|
| 需要你处理 | 等你指派、等你确认权限、验证未收敛、刚创建 | 展开 |
| 正在进行 | 执行中的任务；Rooms 作为子项缩进，不伪装成同级对象 | 展开 |
| 最近完成 | 已完成且验证通过 | 展开 |
| 文档与素材 | 笔记、PRD、参考资料（用户资产，不是代码目录） | 收起 |
| 产出 | Artifact / 完成摘要的历史索引 | 收起 |
| 知识 | Decisions / Memory / Skill Candidates | 收起 |

4. **一级入口钉在最底部**，两组八个，清单与分组见 §3 开头；设置永远在最后一个。

两条依据：

- **V2 的四棵并列树**（任务/资源/产出/知识）要求用户先回答「我要找的东西属于哪一类」，是文件管理器思维。
- **V3.0 的「任务 | 资源库」二级 tab 同样不成立**：它和上方的一级入口都是按钮组，视觉上分不出谁管谁；实测左栏在看到任何内容之前叠了四层控件。对照冻结参考页，multica 与 dsh 的侧栏都是**单一纵向列表 + section label 分隔**，都没有第二层 tab（`ui-reference/multica/pages/issues.html`、`ui-reference/dsh/pages/home.html`）。

一级入口下沉到底部，让「换工作面」（一级）和「换看什么」（二级）在**空间上彻底分开**，不再是两组挨着的按钮。

### 4.2 主舞台：成果面（~60%）

**一次只判断一件事。** 舞台同时只显示一个成果面；tab 决定显示哪一个（§4.2.1）。

成果面自上而下四段：

| 段 | 内容 | 来源 |
|---|---|---|
| 标题区 | 任务名 · 当前状态 · 主操作 | V2 任务页 |
| **成果状态条** | 系统记录 / 实际变化 / 验证独立性 三卡 | V2 `evidence-summary` 升格 |
| 成果本体 | 文档正文 / 变更摘要 / 研究综述 / Artifact 内容 | V2 文档画布 |
| 完成要求与依据 | 逐条挂系统记录、实际文件、验证者结论 | V2 `evidence-summary` |
| 执行计划 | 这份成果是怎么来的（步骤 · 执行者 · 输入输出 · 证据） | V2 概览页搬入 |

**不使用百分比信任评分。** 可信度来自「结论旁能看到原始记录、谁验证、哪些没证明」。

**验证独立性卡受执行体能力约束,不只看「是不是同一个模型」。** 同源判定(PRD 第 7.5 节)是必要条件不是充分条件:验证方即使换了模型,只要它跑在**原生记忆关不掉**的 adapter 上(ADR 0011,当前是 OpenCode),它就可能读得到上一轮的实现细节,ADR 0012 第 4 条的上下文范围三档在那里保证不了。因此这张卡多一档判定:

| 情形 | 这张卡 |
|---|---|
| 换了模型 + 验证方 adapter 的原生记忆已关闭 | 绿勾「已独立验证」 |
| 换了模型,但验证方 adapter 的原生记忆关不掉 | **拿不到绿勾**,显示「有证据待验证 · 该执行体无法保证独立性」,并点得进该 adapter 的诊断视图（§3.5.3） |
| 同一个模型 | 「未独立验证」(原有判定) |

由此 §4.2.2 的「已完成」态**并非总能三张全绿**——这不是缺陷,是把一个原本静默发生的事实显示了出来。**能力不足是一种事实上的放宽**,ADR 0018 第 5 条硬规则二「只能加严,不能放宽」只管住了能力包,管不住执行体本身;这张卡是它在成果面上的唯一显形处。

代码文件与长文档从成果面点进去（「改了 3 个文件」），**在所属任务的 tab 内替换舞台 + 返回条**，不用覆盖层——长内容需要完整阅读宽度。文件视图保留 V2 的修改数量、位置标签和上一处/下一处跳转。

#### 4.2.1 任务 tab 条

**一个 tab = 一个任务的成果面。不是文件 tab。**

V3.0 删掉了 V2 的编辑器标签页排，理由是它「异质对象混装一排」。V3.1 恢复标签页排，但把那条理由变成规则本身：

| 规则 | 含义 |
|---|---|
| 只有任务能占 tab | 任务、协作现场、项目全景。文件、证据、阶段成果**不占 tab** |
| 子文档在所属 tab 内切换 | 点开「改了 3 个文件」不新开 tab；所属任务的 tab 保持选中，舞台顶部出现一条返回条 |
| 返回条不常驻 | 只在子文档时出现。否则 tab 条 + 面包屑会叠成两行 chrome |
| 单击 = 预览 tab | 从左栏单击打开的任务落在同一个**斜体预览 tab**，被下一次单击替换。进入子文档、或直接点这个 tab，就把它钉住 |
| 至少保留一个 tab | 关掉最后一个没有意义——舞台不能空着 |

预览 tab 直接回答 §4.5 对 V2 标签页排的另一半批评——「只增不减、无预览模式」。扫一眼五个任务只会留下一个 tab；真正开始做的那个才会被钉住。

「3 个任务 tab 对 1 个 Dock」的老问题由 §5 原则 1 解决：**切 tab 就是切任务，Dock 必然跟随**。因此不存在「对着错误上下文发指令」的窗口。

保留这条规则的代价：左栏已经列出全部任务，tab 再列一遍打开的任务，重复度比 IDE 高（IDE 是几千文件对十个 tab）。见 §7.4。

#### 4.2.2 七个任务态

同一套五段结构，**状态差异只体现在每段的填充程度，不换布局**。左栏点进任何一个任务，看到的都是同一张表的同一个位置。

| 状态 | 状态卡 | 本次成果 | 完成要求 | 执行计划 |
|---|---|---|---|---|
| 刚创建 | 三张全为「还没有」 | **空态**：还没有任何产出 | 你写的要求，全部无依据 | **空态** + 让 Coordinator 拟计划 / 自己指派第一步 |
| 执行中 | 系统记录「仍在增加」；验证独立性未达成 | 已完成的文件 + 正在写入的文件（虚线、不计入） | 已拿到依据的打勾，其余标「执行中 / 未开始」 | 当前步骤高亮，后续标「排队中」；正文顶部有常驻活动条 |
| 等待指派 | 验证独立性明确「尚未独立验证」 | 完整 | 最后一条是「还没有人验证过」，可预填验证指令 | 最后一步「等待你指派」 |
| 已完成 | 三张全绿，含验证者是谁 | 完整 + 完成摘要 revision | 全部可点到依据 | 全部完成 + **验证员的后续建议单独在场**，不被「已完成」吞掉 |
| Research 进行中 | 实际变化「0 个文件」——研究不改代码 | 固定为 revision 的**结论**，不是文件 | 前两条有结论支撑，第三条是阶段出口 | 并行检索 → 整理来源 → 收敛 synthesis_plan |
| 验证未收敛 | 验证独立性「2 次都未通过」 | 两轮改动**都保留**，验证不通过不回滚 | 被打回的那条展开两轮各自结论 | 两次失败**各占一步不合并** + 换策略的下一步 |
| 等待权限确认 | 实际变化「0 个文件」——暂停发生在写入之前 | 换成「你在批准什么」四条 | 全部待决定 | 被阻塞的那一步显式标出 |

两条判断：

- **空态不填占位数字。** 刚创建的任务显示「0 个文件」「还没有执行」，不显示进度条或预估。空白本身就是「还没发生」的证据。
- **「还没拿到依据」的完成要求可读但不可点。** 它们渲染成不可点击的行，避免伪装成「能点开证据」而点了没反应。
- **阻塞条自带动作。** 「在跑，不用你管」（执行中）用常驻活动条；「停住了，等你」（权限确认、验证未收敛）用阻塞条，允许/拒绝、预填改派指令**就在条上**，不需要先去右栏找。
- **两次失败各占一个步骤，不合并成「重试 2 次」。** 合并会抹掉「两轮是同一个执行者、同一个结论」这条最关键的事实——它正是「该换策略而不是再修一次」的依据。
- **验证不通过不回滚已有改动。** 换策略时它们是输入，不是垃圾。

#### 4.2.3 协作现场的舞台

协作现场不是任务，回答的问题也不同。PRD 第 5 节：

> Room 回答的是「这个阶段需要谁一起解决、采用什么协作模式、交付什么结果」。

因此它**沿用成果面的骨架，只换最后一段**：

| 段 | 任务成果面 | 协作现场 |
|---|---|---|
| 状态卡 ×3 | 系统记录 / 实际变化 / 验证独立性 | 阶段进度 / 几个组合在跑 / 交付契约达成度 |
| 目标 | 任务目标 | 阶段目标 **+ 为什么是这些人** |
| 本次成果 | 文件 + 阶段成果 | 本阶段产出 |
| 完成要求与依据 | 任务完成要求 | **交付契约与终止条件** |
| 末段 | 这份成果是怎么来的（线性 plan-list） | **谁在做什么（并行执行组合泳道）** |

**末段必须换。** Room 的本质是并行：三个执行组合同时在跑，线性 `plan-list` 只能说「第 2 步执行中」，说不了「三个组合各自到哪了」。泳道有三态——已交付 / 执行中 / 排队中，排队中的必须写明**前置为什么没满足**。

两条附带判断：

- **选人理由必须在场。** PRD 第 5 节明确要求 Human Lead 能「查看 Coordinator Agent 为什么创建该 Room，以及**为什么选择这些 agents**」。V3.1 之前原型里一个字都没有。
- **介入动作挂在泳道上，不做全局工具条。** PRD 列的六项 Human Lead 能力里，移除某个执行组合、指定某个 agent 接手、要求某个 agent 提供证据都是**针对具体那一条泳道**的；顶部三个通用按钮表达不了「改派谁」。

这样一来，协作现场的舞台与 Dock 面板是「结构视图 vs 对话流」，和「成果面 vs 任务会话」完全同构。整个产品只有一条规则：**舞台看结构，Dock 看对话**。

**一个任务可以有多个协作现场**（PRD `Issue.rooms[]`）。因此 Dock 的「协作现场」tab 必须显示**当前舞台所属的那一个**，而不是永远同一个——V3.1 之前打开 Research 现场，Dock 里显示的仍是 Implementation 现场。

### 4.3 右栏：协作 Dock（440px，常驻）

**常驻不折叠。** 当前阶段用户对 Agent 的信任尚在建立中，需要频繁盯会话；这是一条会随信任度变化的判断，见 §7.2。

结构自上而下：

1. **发送目标条（常驻）**：`指令将发送到 · <任务会话 / 协作现场> · <任务名>`。切换任务时 Dock 自动跟随；可显式固定某个 Room，固定后持续显示固定状态，避免向旧上下文误发指令。
2. **执行状态两行（常驻）**：谁在做 · 第几步 · 卡在哪。这是 V2「概览」页里唯一高频的部分，拆出来常驻，不再需要切 tab 才能看到。
3. **会话流**：任务会话 / 协作现场 两页。用户消息靠右，Agent 消息靠左，工具调用与执行事件折叠进 Agent 的那条消息。
4. **指派草稿 + 输入框**：等待指派时系统预填 `@执行组合 + 建议做的事`，随时可改。**不设独立的「照做 / 不照做」按钮**——按钮只有两种结果，不同意时用户得自己从头组织指令。

> V2 的「概览」tab 被拆解：高频的执行状态上提为常驻两行，低频的「详细执行计划」下沉到成果面（它本来就是「这份成果怎么来的」）。Dock 不再有第三个 tab。

#### 4.3.1 项目级会话

**当前没有选中任务时，Dock 显示项目级会话**，而不是空态或上一个任务的残留。

它不绑定任何 Issue，用来问「这个项目现在什么情况」「上周那批改动结论是什么」，也可以直接从这里发起一个新任务。这让 Dock 在任何时刻都有意义，也给了用户一个「和项目对话」而不是「和某个任务对话」的入口。

选中任务后，Dock 切到该任务的会话；项目会话仍可从发送目标条切回。

#### 4.3.2 两个会话的关系必须显式表达

Dock 顶部「任务会话 | 协作现场」两个 tab 并排，看起来像**两个聊天窗口**；实际是**一条主线 + 一个阶段的支线**。PRD 第 5 节的原话是：

> Thread 记录事情怎么一路发生，Room 组织谁一起解决其中某一段问题。

| | 任务会话（Thread） | 协作现场（Room） |
|---|---|---|
| 方向 | 纵向：创建到完成的完整生命周期 | 横向：只覆盖其中一个阶段 |
| 数量 | 每个任务恰好一条（v0.1） | 0 到多个，按阶段临时开 |
| 存在时长 | 与任务同寿 | 阶段结束即 archived，记录不删除 |
| 有无参与者名单 | 无。是你和系统的主控制线 | 有：执行组合 + 拓扑 + 交付契约 |
| 下一条指令发给谁 | **这里** | 不在这里 |

数据上的区别是 `Thread.room_id`：为空是任务会话，有值是某个协作现场的会话——**协作现场里也有对话**，这正是最容易混的地方。

**因此两个面板各自带一行来源说明**，不依赖用户已经知道 Thread / Room 模型：

- 任务会话：「贯穿这个任务的全程 · 每个任务只有一条 · 要下指令、改目标、指派下一步都在这里」
- 协作现场：「只覆盖 *Implementation* 这一个阶段 · 属于任务「⋯」· 3 个执行组合 · 阶段结束后归档，记录不删除」，任务名可点回成果面

两个 tab 另有 `title` 悬停说明（§6：能力与边界提前标注）。

**这条是 V3.1 补的**，起因是设计过程中自己都要回查 PRD 才说得清两者区别——设计者需要回查，用户就一定会问。

### 4.6 执行组合选择器

指派前要选一个执行组合。**这不是从一份平铺名单里挑一个,而是一次要向 Human Lead 解释的判断**——这正是产品「可解释」承诺最该兑现的地方之一。

名单本身不在这里维护：有哪些组合由设置 · 运行时（§3.5.3）的 adapter 检查决定，弹层只负责选和解释。因此选择器有八条规则:

1. **硬约束先说,名单后给。** 弹层顶部先写这一次选人的规则,例如验证角色写「实现与验证不能同源(PRD 第 7.5 节)。同源看的是**模型**,不是深度——同一个模型换个深度再验一遍,验的还是它自己」。放在名单后面等于让用户读完才知道有规则。
2. **「这一步需要什么」由两处贡献,取并集。** 要求 tag 有两个来源——**命中的 Skill**（A）与**工作流 / 编组这一步**（B）——**不设优先级,取并集**。要求的语义是「这一步至少要满足什么」,并集只会更严不会更松,因此天然没有「冲突时听谁的」;这与 ADR 0018 第 5 条硬规则二「只能加严,不能放宽」是同一条判断。弹层顶部那排 tag **必须逐个标出它从哪来**,理由同 §3.2.7「没有来源的行不允许出现」。

   两个来源各自补对方的洞：B 最准但 ad-hoc 派工（直接在会话里说一句）没有步骤,等于不设防;A 覆盖 ad-hoc,但只有**派工前就能确定命中**的 Skill 才算数——按触碰路径命中的那类,派工时还不知道会改哪些文件,算不出来。**算不出来的不猜,不进这一排。**

3. **每一行都写明为什么。** 分建议 / 可选 / 不可选三档,理由具体到这一次:「本次实现就是它做的,自己验自己不成立」「登录状态需要重新检查,现在派过去会直接失败」。

4. **三档的分界是「能不能」,不是「好不好」。**

   | 档 | 能不能选 | 落在这里的是 |
   |---|---|---|
   | 建议 | ✅ | 满足全部要求 |
   | **可选** | ✅ | **不满足某项要求**——它是质量判断,归使用者 |
   | **不可选** | ❌ 置灰 | 硬约束:同源、登录未确认、额度不足、兼任、结构性不具备 |

   **中间那档叫「可选」而不是「不建议」,末档叫「不可选」而不是「不建议」。** 早期版本把硬禁止那一档标成「不建议」——一个读到「不建议」的人会以为自己能坚持选,实际点不动,这与第 1 条「硬约束先说」的意图相反。

5. **不可选的不隐藏,只置灰。** 藏起来等于替用户做了判断,而这里的承诺恰恰是把判断依据摊开。

6. **不满足要求可以派,但要留痕。** 系统不挡「拿 `haiku-4.5-low` 跑架构设计」——先用便宜组合过一遍草稿、试试 Skill 写得对不对,都是明知它弱就是要它便宜,而 §3.5 已经裁定「更换组合会改变结果质量,**这属于使用者的质量判断**」。系统既不替你降级省钱,就不该替你升级保质。

   代价是这次产出的主张上必须留一条标注：**「本次由不满足 `架构` 要求的组合执行（`claude-haiku4.5-low`）」**,并在成果面的「这份成果是怎么来的」里可见。形态照 ADR 0012 第 4 条的保护条款——把验证上下文手动改回「全部」时不禁止、但结论降级。**推翻默认可以,但不能静默地推翻。**
7. **不可选与「可选但不满足要求」的理由分三类,混成一条就废了。**

   | 类 | 说的是 | 会不会变 | 理由指回哪 |
   |---|---|---|---|
   | 额度不足 | 今天跑不动 | 明天可能就能用 | 设置 · 运行时的额度池（§3.5.3） |
   | 能力不匹配 | 这一步不该用它 | 换一步就能用 | 这一次的任务性质 |
   | **结构性不具备** | 这个执行体给不出本步要的保证 | **既不随时间也不随任务变化** | 该 adapter 的诊断视图（§3.5.3） |

   前两类落「可选」或「不可选」要看具体哪一项：额度不足与结构性不具备是硬的（不可选），能力不匹配是软的（可选）。

   第三类是 V3.14 补的。它与前两类的差别不是程度而是性质：额度会回来、任务会换,而**一个 adapter 关不掉原生记忆这件事,等到明天、换个任务也还是关不掉**。把它混进「不建议」,使用者会以为再等等、或者换个说法就能用它——而实际上这一格永远不会亮。

8. **结构性不具备的行必须写出后果,并点得进该 adapter 的诊断视图。** 不写成「不建议」三个字,写成「它的原生记忆关不掉(ADR 0011),读得到上一轮的实现细节,这次验证不构成独立验证」。这条和 §3.2.7「每一条都带来源,且点得进设置 · 插件」是同一条判断:**没有来源的禁用理由等于没有理由**,使用者只能选择相信或者绕过它。

三个角色各有自己的判定规则:

| 角色 | 硬约束 |
|---|---|
| 实现者 | 无硬约束;换人不丢已有改动。登录未确认的不可选 |
| 独立验证员 | **不能是本次实现者**(PRD 第 7.5 节);**且其 adapter 的原生记忆必须可关闭**(ADR 0011)——关不掉就读得到上一轮,独立性从一开始就无从保证 |
| 综合员 | **不能是参与本阶段检索的研究员**——兼任会偏向自己那份结论 |

两处全局不可选,理由不同因而措辞也必须不同:

- **登录状态未确认(`需检查`)**:在所有角色下不可选——派过去会直接失败,让它可选等于制造一次注定失败的执行记录。**这是可恢复的**,理由里要给出终端命令。
- **能力位不满足本步的硬约束**:也不可选,但**不可恢复**——它不是「还没弄好」,是「这个执行体就不提供这个保证」。两者用同一句「不可选」会让使用者去做一件根本做不成的事。

## 5. 关键交互原则

1. **舞台是单例，Dock 跟随舞台。** 切换文件、Artifact、证据、知识不改变 Dock；切换任务必然切换 Dock。
2. **任务像工作文档。** Task 不是字段表格，而是目标、决策、活动、产出和验收条件的持续记录。
3. **证据可双向追溯。** 从结论能到原始事件，从文件或 Artifact 能看到由谁、在哪次尝试中产生。
4. **注意力高于时间。** 任务列表优先显示需要用户动作的对象，而不是最近更新时间。
5. **高级内部信息渐进披露。** 默认展示结果语言，诊断层才出现 Run ID、事件、命令和底层错误。

## 6. 反馈与状态表达

V2 把新建、指派、预填、暂停、跳转、发送、缺失说明全部塞进同一个 2.2 秒 toast。V3 分三类：

| 类型 | 表达方式 | 例 |
|---|---|---|
| **状态变更** | 持久可见，不消失 | 已暂停 → Dock 内常驻横幅「已暂停 · 3 个步骤在队列等待 · [恢复]」 |
| **操作确认** | 短提示，可消失 | 「已把建议指令写入输入框」 |
| **能力缺失** | `title` 提前标注，不等点击 | 「本轮草案未覆盖：设置 · 运行时的配置」 |

**指派有撤销窗口。** 发出 `@执行组合` 指令后进入「正在启动… [取消]」，而非立即判定「已指派」。指派与否由派工结果决定，不由文本前缀猜测。

这条 V3.1 已落地：撤销条常驻 Dock 顶部（不是 toast，因为它必须撑满整个可取消窗口），文案明说「还没有真正开始执行，现在取消不会留下痕迹」；窗口过去后变成「已开始执行」并撤掉取消入口，随后自行退场。取消不产生执行记录。

## 7. 待观察的判断

这些是本轮明确选择、但需要真实使用验证的决定。效果不佳时按备选方案切换。

### 7.1 「开始中心」降级为范围切换

- **现选**：删除独立工作面，任务列表顶部加「当前项目 / 全部项目」切换。
- **风险**：用户常态是同时推进 2 个项目并行 vibe coding，来回切范围可能比切页面更烦。
- **触发切换的信号**：一天内范围切换次数 > 10，或用户反馈「找不到另一个项目在等我的事」。
- **备选**：恢复独立的开始中心工作面（跨项目时信息组织本来就不同）。

### 7.2 协作 Dock 常驻不折叠

- **现选**：常驻 440px，因为当前对 Agent 的信任仍在建立中。
- **风险**：信任建立后，440px 长期显示一条已读完的会话是浪费。
- **备选**：默认收成竖条，有新消息或需要指派时自动展开。

### 7.3 资源库收成左栏的三个可折叠分节

- **现选**：左栏是单一纵向列表（§4.1），资源库退化为下半部的三个分节——文档与素材 / 产出 / 知识，默认全部收起。V3.1 已删掉「任务 | 资源库」二级 tab（§4.5）。
- **风险**：产出的历史检索路径变长一层；分节收起后资源库在视觉上几乎不存在。
- **备选**：产出恢复为独立分节并默认展开。

### 7.4 任务 tab 与左栏任务列表重复

**判断**：舞台顶部的任务 tab 和左栏的任务列表列的是同一批对象，只是 tab 是「打开的」子集。

**支持保留的理由**：tab 保留每个任务的滚动位置与展开状态，两个项目并行时切换成本明显低于每次回左栏点一遍（这正是 §7.1 记录的场景）。

**触发调整的信号**：常开 tab 数长期 ≤ 2，或使用者反映「两处都在看任务，眼睛不知道该看哪」。

**调整方向**：把左栏任务列表默认只展开「需要你处理」，其余两组默认收起——分节折叠已经就位，改默认值即可，不动结构。

### 7.5 跨项目资料没有落点

**判断**：资源库挂在 Project 下（ADR 0012），而 Issue 有游离态（`project_id` 可空）、资源没有。抓取类插件（§3.2.6）拿回来的东西在归档之前不属于任何项目。

**现选**：不为资源引入游离态，由插件 surface 自己承载「还没归属」的那一段——归档动作带一个选项目的步骤，深入拆解则由新建 Issue 时确定。

**触发调整的信号**：出现第二个抓取类插件，各自维护一份「未归属」列表；或使用者反映「抓回来的东西找不到在哪」。

**调整方向**：给资源补一个与 Issue 对称的游离态，未归属资料进一个跨项目的收件视图。这会新增一个一级面，代价明显，因此要等真实信号。

### 7.6 声明式 surface 只有一种 `kind`

**判断**：插件的 tab 由宿主渲染（§3.2.6），当前只提供 `table` 一种形态。第二个插件需要时间线或列表-详情时，就要宿主再建一种。

**支持保留一种的理由**：形态是宿主的一次性投入，预先建三种等于为还没出现的插件先付账；而 ADR 0014 第 1 节的门控本来就是「有真实需求再开缝」。

**触发调整的信号**：第二个 T2 插件落地，且它的内容用表格表达明显别扭。

**调整方向**：加第二种 `kind`，不开放插件提供渲染代码——后者的理由（本机没有沙箱）不随 kind 数量变化。

## 8. 与 V2 的差异及理由

| V2 | V3 | 理由 |
|---|---|---|
| 中间画布 39% + Dock 39% | 舞台 ~60% + Dock 440px | 参考产品的主舞台都占约 60%；对半劈导致没有主角 |
| 画布 = 打开任意对象的容器 | 舞台 = 成果面 | 舞台要承载产品的独有承诺，而不是做一个通用阅读器 |
| 图标栏 + 列表栏两栏 | 合并为一栏 248px | 省出宽度给舞台；带文字提高辨识度 |
| 四棵并列对象树 | 单一列表 + 可折叠分节 | 收敛为「在做的事」与「积累的东西」；V3.0 曾用两个 tab 表达，V3.1 发现它和一级入口分不出层级，改为分节（§4.1） |
| 一级入口在左栏顶部 | 钉在左栏底部 | 让「换工作面」与「换看什么」在空间上分开 |
| 编辑器标签页排（文件 tab） | 任务 tab | V3.0 删除标签页排导致切任务必须回左栏；恢复为 tab，但只允许任务占位（§4.2.1） |
| 资源树混装 docs 与 server/src | 资源库只放用户资产 | Workspace 是机器的工作区，不是用户的资料库 |
| Evidence Summary 是产出树下的页面 | 升格为成果面的固定结构 | 它是全套最强的一屏，也是产品独特性所在 |
| 概览是 Dock 的第二 tab | 拆为常驻两行 + 成果面里的执行计划 | 高频信息不该藏在 tab 后面；执行计划属于成果来源 |
| 底部执行面板 + 状态栏 | 删除 | IDE 隐喻，Human Lead 不看终端 |
| 无当前任务时 Dock 空/残留 | 项目级会话 | 让 Dock 在任何时刻都有意义 |

## 9. 暂不表达

- 真实文件编辑、Git 写操作和终端输入。
- 复杂拖拽、面板尺寸持久化和多编辑器分屏。
- 真实 Agent 执行、流式事件和后端数据。
- 移动端和多人协作形态。

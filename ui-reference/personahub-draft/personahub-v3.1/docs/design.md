# PersonaHub V3.44 页面结构与功能设计

> 维护状态：当前设计基线。2026-09-08 最终检视完成，无待确认交互问题。
>
> 本文记录“产品怎样组织以及为什么”；不可省略的实现规则见 [`implementation-notes.md`](implementation-notes.md)。历史方案可从 Git 历史和 `v3.2-claim-evidence-proposal.md` 查阅，不再与当前结论混排。

## 1. 设计结论

PersonaHub 是一个以任务结果为中心的 AI 工作台。默认工作面先回答三件事：现在发生了什么、成果是否可信、下一步需要谁做什么；会话、轨迹、文件和底层运行记录都服务于这三个判断。

```text
竖栏：切换一级工作面
左栏：在需要先选对象的工作面中定位任务、会话、项目或执行机器
主栏：完成当前判断与操作
副栏：同时展示最相关的活动、轨迹、大纲或预览，可折叠
```

产品不使用 IDE 式通用画布、文件标签排、底部终端面板和协作 Dock。用户无需理解 GraphRun、NodeRun、SSE 或 SQLite 才能完成工作；这些只在轨迹和诊断层按需披露。

## 2. 核心对象与用户语言

```text
工作区（Space）
├─ 项目 0..N
│  ├─ 主代码目录 0..1 + 只读参考仓库 0..N
│  ├─ 项目记忆（全局记忆库的作用域视图）
│  └─ 默认 Skills
├─ 任务 0..N（project_id 可空）
│  ├─ 会话 1..N（Room；Thread 不单独露出）
│  ├─ 派工记录 0..N
│  │  └─ Run / Attempt
│  ├─ Work Graph / NodeRun（需要多节点时）
│  ├─ Artifact revisions
│  └─ 主张 / 论证 / 证据
├─ Skills / 编组
├─ Memory
└─ 自动化规则

全局
├─ 执行机器 1..N
│  └─ adapter 0..N
│     └─ 接入方式 1..N（仅真实存在多套凭据时出现）
├─ 插件
└─ 应用设置与系统诊断
```

界面术语固定如下：

| 代码 / 领域名 | 界面名称 | 说明 |
|---|---|---|
| `issue` | 任务 | 最小可验收工作单位 |
| `room` | 会话 | 任务中的讨论与派工容器；也允许独立会话 |
| `thread` | 不单独显示 | 会话的一对一记录流 |
| `workspace` | 代码目录 | 文件访问与执行边界，不得称“工作区” |
| `space` | 工作区 | 项目、任务、能力和记忆的归属边界 |
| `artifact` | 阶段成果 | 有不可变 revision 与来源 |
| `evidence summary` | 完成摘要 | 按完成要求组织依据 |
| `adapter + config + model + depth` | 执行组合 | 一次派工的实际执行选择 |
| `skill` with `steps` | 编组 | Skill 的一种形态，不是独立类型 |

AI 成员、Primary Thread、Project Thread、独立 Validation Policy、能力包和协作现场对象均不再是当前产品概念。验证要求属于 Skill/步骤的完成要求；“协作现场”只可作为多执行组合并行时的呈现描述。

## 3. 一级工作面

竖栏是唯一一级导航。日常入口在上（任务、会话、项目、自动化），配置与复盘入口在下（记忆、能力、运行时、统计、设置）。各工作面内部不得再复制一级导航。

### 3.1 任务

任务是默认入口。左栏按置顶、最近、项目和收藏等稳定组织维度排列，不按会不断变化的状态搬组；状态由行内标记表达。顶部全局搜索负责查找，左栏不再放第二个搜索框。

任务头第一行放标识、标题与元信息，第二行固定四个视图：

| 视图 | 主栏回答 | 副栏 |
|---|---|---|
| 概览 | 目标、等待用户决定的事项、当前情况、下一步建议 | 活动：状态、基线、派工、记忆写入等任务级事件 |
| 会话 | 当前 Room 的消息与派工 | 轨迹：输入、模型、工具与耗时；可放大全屏复盘 |
| 验收 | 主张—论证—证据、用例和未覆盖要求 | 大纲：主张、用例、未覆盖要求导航 |
| 资源 | 产出与输入清单 | 文件 / Artifact 预览 |

tab 上的数字只表示需要人工介入的件数，不表示内容总数。同一事项只能在它的处理位置计数一次。

任务面底部只有一个输入框，切四个视图时保留草稿。派工分开选择模型与思考深度，并选择上下文范围：全部、只给结果、只给目标。验证类派工默认“只给结果 + 冷启动”；改回“全部”时必须提示并降低独立性结论。

新建任务只要求目标和必要归属，不强迫用户先取标题；确认前不创建，重复提交不重复创建，创建后进入该任务会话。标题可由第一次执行总结并随时修改。

### 3.2 会话

会话面与任务面复用同一消息骨架，tab 区分独立会话与项目 / 任务会话。用户消息靠右，执行组合消息靠左，工具事件折叠在对应消息内。

- 独立会话用于讨论，不产生验收、不写记忆；要形成交付结果必须“转成任务”。
- 一个任务可有多个会话；Room 是用户组织阅读与协作的容器，不承担第二套执行状态机。
- 结束会话不删除 Run、Artifact、证据或历史消息。

### 3.3 项目

左栏选择项目，右侧固定四个 tab：文件、项目记忆、Skills、设置。

- 文件：目录树 + 就地预览；Markdown 渲染，代码显示行号和变更。
- 项目记忆：记忆 · 知识库按当前项目生成的筛选视图，不独立存储。
- Skills：直接引用能力面的 Skill，只设置项目默认项，不复制步骤或完成标准。
- 设置：项目信息、代码仓、文件访问、项目管理。一个项目最多一个可写主目录，可有多个只读参考仓库。

网络和 `git push` 不做项目级开关；文件访问只配置读写路径，任务派工还可继续收紧。

### 3.4 自动化

自动化由规则列表与详情组成。详情只有“属性 / 运行记录”两层；属性按“触发条件与执行组合并排，任务内容在下”排列。

- 任务内容是一份可编辑 Markdown，确认后每次触发读取同一 revision，不重新生成。
- 定时触发使用频率、日期、时间、时区与下次运行预览，不要求用户填写 cron。
- Webhook 用用户语言表达验签、去重和事件过滤，协议细节进入诊断。
- 启用状态是开关；暂停只阻止后续触发，不影响正在执行的任务。
- 自动化永远创建普通任务，不提供“仅运行、不建任务”模式。
- 权限跟项目走，只能收紧；投递正文永远不能扩大权限。
- 未触发、执行失败、已暂停是三种不同结果；手动重跑产生新记录和新任务，不改写历史。

### 3.5 记忆

记忆面只管理内容，三个互斥 tab 为：待办、知识库、知识图谱。

- 待办按新候选、需要复核、整理建议分组，同一条只出现一次，每行都有直接动作。
- 知识库同时展示可信等级、内容、类型、作用域、生命周期、验证记录、最近召回、引用与采纳。
- 知识图谱以选中记忆为锚点，默认一跳、可看两跳，支持范围 / 生命周期 / 关系类型筛选、节点检索与关系明细。
- 知识库与知识图谱读取同一数据并能双向定位。

记忆策略不在此处编辑；唯一入口是设置 · 工作区 · 记忆。基础设施故障在系统诊断，记忆价值在统计 · 记忆效用。

### 3.6 能力

能力面承载缺失时仍不影响核心任务闭环的可选能力。内建 tab 为 Skills 与 MCP，插件可以声明新的数据 tab，但由宿主统一渲染。

Skills 使用一张可筛选表。带 `steps` 的行自动标“编组”；普通 Skill 与编组共享 `id@version`、来源、能力要求、下发状态与版本治理。详情整页下钻，显示面包屑、关键信息和只读文件；编辑应回到磁盘文件或创建新版本。

MCP 页表示想安装和同步什么；运行时 adapter 的工具表表示某台机器上实际带着什么。两处不一致时以后者为准。

### 3.7 运行时

运行时盘点可派工的执行资源。左栏是一台执行机器一行，不分“本地 / 远程”；右侧先是概览，之后每个 adapter 一个 tab。

概览包含机器读数、adapter 列表和执行组合表。adapter 页包含状态 / 接入方式 / 额度 / 可用模型卡片，以及只读的运行中清单与完整工具表。工具表同时列 CLI 内置工具和 MCP 工具。

adapter 状态只有在线 / 离线；额度是独立事实。只有真正支持多套地址或凭据的 adapter 才出现可增删的“接入方式”，CLI 自管登录时只显示状态和终端命令。

运行时不停止具体任务；具体执行控制在任务或统计 · 监控。跨机器的“暂停全部派工”属于资源准入闸门，可保留在运行时，但确认前后都必须持续展示影响与恢复入口。

### 3.8 统计

统计无左列表，固定三个 tab：用量、监控、记忆效用。

- 用量按任务去向与用途回顾 Token、耗时和成本；API 实付与订阅等价永不相加。
- 监控展示执行中、排队、故障率和故障列表，并注明刷新间隔与时间；验证未通过和额度不足不算故障。
- 记忆效用分别展示被展示、被引用、被采纳、确实帮助四层，不合成分数。

逐次调用明细回到任务的轨迹视图，不在统计里建立第四层钻取。基础设施健康不属于监控，统一进入系统诊断。

### 3.9 设置

设置只按作用域分组，不把实体实例或动作放进一级目录：

| 应用 | 工作区 |
|---|---|
| 偏好设置、插件管理、通知、系统诊断、关于 | 通用、记忆、标签、代码仓 |

同一设置只有一个可编辑入口。系统诊断统一承接服务、数据库、事件流、记忆写入、索引关系、召回降级、磁盘快照、路径和诊断包；“关于”只保留版本、更新和许可。

代码仓只有一个添加入口，输入本地路径或仓库地址后自动判断。授权按解析后的真实路径和执行机器设置；主目录可读写，参考仓库只读。提交身份读取执行机器的 Git 配置，PersonaHub 不另存一份。

## 4. 可信交付

任务验收的基本结构是：

```text
完成要求
└─ 主张
   ├─ 论证：为什么这些证据足以支持主张
   └─ 证据：系统事件、测试、实际文件、Artifact revision、外部来源
```

状态只用三个视觉符号：已独立验证、有证据待验证、需要处理；精确结论写在主张文本中。同源验证、缺失依据和范围受污染不能获得“独立验证”状态。证据使用仓库或系统已有的天然标识，不新造编号体系。

验收基线变更必须事前确认；新增证据不拦截。实现回归与端到端验收分段展示，不能用一类结果替代另一类。任何被消费的 Artifact 都钉住 revision，任何进入执行上下文的输入都能从持久事件重建。

## 5. 状态、反馈与恢复

任务状态至少能区分刚创建、排队、执行中、等待指派、等待权限、验证未收敛、执行失败、已中断、已取消、已完成和已归档。它们复用同一数据骨架，但首屏按当前风险重排，不把异常埋在页面下方。

异常先回答“发生了什么 / 影响什么 / 建议做什么”，再给唯一主操作。失败、中断、取消和排队不得互相冒充：它们保留的内容、恢复动作与证据含义不同。

反馈分三类：

- 状态变更：持久可见并带恢复入口。
- 操作确认：短提示，可消失。
- 能力缺失：操作前置灰并写明原因与替代路径。

派工发出后先进入可撤销的启动窗口；只有真实创建派工记录后才显示“已指派”。取消窗口内撤销不产生执行记录。

## 6. 全局交互规则

1. 界面只写事实、后果与动作；设计论证、ADR 编号和实现阶段说明留在文档。
2. 一个对象一个名字、一个配置一个编辑入口、一个动作一个负责工作面。
3. 不能做的操作置灰并解释，不通过隐藏替用户判断。
4. 高风险动作确认必须说明“会动什么 / 不动什么 / 如何恢复”，确认后状态常驻。
5. 密钥和 token 默认遮罩，显式操作才能查看；保存后不回显。
6. 数据表必须有可访问名称、完整表头与明确缺省值，不使用空表头或破折号占位。
7. 弹窗统一 `dialog` 语义、焦点圈与 Esc 行为；页签支持方向键和 Home/End；所有新增交互形态都进入浏览器门禁。
8. 页面说明单段不超过 150 字；避免靠长说明维持一个不成立的名词或结构。

## 7. 实现边界

本静态稿不实现真实 CLI、持久化、流式事件、Git 写入或远程机器通信。它也不承诺一次版本交付全部最终面。生产实现可以分批开放，但每一批必须：

- 保持最终对象模型与唯一入口，不建设随后要删除的平行模型；
- 未开放能力置灰说明，不伪装可用；
- 以真实用户旅程和浏览器 E2E 验收，不以组件存在替代旅程完成；
- 在变更本设计结论前先修订 PRD / ADR / Feature，而不是让实现成为新的隐性真相源。

## 8. 待确认问题

无。此前“待观察”项已经在 V3.44 前的连续检视中完成取舍；新的真实使用反馈按新问题进入 PRD/ADR，不再保留无 owner 的观察清单。

# V3.2 提案：成果面改为「主张 → 论证 → 证据」

> **状态：评审修订中，尚未实现。** 本文是给使用者审视用的提案，不是设计基线。
> 基线仍是同目录的 `design.md`；本文获批后再合入基线并改原型。
> 结构模型的理论依据见 `docs/decisions/0010-claim-evidence-structure.md`（`proposed`，已落盘，未提交）。

---

## 1. 这份提案要解决的三个问题

三条都来自使用者在设计评审中的原话，不是推测出来的：

| #   | 原话                                                                               | 诊断                                                           |
| --- | ---------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 1   | 「主舞台的内容我认为太复杂了」                                                     | 成果面有 8 段                                                  |
| 2   | 「完成要求与依据、还没有被证明、实现与验证……感觉在讲同一件事情但是我又抓不住联系」 | 三段确实是同一棵树的三种切片，且缺少把主张和证据连起来的那一层 |
| 3   | 「充分考虑通用性和可复用，不要仅仅局限于代码开发层面」                             | 现有结构里「用例」是硬编码的，换场景就得换结构                 |

第 2 条是核心。**「抓不住联系」不是表达问题，是结构缺件**——主张与证据之间没有显式的连线，读者只能自己脑补。

---

## 2. 结构模型

采用三个角色，与 Goal Structuring Notation 同构（详见 ADR 0010）：

| 角色              | 含义                                   | coding 实例                      | 写作/研究实例                   |
| ----------------- | -------------------------------------- | -------------------------------- | ------------------------------- |
| **主张** Claim    | 一句可判真假的断言                     | 完成要求 / AC                    | 一个论点                        |
| **论证** Strategy | **凭什么这么说**——主张到证据的连接方式 | 「两条端到端用例走完整读取路径」 | 「三处原始出处 + 一次交叉核对」 |
| **证据** Evidence | 可核对的原件                           | 用例执行结果                     | 引用与出处                      |

`J3 › F009 › US-002` 是**范围血统**，回答「这条主张属于哪里」；它不是主张树的上层节点。主张从可判真假的完成要求开始，例如 `AC-002`。测试、文件、引用和验证结论使用各自的 Evidence ID，不再复用 `AC-xxx`。

五条约束：

1. **范围层数不预先规定。** coding 常见 `旅程 → Feature → US`，写作可能只有作品与章节；这些层级只负责归属和汇总。
2. **「论证」不可省略。** 它就是第 1 节问题 2 缺的那一件。
3. **未被支撑的主张必须显式在场**，与已支撑的主张放同一张表，不折叠、不下沉。（GSN 的 `UndevelopedGoal`，四个独立实现中已核实存在。）
4. **证据覆盖不等于验证通过。** 至少区分 `无证据 / 有证据待验证 / 独立验证通过 / 同源验证 / 验证失败`；实现者自产自验不能显示最终绿勾。
5. **证据不可原地修改。** 新结果产生新 revision；需要 Human Lead 批准的是主张或验收基线的变更，不是新增证据本身。

## 3. 设计：成果面（coding 场景）

```text
  任务 · 等待你指派                              [ 成果 | 轨迹 ]
  artifact 引用不漂移与来源可追
 ─────────────────────────────────────────────────
  US-002 稳定引用与历史复现                       [展开血统]
 ─────────────────────────────────────────────────
  全部 3 · 需处理 1 · 独立验证 1 · 上次查看后变更 1
 ─────────────────────────────────────────────────

  ✓  AC-002 · 旧 revision ref 永远解析旧内容
     凭什么  两条端到端用例走完整读取路径
     ├ TEST-041  e2e   通过 412ms    实现者执行
     └ TEST-052  e2e   通过 188ms    验证员执行 · ⊘ 冷启动
     结论  独立验证通过

  ◐  AC-003 · 归档路径由内容派生，调用方不可指定或覆盖
     凭什么  一条端到端用例 + 服务端派生逻辑的实际改动
     ├ TEST-061  e2e   通过 233ms    实现者执行
     └ FILE-018  artifact.ts  +48 −9           [打开全文]
     结论  有证据，等待独立验证

  ⚠  AC-004 · 双向追溯跨 scope 不泄露存在性
     没有证据 —— 这条主张目前只是一句话
     [ 补一条用例 ]   [ 申请标记不适用 ]

 ─────────────────────────────────────────────────
  实现回归  15 / 15   当前无失败                   ▸ 展开
 ─────────────────────────────────────────────────
  本次成果  2 个文件                        [ 打开全文 ]
```

**四段：** 当前范围 / 紧凑过滤器 / 主张—论证—证据 / 本次成果。相对现状少四段。

这里的 `✓` 只表示独立验证通过；`◐` 表示已有实现证据但尚未完成独立验证；`⚠` 表示需要用户或 Agent 处理。证据来源、执行者和上下文血统共同决定结论，不能只按“测试有没有通过”着色。

## 4. 设计：同一骨架，换成非代码任务

复用的是信息骨架，不承诺界面代码零改动。不同任务类型通过 Evidence Adapter 提供摘要、来源、预览、打开动作、时效、独立性和结论语义；研究允许出现互相矛盾或仅部分支持的证据，不能强压成二元通过/失败。

```text
  任务 · 进行中                                  [ 成果 | 轨迹 ]
  Agent session 生命周期调研
 ─────────────────────────────────────────────────
  全部 3 · 需处理 1 · 已核对 1 · 有争议 1

  ✓  multica 不是纯冷启动，而是有条件 resume
     凭什么  两处源码原文 + 一处反证
     ├ SRC-031  agent.sql · GetLastTaskSession   [跳回原文]
     ├ SRC-032  六种中毒终态禁止 resume 的注释    [跳回原文]
     └ SRC-033  手动重跑强制冷启动                [跳回原文]
     结论  已由独立研究员复核

  ◇  只有冷启动能保证验证者看不到实现者自述
     凭什么  与 PRD 第 7.5 节比对 + 安全研究员独立核对
     ├ SRC-041  PRD §7.5 实现与验证不能同源       [跳回原文]
     ├ REVIEW-012  安全研究员结论        ⊘ 独立 · 未参与检索
     └ COUNTER-003  provider/model 不同不必然隔离上下文
     结论  部分支持，边界仍有争议

  ⚠  同成员长链的成本反转点在哪
     没有证据 —— 本地没有数据，只有结构性推断
     [ 补一次测量 ]   [ 标为本轮不解决 ]

 ─────────────────────────────────────────────────
  本次产出  research_findings · r1              [ 打开 ]
```

非代码任务至少需要 `已核对 / 部分支持 / 有争议 / 已失效 / 无证据` 五种结论。Adapter 可以增加领域状态，但必须映射回这组通用语义，避免每种 Issue Type 长出一套互不相通的界面。

## 5. 设计：验收基线变更需要你批准

证据是不可变记录：新增测试结果、引用或验证结论会创建新 revision，不需要逐条批准。需要在改之前拦住的是**主张或验收基线被改弱**，因为这会改变“什么算完成”。

```text
 ┌───────────────────────────────────────────┐
 │ ⏸  实现者申请修改验收基线，等你决定                    │
 │                                                       │
 │    主张   AC-002 · 旧 revision ref 永远解析旧内容      │
 │    原     resolve("...@1") 返回 r1 原文               │
 │    改     resolve("...@1") 返回 r1 原文 或 null       │
 │                                                       │
 │    理由（实现者写的）：源文件被删时拿不到原文          │
 │    ⚠ 系统提示：这可能把主张改弱                        │
 │      原来断言「永远」，改后允许返回 null               │
 │                                                       │
 │    在你决定之前，验收基线停在 r1；已有证据保持不变      │
 │                                                       │
 │    [ 批准为 r2 ]  [ 拒绝并保持 r1 ]  [ 看完整差异 ]    │
 └───────────────────────────────────────────┘
```

系统只负责展示文本差异、受影响主张和 Agent 给出的理由，不承诺自动完成语义裁决。`可能改弱` 是风险提示，最终由 Human Lead 决定。批准后产生新的验收基线 revision；旧主张、旧证据和旧结论仍可追溯，不原地覆盖。

与 git push 授权是同一种交互原语，原型里已有，直接复用。

## 6. 紧凑摘要与过滤器

不再使用三张等权卡。成果面顶部只保留一行可点击过滤器：

```text
全部 3 · 需处理 1 · 独立验证 1 · 上次查看后变更 1
```

`需处理` 是当前状态，`上次查看后变更` 是历史事件，两者不伪装成同维度指标卡，只共享过滤入口。默认顺序固定为：需处理 → 有争议或已变化 → 有证据待验证 → 已独立验证。**「对齐」卡取消**；主张与证据之间的「凭什么」直接表达追溯关系。

## 7. 相对现状的逐条变更

| #   | 现状                        | 提案                                               | 理由                                                             |
| --- | --------------------------- | -------------------------------------------------- | ---------------------------------------------------------------- |
| 1   | 三卡：覆盖 / 对齐 / 时序    | 一行紧凑过滤器                                     | 状态与历史事件不再伪装成三项等权指标；对齐被「凭什么」吸收       |
| 2   | 「完成要求与依据」段        | 合入主张树                                         | 同一棵树的切片                                                   |
| 3   | 「还没有被证明」段          | 合入主张树，成为 `⚠` 行                            | 同上；GSN 要求同表在场                                           |
| 4   | 「实现与验证」双列 + 围栏图 | 移入轨迹页；成果页保留证据执行者、独立性与最终结论 | 双列讲的是过程，但独立性仍是 Done 的持续可信度信号               |
| 5   | 单元与端到端混算 18 / 18    | 实现回归单独一段，默认折叠；失败时自动展开         | 两者性质不同，合计无意义；低层技术主张仍可显式引用单元或属性测试 |
| 6   | 无血统路径                  | 默认显示当前范围，按需展开 `J3 › F009 › US-002`    | 回答「我在哪一层」，但不长期占据首屏                             |
| 7   | 用例变更事后告警            | 验收基线变更事前阻塞；新增证据不拦截               | 拦住的是“什么算完成”被修改，不是证据正常生长                     |
| 8   | 成果面 8 段                 | 4 段                                               | 使用者反馈「太复杂」                                             |

## 9. 本轮评审后的裁决建议

以下五项已按本轮评审收敛为推荐方案；使用者仍可推翻，但改原型时不再留给实现阶段临时判断。

### 9.1 「凭什么」这一行会不会变成套话

**风险**：Strategy 在 GSN 里是人写的。如果 agent 生成，很可能退化成「因为测试通过了」这种废话，反而增加噪音。

**裁决建议**：条件显示，但不按证据数量机械判断。当证据与主张的连接关系不显然、存在组合证据或反证时显示；单一直接证据默认省略。禁止生成「因为测试通过了」这类同义反复。

### 9.2 血统路径在单任务视角下是否有价值

**风险**：`J3 › F009 › US-002` 这一行，对每天只看这个任务的人可能是纯装饰——他本来就知道自己在做什么。

**裁决建议**：默认只显示当前范围 `US-002`，点击展开完整路径。`F009 3/9` 这类上层贡献放项目全景，不长期占据任务首屏。

### 9.3 「未支撑」的两个按钮是不是给了太容易的逃生口

`[ 申请标记不适用 ]` 必须填写理由并由 Human Lead 确认。确认后该行持续显示为 `○ 不适用 · 理由…`，原始总数不静默缩小，摘要写成 `2 已验证 · 1 不适用`；不能把它伪装成第三条已支撑。

### 9.4 单元用例默认折叠，会不会让人忽略回归风险

实现回归默认折叠并保留状态：`15 / 15` 通过时弱化；一旦失败或相对上次新增失败，自动展开并进入 `需处理`。不绝对规定单元测试永远不能支撑主张；低层技术主张可以显式引用单元或属性测试，但不与端到端覆盖混算。

### 9.5 主张树在主张多的任务上会不会又变长

F009 有 9 条 AC。如果一个任务的主张有 9 条，每条带 2 条证据，主张树就有 27 行——「太复杂」的问题可能以另一种形式回来。

**裁决建议**：已独立验证的主张默认收起，只显示 `✓ 主张 · 2 条证据 ▸`；需处理、有争议、验收基线已变化的主张默认展开。单条主张默认最多预览两项证据，其余显示 `另有 N 项`。

## 10. 状态差异：同一数据骨架，不同首屏主角

数据模型保持主张—论证—证据一致，但页面顺序按任务状态变化。不能为了布局一致，让七个任务态继续争抢同一套首屏位置。

### 10.1 执行中：当前动作优先

```text
任务 · 正在执行                              [成果 | 轨迹]
补齐 Inspector 的 artifact 状态
─────────────────────────────────────────────────
● Claude 正在检查项目级 CLI 可用性 · 第 2 / 4 步   [先停一下]

最新结果
  executable-resolver.ts  +23 −4
  EvidenceSection.tsx     正在写入，不计入成果

需处理 0 · 有证据待验证 1 · 独立验证 0
  ◐ AC-008 · 六种 Inspector 状态可区分             ▸
─────────────────────────────────────────────────
目标与完整执行计划                              [展开详情]
```

### 10.2 验证失败：差异与换策略优先

```text
任务 · 验证未收敛                          [成果 | 轨迹]
修复图重启的并发认领
─────────────────────────────────────────────────
⚠ 连续两次验证得到同一 finding，自动继续已停止
  两轮都指向恢复时的并发窗口，不是两个独立问题
  [换执行者]  [修改约束]  [停止任务]

需处理的主张
  ✕ AC-014 · 并发恢复只认领一次
    第 1 次  VALIDATION-071 · 失败 · 同一窗口重复认领
    第 2 次  VALIDATION-084 · 失败 · finding 未变化
    结论  当前策略未收敛

保留的成果  2 个文件                             [打开]
```

### 10.3 已完成：交付与可信结论优先

```text
任务 · 已完成                              [成果 | 轨迹]
Graph 启动恢复
─────────────────────────────────────────────────
结论
  重启后已完成节点不会重跑；进行中的 Attempt 标记为 interrupted。

交付物
  graph-recovery.ts  +71 −14
  node-run.ts        +29  −8
  完成摘要 · revision 1                         [打开]

3 条主张全部独立验证通过
  ✓ AC-011 · 已完成节点不重跑 · 2 条证据          ▸
  ✓ AC-012 · 进行中 Attempt 可恢复 · 3 条证据     ▸
  ✓ AC-013 · 新旧尝试可追溯 · 2 条证据            ▸

后续建议  1 条                                   [基于结果继续]
```

等待指派见 §3，权限确认见 §5。至此覆盖四个最能改变首屏优先级的状态；刚创建、Research 进行中和普通阻塞态在原型阶段复用相邻规则并单独验收。

# V3.2 提案：成果面改为「主张 → 论证 → 证据」

> **状态：评审修订中，尚未实现。** 本文是给使用者审视用的提案，不是设计基线。
> 基线仍是同目录的 `design.md`；本文获批后再合入基线并改原型。
> 结构模型的理论依据见 `docs/decisions/0010-claim-evidence-structure.md`（`proposed`，已落盘，未提交）。

## 1. 这份提案要解决的三个问题

三条都来自使用者在设计评审中的原话，不是推测出来的：

| #   | 原话                                                                               | 诊断                                                           |
| --- | ---------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 1   | 「主舞台的内容我认为太复杂了」                                                     | 成果面有 8 段                                                  |
| 2   | 「完成要求与依据、还没有被证明、实现与验证……感觉在讲同一件事情但是我又抓不住联系」 | 三段确实是同一棵树的三种切片，且缺少把主张和证据连起来的那一层 |
| 3   | 「充分考虑通用性和可复用，不要仅仅局限于代码开发层面」                             | 现有结构里「用例」是硬编码的，换场景就得换结构                 |

第 2 条是核心。**「抓不住联系」不是表达问题，是结构缺件**——主张与证据之间没有显式的连线，读者只能自己脑补。

## 2. 结构模型

采用三个角色，与 Goal Structuring Notation 同构（详见 ADR 0010）：

| 角色              | 含义                                   | coding 实例                      | 写作/研究实例                   |
| ----------------- | -------------------------------------- | -------------------------------- | ------------------------------- |
| **主张** Claim    | 一句可判真假的断言                     | 完成要求 / AC                    | 一个论点                        |
| **论证** Strategy | **凭什么这么说**——主张到证据的连接方式 | 「两条端到端用例走完整读取路径」 | 「三处原始出处 + 一次交叉核对」 |
| **证据** Evidence | 可核对的原件                           | 用例执行结果                     | 引用与出处                      |

`J3 › F009 › US-002` 是**范围血统**，回答「这条主张属于哪里」；它不是主张树的上层节点。主张从可判真假的完成要求开始，例如 `AC-002`。

证据**不复用 `AC-xxx`，也不新造编号体系**：用仓库里已有的天然标识——测试用测试名、文件用路径、源码引用用「仓库 · 路径 · 符号」、验证结论用「成员 · Run」、反证用文字标签。新造一套 `TEST-xxx` / `SRC-xxx` 前缀等于多一份要人工维护的编号表，而这些对象本来就各自可寻址。

五条约束：

1. **范围层数不预先规定。** coding 常见 `旅程 → Feature → US`，写作可能只有作品与章节；这些层级只负责归属和汇总。
2. **「论证」不可省略。** 它就是第 1 节问题 2 缺的那一件。
3. **未被支撑的主张必须显式在场**，与已支撑的主张放同一张表，不折叠、不下沉。（GSN 的 `UndevelopedGoal`，四个独立实现中已核实存在。）
4. **证据覆盖不等于验证通过。** 至少区分 `无证据 / 有证据待验证 / 独立验证通过 / 同源验证 / 验证失败`；实现者自产自验不能显示最终绿勾。
5. **证据不可原地修改。** 新结果产生新 revision；需要 Human Lead 批准的是主张或验收基线的变更，不是新增证据本身。

## 3. 设计：成果面（coding 场景）

```text
  任务 · 等待你指派                              [ 成果 | 轨迹 ]
  artifact 引用不漂移与来源可追
 ─────────────────────────────────────────────────
  US-002 稳定引用与历史复现                       [展开血统]
 ─────────────────────────────────────────────────
  ┌ 已独立验证 ──┬ 有证据待验证 ─┬ 需要你处理 ──┐
  │ 1 / 3 条主张  │ 1 条            │ 1 条           │
  └─────────┴──────────┴──────────┘
  上次查看后：AC-002 的验收基线被改过一次        [看变更]
 ─────────────────────────────────────────────────

  ✓  AC-002 · 旧 revision ref 永远解析旧内容
     凭什么  两条端到端用例走完整读取路径
     ├ artifact-ref.test.ts › old ref resolves to r1
     │                        通过 412ms   实现者执行
     └ artifact-ref.test.ts › content survives mutation
                              通过 188ms   验证员执行 · ⊘ 冷启动
     结论  独立验证通过

  ◐  AC-003 · 归档路径由内容派生，调用方不可指定或覆盖
     凭什么  一条端到端用例 + 服务端派生逻辑的实际改动
     ├ artifact-ref.test.ts › locator derives from sha256
     │                        通过 233ms   实现者执行
     └ server/src/services/artifact.ts  +48 −9   [打开全文]
     结论  有证据，但执行者与实现者同源，等待独立验证

  ⚠  AC-004 · 双向追溯跨 scope 不泄露存在性
     没有证据 —— 这条主张目前只是一句话
     [ 补一条用例 ]   [ 申请标记不适用 ]

 ─────────────────────────────────────────────────
  实现回归  15 / 15   当前无失败                   ▸ 展开
 ─────────────────────────────────────────────────
  本次成果  2 个文件                        [ 打开全文 ]
```

**四段：** 当前范围 / 状态卡 + 变更行 / 主张—论证—证据 / 本次成果。相对现状少四段。

**只用三个符号**，与上面三张卡一一对应：

| 符号 | 卡 | 含义 |
| --- | --- | --- |
| `✓` | 已独立验证 | 已收敛，不用你管 |
| `◐` | 有证据待验证 | 有进展但没完（含同源验证、部分支持） |
| `⚠` | 需要你处理 | 无证据、验证失败、或结论有争议 |

**精确状态由每条主张末尾的「结论」文字行承担**，不再增加符号。第 2 节要求区分的五种状态（无证据 / 有证据待验证 / 独立验证通过 / 同源验证 / 验证失败）全部落在结论行里，例如上面 `AC-003` 写的是「有证据，但执行者与实现者同源，等待独立验证」——同源这件事没有丢，只是不占一个新符号。

理由：使用者已明确反馈过界面太复杂。六个符号必须配图例才看得懂，而图例本身就是复杂度；三个符号与三张卡同构，学一次即可。

已声明「不适用」的主张不占符号，渲染为缩进的灰行（见 §9.3）——它不在「验证与否」这条轴上。

证据来源、执行者和上下文血统共同决定结论，不能只按“测试有没有通过”着色。

## 4. 设计：同一骨架，换成非代码任务

复用的是信息骨架，不承诺界面代码零改动。不同任务类型通过 Evidence Adapter 提供摘要、来源、预览、打开动作、时效、独立性和结论语义；研究允许出现互相矛盾或仅部分支持的证据，不能强压成二元通过/失败。

```text
  任务 · 进行中                                  [ 成果 | 轨迹 ]
  Agent session 生命周期调研
 ─────────────────────────────────────────────────
  ┌ 已核对 ────┬ 待核对 ─────┬ 需要你处理 ──┐
  │ 1 / 3 条主张 │ 1 条（有争议） │ 1 条           │
  └────────┴──────────┴──────────┘

  ✓  multica 不是纯冷启动，而是有条件 resume
     凭什么  两处源码原文 + 一处反向证据
     ├ multica · server/pkg/db/queries/agent.sql
     │    GetLastTaskSession                     [跳回原文]
     ├ 同上 · 六种中毒终态禁止 resume 的注释      [跳回原文]
     └ 同上 · force_fresh_session 手动重跑冷启动  [跳回原文]
     结论  已由独立研究员复核

  ◐  只有冷启动能保证验证者看不到实现者自述
     凭什么  与 PRD 第 7.5 节比对 + 安全研究员独立核对
     ├ PRD §7.5 实现与验证不能同源                [跳回原文]
     ├ 安全研究员结论 · Run #7        ⊘ 独立 · 未参与检索
     └ 反证  provider/model 不同不必然隔离上下文
     结论  部分支持，边界仍有争议

  ⚠  同成员长链的成本反转点在哪
     没有证据 —— 本地没有数据，只有结构性推断
     [ 补一次测量 ]   [ 标为本轮不解决 ]

 ─────────────────────────────────────────────────
  本次产出  research_findings · r1              [ 打开 ]
```

非代码任务至少需要 `已核对 / 部分支持 / 有争议 / 已失效 / 无证据` 五种结论。它们同样落在**结论文字行**里，符号仍只有三个：`已核对` → `✓`，`部分支持` / `待核对` → `◐`，`有争议` / `已失效` / `无证据` → `⚠`。Adapter 可以增加领域状态，但必须映射回这组通用语义，避免每种 Issue Type 长出一套互不相通的界面。

## 5. 设计：验收基线变更需要你批准

证据是不可变记录：新增测试结果、引用或验证结论会创建新 revision，不需要逐条批准。需要在改之前拦住的是**主张或验收基线被改弱**，因为这会改变“什么算完成”。

```text
 ┌───────────────────────────────────────────┐
 │ ⏸  实现者申请修改验收基线，等你决定                    │
 │                                                       │
 │    主张   AC-002 · 旧 revision ref 永远解析旧内容      │
 │    原     resolve("...@1") 返回 r1 原文               │
 │    改     resolve("...@1") 返回 r1 原文 或 null       │
 │                                                       │
 │    理由（实现者写的）：源文件被删时拿不到原文          │
 │    ⚠ 系统提示：这可能把主张改弱                        │
 │      原来断言「永远」，改后允许返回 null               │
 │                                                       │
 │    在你决定之前，验收基线停在 r1；已有证据保持不变      │
 │                                                       │
 │    [ 批准为 r2 ]  [ 拒绝并保持 r1 ]  [ 看完整差异 ]    │
 └───────────────────────────────────────────┘
```

系统只负责展示文本差异、受影响主张和 Agent 给出的理由，不承诺自动完成语义裁决。`可能改弱` 是风险提示，最终由 Human Lead 决定。批准后产生新的验收基线 revision；旧主张、旧证据和旧结论仍可追溯，不原地覆盖。

与 git push 授权是同一种交互原语，原型里已有，直接复用。

## 6. 状态卡与变更行

保留三张卡，但把维度理清：**三张卡是同一条「验证进度」轴上的三段，可以并列**；「上次查看后变更」是历史事件，不在这条轴上，因此拆成卡下面的独立一行。

```text
┌ 已独立验证 ──┬ 有证据待验证 ─┬ 需要你处理 ──┐
│ 1 / 3 条主张  │ 1 条            │ 1 条           │
└─────────┴──────────┴──────────┘
上次查看后：AC-002 的验收基线被改过一次        [看变更]
```

点卡片 = 筛下面的主张树；点变更行 = 只看被改过验收基线的主张。

三张卡的数字**必须加起来等于主张总数**，这是它们能并列的前提；`不适用` 的主张不计入任何一张卡，只出现在树里（§9.3）。

默认排序：需要你处理 → 有争议或验收基线已变化 → 有证据待验证 → 已独立验证。

**「对齐」卡取消**；主张与证据之间的「凭什么」直接表达追溯关系。

> **本轮取舍说明**：评审版曾把三卡改为一行紧凑过滤器（`全部 3 · 需处理 1 · …`），理由是「状态与历史事件不是同维度」。该诊断成立，但结论换成了另一个问题：一行密排的中文标签加数字，可扫描性明显低于卡片，而这一版的首要目标是降低复杂度。因此采用「卡片保留 + 变更行拆出」，两个问题各自解决。

## 9. 本轮评审后的裁决建议

以下五项已按本轮评审收敛为推荐方案；使用者仍可推翻，但改原型时不再留给实现阶段临时判断。

### 9.1 「凭什么」这一行会不会变成套话

**风险**：Strategy 在 GSN 里是人写的。如果 agent 生成，很可能退化成「因为测试通过了」这种废话，反而增加噪音。

**裁决建议**：条件显示，但不按证据数量机械判断。当证据与主张的连接关系不显然、存在组合证据或反证时显示；单一直接证据默认省略。禁止生成「因为测试通过了」这类同义反复。

### 9.2 血统路径在单任务视角下是否有价值

**风险**：`J3 › F009 › US-002` 这一行，对每天只看这个任务的人可能是纯装饰——他本来就知道自己在做什么。

**裁决建议**：默认只显示当前范围 `US-002`，点击展开完整路径。`F009 3/9` 这类上层贡献放项目全景，不长期占据任务首屏。

### 9.3 「未支撑」的两个按钮是不是给了太容易的逃生口

`[ 申请标记不适用 ]` 必须填写理由并由 Human Lead 确认。确认后该行**不占符号**，渲染为缩进的灰行 `不适用 · 理由…`——它不在「验证与否」这条轴上，因此也不计入三张卡的任何一张。原始总数不静默缩小，卡片下方补一行 `另有 1 条已声明不适用`；不能把它伪装成第三条已支撑。

### 9.4 单元用例默认折叠，会不会让人忽略回归风险

实现回归默认折叠并保留状态：`15 / 15` 通过时弱化；一旦失败或相对上次新增失败，自动展开并进入 `需处理`。不绝对规定单元测试永远不能支撑主张；低层技术主张可以显式引用单元或属性测试，但不与端到端覆盖混算。

### 9.5 主张树在主张多的任务上会不会又变长

F009 有 9 条 AC。如果一个任务的主张有 9 条，每条带 2 条证据，主张树就有 27 行——「太复杂」的问题可能以另一种形式回来。

**裁决建议**：已独立验证的主张默认收起，只显示 `✓ 主张 · 2 条证据 ▸`；需处理、有争议、验收基线已变化的主张默认展开。单条主张默认最多预览两项证据，其余显示 `另有 N 项`。

## 10. 状态差异：同一数据骨架，不同首屏主角

数据模型保持主张—论证—证据一致，三张卡与三个符号在所有状态下含义不变；**变的只有页面顺序**。不能为了布局一致，让七个任务态继续争抢同一套首屏位置。

## 12. 决策的两处落点：舞台给结构，Dock 给原文

使用者在原型上发现的问题：点「批准为 r2」时，右侧会话里是不是也要发一条给实现者的消息？如果要，那舞台上的内容和这条消息有什么不同？

### 12.1 「发消息给实现者」这个心智模型是错的

实现者不在线。ADR 0009 已裁定：每次执行都 spawn 一个全新 CLI 进程，跑完退出，没有常驻进程。**它收不到任何消息**——下次被调度时，上下文里的验收基线已经是 r2。

所以批准产生的不是消息，是**状态变更**。三条理由：

1. 你一个字都没写，凭什么算你说的话
2. 消息可以编辑撤回，状态变更不能
3. 消息是给人看的，状态变更是系统要执行的

### 12.2 分工

| | 舞台的基线变更条 | Dock 里实现者那条消息 |
| --- | --- | --- |
| 是什么 | 待决状态 + 决策界面 | 对话原文 |
| 内容 | 主张、原→改差异、风险提示、三个按钮 | 实现者用自然语言写的理由 |
| 谁产生 | 系统从对话里提取的结构 | 成员写的文字 |
| 批准后 | 消失（状态解除） | 留着（历史不可改） |

三条规则，已在原型上实现并有断言守着：

1. **舞台不复述对话**，理由只留一行「看原文 →」回链，点击跳到 Dock 并高亮那条消息
2. **决定在 Dock 里留事件行，不是消息气泡**——断言检查批准前后消息条数不变
3. **批准改基线会让已有的绿勾失效**：AC-002 从 `✓` 降为 `◐`，标上 `r2 · 你批准于 14:32`，结论改为「下面两条证据验的是 r1，r2 的证据尚未产生」；三卡同步为 `已独立验证 0 / 3`，且三数之和仍等于主张总数

第 3 条是这次讨论的意外收获：**改了验收基线，原来的独立验证就不算数了**，因为证据验的是旧断言。原设计没有表达这一点。

### 12.3 同一规则待推广的三处

| 场景 | 舞台该有 | Dock 该有 |
| --- | --- | --- |
| 权限确认（git push） | 批准范围 + 两个按钮 | 请求原文 |
| 指派下一步 | 建议成员 + 理由 | 指令原文（可改后发送） |
| 验证未收敛换策略 | 两轮差异 + 三个动作 | 验证员的结论原文 |

**通用规则**：凡是需要你做决定的事，舞台给结构化的决策界面，Dock 只留自然语言原文和后续讨论；决定本身产生状态变更，不产生消息。

这三处目前仍是两边各有一份，本轮未改。

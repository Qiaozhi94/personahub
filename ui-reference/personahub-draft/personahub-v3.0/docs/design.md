# PersonaHub V3 页面结构与功能设计

> V3 承接 V2 的对象模型、用户语言和视觉语言，**只改布局与主次关系**。
> 变更起因见第 8 节「与 V2 的差异及理由」。

## 1. 设计结论

**PersonaHub 的主舞台是「成果面」——一份随工作推进不断生长的任务文档。**

它一开始只有目标和完成要求；Agent 每推进一步，它就长出产出、证据和决策；完成时它本身就是交付物。任务从「一张目标」长成「一份可信成果」，舞台全程显示同一个东西的当前形态。

```text
左栏（260px）  定位：一级入口 + 任务列表 / 资源库
主舞台（~60%） 成果面：这件事现在做成什么样了、可不可信
右栏（440px）  协作 Dock：谁在做、下一步交给谁
```

### 1.1 为什么是「成果面」

| 参考产品 | 主舞台 | 中心问题 |
|---|---|---|
| Multica | 任务文档 / 看板 | 要做什么 |
| Clowder | 会话流 | 正在说什么 |
| Obsidian | 笔记 | 我写下了什么 |
| **PersonaHub** | **成果面** | **现在做成什么样了、可不可信** |

三条理由：

1. **它是 PersonaHub 独有承诺的载体。** 计划管理 Multica 有，聊天 Clowder 有；只有 Artifact + Evidence + Provenance 构成的「可信交付」是 PersonaHub 独有的。舞台必须承载它，否则产品的独特性在界面上看不见。
2. **它匹配真实的高频动作。** PRD §6「第一屏」与 `user-journeys` 的 P0 常态是同一件事：**看一眼成果，决定下一步交给谁。** 这是审阅 + 决策，既不是读文档也不是聊天。
3. **它对三种用途都成立。** 见 §1.2。

### 1.2 三种用途的同一张舞台

| 场景 | 舞台上是什么 | 左栏资源库里是什么 |
|---|---|---|
| 代码开发 | 改了 3 个文件 · 24/24 通过 · 独立验证一致 | 项目文档、PRD、决策记录 |
| 书籍拆解 / 写作 | 拆解稿现在写成什么样 · 覆盖了哪些章节 · 引用来源 | 原书、笔记、参考资料 |
| 系统排障 | 查到哪了 · 结论是什么 · 凭什么这么说 | 日志归档、历史案例 |

V2 的「文档画布 + 协作 Dock 对半」只有代码场景勉强成立；写作场景下右侧会话基本闲置。

## 2. 核心对象关系

```text
Space
├─ AI Members
├─ Skills
└─ Projects
   └─ Project
      ├─ Workspace：真实文件和执行边界（机器的工作区）
      ├─ Resource Library：文档、笔记、素材、知识（用户的资产）
      ├─ Issue：目标与生命周期
      │  ├─ Primary Thread：完整活动线
      │  ├─ Rooms：阶段协作现场
      │  │  ├─ Room Thread
      │  │  └─ Work Graph
      │  ├─ Runs / Attempts
      │  ├─ Artifacts
      │  └─ Evidence
      └─ Project Thread：项目级会话（不绑定任何 Issue）
```

两条约束：

- Room 是 Issue 某个阶段的协作与控制边界，不拥有第二套执行状态机；Run 仍是实际执行记录。
- **Workspace ≠ Resource Library。** 前者是 Agent 的执行边界（`server/src/…`），是机器的工作区；后者是用户拥有的、跨任务的长期资产。V2 把两者混在同一棵「资源」树里，V3 拆开：资源库常驻左栏，Workspace 目录不常驻，从成果面的「改了 N 个文件」点进去。

### 2.1 用户语言

界面默认使用结果语言；英文领域名只在技术文档、诊断信息或二级说明中出现：

| 领域对象 | 用户界面名称 |
|---|---|
| Issue | 任务 |
| Thread | 会话 |
| Room | 协作现场 |
| Workspace | 代码目录 |
| Run | 执行记录 |
| Artifact / Evidence Summary | 阶段成果 / 完成摘要 |
| Resource Library | 资源库 |

## 3. 一级工作面

左栏顶部四个入口，**带文字**（V2 的纯图标栏辨识度不足，且 PRD §10 要求 AI 成员一级入口可见）：

### 3.1 项目工作台

默认主页面，见第 4 节。

### 3.2 能力库

管理 AI 成员、Squads、Workflows、Skills 和跨项目 Memory。AI 成员与 CLI 分离：成员描述能力和行为，CLI 只属于运行配置。

### 3.3 自动化中心

管理 Scheduled Issues、Webhook、执行队列和历史。自动化只负责创建或推进 Project 下的 Issue，不形成第二套任务体系。

### 3.4 设置与诊断

管理 CLI Runtime、模型认证、Workspace 权限、本地数据与健康诊断。GraphRun、NodeRun、SSE、SQLite 等内部概念默认不向普通用户暴露。

> **「开始中心」已取消独立入口。** 跨项目注意力降级为任务列表上的范围切换（当前项目 / 全部项目）。理由与待观察风险见 §7.1。

## 4. 项目工作台结构

### 4.1 左栏（260px）

一栏承担三件事，自上而下：

1. **全局范围**：Workspace · Project（顶栏已显示名称，此处不重复标签）。
2. **一级入口**：项目 · 能力库 · 自动化 · 设置。
3. **对象列表**，两个 tab：
   - **任务**（默认）：按「需要你处理 / 正在进行 / 最近完成」分组；顶部有范围切换（当前项目 / 全部项目）。Rooms 作为任务的子项缩进显示，不伪装成同级对象。
   - **资源库**：用户拥有的长期资产，内部分三组——**文档**（笔记、PRD、参考资料）、**产出**（Artifact / 完成摘要的历史索引）、**知识**（Decisions / Memory / Skill Candidates）。

V2 的四棵并列树（任务/资源/产出/知识）要求用户先回答「我要找的东西属于哪一类」，这是文件管理器思维。V3 收敛为「**在做的事**」和「**积累的东西**」两类。

### 4.2 主舞台：成果面（~60%）

**单例主视图，不设标签页排。** 一次只判断一件事；打开新对象即替换，靠面包屑返回。

成果面自上而下四段：

| 段 | 内容 | 来源 |
|---|---|---|
| 标题区 | 任务名 · 当前状态 · 主操作 | V2 任务页 |
| **成果状态条** | 系统记录 / 实际变化 / 验证独立性 三卡 | V2 `evidence-summary` 升格 |
| 成果本体 | 文档正文 / 变更摘要 / 研究综述 / Artifact 内容 | V2 文档画布 |
| 完成要求与依据 | 逐条挂系统记录、实际文件、验证者结论 | V2 `evidence-summary` |
| 执行计划 | 这份成果是怎么来的（步骤 · 执行者 · 输入输出 · 证据） | V2 概览页搬入 |

**不使用百分比信任评分。** 可信度来自「结论旁能看到原始记录、谁验证、哪些没证明」。

四个状态（同一结构的不同填充程度）：

- **刚创建**：只有目标与完成要求，成果本体是空态 + 建议的第一步。
- **执行中**：成果本体逐步填充，执行计划显示当前步骤。
- **等待指派**：成果状态条置顶「已完成 N/M，下一步待你决定」，建议指令预填进右栏输入框。
- **已完成**：完整的成果状态条 + 完成要求全绿 + 完整证据链。

代码文件与长文档从成果面点进去（「改了 3 个文件」），**替换舞台 + 面包屑返回**，不用覆盖层——长内容需要完整阅读宽度。文件视图保留 V2 的修改数量、位置标签和上一处/下一处跳转。

### 4.3 右栏：协作 Dock（440px，常驻）

**常驻不折叠。** 当前阶段用户对 Agent 的信任尚在建立中，需要频繁盯会话；这是一条会随信任度变化的判断，见 §7.2。

结构自上而下：

1. **发送目标条（常驻）**：`指令将发送到 · <任务会话 / 协作现场> · <任务名>`。切换任务时 Dock 自动跟随；可显式固定某个 Room，固定后持续显示固定状态，避免向旧上下文误发指令。
2. **执行状态两行（常驻）**：谁在做 · 第几步 · 卡在哪。这是 V2「概览」页里唯一高频的部分，拆出来常驻，不再需要切 tab 才能看到。
3. **会话流**：任务会话 / 协作现场 两页。用户消息靠右，Agent 消息靠左，工具调用与执行事件折叠进 Agent 的那条消息。
4. **指派草稿 + 输入框**：等待指派时系统预填 `@成员 + 建议做的事`，随时可改。**不设独立的「照做 / 不照做」按钮**——按钮只有两种结果，不同意时用户得自己从头组织指令。

> V2 的「概览」tab 被拆解：高频的执行状态上提为常驻两行，低频的「详细执行计划」下沉到成果面（它本来就是「这份成果怎么来的」）。Dock 不再有第三个 tab。

#### 4.3.1 项目级会话

**当前没有选中任务时，Dock 显示项目级会话**，而不是空态或上一个任务的残留。

它不绑定任何 Issue，用来问「这个项目现在什么情况」「上周那批改动结论是什么」，也可以直接从这里发起一个新任务。这让 Dock 在任何时刻都有意义，也给了用户一个「和项目对话」而不是「和某个任务对话」的入口。

选中任务后，Dock 切到该任务的会话；项目会话仍可从发送目标条切回。

### 4.4 布局模式

顶栏三档，改变的是主次比例，不改变结构：

| 模式 | 舞台 | Dock | 用途 |
|---|---|---|---|
| **均衡**（默认） | ~60% | 440px | 常态 |
| 阅读 | ~85% | 收成竖条（状态灯 + 未读数 + 最后一句） | 审长文档 |
| 协作 | ~45% | ~50% | 盯执行、连续指派 |

V2 的均衡模式是 39% / 39%（两个 565px），谁都不是主角；V3 的均衡有明确主角。

### 4.5 已删除的结构

| 删除项 | 理由 |
|---|---|
| 底部执行面板 | VS Code 的 Terminal/Problems 隐喻。Human Lead 不看终端。降级为「某次执行记录的详情」，从会话里的「执行了 3 步」展开进入。 |
| 底部状态栏 | `0 errors · 1 finding · Workspace: idle` 是 IDE 语汇在替用户操心编译状态。只保留一处常驻提示：**有没有事在等我**。 |
| 编辑器标签页排 | 异质对象（文件/任务/Room/Artifact/证据/知识）混装一排，只增不减、无预览模式；且「3 个任务 tab 对 1 个 Dock」会导致向错误上下文发指令。 |
| 48px 图标活动栏 | 5 个抽象图标无文字，辨识度低；并入左栏后省出一栏宽度给舞台。 |
| 「开始中心」独立工作面 | 降级为任务列表的范围切换，见 §7.1。 |

## 5. 关键交互原则

1. **舞台是单例，Dock 跟随舞台。** 切换文件、Artifact、证据、知识不改变 Dock；切换任务必然切换 Dock。
2. **任务像工作文档。** Task 不是字段表格，而是目标、决策、活动、产出和验收条件的持续记录。
3. **证据可双向追溯。** 从结论能到原始事件，从文件或 Artifact 能看到由谁、在哪次尝试中产生。
4. **注意力高于时间。** 任务列表优先显示需要用户动作的对象，而不是最近更新时间。
5. **高级内部信息渐进披露。** 默认展示结果语言，诊断层才出现 Run ID、事件、命令和底层错误。

## 6. 反馈与状态表达

V2 把新建、指派、预填、暂停、跳转、发送、缺失说明全部塞进同一个 2.2 秒 toast。V3 分三类：

| 类型 | 表达方式 | 例 |
|---|---|---|
| **状态变更** | 持久可见，不消失 | 已暂停 → Dock 内常驻横幅「已暂停 · 3 个步骤在队列等待 · [恢复]」 |
| **操作确认** | 短提示，可消失 | 「已把建议指令写入输入框」 |
| **能力缺失** | `title` 提前标注，不等点击 | 「本轮草案未覆盖：成员详情页」 |

**指派有撤销窗口。** 发出 `@成员` 指令后进入「正在启动… [取消]」，而非立即判定「已指派」。指派与否由派工结果决定，不由文本前缀猜测。

## 7. 待观察的判断

这些是本轮明确选择、但需要真实使用验证的决定。效果不佳时按备选方案切换。

### 7.1 「开始中心」降级为范围切换

- **现选**：删除独立工作面，任务列表顶部加「当前项目 / 全部项目」切换。
- **风险**：用户常态是同时推进 2 个项目并行 vibe coding，来回切范围可能比切页面更烦。
- **触发切换的信号**：一天内范围切换次数 > 10，或用户反馈「找不到另一个项目在等我的事」。
- **备选**：恢复独立的开始中心工作面（跨项目时信息组织本来就不同）。

### 7.2 协作 Dock 常驻不折叠

- **现选**：常驻 440px，因为当前对 Agent 的信任仍在建立中。
- **风险**：信任建立后，440px 长期显示一条已读完的会话是浪费。
- **备选**：默认收成竖条，有新消息或需要指派时自动展开。

### 7.3 资源库把「产出」和「知识」收成二级分组

- **现选**：左栏两 tab（任务 / 资源库），资源库内分文档 / 产出 / 知识三组。
- **风险**：产出的历史检索路径变长一层。
- **备选**：产出恢复为独立 tab。

## 8. 与 V2 的差异及理由

| V2 | V3 | 理由 |
|---|---|---|
| 中间画布 39% + Dock 39% | 舞台 ~60% + Dock 440px | 参考产品的主舞台都占约 60%；对半劈导致没有主角 |
| 画布 = 打开任意对象的容器 | 舞台 = 成果面 | 舞台要承载产品的独有承诺，而不是做一个通用阅读器 |
| 图标栏 + 列表栏两栏 | 合并为一栏 260px | 省出宽度给舞台；带文字提高辨识度 |
| 四棵并列对象树 | 任务 / 资源库 两 tab | 收敛为「在做的事」与「积累的东西」 |
| 资源树混装 docs 与 server/src | 资源库只放用户资产 | Workspace 是机器的工作区，不是用户的资料库 |
| Evidence Summary 是产出树下的页面 | 升格为成果面的固定结构 | 它是全套最强的一屏，也是产品独特性所在 |
| 概览是 Dock 的第二 tab | 拆为常驻两行 + 成果面里的执行计划 | 高频信息不该藏在 tab 后面；执行计划属于成果来源 |
| 底部执行面板 + 状态栏 | 删除 | IDE 隐喻，Human Lead 不看终端 |
| 无当前任务时 Dock 空/残留 | 项目级会话 | 让 Dock 在任何时刻都有意义 |

## 9. 暂不表达

- 真实文件编辑、Git 写操作和终端输入。
- 复杂拖拽、面板尺寸持久化和多编辑器分屏。
- 真实 Agent 执行、流式事件和后端数据。
- 移动端和多人协作形态。
